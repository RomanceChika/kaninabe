# 保証台帳（guarantee_spec）の書き方

`docs/specs/backend/guarantees.md` に置く `guarantee_spec`（保証台帳）の YAML スキーマと、検証器が実行するチェック（Z0〜Z3）を定義する。保証台帳は 2 本ある —— 製品のもの（`docs/specs/backend/guarantees.md`）と、仕組み自身のもの（`framework/guarantees.md`。下の「仕組みの保証は仕組みの台帳に」）。

## 目的

- **「保証している」を主張でなく目録にする。** 「RLS を有効にしてある」「書き込みは RPC 経由だけ」は、これまで口頭や README の 1 文でしか確認できない**主張だけの安全性**だった。消えても誰も気づかない（PRIN-0001）。
- **見張りテストを宣言していない保証を許さない。** 保証 1 行ごとに、それが本当に守られていることを確かめるテスト(`canaries`)を必須にする。見張りテストを宣言していない保証は仕様として受理できない(Z0 がエラーにする)。
- **「これから」を正直に出す。** まだ執行できていない保証は `status: planned` として隠さず書き、消し込まれるまで `npm run verify` が毎回 warning を出す(免除の口を作らない)。

## 参照するもの

- **配置**: [ARCH-SP-BE-0001](../../../../architecture/specification/backend/ARCH-SP-BE-0001-backend-spec-structure.md) §保証台帳
- **テンプレート**: `docs/specs/backend/template.guarantee_spec.md`

## ルール・基準

### 器の選び方（なぜ新しい機構を作らないのか）

保証は「執行者(何が守っているか)」「状態(いま守られているか)」「見張りテスト(どう確かめるか)」の 3 つを持つ行の集合であり、これは `notification_spec` / `job_spec` / `config_spec` / `auth_spec` と同じ「**1 プロジェクト 1 カタログ・行の集合・実装と双方向に閉じる**」の 5 例目である。新しい DSL は作らない。

### 語彙をどちらが持つか（フレームワークとアプリの線）

| 軸 | 語彙の持ち主 | 理由 |
|---|---|---|
| `status`(`enforced` / `planned`) | **体系(`lib/model/guarantee/types.ts`)** | Z0 / Z2 と生成物が**この値で分岐する** |
| `enforcer`(執行者) | **カタログ自身の `vocabulary`** | 「RLS で守るか GRANT で守るか」はこのアプリの事情であり、`config_spec` の `used_by` と同じ理由で体系に持たせない |

### 共通形式

- **YAML フロントマターが正**とする。本文の手書き散文は標識(否定・線引き)のみ。
- 1 プロジェクト 1 ファイル(`docs/specs/backend/guarantees.md`)で、`id` は `guarantee-catalog` 固定である。
- **フレームワーク自身の保証もここに載せる。** 「エンジンは生成した表どおりにしか動かない」「5 形の定型は照会を飛ばして書き込まない」「ジョブは失敗しても取りこぼされない」のような、特定のドメインイベントに紐づかない体系そのものの性質(エンジン・定型・ジョブ基盤)も、`action_spec` / `job_spec` の外に置き場を持たないため保証台帳が受け皿になる(テスト義務の全域化。2026-09-04)。注釈の名前空間は**プロジェクト全体で `@tc` の 1 本だけ**であり、`guarantee_spec` 固有の別名前空間(`@check` 等)は作らない — 突合器が読む注釈が増えると、テストコード側は「このアノテーションはどの検査が見るのか」を仕様種ごとに覚える必要が生まれる。

### 1 行が宣言すること

**`guarantees`(保証 1 件)**

| キー | 必須 | 意味 |
|---|:---:|---|
| `id` | ○ | 保証 ID(スネークケース・一意) |
| `label` | ○ | 何が起こりえないかを短く言い切る(人間向け) |
| `enforced_by` | ○ | 執行者(1 つ以上)。`vocabulary.enforcer` に宣言された語のいずれか |
| `status` | ○ | `enforced`(いま守られている)/ `planned`(まだ執行されていない) |
| `canaries` | △ | 見張りテストの `test_cases` の id。**`status: enforced` の行だけが持ち、1 つ以上必須** |
| `planned_reason` | △ | まだ執行されていない理由。**`status: planned` の行だけが持ち、必須** |
| `summary` | ○ | 何をどう保証しているかを 1 行で |

`status: enforced` に `planned_reason` は書けず、`status: planned` に `canaries` は書けない(Z0)。**中途半端な宣言(執行しているのに理由だけ・まだなのに見張りテストだけ)を許さない。**

### 見張りテストの置き場(道具の木)

道具(`@kaninabe/spec-tools`)のテストのうち、保証台帳の見張りテスト(`@spec` / `@tc` を持つもの)は `legacy/spec-tools/__tests__/guarantees/` に置く。それ以外の道具のテストは注釈を持たず、母集合に入らない。実行時パッケージ(`framework/runtime/src`)のテストも、守る対象の隣に住む見張りテストとして同じ扱いである。この 2 つの置き場(**仕組みの根の見張りテストの置き場**)は**仕組みの台帳**の見張りテストが住む場所で、製品の木の走査には入らない(Z3 が走査する)。

### 仕組みの保証は仕組みの台帳に(2 本の台帳と名前空間の予約)

仕組みが自分自身について言い切る事実(エンジンは表に無い遷移を許さない・実行時パッケージは DB 製品の依存を持たない、など)は、製品の台帳ではなく**仕組みの台帳(`framework/guarantees.md`)**に宣言する。製品が採る種類(`product.md` の `uses`)にも製品の台帳の有無にも依らず、**製品が外せない義務**である(根は検査器の位置から引く。製品の宣言には書かない)。

| | 製品の台帳 | 仕組みの台帳 |
|---|---|---|
| 置き場 | `docs/specs/backend/guarantees.md`(製品の仕様の木) | `framework/guarantees.md` |
| 文書 `id` | `guarantee-catalog` | `framework-guarantee-catalog` |
| 保証 ID | `fw_` で始まってはならない | **`fw_` で始まる** |
| テストケース ID | `TC-FW-` で始まってはならない | **`TC-FW-` で始まる** |
| 見張りテストの置き場 | 製品の木(と、製品の実物を読む配線の突合の 1 件) | 仕組みの根の置き場だけ |
| 無いとき | 台帳をまだ開設していない正常な状態(Z1・Z2 を飛ばす) | **阻害(error)** —— 空の台帳で緑にしない |
| `vocabulary` | 製品の事情で宣言する | **仕組みの語だけ**(製品の語を書かない) |

**製品の台帳は `fw_` / `TC-FW-` / `framework-guarantee-catalog` を使えない**(Z0 の error)。ID は 2 本の台帳をまたいで全体で一意になり、持ち主つきのキー(`(持ち主, ID)`)にしない —— 台帳をまたぐ重複は綴りの違反か、テストケース ID の台帳(A9)の重複として現れる。canary(`canaries`)は自分の台帳の `test_cases` にしか置けない。1 つの事実を製品と仕組みで割る(混在する保証)ときは、製品の側が旧い ID のまま残り、仕組みの側が別の保証 ID(`fw_…`)を新しく持つ。

### 見張りテストが**生成物**のとき(束 ⑳-4b / ⑳-5a)

保証の中には、見張りテストを**手で並べきれない**ものがある —— 「RLS が宣言どおりの行集合を返す」「engine の
先読みと RPC の執行が同じ判定を下す」は、表や操作が増えるたびに見張りテストが増える。そういう保証の
見張りテストは**仕様から生成する**(`TC-RLS-…` / `TC-EQ-…`。テストケースの宣言も data_table の `test_cases` の生成ブロック)。

そのとき `canaries` に**必ず「閉世界の見張りテスト」を 1 本足す**。生成物は「生成されなかったもの」を
自分では宣言できないので、置き場に載っているものと載っていないものを突き合わせるテストが要る ——
足りなければ「たまたま抜けているのか、原理的に無理なのか」が誰にも区別できない。**なぜ生成されないか**は
verify の検査器(T8 / T11)が warning で報告し、その判定は生成器とまったく同じ関数から出す
(検査と生成が別の規則で決めると「検査は通ったのに生成されない」が静かに入る)。

### 変異の目録 —— その見張りテストは、壊れたときに赤くなるのか(束 ⑳-5c)

保証の主張は「見張りテストがある」ことで支えられているが、**見張りテストがあること自体は「壊れたら赤くなる」を
意味しない**。期待を生成物から取っていれば、仕様を壊せば期待も一緒に壊れて緑のままになりうる。正しい
仕様で緑になることは、検査の効き目の証拠ではない。

そこで **仕様の宣言を機械で 1 か所わざと壊し、どの検査が気づくかを実測する**(`legacy/spec-tools/lib/mutation/**`。
`npm run test` の `__tests__/mutation/mutation-matrix.test.ts` が製品 + `fixture` 4 題材で走る)。

人が手で同じことをするときは、検査が赤になるのを確かめるために違反を 1 つだけ入れる。この確認を**わざと壊す確認**と呼ぶ(自己レビューの観点にもテストの題にも使う)。

- **変異器**(壊し方)は束 ⑳-3〜⑳-5b が手で行った変異確認をそのまま機械にしたもので、新しい壊し方を
  発明しない: 遷移の `by` からロールを 1 つ落とす / ガードの比較演算子を反転する /
  `reads[].filters` を落とす / `reads[].scope` を `all` に広げる / 作成・編集・削除の `when` を落とす /
  ロール階層(`implies`)から 1 つ落とす / 役の根拠の欄(`claim` / `binding` の欄)を既定のログインロールが書ける編集の規則を 1 本足す
  (R2 の負例。敵対的な点検 2 回目が手で確かめた「誰でも部門の管理者の欄を書ける」形)。**どの変異も 1 か所だけを壊す**(2 か所同時だと、捕った検査が
  どちらを捕ったのか読めない)。
- **検査**(捕る側)は実 DB を使わないシミュレーション上の観測である: 定型 RPC の本文 / 表の DDL と権限の本文 /
  RLS ポリシーの本文 / RLS の world の設計図(挙動テストの期待の入力)/ 一致の証明の期待(engine の判定)/
  `verify` の Finding / 危ない形の検査(R 群。R2・R10)の Finding。**この一覧が列の正**であり、`ALL_MUTATION_DETECTORS` との一致は
  ユニットテスト(`__tests__/unit/gates/mutation-detector-parity.test.ts`)が見る ——
  検査を 1 つ足してここを直し忘れたら落ちる。
- **軸は変異の前のまま**にする(⑳-5a2 の申し送り)。`world` や組み合わせの軸まで変異させると、ロールを
  落とす変異が `world` からその実行者ごと消してしまい、変異が見えなくなる。
- **壊せる場所は全部実行する。件数の上限を持たない**(束 ⑳-5c-b)。「1 変異器あたり先頭 N 件だけ」は一見ただの
  手加減だが、実際には**残りを黙って見ないことにする免除リスト**として働く —— 束 ⑳-5c は上限 2 で
  「穴 0 件」を出し、上限を外すと 202 件中 6 件の穴が出た。重ければテストの並列化で解き、件数で解かない。
- **捕る検査が 1 つも無い変異は検査の漏れ**である。受け入れる口(免除リスト)は作らない —— 出口は
  「検査を足す」か「仕様を直す」だけである。壊せる場所がその仕様に無かった変異器は、穴ではなく
  **未実施**として区別する。捕られなかった変異は次の 3 つに分かれ、**どの分け方も機械が宣言と
  検査器から読む**(書き足せる台帳はどこにも無い)。

  | 分類 | 根拠 | 出口 |
  |---|---|---|
  | **宣言された例外** | action_spec の `runner`(生成に乗らない操作。A15 が両方向を見る)/ data_table の `functions[].handwritten`(本文が手写し。T6 が理由を必須にする)。**どちらも見張りテストの宣言(`test_cases`)が無ければ例外として認めない** | そのまま(手写しはテストの宣言が見張る) |
  | **検査器が報告している漏れ** | その所在を `verify` が warning で出している(例: A18 の「執行点が無い書き込み規則」) | 警告を消すには仕様を直す(執行点を宣言する / 規則を消す) |
  | **検査の漏れ** | どちらでもない —— 誰も気づかず、どこにも出ない | 検査を足す(赤で止まる) |

  「誰も知らない漏れ」を「場所が判っていて毎回 verify に出ている漏れ」に変えることが、**漏れを検査器に
  変える**である。塞ぐかどうかは仕様側の判断だが、**見えなくすることはできない**。
- 対応表はハンドブックの保証の章(`docs/book/guarantees.html`)に生成される。人が読むのは**行ごとに ✅ が
  1 つ以上あること**と、**表の下の箇条書き(漏れと宣言された例外)**だけでよい。

**実 DB で実行する変異は CI に入れない**(所要が跳ね、変異の数だけ DB を作り直すことになる)。DB を使わないシミュレーションで
「執行点の本文が変わる」ことまでを見て、本文どおりに DB が振る舞うことは既存の突合(`rpc-parity` /
`policy-parity`)と挙動テストが受け持つ —— 鎖を二重に張り直さない。

### ここに書かないもの(正が割れる)

- **保証の中身の実装**(RLS ポリシーの USING 句・GRANT 文・トリガの本体・型の定義)— 実装(migration・TypeScript)が正。ここが宣言するのは「何が守っているか」という執行者の**種別**だけである。
- **テストの中身** — `canaries` が指す `test_cases[].implementation` の先にあるテストコードが正。ここではテストケースの宣言(id と接地)だけを持つ。

### 検証(Z 群)

| ID | 何を見るか | 実行場所 |
|---|---|---|
| **Z0** | スキーマ適合。`id` の固定値(台帳の持ち主ごとに別)・**名前空間の予約**(仕組みの台帳は `fw_` / `TC-FW-`、製品の台帳はそれらを使えない)・保証 ID の形式と重複・`enforced_by` が宣言語彙に閉じること・`status` の値域・**`status` と `canaries` / `planned_reason` の対応**・**`canaries` ⇔ `test_cases` の双方向突合(実在 + 孤児の見張りテストの禁止)** | ローダー(`lib/model/guarantee/loader.ts` + `lib/model/guarantee/parse-guarantee.ts`) |
| **Z1** | **製品の台帳の**テスト突合(`test_cases` ⇔ `@tc`)と `spec_ids` の実在(ドメイン ID + `guarantee-catalog`)。仕組みの置き場の下を指す製品の宣言は仕組みの走査で突き合わせる | `lib/guarantee/verifiers/z1-test-trace.ts` |
| **Z2** | `status: planned` の保証 1 件につき warning(2 本の台帳の両方)。**免除の口は無い** | `lib/guarantee/verifiers/z2-planned.ts` |
| **Z3** | **仕組みの走査 ⇔ 仕組みの台帳**。製品の採る種類・台帳・実装の木に依らず走る。走査・台帳の阻害は error、根を渡さない呼び手(単体テスト)には「Z3: 未実施」の行を出す。仕組みの台帳の `test_cases` の接地(`spec_ids` は台帳自身の id だけ・`implementation` は仕組みの根の置き場の下)・仕組みの根の注釈の孤児(宣言として認めるのは仕組みの台帳の宣言と、製品の台帳が置き場の下を指した宣言だけ)・同じ `@tc` の重複(製品の木の注釈と合算)・注釈を持たないテストファイル・注釈の形・注釈の中身(assert。A16 と同じ判定) | `lib/guarantee/verifiers/z3-framework-scan.ts` |

**なぜ検査群の記号が `Z` なのか。** `A`(仕様⇔テストのトレース)/ `S`(画面)/ `H`(認証)/ `G`(視覚層)/ `K`(設定)/ `T`(テーブル)/ `N`(通知)/ `J`(ジョブ)/ `M`(文書整合)/ `U`(UX)/ `V`(ドメイン)が使用済みで、`Z` は「穴ゼロ」を連想できる空いている記号である。

**なぜ Z0 が「孤児の見張りテスト」まで見るのか。** `canaries` の実在(保証 → テストケース)だけを見ると、テストケースを作ったのに誰の保証にも紐づけ忘れた宣言(= 誰も守っていることを主張していないのに存在するテスト)が黙って残る。逆方向まで閉じることで、`test_cases` の集合と `guarantees[].canaries` の合併が過不足なく一致することを機械が保証する。

**実装側の閉世界は無い。** 通知・ジョブ・設定・認証と違い、保証台帳は app 側の生成物を持たない(執行者の実体は多様で、1 つの生成物には集約できない)。見張りテスト自体が実装との唯一の接地点である。

### 検証方法

- `npm run verify`(Z0〜Z3 が走る。`status: planned` の件数だけ warning が出るのが正解。Z 群の行に「仕組みの注釈 N 件を突き合わせ(Z3)」が出る。出ずに「Z3: 未実施」と言うなら、入口が仕組みの根を渡していない)
- `npm run generate`(保証のマトリクスとハンドブックの章を再生成)
- `cd app && npm run test:integration`(見張りテストの実行)
