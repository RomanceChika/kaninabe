# ドメイン仕様の追加・変更の手順(Playbook)

`docs/specs/domain/` に仕様を追加・変更するときの標準手順。人間が手で回す場合も、
将来の Skill(仕様生成エージェント)が実行する場合も、この手順に従う。

## 目的

- ドメイン仕様(`docs/specs/domain/`)の追加・変更を、**誰が回しても同じ順番**で終わらせる。
- 変更を**検証器が読める形**に落とし、決めていないことがエラーとして残る状態にする。
- 機械が保証できない判断(禁止の理由・公開範囲)を、レビューと記録で人間の側に残す。

## 前提条件

- 書き方の規約: [domain-spec-writing.md](../standards/domain-spec-writing.md)(スキーマ・ガード式・検証チェック)
- 新しい概念(集約・状態・イベント)を足すと、全域性検証により**関連する未決定事項がすべてエラーとして列挙される**。これは正常な挙動であり、エラーの一覧が「決めるべきことのTODOリスト」になる

## 全体の手順・流れ（概要）

1. **意図の整理** — 何を追加・変更したいかを1〜3文で書き出す(例: 貸出に取り消し待ちを追加したい)
2. **YAMLの編集** — 該当する doc_type のファイルを編集する。新規集約なら `docs/specs/domain/` の template.*.md をコピーして開始。状態・イベント・ロールには `label`(日本語名)を必ず付ける
3. **検証ループ** — `npm run verify` を実行し、エラーが出なくなるまで修正を繰り返す
   - エラーは「何が・どこで・どう直すか」の形式で出る。**エラーを黙らせるための場当たりな定義を書かない**こと(禁止理由は業務の言葉で書く)
   - 表現できない制約(集計など)に出会ったら、無理にDSLへ押し込めず invariant の formal 省略 + `enforced_by: application` で宣言する(規約「DSL の外に置くもの」)
4. **生成** — `npm run generate` で本文(図・表・要約)を再生成する
5. **意味レビュー** — 生成物を人間が確認する。見る場所は2つ:
   - ハンドブック(`docs/book/`。生成物)の変更した集約の章 — 機械が保証できない箇所(DSL外制約・全件公開・ガード条件)に ⚠ と「意味」列が付く
   - 変更した状態機械の **state×event マトリクス** — 暗黙に禁止したマスの理由が意図と合っているか
6. **判断の記録** — レビューで下した判断(例: 「下書きも全員に見せる」)は、該当YAMLのコメントまたはドメイン知識層(W。`docs/specs/` の隣)の design_context に理由ごと残す(PRIN-0004)
7. **コミット** — 仕様YAMLと生成済み本文を同一コミットに含める(`npm run generate:check` がCIで乖離を検出する)

### してはいけないこと

- `<!-- AUTO-GENERATED -->` ブロック内の手書き編集(次回 generate で消える)
- verify が通らない状態でのコミット
- 検証を通すためだけの意味のない禁止理由・ガード
