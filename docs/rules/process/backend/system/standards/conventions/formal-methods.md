# 仕組み側の約束事のモデル検査(TLA+)

仕様の検証器が見ていない領域 ——**複数のトランザクションやワーカーが交錯したときに、仕組み側の約束事が同時に成り立つか**—— を、モデル検査器(TLC)に 1 回だけ問う規約。対象は `formal/` の 4 モデルと台帳 `formal/expectations.json`、執行は `npm run check:formal`(C24)。

## 1. 目的・スコープ

- **目的:** 仕様の検証器は**1 本の実行を追う**見方しか持たない —— 宣言の網羅(V3 / V4)・辺の到達性(V5)・式 1 本の充足性(V9 / V10)・有界の実行列(V21)のどれも、**2 本以上が同時に走ったとき**を見ていない(設計の経緯は非公開の開発記録: なぜ形式仕様か §4)。仕組み側の約束事は 4 つあり、それぞれ自分の実装の中では正しいのに、交錯すると互いの前提を崩しうる。その交錯に**反例つきの答え**を得ることがこの規約の目的である。

  | 約束事 | 交錯の相手 | モデル |
  |---|---|---|
  | outbox とリトライ(リース付きの取り出し) | 遅れて戻ってきた書き戻し | `formal/Outbox.tla` |
  | コミット時評価の不変条件(deferred な制約トリガ) | 同じ判定を同時に済ませたもう 1 本の txn | `formal/CommitTime.tla` |
  | 期待状態の楽観制御(0 行の理由の再照会) | 条件にする集約の前進 | `formal/Occ.tla` |
  | 作成の冪等キー(`on conflict (id) do nothing`) | 同じ id のもう 1 本の送信 | `formal/IdempotentCreate.tla` |

- **スコープ:** `formal/**` と、検査器 `legacy/spec-tools/cli/check-formal.ts` + `legacy/spec-tools/lib/formal/**`。**アプリの仕様はスコープ外である** —— モデルは仕組み側の形を写すものであり、画面や操作が増えてもモデルは増えない。実装を直すこともスコープ外で、ここは「どこが破れるか」を保持する台帳である(§2 の台帳)。

### 検証する性質の一覧

| モデル | 性質 |
|---|---|
| `Outbox` | **S1** 終端は単調 / **S2** 実行は 1 回以上・リース内の実行は重ならない / **S3** 試行回数は上限以下 / **L1** すべて終端に至る |
| `CommitTime` | **S4** 件数は天井以下 / **S5** 件数は下限以上 / **S6** 1 行の中の 2 つの欄が噛み合う |
| `Occ` | **S7** 遷移は宣言された辺 / **S8** 拒否コードは事実と整合 / **S9** コミット時にガードが成り立つ / **S14** 掴む順が 1 つなら詰まらない(デッドロック検査) |
| `IdempotentCreate` | **S10** 同じ id は 1 本 / **S11** 監査ログは作成回数と一致 / **S12** 再送はロールを見る / **S13** 子の行は 1 組 |

**性質を等価に数えない。**(いまは 15 種の性質を 8 つの定数の組で回して 21 回の検査になる。) `S7` / `S10` / `S11` は**模型の構成上ほぼ恒真**である ——
書き込みと条件が 1 つの原子的な動作に入っている、一意索引が 1 本を超えさせない、監査を積む枝が
作成の枝の中にある、という模型の作りがそのまま答えになる。それでも置いてあるのは、
**模型を弱めたときに赤くなる回帰の検査**としてである(`return` を 1 行落とす・行ロックを外す、
といった弱め方を機械が捕る)。「破れなかった」の重みは性質ごとに違う。

## 2. ルール

### モデルに書くこと・書かないこと

- **すべきこと:** PlusCal(アルゴリズム言語)で書き、TLA+ への**翻訳結果を同じファイルにコミットする**。先頭に写し元を宣言し、各アクションと各性質の直前に `\* 意図:` を 1〜2 行置く。性質の名前(`S1`〜`S13` / `L1`)は固定し、番号を使い回さない。写し元の宣言は**2 形**あり、どちらを使うかは「実装を直したときにそのファイルが動くか」で決まる。

  | 形 | いつ使うか |
  |---|---|
  | `\* SOURCE: <パス> <sha256>` | **その場で書き換わるファイル**(生成器の TS・アプリの TS)。直せばそのファイルの内容が変わる。**sha256 はそのファイル 1 本の本文ではなく、そのファイルと相対 import の推移的閉包の hash**(下の「鮮度の hash は閉包である」) |
  | `\* SOURCE-FN: <関数名> <sha256>` | **DB の関数**。migration は追記専用の歴史なので、関数を直すと**新しい番号のファイル**ができ、旧ファイルは 1 バイトも動かない —— パスで宣言すると**実装を直しても鮮度が赤くならず**、モデルは黙って古いまま緑になる。検査器がその関数を `create (or replace) function` で定義する**最新番号の migration** を解決してハッシュを取る |
- **してはいけないこと:** **アプリの語を 1 語も書かない**(item / loan / patron / purchase_request)。書くのは `Parent` / `Child` / `Row` / `Actor` / `Ceiling` / `Floor` である。語を入れると、アプリの仕様が変わるたびにモデルを直すことになり、「仕組み側を 1 回検証する」という前提が崩れる。**推論器を自作しない** —— 反例を探すのは既製品(TLC)であり、仕組み側が持つのは写像と突合だけである([scripts-code-quality.md](../../../../common/tooling/standards/scripts-code-quality.md))。
- **例:**

  ```tla
  \* SOURCE: app/src/infrastructure/jobs/job.queue.ts 0ac405c3…
  \* 意図: markSucceeded / markForRetry / markDead。どれも `where id = …` だけで実行する。
  writeback:
    either { status[held] := Succeeded; … } or { … };
  ```

### Postgres の意味論の写し方

- **すべきこと:** 写すのは 6 つだけにする。① read committed =「文ごとに最新のコミット済みを読む」/ ② 行の write-lock =「同じ行への `update` は先行 txn のコミットを待ち、待った後に**更新後の行**で `where` を評価し直す」(EPQ)/ ③ deferred トリガ =「コミット直前に、自分の書き込みを重ねた最新のコミット済みを見て判定し、**その判定とコミットの確定は原子的ではない**」/ ④ 副問い合わせで読む相手の行は**ロックしない**/ ⑤ 一意索引 =「未コミットの同じ鍵があればそのコミットを待つ」/ ⑥ **外部キー** =「子を作るときに親が実在することを確かめ、親に鍵共有ロックを掛ける(親の削除はそのコミットを待つ)・親が消えれば子も消える」。
- **してはいけないこと:** **緩めない・厳しくしない。** 緩めれば実装に無い反例が出て、厳しくすれば実在の反例が消える —— どちらも台帳の宣言を嘘にする。MVCC の細部・serializable・デッドロック検出は写さない(写さないことで実行列が減るだけなら、その旨をモデルのコメントに書く)。**②⑤⑥ は落としやすい** —— 束 ㉓ では、遷移の行ロック・FK の鍵共有ロック・FK の実在確認の 3 つが抜けていて、定数を上げた途端に**実装には無い反例**が 3 件出た(模型が緩かった側の誤り)。反例が出たら、まず「実装にこの経路が本当にあるか」を読む。
- **例:** 行ロックは「先行 txn の所有を待ってから条件を評価し直す」形で書く。

  ```tla
  either { await ~WhereMatch(…); found := FALSE; }          \* 合致しない → 待たずに 0 行
  or     { await WhereMatch(…) /\ childOwner = NoTxn; … };   \* 合致する → 掴む(埋まっていれば待つ)
  ```

### 定数と `.cfg`

- **すべきこと:** **所要が 10 秒台になるところまで定数を上げ、選んだ理由を `.cfg` のコメントに書く。** 小さい定数は実在の穴を隠す —— 実測で、離散時計を 1 つ伸ばしただけで holds が violated に変わった性質がある(束 ㉓ の独立レビュー)。定数を 1 つずつ +1 しても答えの集合が変わらないことを、束の作業として 1 度実測する(検査には入れない。所要が読めるまで)。**ただし +1 が前提そのものを壊す定数は別扱いである** —— 例えば `Outbox` の `Budget` / `HandlerMax` を +1 すると「予算 + 上限 ≦ リース」が崩れるので、答えが変わるのが正しい(その反例は `Outbox-lease-breach.cfg` が持つ)。掃引するのは**並行度と時間の深さ**を決める定数である。`CHECK_DEADLOCK FALSE` を置く —— 全部の txn が終わった状態は「詰まった」のではなく「終わった」であり、そこへ至れるかは liveness の性質(L1)が見る。
- **してはいけないこと:** **性質の行(`INVARIANT S1`)を `.cfg` に書き込まない。** 1 本の実行は最初に破れた性質で止まるので、全部を書くと残りの性質の答えが取れない ——「どちらが破れたのか」が別の性質の名前で帰ってくる。検査器が性質を 1 つずつ足して回し、混ざっていたら**その `.cfg` を名指して**赤にする(手で回すときだけ一時的に足す)。
- **例:** `SPECIFICATION Spec` / `CONSTANTS Workers = {"w1","w2"} …` / `CHECK_DEADLOCK FALSE`。

### 前提を置くときは、前提の執行点も置く

- **すべきこと:** モデルの答えが**実装のある比に依っている**なら、(1) その前提を `.cfg` のコメントと台帳の `premise` に書き、(2) **前提を外した定数の組を別の `.cfg` に置いて反例を保持し**、(3) **前提が実装で保たれていることを機械が確かめる**。3 つ揃って初めて「この前提の下で守られる」が意味を持つ。例: `Outbox` は「時間予算 + 1 実行の上限 ≦ リースの長さ」の下で S1 / S2 / S3 が守られる。`Outbox-lease-breach.cfg` が外した側の反例を持ち、`check:formal` が 3 つの実装値(予算・外部呼び出しのタイムアウトの**最大**・リースの既定)を読んで比を確かめる。
- **してはいけないこと:** **前提を散文だけで置かない。** 予算を伸ばす人・タイムアウトを伸ばす人・リースを縮める人は別々であり、誰も「モデルの前提」を見ていない。散文だけの前提は、いつの間にか成り立たなくなって誰も気づかない。
- **例:** 台帳の 1 要素は `model` / `cfg` / `premise` / `properties` を持ち、同じモデルを違う `cfg` で並べてよい。**前提を外した側で破れることは、その前提が効いていることの裏返し**であって免除ではない。

### 台帳(expectations.json)—— 破れる性質は破れたまま持つ

- **すべきこと:** 性質ごとに「機械の答えがどうなるはずか」を宣言する。`verdict: "holds"` は破れないはず(破れたら赤)、`verdict: "violated"` はいまの実装で破れる(**破れなくなっても赤**)。`violated` には `reason`(なぜ破れるか)・`where`(実装の `ファイル:行`)・`remedy`(直すなら何をするか)の 3 つを必ず書く。
- **してはいけないこと:** **免除リストにしない。** 免除リストは「この違反は見なかったことにする」と書くものだが、ここは「この性質はいまの実装で破れる」という**事実の宣言**である。破れなくなったときも赤になるので、宣言を放置して緑を買うことはできず、消し忘れも残らない。理由・場所・対処を欠いた `violated` は台帳の読み取りが赤にする。
- **例:**

  ```json
  { "id": "S1", "check": "INVARIANT", "intent": "終端は単調", "verdict": "violated",
    "reason": "書き戻しが locked_by を見ない…", "where": "app/src/…/job.queue.ts:53",
    "remedy": "書き戻しの条件に locked_by = 自分 を足す" }
  ```

### 実装を直したとき・性質を足すとき

- **すべきこと:** 直したら**この順で**進める。① 実装を直す(直すのは app / supabase / 生成器であり、モデルではない)→ ② `SOURCE:` の sha256 を新しい値に更新する(赤い Finding が新しい値を出す)→ ③ **モデルがまだその実装を写しているかを読んで確かめる**(形が変わったならモデルも直す)→ ④ 台帳のその性質を `holds` にして `reason` / `where` / `remedy` を消す → ⑤ `npm run check:formal` が緑になることを確かめる。性質を足すときは、モデルに `\* 意図:` を前置して書き、台帳に 1 要素を足し、答えが合うまでモデルと宣言のどちらが誤っているかを決める。
- **してはいけないこと:** **順序を逆にしない** —— 先に台帳だけを `holds` にすると、その場で赤くなる(それが正しい挙動である)。**答えを合わせるために性質を弱めない** —— 弱めた性質は緑になるだけで、何も保証しない。
- **例:** 鮮度の Finding は `実際: <新しい sha256>` を出すので、②はその値を写すだけで済む。`SOURCE:` が閉包の hash のときは、**閉包のどのファイルが動いたか**(パスと旧 → 新の hash。増えた・減った import も)が同じ Finding の下に並ぶ —— ③で読むのはそのファイルである。

## 3. 注意点・例外

### 鮮度の hash は閉包である

`\* SOURCE: <パス> <sha256>` の sha256 は、**写し元と、そこから相対 import で辿れる全モジュール**(**閉包**)の hash である。写し元 1 本の本文だけを固定すると、`RPC_BODY_WORDS` や `findEntityFields` のように**import 先の本文だけが変わる**束で hash が動かず、モデルが古くなっても鮮度が緑のままになる。

- **hash の作り方:** 閉包の各ファイルの `(リポジトリ相対パス, sha256)` を**パスの昇順**に並べて連結したものの sha256(`legacy/spec-tools/lib/semantics/import-closure.ts`)。import の無い写し元 1 本だけでも**同じ式**で出す(本文の sha256 とは別の値になる。形は 1 つ)。`SOURCE:` の行の形(`<パス> <sha256>`)は変えない。意味だけが閉包になった。
- **辿る辺:** 相対パス(`./` `../`。`.js` → `.ts` の解決を含む)の import の**全部**(値・型だけ・副作用・再輸出・動的。**型だけの import も入れる** —— 区別しない。単純で嘘が無い)。辿るのは TS / JS で、`.sql` などは葉。循環は訪問済みの印で止まる。実体の無い相対 import は解決できないものとして**赤**にする(欠けた閉包の hash で緑にしない)。
- **`@/…` は製品の実装の木に解いて辿る:** `@/x` は `{根の宣言の実装の木のソースの根}/x`(= `sourceRootPath(layout, roots)`。置き場の配置の `source-root`)に解く。**`app/tsconfig.json` の `paths` は読まない** —— `@/` = 実装の木のソースの根は仕組みが決めている in-app の形で、根そのものだけが製品の宣言から来る。Outbox の写し元は app の実装で、`@/operation/jobs/ports` のように別名で import するため、辿らないと import 先だけが変わった束でまた hash が動かない(Outbox の `route.ts` の閉包は `composition/jobs/run` / `composition/cron-auth`、`job.queue.ts` の閉包は `operation/jobs/ports` まで届く)。実装の木を持たない製品では `@/…` は辿らない(境界のまま)。実体の無い `@/…` は相対 import と同じく**解決できないもの**として赤にする。
- **境界はパッケージ import である:** 上の `@/…` を除く、相対でない指定子(`@kaninabe/…` / `node:…` / 素のパッケージ名)で止まる。ここから先は閉包に入れない —— 依存の中身は写し元の外である。**境界の外が動いても hash は動かない**ので、モデルが写している実装が `@kaninabe/…` や素のパッケージの先にあるなら、その先のファイルも `SOURCE:` に**直に名指す**。
- **`SOURCE-FN:` は閉包を持たない**(DB の関数の定義は SQL で、import が無い。解決先の migration 1 本の本文の sha256 のまま)。`premise` が読む 3 ファイルの値も対象外である(読んでいるのは**値**で、その値は hash ではなく値そのもので突き合わせている)。
- **動いたファイルの名指し:** hash が食い違ったとき、検査器は `git log -S<宣言の hash>` でその行を書いたコミットを探し、**そのコミットの版で閉包を計算し直して**、いまの閉包と比べる。動いたファイルのパスと旧 → 新の hash、増えた・減った import を Finding の下に出す。履歴を引けないとき(浅い clone・未コミットの宣言)は、その旨を書いて閉包の全ファイルを出す(名指せないふりをしない)。

**鮮度(と前提の比)は毎 push 見る(`check:formal --freshness`)。** 閉包は静的に列挙できないので、`lib/messages` や `lib/kernel` の変更でも hash は動くが、CI の `formal` ジョブの `changes` 判定(TLC を回す・約 7 分)はそれを表現できず、表現しないことにした(上)。そこで **hash の突合と前提の比だけ**(TLC も Java も呼ばない・数秒)を `npm run check:formal -- --freshness` に切り出し、**CI の docs ジョブ(毎 push)と pre-commit の `legacy/spec-tools/` / `app/` / `supabase/` の 3 スコープ**が回す(写し元が住む木のすべて —— 生成器の TS は道具の木に、Outbox の写し元は app に、`SOURCE-FN:` の関数は migration にある。framework の runtime / lint-config のスコープには入れない)。`formal` ジョブは起きたとき全部(鮮度 + TLC)を回す。これで「閉包のどこが動いても次の push で赤」になる。両者の配線は `legacy/spec-tools/__tests__/dev-repo/unit/gates/scope-parity.test.ts` が見る。

### 検査(C24)が見る 4 つと、道具が無いとき

`npm run check:formal` は ①**鮮度**(`SOURCE:` の sha256 = 写し元の閉包の hash / `SOURCE-FN:` の sha256 と実ファイル)→ ②**翻訳の一致**(`pcal.trans` を回し直して差分 0)→ ③**TLC**(性質ごとに 1 回。**1 回 120 秒で打ち切り**、超えたら答えが出ていないので赤)→ ④**宣言との突合**→ ⑤**模型の前提が実装で保たれているか**、の順に見る。どれか 1 つでも赤なら終了コード 1。所要は手元で 4 分、CI で 7 分ほどである(**pre-commit には全実行を入れない**。鮮度と前提の比だけの `--freshness` は数秒で、pre-commit と毎 push の docs ジョブが回す)。

**道具の故障は「道具」として報告する。** jar が壊れている・Java が動かないときに「PlusCal の括弧を確かめろ」と言うのは嘘であり、直す先が違う —— 外に出た字面が道具の故障を示していれば、その stderr をそのまま見せる。

**TLC の jar の固定(2026-09-25)**: tlaplus/tlaplus の `v1.8.0` タグは**毎日作り直される pre-release**で `tla2tools.jar` が差し替わる(sha256 の固定が実際に落ちた)。安定版 `v1.7.4` は `-noTE` を持たず走らない。そこで CI は**このリポジトリの release**(`tla2tools-v1.8.0-9d36716`)に写した検証済みのビルドを sha256 つきで取る。手元は `~/.tla/tla2tools.jar` に同じビルド(sha256 `9d36716f…3fef`)を置く。版を上げるときは新しい release を足し、`ci.yml` の 2 行とこの段落を更新する。

**道具(Java 21 / `tla2tools.jar`)が無ければ error で報告して落ちる。検査を飛ばして緑にはしない。** 道具が無い実行と全部を見た実行が見分けのつかない形で出ると、緑の意味が失われる(C23 が「git が答えなかったら赤」にしているのと同じ線)。jar は `TLA_TOOLS_JAR` → `~/.tla/tla2tools.jar` の順に探し、**リポジトリには入れない**。Java は `JAVA_HOME` → Homebrew の openjdk@21 → PATH の順に探し、見つけた `java` が実際に動くかまで確かめる。

CI は `formal` ジョブ(TLC・約 7 分)が回す。**起こすのは「モデルそのもの」が動いたときだけ**である(束 CI-cost・2026-10-06)。TLC が検証するのはモデルの本文・定数(`.cfg`)・性質の台帳で、**写し元との一致は鮮度(`--freshness`)が見る**——この分担が前提である。`changes` の判定は次のとおり。

| 変更 | TLC(`formal` ジョブ) | 代わりに見るもの |
|---|---|---|
| `formal/` の差分に、`\* SOURCE:` / `\* SOURCE-FN:` の行**以外**の +/- の行がある(モデルの本文・`.cfg`・`expectations.json`・ファイルの追加 / 削除 / 改名。**中身の行が出ない空ファイルの追加・削除・モード変更も** `git diff --raw` の種類とモードで拾う) | **回す** | — |
| `formal/` の差分が `SOURCE` / `SOURCE-FN` の行(hash の書き直し)**だけ** | 回さない | 鮮度(docs ジョブが毎 push) |
| 検査器そのもの(`lib/formal/`・`cli/check-formal.ts`・`cli/formal-sources-io.ts`)・`.github/` | **回す** | — |
| 写し元の閉包・migration・前提の 3 ファイルだけの変更(モデルは動いていない) | 回さない | 鮮度と**前提の比**(docs ジョブが毎 push) |
| 基点が取れない・`formal/` の差分を取れない | **回す**(安全側) | — |

**前提の比(予算 + タイムアウト < リース)は鮮度の経路(`--freshness`)でも見る。** 比を読むのは 3 つの実装値だけで TLC も Java も要らないので、毎 push の docs ジョブと pre-commit に置いた。TLC のジョブにだけ置くと、実装の値だけを動かしたコミットでは比を誰も見なくなる。判定のシェルは `legacy/spec-tools/__tests__/dev-repo/unit/formal/formal-scope.test.ts` が**本物の bash で使い捨ての git リポジトリに対して**実行して確かめる(`SOURCE` の行だけ・本文・`.cfg`・差分を取れないときの安全側、など)。

**モデルはアプリの語を持たない**ことを W1(語彙漏れの検査)が見張る —— `formal/**` は W1 の走査範囲に入っており、状態やラベルの名前が仕様の id と一致すると赤になる(`.tla` は二重引用符だけを文字列として読む。`\*` のコメントと `SOURCE` 行は対象外で、業務の語が出るのはそこだけである)。`formal/expectations.json` は**実装を名指すための台帳**なので走査しない。

### 反例の読み方

反例は 4 行の見出しと、状態の**差分だけ**の並びで出る。

```
意図:  この性質が何を言っているか
理由:  いまの実装でなぜ破れるか
実装:  どのファイルの何行目を見ればよいか
対処:  直すなら何をするか
反例(N 状態。変わった変数だけを出す):
  1. 初期状態: status=[j1 |-> "pending"], …
  2. claim("w1"): status: [j1 |-> "pending"] → [j1 |-> "running"]
  …
```

行頭の `claim("w1")` はモデルのアクション名であり、`.tla` の同じ名前のラベルの直前に `\* 意図:` がある。**プログラムカウンタ(`pc`)は出さない** —— アクションの名前が同じことを言っているからである。

### この検査が言えないこと

**「反例が無い」は「そのモデルの定数の範囲で無い」である。** ワーカー 3 本・txn 4 本で初めて現れる交錯はこの実行が見ていない。定数を上げれば見えるが、状態数と所要が伸びるので、上げるのは「その規模でしか起きない」と読めたときだけにする。また、モデルが写しているのは §2 の 4 つの意味論だけなので、**写していない意味論に依る穴はここには出ない**。
