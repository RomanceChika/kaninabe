# ルール文書のビルダー×レビュアー手順

ルール文書の新規作成・更新を、**作る側と見る側を分けたループ**で回すための段取りである。[how-to-create-rules.md](./how-to-create-rules.md)(作る)と [rule-evaluation.md](./rule-evaluation.md)(見る)を、誰がどの順で実行するかを決める。

**この文書が守っている一線は 1 つである。上位原則に沿っていないルールを絶対に配置しない。** 評価が不合格なら、必ず修正してから完了とする。ルール文書は他の全ての作業の前提になるので、間違ったまま置かれると、それに従った文書と実装が後から一斉に狂う。

## 目的

- ルール文書の作成・更新の段取りを定める
- **上位原則との整合を品質ループで担保する**
- 誤ったルールが配置されるのを防ぐ

## 前提条件

- ユーザーとの対話で、モード(新規作成 / 更新)と内容が確定していること
- **新規作成なら** doc_type と scope が確定していること
- **更新なら** 対象のファイルパスと変更内容が確定していること

## 全体の手順（概要）

### 手順1: ユーザーとの対話（オーケストレーター自身が行う）

**この段は委譲しない。** 何を書きたいのかを確定させるのは、作業を分ける前の仕事である。曖昧なまま渡すと、ビルダーは曖昧さを自分の解釈で埋めてしまい、その解釈は誰にも見えない。

**新規作成の場合**

1. **何を書きたいか**を自然言語で把握する
2. **doc_type** を決める(principle / domain / architecture / process / decision)。迷うなら [../standards/doc_types.md](../standards/doc_types.md) を参照して選択肢を提示する
3. **scope** を決める(common / backend / frontend)
4. **内容の方向性**を確認する —— 何を書くべきか、上位の原則とどう関係するか

**更新の場合**

1. **更新の対象**(ファイルパスまたは ID)
2. **変更内容**
3. **breaking change の可能性**。大きな変更なら ADR の作成を検討する(判断の基準は [../standards/change_policy.md](../standards/change_policy.md))

ここで決まったことは設計として凍結し、以降の手順で勝手に広げない。

### 手順2: ルール文書の作成（ビルダー）

ビルダーに渡す情報は次のとおり。

- モード(新規作成 / 更新)
- ユーザーの要求
- doc_type と scope(新規の場合)
- 対象のファイルパス(更新の場合)
- 読むべき正典のパス(**サブエージェントは CLAUDE.md を読まないので、必読文書はプロンプトに明示する**)
- worktree のパス(分離した作業場を使う場合)

手順は [how-to-create-rules.md](./how-to-create-rules.md) / [rule-update.md](./rule-update.md) に従う。

**成果物の検査は 2 つである。**

1. ファイルが作成・更新されていること
2. **`npm run verify` がエラーなしで通ること**

### 手順3: 品質評価（レビュアー）

レビュアーに渡す情報は次のとおり。

- 評価対象のファイルパス
- 変更内容の概要(新規か更新か、何を変えたか)
- worktree のパス(ある場合)

評価は [rule-evaluation.md](./rule-evaluation.md) の 6 観点で行う。**レビュアーはビルダーの説明ではなく、仕様と正典から期待を組み立てて突き合わせる。** 説明を先に読むと、評価は説明の追認になる。

### 手順4: 判定と修正ループ

- **合格** → 手順5 へ
- **不合格** → 評価の結果をビルダーに渡して修正を指示し、手順2 に戻る

**修正ループは最大 3 回までとする。** 3 回で合格しない場合は、それは書き手の技量の問題ではなく、要求か既存のルールのどちらかに矛盾がある。次をユーザーに報告して判断を仰ぐ。

- 評価で検出された問題の詳細
- 上位の原則と矛盾しているなら、その内容
- 人間の判断が必要である旨

**裁定を下すのはユーザーである。** ビルダーとレビュアーの意見が割れたまま、どちらかが押し切る形で完了させない。

### 手順5: 完了報告

報告する内容は次のとおり。

- 作成・更新したファイルのパス
- 評価結果の要約
- 次のアクション

**コミットはこのワークフローのスコープ外である。** 文書が正しい状態になったことと、それを履歴に刻む判断は別の決定であり、後者はユーザーが行う。

### 体制を省略してよい場合

**1 本の文書を直すような閉じた作業では、ビルダー 1 人が全検査緑 + 自己レビューで代替してよい。** 体制の目的は独立した目を入れることであり、目的に見合わない場面で形式を守ること自体には価値が無い。ただし、原則・アーキテクチャの変更や breaking change に当たる場合は省略しない —— そこが最も間違えたときの代償が大きい。
