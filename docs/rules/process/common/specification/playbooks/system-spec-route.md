# システム仕様化ルート — 構想から本採用・実装まで

システム(または大きなドメイン拡張)をこのフレームワークで仕様化するときの推奨ルートである。
対象は「1操作を足す」(それは [domain-spec-change.md](./domain-spec-change.md) と各スキルの守備範囲)ではなく、
**ドメイン全体を新しく書き起こす・作り直す**規模の仕事。あわせて、**人間が何をどの時点でレビューするか**を定める。

出典(実測3件): 初代ドメインの構築・外部ドメインのストレステスト・超拡張版の全面書き起こし。
いずれも「このルートの形が先にあって従った」のではなく、**うまくいった進め方から抽出した**(三の法則)。

## 目的

- 仕様化の進め方を、担当者の勘ではなく**再現可能なルート**にする。
- 人間のレビューを**意味の判断だけ**に絞り、形式・整合・網羅の確認を機械に移し切る。
- 仮定と決定の流れ(保留の仮定 → 会話 → NOTES)を固定し、未決の一括レビューをなくす。

### 原則(4つ)

1. **シミュレーションで確かめる。** シミュレーションとは、実装せずに、書いた仕様だけを使って場面を順に通して確かめることである。
   「書けるか」は頭の中や正典の上で確かめない。隔離環境(worktree等)に仕様一式を置き、
   **実物の verify / generate に掛けて**確かめる。正典(`docs/specs/`)に書き始めるのは本採用後である。
2. **表現力を買う前に、要求を疑う。** 「書けない」の多くは DSL の不足ではなく、モデリングか要求の側で解ける
   ([拡張トリアージ](./dsl-extension-triage.md))。実測では、要求の単純化 1 つが拡張候補を複数消すことが繰り返し起きている。
3. **決定は小出しに。** 未決を溜めて一括レビューにしない。仮定は保留の仮定として明示し、会話で 1 つずつ決め、
   決定は都度 `NOTES.md` に記録する(PRIN-0004)。
4. **機械は形式、人間は意味。** 形式・整合・網羅の検査は機械に全部やらせ、人間は
   「見せていいか・できていいか・その判断でいいか」だけを見る。人間に形式チェックをさせた時点でルートの失敗である。

## 前提条件

- **事前に読むもの**
  - [拡張トリアージ](./dsl-extension-triage.md) — 「書けない」に当たったときの判定手順(フェーズ1で必ず使う)
  - [domain-spec-writing.md](../standards/domain-spec-writing.md) — DSL の守備範囲と散文の規則
- **対象規模の線引き**: 既存ドメインへの 1 操作・1 画面の追加はこのルートではなく、ルーティング表の該当行(スキル)へ。

## 全体の手順・流れ（概要）

| # | フェーズ | やること | 成果物 | 人間の関門 |
|---|---------|---------|--------|-------------|
| 0 | **聴取** | 構想を遮らず聞き切る。資料の**信頼度序列**を決める(実測の既定: **構想 > 一次資料(議事録等) > 既存コード** — コードは「現状」であって「決定版」ではない) | 構想メモ(NOTES) | 序列の確認 |
| 1 | **シミュレーション(書き起こし)** | 隔離環境で全ドメインを DSL 化し、verify を実際に実行する。**A/B/C/D 分類**(下記)。**変異注入**で検査の実効を測る | `docs/design/{名前}/findings.md`(設計ドラフト。**正典ではない**)+ `specs/` 一式 + verify 生ログ | findings を読む(特に C 表と保留の仮定) |
| 2 | **決定ラウンド** | 保留の仮定を会話で 1 つずつ。拡張候補は先に**要求の単純化**を検討する。決定は都度 NOTES へ | NOTES の決定記録 | 決定そのもの |
| 3 | **改訂と本採用判定** | 全決定を反映した改訂版で、もう一度シミュレーションする。findings を改訂し、**「本採用に耐えるか」を言い切る**(根拠: blocker が構造で解けたか・残る拡張候補は後入れで壊れないか) | findings 第 2 版(初版は保全) | 言い切りへの ○× |
| 4 | **本採用** | ドラフトの**足場を剥がす**(変更史・検証記録の類は findings へ)。仕様を正典 `docs/specs/` に移す(**YAML+生成図表+標識**の最終形)。業務の意味論(W)を W 層に書く | 正典の仕様・W 層 | 意味レビュー 3 点(§詳細) |
| 5 | **実装** | 通常のルーティング(スキル・operation 定型・テスト義務)へ接続 | 実装+全検査緑 | U 群 warning の裁定・variant 昇格判断 |

### フェーズ1の A/B/C/D 分類

| 区分 | 意味 | 行き先 |
|----|------|--------|
| A | 書けて検査も通った | そのまま |
| B | DSL 外隔離で書けた(算術・集計など最初から線の外) | テスト義務 |
| C | 書けない=拡張候補。**「迂回検討済み」列必須**([拡張トリアージ](./dsl-extension-triage.md)の起票要件) | トリアージへ |
| D | 仮定(ユーザー確認事項) | 決定ラウンドへ |

## 詳細

### 変異注入(フェーズ1・3)

「検査が実際に何を捕まえるか」の実測である。壊れた仕様を意図的に書き、verify が鳴るかを見る。
素通りした変異は「検査の穴」として**表現力の議論と分離して**起票する(「書けたように見えて何もしない」型は最優先)。

### 人間レビューの 3 点セット(フェーズ4以降の定常形)

レビューは**ハンドブック(`docs/book/`。生成物)の章を読みながら、その場で判断する**。
どの章にどれだけ判断が乗っているかはレビューの手引き(ハンドブックの `review-guide`。生成物)が配る。見るのは:

1. **⚠ の行** — `scope: all` の全件公開(本当に全員に見せてよいか)・DSL 外不変条件(コードに任せてよいか)・
   ガード条件の「意味」列(業務のタイミングとして足りているか)。各章の表にインラインで印が付く。
2. **マトリクス(state×event)の ✓/✗ チェック** — 形式的には合法だが業務的に変なマスは人間にしか見えない
   (変異注入で実証済みの、人間固有の守備範囲)。各集約の章のライフサイクル節にある。
3. **標識への異議** — 各仕様に残る手書き 1〜3 行(否定・線引き)は判断の記録である。違うと思ったら言う場所。
   章の文脈にそのまま引用される(別冊の台帳は無い)。

レビューで見るものは**この 3 つだけ**であり、それ以上を人間に要求する状態はルートの失敗として扱う
(足りないのはレビュー時間ではなく、機械の検査かハンドブックの章である)。
**人間の入口は `docs/book/`(ハンドブック。全部生成物)であり、specs/ を歩く必要がある状態は仕組みの失敗として扱う。**

### 保証マップ — 人間が見る仕様と、ほぼ自動保証の仕様

切り分けの基準は 1 つ: **その宣言の正しさを機械が判定できるか**。
「業務としてそれでいいか」だけが人間に残り、形式・整合・導出はすべて機械の側にある。

| 仕様 | 人間の判断が乗る宣言 | 機械が保証する部分 |
|------|--------------------|-------------------|
| **access_spec** | **ほぼ全部**(reads の scope・writes/creates の by — 「誰に見せるか・誰ができるか」は業務の意味そのもの) | 整合(ロール実在・未知キー・二層可視性との対応) |
| **state_spec** | 遷移の ✓/✗ と guard の中身・otherwise_forbidden の理由 | 決定性・到達性・禁止理由の網羅(V群)・マトリクスの導出 |
| **invariant_spec** | statement と formal の**意味の一致**・DSL 外(テスト義務でよいか) | formal の文法・フィールド実在・執行点の対応 |
| **query_spec** | **for / via / projection**(露出の口 = 誰に何を返すか)・filters の業務妥当性 | Q0〜Q7 の全突合・スコープ条件(binding の写し = 決定的) |
| entity_spec | 値域(min/max・enum の語彙)の業務妥当性のみ — 軽い | 型・制約の実装対応(zod 生成)・参照実在 |
| action_spec | **ほぼ無し**(handles・前提・input はドメイン仕様からの接地で決まる) | 接地検査・TC 台帳との突合(A群) |
| screen_spec | 操作の**束ね方**・variants・navigations(動線) | layout 形式・宣言∩遷移の導出・testid・S群 |
| design_token | contrast に**どの組を宣言するか**・値の意匠(shots 目視) | 値域・参照解決・宣言済み contrast の実比(G群) |

太字が「読まないといけない」場所、それ以外は「見れてもいいがほぼ自動保証」。
章単位の具体的な内訳はハンドブックの**レビューの手引き**(ハンドブックの `review-guide`。生成物)が配る —
章ごとに人間の判断が乗る宣言の件数と標識の本数を列挙する。**「流し読みでよい」と機械が言うのは、
章の定義が理由つきで精読不要を宣言している場合だけ**である(章の定義の `reviewFree`。理由の無い宣言は型で書けない)。
宣言が無いまま件数が 0 の章は**「未分類(要確認)」**と出す —— **「数えていない」と「数えた結果 0 だった」を
見分けのつかない形で配らない**ため(上の表に行が無い宣言種別は、そもそも数えられていない)。
未分類が出たときの人の動作は [human-review-guide.md](./human-review-guide.md) モード B にある。

### 画面の仕様化(フェーズ5の内訳)

画面はドメインと**進み方が逆**である。ドメインは構想を聞き切って書き起こすが、画面は
**機械が作るべきものの母集合を配ってくれる** — 本採用直後の verify で出る **S10 エラー
(人間ロールが実行できるのに、どの画面にも露出していない操作)の一覧が、そのまま画面の作業台帳**になる。

| 手順 | やること | 人間の関門 |
|------|---------|-------------|
| 1. 束ね方 | S10 の未露出操作を**どの画面に束ねるか**を決める(画面一覧と動線の設計。**ここが人間の意図が入る主戦場** — 機械は「何が要るか」までしか言えない) | 画面一覧・動線への ○× |
| 2. 画面ごとの仕様化 | screen_spec / chrome_spec を 1 枚ずつ(入場の関門・layout・variants・overlays・actions)。実装まで含めてスキル(/add-screen 相当)の守備範囲 | — |
| 3. 消し込み | S10 と unexposed 台帳が減っていくのを進捗として使う。**ゼロ=全操作に UI の口がある** | — |
| 4. 見た目のレビュー | 生成ワイヤーフレーム・ナビグラフ(README 側の生成物)と**画面カードの SSR プレビュー**(実装を偽データで描いた実物)で目視 | レイアウトの意図・トーン |
| 5. UX 裁定 | U 群 warning(破壊的操作の確認など)の裁定と、**データ依存の表示分岐を variant に昇格させるか**の判断(昇格した分だけ機械の保証が広がる) | 裁定そのもの |

ドメインの保留の仮定に相当するのは「束ね方」と「variant 昇格」である — どちらも機械が決められない意図の領分で、
それ以外(何が要るか・どのボタンが出るか・テスト義務)は宣言から導出される。

### 判断待ちの台帳

- 仮定・裁定待ちは **保留の仮定 → レビューキュー**(`docs/handoff/review-queue.md`)に集約する。決まったら本文から消し、決定は NOTES へ。
- 機械の指摘を意図的に受け入れない場合は**免除台帳**(理由必須)に記録する。黙殺の経路は作らない。
