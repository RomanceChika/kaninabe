# 日時とタイムゾーンの規約

日時が層をまたぐときにどの表記で運ぶか、どこで壁時計に戻すかを固定する。**保存は UTC・境界はオフセット付き ISO 8601 文字列・壁時計に戻すのは入出力の縁だけ**、が全体の形である。

## 1. 目的・スコープ

- **目的:** 日時は「同じ瞬間」を指しているのに表記が何通りもあり、変換の**向き**を 1 か所間違えても平常時は誰も気づかない（開発機が JST、CI とサーバーが UTC なら、ずれるのは本番だけ）。どこで壁時計に戻すかを 1 か所に書き、それ以外の層は瞬間だけを運ぶようにする。
- **スコープ:** DB の列型、層の境界で運ぶ表記、ガードの時刻比較、画面の表示、テストのタイムゾーン。入力フォームの変換規則そのものは [server-actions.md](./server-actions.md) §日時のタイムゾーンと精度が正であり、ここでは全体の中の位置づけだけを書く。

## 2. ルール

### 保存（DB）

- **すべきこと:** 日時の列は例外なく `timestamptz` にする。既定値が要るなら `now()`。
- **してはいけないこと:** `timestamp`（タイムゾーンを持たない）や `date` を使う。列名が `_on` で終わっていても型は `timestamptz` である（例: `loans.due_on`）。
- **してはいけないこと:** DB セッションのタイムゾーンに依存する計算を書く。`timestamptz - interval '1 day'` は**セッションの TZ で意味が変わる**（夏時間を跨ぐと 24 時間ではなくなる）。仕様の `derives` が出す `day` の加算もこの形で、**夏時間のある TZ では暦日の計算になる**（いま問題にならないのは、DB セッションの TZ が既定のまま UTC で、UTC には**夏時間が無い**ため。`Asia/Tokyo` は画面の表示用の TZ で、DB の計算には掛からない。`timestamptz` で保存していることも理由にならない —— 加算は保存の型ではなくセッションの TZ で解かれる。DB セッションの TZ を設定で変えるなら、この計算が暦日になることを先に確かめる）。
- **例:** `due_at timestamptz not null` / `created_at timestamptz not null default now()`。仕様側の型は `datetime` の 1 語で、`datetime → timestamptz` の写像はこの規約が持つ（`data_table` は列の物理型を宣言しない）。

### 層の境界で運ぶ表記

- **すべきこと:** アプリの中では日時を**オフセット付きの ISO 8601 文字列**として運ぶ。生成される zod は `z.iso.datetime({ offset: true })` であり、これが境界の唯一の形である。
- **すべきこと:** DB から読んだ値は `new Date(row.x).toISOString()` で表記を揃えてからドメインへ渡す。PostgREST は `+00:00`、`Clock` は `Z` を返すため、揃えないと**同じ瞬間が別の文字列**になる。
- **してはいけないこと:** 層をまたいで `Date` オブジェクトを運ぶ。`Date` は「どのタイムゾーンで作られたか」を持たず、`getHours()` を呼んだ側の環境で結果が変わる。
- **例:** 読み取りの正規化は、コメント付きの実装で示す。

### 比較（ガード・締切）

- **すべきこと:** 時刻の比較はガード式（`now >= loan.due_at`）で宣言し、`now` は `Clock` から `toISOString()` で渡す。エンジンは**文字列を字句順で比べる**ので、表記が揃っていることが正しさの前提である。
- **してはいけないこと:** アプリ側の `if` で締切を判定する（仕様に現れない分岐になる）。DB の `now()` とアプリの `Clock` を同じ判定の中で混ぜる。
- **例:** 走査の絞り込みは `lte('due_at', clock.now())`、可否の判定はガード。

### 表示（壁時計に戻す縁）

- **すべきこと:** 表示は `app/src/app/_lib/format.ts` の口を通す。ロケールとタイムゾーンを**明示指定**するので、サーバー（UTC）で描いてもブラウザ（JST）で描いても同じ文字列になる。**表示の基準 TZ は設定カタログの `DISPLAY_TIMEZONE`（必須。docs/specs/backend/config.md）で、`domain` の整形関数（`@/domain/datetime`）は TZ を引数で受ける**（`domain` は `process.env` を読めないため — ARCH-BE-0001）。読む口は `@/composition/config` の `displayTimeZone()` の 1 か所に集める。
- **してはいけないこと:** `getFullYear()` / `getHours()` を並べて日時を組み立てる。それは**描画した環境のタイムゾーン**の壁時計であり、RSC で作れば UTC、クライアントで作れば端末の設定になる。
- **してはいけないこと:** 「時刻を今の値にする」処理をブラウザに書く。端末の時計がずれていればその値がそのまま保存される（サーバー側の `Clock` か DB の `now()` を使う）。
- **例:** `formatDateTime(iso, timeZone)`（`toLocaleString('ja-JP', { timeZone })`。`timeZone` は呼び出し側が `displayTimeZone()` で解決して渡す）。

### 入力（詳細は server-actions.md）

- **すべきこと:** `datetime-local` の値は**実行環境の壁時計**として読み、UTC の ISO 8601 に正規化する。表示はその逆。往復（表示 → 編集 → 送信 → 再表示）で値が変わらないことをテストが固定する。
- **してはいけないこと:** 存在しない日時（`2026-02-30T10:00`・夏時間で飛んだ 1 時間）を黙って繰り上げる。変換結果を入力の表記に戻して照合し、違えば変換せず zod に落とす。

### テスト

- **すべきこと:** 日時の往復を確かめるテストは**零オフセットでないタイムゾーン**で実行する（`app/vitest.config.mts` の `env.TZ = "Pacific/Chatham"`。+12:45・夏時間あり・半端なオフセット）。同じ値を統合テスト（`vitest.integration.config.mts` の `test.env.TZ`）・E2E スモーク／shots／walker（`playwright.config.mts` 系の `process.env.TZ` とブラウザコンテキストの `timezoneId`・`webServer.env.TZ`）にも入れ、レイヤーごとに素通りする経路を作らない。
- **してはいけないこと:** UTC で実行して緑を確認する。UTC では「ローカル壁時計として読む」と「UTC として読む」が同じ結果になり、**変換の向きの誤りが 1 件も落ちない**。DISPLAY_TIMEZONE と同じ値の TZ で実行するのも同様(表示の基準と一致して偶然正しく見える)。

## 3. 注意点・例外

**この規約は実装の実態を書き起こしたものであり、実態の側に既知のズレが 3 つある**（この規約は「あるべき姿」ではなく「守られている線」を書いているので、ズレは規約の側で言い換えず、そのまま宿題として置く。台帳は BACKLOG.md）。

- **告知文の日時だけが実行環境のタイムゾーンに依存する。** (例)クリップボード用の告知文の整形が `getFullYear()` 系で手書き整形しており、その文面を RSC が作る。Vercel（UTC）では、同じ画面の「返却期限の日時」（`Asia/Tokyo` 固定）と告知文の日時が 9 時間食い違う。ローカル（JST）では一致するので気づけない。
- **「地域を実装に書かない」と「表示は `Asia/Tokyo` 固定」が正面から衝突している。** 入力はローカル壁時計、表示は JST 固定なので、JST 以外の環境から入力すると**打った数字と一覧に出る数字が違う**。表示の基準タイムゾーンをどこで宣言するか（`entity_spec` か・運用設定か）は未決である。
- **「N 日前」の逆算が 2 実装ある。** アプリ側は固定ミリ秒（`reminder-schedule.ts`）、DB 側は `interval '1 day'`（`check_rpc.sql` の `due_on`）。夏時間を跨ぐと一致しない（日本運用では顕在化しない）。
