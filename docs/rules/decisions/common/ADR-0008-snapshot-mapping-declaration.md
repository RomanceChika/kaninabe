# ADR-0008: スナップショットの写像を DSL に載せ、写像先の列の覆いを検査する

## Status

accepted (2026-08-27)

---

## Context

### 背景

元の製品 v2 は「公開してよい情報しか列が無い集約（`public_*`）を作り、公開の遷移がそこへ写す」という形（**公開時Fix**。迂回パターン P-1）を採った。第1版は同じ要求を「読み取り経路の `projection` に列を書かない」で表しており、**`projection` に 1 語足すと内輪の利用者名が公開サイトに出るのに verify は緑**という状態だった（第1版の変異注入 #1・#2 で実測）。公開時Fix はこれを構造的に消す —— 列が存在しないものは書けず、書けばスキーマ生成が落ちる。

**ところが、その代償として新しい無防備な不作為が生まれた。**

公開側の集約に列を 1 つ足しても、何も鳴らない（第2版の変異 #10 = 起票 C-29a）。写像そのもの（どの列をどこへ写すか）は `effects: [snapshot_public_item]` という**副作用 ID の中にしか無く**、写し漏れ・写し過ぎを見る機械が 1 つも無い。「公開側にあるのだから公開してよい情報だ」という誤読を誘う列が、`null` のまま静かに増える。

### 前提条件

- 拡張トリアージ（dsl-extension-triage.md）は通してある。**迂回検討済み = P-1 そのものの代償**であり、上位の迂回が存在しない（公開時Fix を採ったからこそ生まれた不足である）。
- 2 実例ルールには**形式的には足りない**（元の製品の 3 か所は同一ドメイン内なので 1 実例）。ただし同playbook §手順3 の**例外条項**「いま入れないと後から入れられない」に該当する —— 公開側の列が増えたあとで写像の宣言を後付けすると、既存の写しとの整合を取り直す全面改修になる。
- ADR-0003（DSL の表現力を意図的に制限する）の適用範囲を広げる変更にあたるため、同playbook §手順4 の要求どおり ADR を書く。

---

## Decision

### 決定内容

**`state_spec` の `effects[]` に、任意項目として `snapshot`（スナップショットの列対応表）を持たせる。検証器 V12 がその写像を検査し、写像先エンティティの列で写像に現れないものを警告する。**

```yaml
effects:
  - on: publish_public
    do: [snapshot_public_item]
    snapshot:
      to: public_item                 # 写像先エンティティ
      fields:
        - { from: item.id,    to: item_id }
        - { from: item.title, to: title }
        - { from: branch.name,    to: branch_name }
        - { from: now,           to: published_at }
```

1. **書けるのは列の対応表だけである。式ではない。** 変換（匿名化・連結・切り詰め）の中身はここに書けず、`do` に並ぶ副作用 ID の実装が持つ。その正しさは不変条件（`enforced_by: application`）とプロパティテストが守る。
2. **写像元（`from`）に書けるのは `{entity}.{field}` の 2 段か、予約語 `now`（この写しを作った時刻）だけ。**
3. **V12 の 3 観点**（正は domain-spec-writing.md §検証チェック）:
   - ① 写像先（`to`）のエンティティと列が実在し、型が一致する — **error**
   - ② 写像先の `auto: true` でない列で写像に現れないものがある — **warning**（これが変異 #10 を塞ぐ）
   - ③ 写像元（`from`）のエンティティと列が実在する — **error**
4. **写像元は「実在」までを見て「接地」を要求しない。** ガード式の参照パスは `context` で解決できることまで要求する（V2）が、スナップショットは**子の行の集まり**から写す（蔵書 1 件 → 予約 N 件）ことがあり、その関係は `context`（1 対 1 の参照パス）では表せない。どう辿るかは副作用の実装が持つ。
5. **生成物を 1 つ増やす。** `app/src/domain/generated/snapshots.ts` に写像表を出し、実装は**この表が持つ列だけ**を書く。app 側のテストが表と実際に書いた列を突き合わせる（V12 が仕様の内側を、生成物が仕様と実装の間を見る）。

### 適用範囲

`docs/specs/domain/{aggregate}/states.md` の `effects[]` のみ。`creates` / `deletes` / `writes` には `effects` 自体が無いので（domain-spec-writing.md）、この拡張も及ばない。

---

## Consequences

### Positive（メリット）

- **変異 #10 が塞がる。** 公開側の集約に列を足して写像を書かないと、verify が警告として鳴る（このリポジトリは警告 0 も出荷条件にしている）。
- **「何を公開しているか」が 1 か所に集まる。** レビュー時に読むのは対応表 1 つで、副作用の実装を読まなくてよい。
- **決定可能性を 1 ミリも壊さない。** 検査は列名の照合と型の照合だけで、式の評価が入らない（ADR-0003 の取引に影響しない）。
- **匿名化のような変換も宣言に痕跡が残る。** `hold.patron_label → patron_label` という行があることで、「この列は写しである」がレビューに見える。

### Negative（デメリット・トレードオフ）

- **写像の宣言と副作用の実装が二重管理になりうる。** 生成物（`snapshots.ts`）を実装が消費する形にして緩和しているが、SQL（RPC）側の insert 列は生成物を直接読めない（突合は `rpc-parity` と写像表を使う app 側テストで行う）。
- **変換の正しさは依然として宣言の外にある。** 「公開用の写しに利用者の実名を書いていない」は対応表からは読めず、不変条件 + プロパティテストが守る。
- **写像元の綴りは実在までしか見ない。** `hold.hold_position` が「この蔵書の予約」であることは検査していない（実装が別の蔵書の行を写しても V12 は黙る）。
- 検証器が 1 つ、生成器が 1 つ増える（保守対象の増加）。

### Neutral（その他の影響）

- `snapshot` は**任意項目**なので、スナップショットを持たない既存の `effects` は 1 文字も変わらない。
- V12 は `snapshot` 宣言がある effects だけを見るため、宣言しなければ検査も走らない（**宣言しないことで検査から逃げられる**）。これは `unhandled` / `unexposed` のような免除の口を持たない点で他の検査より弱く、規約でのみ縛る。

## Alternatives Considered

### Option 1: 拡張せず、公開側集約の列をレビューでだけ見る

- **Pros**: DSL が増えない。ADR-0003 の取引に手を触れない。
- **Cons**: 第1版で「不作為は検査できない」と実測した穴の、置き場所が変わっただけの再演になる。公開側の列は今後も増える（写真・チケット導線・配信 URL）。
- **Why rejected**: 公開時Fix の価値は「後から 1 語足しても壊れない」ことにあり、その価値を最も損なう変更（列の追加）だけが無検査で残るのは本末転倒である。

### Option 2: 写像を式として書けるようにする（`to: title, expr: item.title`）

- **Pros**: 連結・切り詰め・匿名化まで宣言に載る。
- **Cons**: 式の評価器がガード式とは別に要る。文字列演算は変数のドメインが有限でなくなり、**ADR-0003 の決定そのものを変える提案**になる。
- **Why rejected**: 買いたいのは「列の覆いの検査」であって「変換の宣言」ではない。変換の正しさは 1 つの純粋関数のプロパティテストに閉じており、そこは既に守れている。

### Option 3: 公開側集約に専用の `doc_type: projection_spec` を作る

- **Pros**: 写像が独立した文書になり、レビューの単位が明確。
- **Cons**: 「いつ写すか」（遷移）と「何を写すか」（写像）が別文書に割れる。両者は同じ 1 つの判断であり、割ると片方だけ直る。
- **Why rejected**: `effects` は既に「この遷移が何を起こすか」の欄であり、写像はその内訳である。同じ場所に置くほうが SoT として正しい。

## Notes

この拡張は「公開時Fix を採ったからこそ生まれた不足」を埋めるものであり、**モデリングを変えて回避する余地が無い**（迂回の上位が存在しない）という点で、これまでの拡張候補と性質が違う。2 実例ルールを例外条項で越えた記録として残す。

**追記(2026-10-03。束 F-warn-ledger)**: Positive の「このリポジトリは警告 0 も出荷条件にしている」は、**「拡張候補でない警告が 0 であること」**(受け入れの宣言を書いて通したものは、元々警告にならない)に読み替える。決定(2026-10-03)で「警告 0」は決定版の基準から外れた —— 警告 18 件は全部「仕組みがまだ作りきっていないもの」で、自己矛盾ではなかった。そのうえでユーザーは「警告の中にも管理の仕方を分けた方がいい。仕組みを拡張すれば吸収すべき問題か、仕組みは変えるべきでないが警告になる例外か。同じ扱いだと後々ややこしい」と指示した。verify の warning は**拡張候補**(仕組みの宿題。台帳 `legacy/spec-tools/extension-candidates.md`)と**未分類**(どの候補にも当たらない)に分けて出し、出荷を止めるのは未分類(拡張候補でない警告)のほうである。拡張候補に当たる警告が残ることは出荷を止めない(仕様の欠陥ではなく仕組みの宿題だから)。この ADR の決定(写像の宣言と V12 の覆いの検査)は変わらない。写像が覆われていない警告は V12 の検査 ID で出るので、台帳に載らない限り**未分類**として数えられ、出荷の前に消す対象のままである。

**追記(2026-10-06。束 CI-nightly)**: 出荷の条件の置き場所を変えた。決定(2026-10-06)で、**本番 DB への出荷(`deploy`)は push の `ci.yml` から外れ、夜間の `nightly.yml` が持つ**。push は軽い検査(docs / app / formal)だけを回して約 10 分で終わり、実 DB を使う重い検査(integration / samples-db / e2e。約 30 分)と出荷は、**main が前回の夜間から動いた日だけ、夜に 1 回**回る(動いていない日は判定のジョブ 1 本で終了し、分数をほぼ使わない)。出荷の条件はこうなった: **夜間の重い 3 本が全緑**・**main の最新の push の CI が success**(台帳だけの push は CI が起動しないので、その間が台帳だけなら許す)・この run のコミットが main の先頭・secrets が揃っている。**push が赤のまま夜になった場合は、出荷せず夜間を赤にする**(skip で緑にすると、main が動かない限り次の夜間が「動いていない」で終了し、直ったあとも出荷されない)。この ADR の決定(写像の宣言と V12 の覆いの検査)と、上の「警告」の読み替えは変わらない —— 変わったのは「出荷」が **push 即時ではなく夜間の全緑のあと**になったことだけである。**push しても本番は変わらない**(出荷が 1 日遅れる代わりに、1 日の Actions 分数は約 40 分 × push 回数から、約 10 分 × push 回数 + 約 30 分 × 1 回になる)。運用(夜間が赤だったときの手順・手動実行の打ち方)は 開発用リポジトリの運用手順書(runbook §5-2。非公開)、構造の見張りは `legacy/spec-tools/__tests__/unit/gates/{nightly,ci-cost}.test.ts`。

**追記(2026-10-07。束 ㉓-c)**: 上の「出荷を止めるのは未分類」を**執行した**。`npm run verify` に `--fail-on-unclassified` を持たせ(未分類の警告が 1 件でもあれば exit 1。拡張候補に当たる警告は exit 0 のまま)、CI の docs ジョブと pre-commit のすべての verify が付ける(題材 6 つの通し実行には付けない)。それまでは「未分類 0」が目標の文言でしかなく、製品の表の `lookup` を消して未分類が 1 になっても push の CI も夜間の出荷も緑だった(監査 2026-10-06 の H6)。あわせて台帳が製品の直せる警告を吸い込む口を 2 つ塞いだ: 絞りの鍵がある検査を挙げる候補は `scope` 必須(W5)・`framework_tables` の絞りは「製品がその表を持ち場とする関数を宣言していない」ものだけ(宣言していれば製品が `lookup` を書ける)。この ADR の決定(写像の宣言と V12 の覆いの検査)と、上の「警告」「出荷」の読み替えは変わらない。
