# PRIN-0009 — セキュリティはデフォルトで担保する

安全側を**初期値**にし、危険側を**オプトイン**にする原則。考慮漏れが起きても安全な側に寄る状態を保つ。

## 原則 {#statement}

- セキュリティが担保される時点は**初期値**である。「後から設定する」ものにしない。
- **安全でない状態をオプトインにし、安全な状態を初期値・標準にする。** この非対称がこの原則の核である。
- 失敗時の挙動を指定しておく。すなわち、**考慮が漏れても既定が安全側に寄る**ようにする。

## 背景 {#rationale}

セキュリティの考慮漏れは、起きたときの被害が大きい。他の不具合のように「気づいてから直す」で済むとは限らない。

そして「後で設定する」「オプトアウトで無効化する」という方式では、設定を忘れたまま、あるいは初期値のまま本番に出る事故が起きやすい。事故の形はいつも同じで、**誰も何もしなかった**である。

だから初期値を安全側に固定する。そうすれば、何もしなかったときに残るのが安全な状態のほうになる。認証・認可・暗号化・入出力検証といった、スタックによって中身の変わる要件が、既定で満たされている状態から始まる。

## 影響 {#implications}

- **初期値・標準**: 認証が要るものは既定で認証を要求する。機密は既定で保護する。外部からの入力は既定で検証する。無効化・緩和は、明示的な設定に限る。
- **オプトアウトの禁止**: 保護を弱める設定を認める条件は、やむを得ない事情があり、かつその理由が decision に記録されていることである。**既定値を「無効」にしない。**
- どの認証方式を、どの暗号化を、どの検証を既定とするかという個別の要件は、この原則の**適用**として各スタックの architecture・規約側に置く。

## 例外 {#exceptions}

- 開発・検証用のローカル環境では、既定を緩めてよい。ただし条件として、**本番・共有環境では安全側の既定が適用される旨を規約で明示する**こと。緩和が本番へ漏れる経路を、文書の上で塞いでおく。
