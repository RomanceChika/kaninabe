# Known limitations (0.x)

kaninabe is at 0.x and not stable. The tree was carved from a larger private repository, so some things are missing or rough. Each item is meant to be closed by its own change.

1. **The demo product has no implementation tree.** `product.md` points at `app/`, but the repository carries only the specs and the generated `supabase/migrations`. Root `verify` is green; `generate:check` is not run at the root. Generator behaviour is checked by `test:spec-tools` on the samples.
2. **No sample covers some real-world checks.** A product-bound test of a real `config.toml` against an OAuth auth spec was removed; no sample has an auth flow with a callback and a `supabase/config.toml`, so that end-to-end check is untested here. Two scans (`session-alive`, `session-lifecycle`) run with lower thresholds until a sample covers them.
3. **Formal models (`formal/`, `check:formal`) are not included yet.** Their `SOURCE` pins name files that do not exist here and must be re-pointed first.
4. **Tests that fail only when run as root** (for example a test that makes a directory unreadable) pass as a normal user.
5. **Timing tests.** `markdown.test.ts` bounds CPU time in absolute milliseconds (30 s). Replace it with a machine-independent check: the CPU time ratio when the input length doubles.
6. **Vocabulary in tests and fixtures.** `framework/` and the rules under `docs/rules/` are neutral. The code, tests and fixtures under `legacy/spec-tools` still use the vocabulary of the project they came from in many files, including text rendered into the generated handbook examples. They are being replaced by the neutral sample domain.
7. **Guarantee ids.** `TC-GUAR-` is the namespace for a product's guarantee rows. Two generators emit fixed ids such as `TC-GUAR-HEADERS-001` that a product's rows must use, and no sample declares them yet. Add a sample row for each kind, or derive the ids from the product catalog.
8. **Dangling references and process residue.** Docs and comments still mention working files that are not in this repository (a notes file, a backlog, a review queue, a handoff folder, a nightly workflow) and numbered review rounds. `vitest.heavy.config.ts` lists test paths that do not exist.
9. **CI** lacks "generate --check on samples" and tests against a Postgres service, and the actions are pinned by tag, not by commit SHA.
10. **Docs describe machinery that is absent here** (an integration-test row in CLAUDE.md, enforcement-matrix figures, a pre-commit that "runs verify"). The pre-commit hook only scans for secrets.
11. **Runtime coverage exclusions.** The 100% threshold on `framework/runtime/src/**` was met partly by generated tests of the original product. 22 runtime files that only those tests reached are listed by name in the coverage `exclude` of `vitest.config.mts` instead of lowering the threshold. Close it by generating and running unit tests for a sample product, then delete the list.
12. **Citations of things that do not exist here.** Docs and comments cite historical migrations, `__tests__/dev-repo/...`, `lib/fs-io.ts`, `@kaninabe/runtime/rpc`, working files, round ids such as "束" and "点検 N 回目", and `NOTES.md` / `BACKLOG` pointers. Each is to be removed or reworded as history without a path.
13. **The push-before gate depends on the hook being called.** `scripts/push-gate.sh` and `.githooks/pre-push` work only where `core.hooksPath` is set (`scripts/setup-dev-env.sh` sets it); an environment without it, `--no-verify` and a push of a ref the hook does not see are not stopped. The rule is to check at the start of work that the hook path is set, and never to skip the hook. Nothing checks this. What a push is scanned over is the set of commits that the destination does not advertise on its branches (asked at push time with `git ls-remote --heads`; `scripts/push-range.sh` prints the set); commits it holds only under other refs (tags, pull request refs, hidden refs) are scanned again, which is only more work, and a destination that cannot be asked, or a history that cannot be read to the end, stops the push. The URL that is asked is the URL the push really goes to: `git ls-remote` applies `url.<x>.insteadOf` to a URL again, so `push-range.sh` compares the URL it was given with `git ls-remote --get-url` in the same configuration, and when they differ it subtracts nothing (every commit is scanned) rather than use another repository's answer. Both the hook and the reviewer's by-name call resolve the URL in the caller's configuration, the way push does. The repository is the caller's (`GIT_DIR`, `--git-dir`/`--work-tree`), found once in the caller's environment and handed to the clean environment; a bare repository, no work tree, or `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` stop the scripts with a reason. `push.recurseSubmodules` pushes a submodule with the hook of the submodule's own repository, which this repository's hook does not cover. A remote with several push URLs runs the hook once per URL, and each URL is asked about itself.
14. **The content review record can be written by the author.** `kaninabe.contentReviewed` stops a push whose commit has no record of having been read for publication, but anyone can write the sha without reading. That is a rule, not a check. What the record is bound to is checked: it is `<head sha> <range id>`, where the range id is a sha256 over the destination URL actually contacted, the head sha and the exact ordered list of commits to scan (`scripts/push-range.sh` prints it, with the command that records it). The hook recomputes it at push time and refuses when it differs (the destination's branch was deleted or moved, another URL is pushed to, a commit was added); the gate is given the id of the commit list and stops if it would scan another list. A record in the old form (a commit id only) is refused, and so is a record or a computed range id that is not 64 lowercase hex digits (one shared check). A remote with several push URLs has one range id per URL, so a record fits one of them. The hook allows pushes to `refs/heads/*` only (a branch deletion passes), and compares the pushed object itself, not what it points to, with HEAD. A tag push, a deletion included, is refused (tags are created and deleted only by the tag workflow); so is any push to `refs/notes/*`, `refs/remotes/*`, a pull request ref and the like, and an annotated tag object pushed by id to a branch. Reason: the message of a tag, a note and any other non-branch object is not scanned, and the object reaches the destination's object store even when the ref update is refused afterwards.
15. **A branch with no pull request yet gets only the general scan in CI.** Before a pull request exists, the word list is applied only by the pre-push hook on the developer's machine. In `ci.yml` the older word-scan step (`scripts/scan-public.sh`) still reads the word list on pull request runs (the gate step does not); it stays until the CI rework. The key-scan steps and the scan of the pull request text are gone from `ci.yml`: keys are scanned by the gate only, and the title and body of a pull request are scanned by `pr-gate.yml` (`scan-pr-text.sh`), which is why the `edited` pull request type no longer starts `ci.yml`. CI now scans only what is reachable from `HEAD`; commits under other refs are checked by the push or CI run of those refs. That holds only for a ref that actually goes through a push or a CI run with these checks: one run reads what its own `HEAD` reaches, and nothing goes back over refs that already exist (the old key step listed the commits under every ref of the checkout; that is gone). The word-list step of the gate in `ci.yml` is guarded by `if: github.event_name == 'push' && github.ref == 'refs/heads/dev'`, which only stops it from running by mistake; **it is not a boundary**: a branch or a pull request from this repository can change the workflow file and still read the secret. The boundary (the word list readable only by reviewed definitions that run from the base branch, for example an environment secret restricted to the main branch) comes with the CI rework and needs a repository setting that only the owner can make; until then the word list is readable by any workflow run of this repository. The public output of the old word step is limited to counts (`SCAN_QUIET`); `scripts/gitleaks-public.sh` no longer exists. What stays true: the pre-commit hook (`gitleaks git --pre-commit --staged`) still honours a gitleaks config, an ignore file and inline `gitleaks:allow` comments of the scanned tree, and the tool's default allowlist; it is a convenience before the gate, not a boundary. In the gate, public output is counts only too, and an unreadable gitleaks or actionlint result stops the gate (exit 2). **CI is not an independent judge of a pull request yet.** In a `pull_request` run of `ci.yml` the gate script, the rules and the exclusion list are the ones of the pull request's own head, so a change to them is judged by itself; the isolation described in 16 is about the scanned tree's data (its config, ignore files and attributes), not about who supplies the scanner. Until the CI rework pins the scanner, the rules and the list to a reviewed version and hands the checked version over as data, a change under `scripts/`, `.githooks/` or `.github/workflows/` relies on review.
16. **Parts of the gate in the design that are not built yet: (c) and (d).** (a) **Exclusions** are one list, `scripts/scan-exclusions.tsv`, and nothing else skips a file. A line is `kind<TAB>path<TAB>value<TAB>reason`, with no blank line, no comment line and no carriage return; `path` is literal and relative (no `*`, `?`, `[` or `]`, no leading or trailing `/`, no empty, `.` or `..` segment, no control character); `reason` is not empty. The path need not exist any more: history still holds the file. Kind `binary` names a file the scans cannot read; its value is the blob id (40 lowercase hex digits), so changed content at that path is red again, and the same content at another path is red (a file renamed later is red at its new path). Kind `keys` names one content at one path for the key scan; its value is the blob id too, so a changed file is scanned again, a directory entry does not cover the files in it, and a name that only looks alike (`P.bak`, `P` with another character for the dot, `x/P`, `P/inner`) is scanned. A `keys` entry silences nothing else: a mail string, a word of the list and an unreadable file at that path stay red. The repository root holds a `.gitleaksignore` with one line for the vendored rule that is itself shaped like a key; it exists only for the pre-commit hook, mirrors the `keys` entry for `scripts/push-gate.gitleaks.toml`, and the gate ignores it (the gate reads only the list). Kind `mail` names one mail-like string in one file; its value is `sha256:<64 lowercase hex digits>` of the exact string (the bytes of the string with no line break, made by `sha256sum`, which the gate needs anyway; a `sha256sum` that is missing or fails is exit 2 with `could not check the mail entries`, never "allowed" or "not allowed"; the check does not depend on which awk is installed, and a test runs it with every awk found on the machine), so the list holds no address, and the string is allowed in that path only (in any other path and in a commit message it is red). Only an exact duplicate line (same kind, path and value) is refused; several `mail` lines for one path, and several `binary` lines for one path (one per blob over the history), are valid. A line that does not fit, an unknown kind, an exact duplicate and a missing list file are exit 2; an empty file is an empty list. The list is read from the scripts directory of the gate that runs (next to `push-gate.sh`), never from the scanned tree and never from the environment, so a list inside the tree being scanned is not the list (the tests run a copy of the scripts directory with the list they need). No other mechanism exists: the vendored `scripts/push-gate.gitleaks.toml` holds the rules of the pinned gitleaks' default configuration (`tests/push-gate/scan-exclusions.test.mjs` compares them with the default carried inside the pinned binary, found offline), without `useDefault` or `[extend]`, without the global allowlist, and without any `paths =` list; before its first rule it holds only comments, `title` and `minVersion`. The default has three `paths` lists inside rule-level allowlists (`.bb` files for `generic-api-key`, and `@octokit/auth-token/README.md` for two GitHub rules); a key there is now found. An allowlist that combines its parts with OR loses only its `paths`; one with `condition = "AND"` that had `paths` is dropped whole, because dropping only the paths would widen it to every file. So a key under `node_modules/`, in a `.svg`, or in a file named `gitleaks.toml` or `.gitleaks.toml` at any depth is found. No script has a `:!` pathspec, an `--exclude` or a glob that skips files (the same test checks it). A change to the list is a change of the same kind as one to `.github/**`. (b) **Mail-address strings** are matched whole: the allow pattern is anchored at both ends and holds exactly these: an address whose host ends in the label `example`; `example.com`, `example.org` and `example.net` themselves (not a subdomain of them); the noreply forms (`[<number>+]<login>@users.noreply.github.com`); `git@github.com`; and a string whose last label is digits only (`pkg@1.2.3`, a loopback address). `.test`, `.invalid` and `.localhost` are NOT in the set and are red, and so is the web-flow address (the `noreply` account at `github.com`) written as text (it is allowed only as the committer identity of a commit). The old prefix-style entries are gone, so an address that starts like one of them and has a tail, or that ends like a file name (`.md`, `.ts` and so on), is red. The full-width at sign (U+FF20) and the small at sign (U+FE6B) count as at signs. A single line of 3 MB is scanned within 30 s with an exact count (a test). Stated limits: a digits-only last label lets an address on an IP literal through; an address written entirely in full-width letters is not detected (only the two at-sign variants with ASCII characters around them are). (c) The host rule inside test and fixture trees does not exist. (d) The check of workflow permissions and secret shapes (the checks of "何から守るか") does not exist: the gate checks only that workflow files parse and pass actionlint. (e) **Files the scans cannot read are red** unless named in the list. Unreadable means: content with a NUL byte (anywhere in the file, not only in the first 8000 bytes that git looks at; archives are not opened, so they are binary here) or that is not valid UTF-8 (latin-1 and the like, and UTF-16 with a byte order mark, which is not valid UTF-8). A limit: UTF-16 without a byte order mark that has no NUL byte can happen to be valid UTF-8 and then is read as text, not found as unreadable. The result is exit 1 and two count lines in both modes, in the shape of the key counts: `unreadable file(s): N` for the files that the commits of the range add or change (so a binary file added and deleted again inside the range is counted), and `unreadable file(s) in the tree of HEAD: N`, which a line with N = 0 may leave out. Not red: valid UTF-8 text (Japanese included), a 0-byte file, a symbolic link (the link, not its target, is read), and a submodule gitlink (it holds a commit id, not a file: nothing is read and it is not red; `.gitmodules` is a file and is read). A file name with a line feed, a tab or another control character, or with a byte that is not UTF-8, is exit 2: it cannot be written in the list, so it cannot be named. A name with a space, a quote, a backslash, a leading dash or UTF-8 characters is scanned like any other and can be named in the list. Files of any size are scanned (no size limit is set), and values encoded up to the tool's default decode depth (5) are decoded. A `.gitignore` is not honoured by gitleaks, and `.gitattributes` does not change what it reads (checked, with tests, for `filter=lfs` in the same commit, in a later commit and in a nested file). Files that a `filter=lfs` attribute makes LFS-managed: with a usual LFS setup, `git add` replaces the content with a pointer, the content stays in the local LFS store, and only the pointer is committed, so the scans see the pointer. Neither the gate nor the hook sends LFS objects, and the LFS hook of git-lfs is not run while `core.hooksPath` is set; a manual `git lfs push`, or an LFS hook in an environment without `core.hooksPath`, would send content that no scan has read. (f) The scans need git 2.40 or newer (they read no attributes from the tree, so that `.gitattributes` cannot make files unreadable to them); with an older git they stop instead of scanning less. A repository with no commit is exit 2 (`push-gate: HEAD is not a commit`) whatever way the range is named; it is not a clean scan (a test pins this). (g) Workflow files are checked at the tip (`HEAD`) only, not at each intermediate commit. (h) State inside the repository (`.git/config`, `.git/info/attributes`, `.git/info/grafts`, `refs/replace/*`) does not change what the scans read: the history is read from a neutral repository that borrows only the objects (no config, no `info/`, no refs), with the range given as commit ids, and `GIT_NO_REPLACE_OBJECTS=1` is set in every clean environment. What still runs against the real repository is limited to finding the repository (`rev-parse --absolute-git-dir`, `--show-toplevel`, `--git-path objects`), resolving `HEAD` and a `--base` name to a commit id (replace refs ignored), the shallow check, and `remote get-url` / `ls-remote` (which are about the destination, in the caller's configuration, as push is). The neutral repository reaches the objects through the real object directory and whatever `objects/info/alternates` chain it holds; objects are addressed by their content, so a redirected alternate can only make an object missing (the scans then stop), not different. The commit-graph and the multi-pack-index of the borrowed object directory are not content-addressed (git reads parent links from a commit-graph), so the neutral repository turns both off (`core.commitGraph=false`, `core.multiPackIndex=false`, in its own config, which also applies to gitleaks' git); a test forges a commit-graph that cuts the tip's parent. A SHA-256 repository is not supported: the neutral repository is SHA-1, so the scans stop; a shallow clone stops them too. Both are one shared check (`neutral_git_setup`) used by the gate, push-range and scan-public. History is read by `gitleaks git` over the neutral repository, **one commit at a time** (`--log-opts="-1 -m <id>"`, ids only, never names), in the gate (`scan_history`, one implementation). Each commit is checked on its own: `git diff-tree --root -m -M --numstat -z` (status checked, any failure is exit 2) says whether the commit adds at least one line of text (a number above 0; a binary file, a deletion, a mode change, an empty file and a pure rename add none), and the "N commits scanned" line in gitleaks' info log (kept in a private temporary file, never printed) must be a number and must be 1 when text was added, and 0 or 1 when none was; anything else is exit 2. Findings are summed over the commits. Measured with gitleaks 8.30.0 for text add, line replace, lines removed from an existing file, file deletion, symlink add, blank-line add, empty commit, mode only, binary add, 0-byte file, rename only, rename with edit, clean merge, merge with a resolution, octopus merge, submodule change and a root commit: the rule "text added is 1 scanned" holds in every case. Because gitleaks reads the history itself, rules that match by path and regex work in history; the gate's configuration holds no allowlist, so every path is scanned (16(a)). **Chunks:** `gitleaks stdin` and `gitleaks dir` cut large input into chunks and can lose a secret that straddles a chunk boundary (measured: about 4.8 MB of short lines with 5000 keys, 4993 found by `stdin`; about 50 MB with 500 keys, 497 by `stdin` and by `dir`; `git` found all). The tree of `HEAD` is therefore not read with `gitleaks dir`: it is scanned as a synthetic root commit (`git commit-tree` on the tree id of `HEAD`, in the neutral repository) through the same per-commit path as the history (`gitleaks git`, which does not chunk), and it must be reported as 1 commit scanned when the tree has text, else exit 2. A failure in building, listing or reading the tree of `HEAD` (the commit, the list of files, a file's content) is exit 2 with the message `the tree of HEAD could not be read`, never a clean tree line; the tree step runs even when the range of commits is empty. Measured on the code before this change: one 10 MB line with 100 keys at multiples of 100 000 bytes (give or take 20) gave 99 by `gitleaks dir` (a line of 2 MB with 20 keys gave 20); a test holds the exact count. The text of a commit is the whole raw commit object read from the neutral repository (`git cat-file commit`: tree, parents, author and committer lines, every other header such as `mergetag`, `gpgsig` and any extra header, and the whole message), with each NUL byte turned into a line break (the formats of `git log` stop at a NUL, so text after it would otherwise be unread); the status of both steps is checked and one function (`neutral_commit_text`) makes it for the gate and for `scan-public.sh`. It is not re-encoded: a commit with an `encoding` header carries non-UTF-8 bytes, which are scanned as they are (gitleaks reads bytes; the word list runs once in the locale of the scan and once byte for byte). A word written in an encoding that is not UTF-8 does not match a pattern in UTF-8: the limit of (e) applies to commit text too. The key scan of the text (`gitleaks stdin`) is bounded instead: texts are put together in batches that stay at or under 64 KiB (65 536 bytes), each text followed by one separator line break that counts toward the bound (a text that does not end with a line break never joins the line of the next), one `gitleaks stdin` per batch, so no boundary can occur inside a batch, and a single text above 64 KiB stops the gate (exit 2, "the text of a commit is over 64 KiB"). Findings in texts are counted, not named. A step that fails never reads as "nothing found" or as a smaller list, in `push-gate.sh`, `push-range.sh`, `scan-public.sh`, `scan-pr-text.sh` and the helpers they source (`neutral-git.sh`, `scan-rules.sh`, `range-id.sh`, `repo-context.sh`): a `grep` in a condition is `grep_q` (found, not found, or failed = exit 2); stages that decide something go through files with every status checked, not through a pipe; a gitleaks report is read by one function (`x_count`); every number that is compared or added is read once, from one `wc` with its status checked and digits only (`wc_num`; a count from a gitleaks report is `x_count`, one from its log is checked to be digits), and a `wc` that fails or prints anything else is exit 2, never 0 and never a skipped bound (a failing `wc` used to read as "no commits" and as a text under 64 KiB); **the rule for every script that scans or decides** (`push-gate.sh`, `push-range.sh`, `range-id.sh`, `neutral-git.sh`, `scan-public.sh`, `scan-rules.sh`, `scan-pr-text.sh`, `repo-context.sh` and `.githooks/pre-push`): no pipeline at all, no `|| true` or `|| :`, and no bare `grep` (a search is `grep_q`, or `scan_grep` which is `grep_q`; the one place that runs `grep` itself is `grep_q`, marked on its line). A multi-stage computation goes stage by stage through files in the private temporary directory (or a checked substitution of a single command), with each status checked, including the ones once called fail-closed (`scan_attribution` and `scan_bad_email` read standard input into a file, `gl_scanned` and the hash of a range are file stages, the hook cuts its lines with parameter expansion). A test (`tests/push-gate/no-pipes.test.mjs`) reads those files and fails on any such line unless it carries the marker `# GATE-EXCEPTION: <reason>`; the only marked line is `grep_q` itself; the same test also refuses `egrep`, `fgrep`, `\grep`, `command grep`, a path to grep, `eval` and `sh -c`, and a one-line group `{ a; b; }` or `( a; b )` whose status or output is used (only the last command of a group counts, so each command is joined with `&&`). It does not see a group that spans lines, a construct built at run time, or a function called in a condition (where `set -e` is off) that relies on `set -e` inside: that last one is a review item, and every function of these files that is ever called in a condition (`if f`, `f || …`, `f && …`, `! f`) checks the status of each of its commands explicitly (`|| return`, `case`, `[ … ]`). A loop over a list is complete or the run stops: `scan_history` (called under `||`, where `set -e` is off, so a list that cannot be opened would otherwise read as "no findings") checks the list is readable and compares the lines its loop processed with `wc_num -l` of the list; the other loops over a file or a list of commits (`push-range.sh` advertised commits, `scan-public.sh` scoped words and commits, the commit texts in `push-gate.sh`) do the same count at top level, so that a read that fails midway, or a last line without a line break, is exit 2 (a scan function takes its input as a path and checks it (`scan_input_ok`), never as a redirect written on the call in an `if`, where a failed open would read as "no finding"; every `… > file || [ $? = 1 ]` creates the output file first (`scan_filter`, or `: > file` in the gate), so that a failed redirect is exit 2 in any shell; the test refuses a `<` on a command in a condition; the redirects of other conditional commands are to `/dev/null` for noise only; the expected count is `wc_lines`, an awk line count that counts an unterminated last line, where `wc -l` would not; the hook reads git's last line even without a line break); the loops over arguments and the hook's loop over the lines git sends on standard input have no file to count (the hook's input is git's own); each script has exactly one `trap ... EXIT`, holding both its cleanup and `guard_exit` (a second trap on the same signal replaces the first, so it would drop one of them; a test checks this), and a command that fails under `set -e` with exit 1 (which means "found something") is turned into exit 2 by that trap (`guard_exit`), unless the script set `verdict_exit` just before its own exit 1. The word list is read by one function (`word_list_read`) for the gate, `scan-public.sh` and `scan-pr-text.sh`: a list that contains a NUL byte, a carriage return (a CRLF file), a UTF-8 byte order mark at the start of a line, or a line that is not valid UTF-8 is exit 2 with a fixed reason (a CR would become part of a pattern and a BOM part of the first word, so a word would silently not match) (a `grep` in a UTF-8 locale would silently drop such a line, so a word in another encoding would leave the list), a list that is named (`SCAN_WORDS_FILE` set) but missing or empty is exit 2 in the scans, and no line of the list is ever shown. In `scan-public.sh` the word list, the attribution check and the mail check read the same text. The mail check reads that text with one thing taken out: from the first `author` line and the first `committer` line, only the first `<...>` (from the first `<` to the first `>` after it), which is the address git itself reads as the author's and the committer's address and which the identity rule checks (GitHub's web-flow committer address is allowed there). The name, anything after the address (the date, and any text after it in a hand-built object), a second such line, a line after the headers, and the `tagger` line inside a merged `mergetag` are all read by the mail rule, and an address there that is not a noreply or reserved-domain one is a finding. The identity rule reads only the four identity fields as git parses them (AI words in the names; every address must be exactly a GitHub noreply form, `[<number>+]<login>@users.noreply.github.com` with a login of letters, digits, `-` and `_`, or GitHub's web-flow address (the `noreply` account at `github.com`); the pattern is anchored at both ends and applied to one address per line, so text before or after the address, or a second address inside the same `<...>`, is not a pass): an address that is empty, because the line has no `<...>` or one that is never closed, is not a noreply address and is a finding, not a pass. The rule keeps to those fields because its meaning is who the author is, not what a message says. Measured with gitleaks 8.30.0: on `stdin` input of 65 536 and of 98 000 bytes, 40 inputs each with about 33 000 to 49 000 keys at random offsets (single line and one per line), every key was found; at 140 000 bytes some were lost (70 375 of 70 391, 70 400 of 70 422) and at 400 000 bytes more (201 083 of 201 270). The first boundary is near 100 000 bytes, so a batch within the bound cannot straddle one. A file that git treats as binary shows no content in a patch, so a key inside is not found by the key scan; such a file is red as unreadable (16(e)) unless it is named in the list. A log line at level ERR or FTL in gitleaks' own log makes the run "could not run" (exit 2) even when it exits 0 or reports findings. A repository whose objects are not all present (a shallow clone, a partial clone with missing objects) stops the scans instead of being scanned in part. (c) and (d) remain; the design text in `development-flow.md` ("security") describes them as required. **awk:** the scripts are run with gawk and mawk in the tests. The step for unreadable files reads NUL-separated records (`RS` set to NUL), which the one-true-awk (the awk of macOS) and busybox awk do not split; measured with original-awk and busybox awk: on those awks the step for unreadable files always stops with exit 2, also on a clean tree, so the gate cannot be used there.
17. **The history scan costs one `gitleaks git` start per commit, and CI scans the whole history several times on every event.** The gate prints the wall time of each step and of the whole run (from the very start of the gate to its end) in whole seconds (`push-gate: step gitleaks: ok (N commit(s)) in S s`). Measured with `--mode general --all` on a synthetic repository of small commits (one new file each), gitleaks 8.30.0, **one machine** (the figures are for orders of magnitude, not a guarantee): 100 commits 58 s in all (step gitleaks 55 s, scan-public 3 s), 500 commits 287 s (269 s, 18 s). The time is linear in the number of commits: about 0.55 s per commit for the gitleaks step, nearly all of it the start of one `gitleaks git` per commit (a bare gitleaks start, which loads the default rules, costs about 0.5 s whatever the input), and about 0.04 s per commit for scan-public. The texts of the commits (names, emails, message) are scanned in batches of at most 64 KiB, so they cost almost nothing per commit; before that was done, the same figures were 105 s and 535 s (100 and 500 commits) and 2184 s for 2000. On this repository `--base origin/dev` over 33 commits took 63 s. **How often:** CI runs the whole history on every event: once in the gate's general mode on most events (about 0.57 s per commit), and twice on a push to the main branch (plus the gate's words mode, another 0.57 s per commit); the old `gitleaks-public.sh` step, which made it twice on most events, is removed. CI scans only what is reachable from `HEAD` (`--all`); commits that are only under other refs are checked by the push or CI run of those refs. The same limit as in 15 applies: no run goes back over other refs that already exist. The scan of the tree of `HEAD` is one more `gitleaks git` start per run, a fixed cost of about 0.5 s. Measured on the main branch (`dev`) in the push run of the commit before the old key step was removed (12 commits): the gate in general mode 25 s, the gate in words mode 26 s, the old key step 10 s and the old word step 15 s. The job has a 15 minute timeout (`ci.yml`). With the figures above (about 0.57 s per commit on most events, about 1.1 s per commit on the main branch, the fixed costs of installing and of the tree scans left out) the job times out at roughly 1500 commits on most events and roughly 800 commits on a push to the main branch. Reaching it fails closed, but it makes every push and pull request red, so it is the deadline for the CI rework. Narrowing what CI scans per event (a range for pull requests, the whole history on the main branch and in the nightly run; an unknown range means the whole history) belongs to the CI rework and is not done here. The mail-entry check runs only for a commit whose text has an address hit: it adds about 4 ms per distinct hit string (one `sha256sum` and one list lookup each, measured on this box with 100 repeats) plus two short awk runs, which is small beside the one `gitleaks git` start per commit.
18. **The review-record check protects only as far as the owner's ruleset does.** `pr-gate.yml` (job `gate`) runs `scripts/check-review-record.sh`, and the ruleset on `dev` requires it as a status check. GitHub matches a required check by the job name: a job named `gate` in a workflow that a pull request adds could satisfy it (a writer-side risk; review covers `.github/`). A cancelled `gate` run can sit next to a successful one on the same head (concurrency with cancel-in-progress), so the newest run for the head is the one that counts. A run is found by event `pull_request_target`, workflow path `.github/workflows/pr-gate.yml` and the pull request's head sha (the `GITHUB_SHA` inside the run is the base's). A pull request from a fork is red in pr-gate (the word list is not available to it) and is not judged with a general-only scan; the owner re-pushes the branch from the repository itself. All of this depends on the owner's ruleset, which has to name the branch and the check; the rule in `AGENTS.md` covers what the check does not.
19. **Generated files, and blocks that a generator writes inside a basis file, stay basis.** `basis-paths.tsv` classifies by path only, and it has no `generated` line: a directory is trusted as generated only once CI proves its files fresh, and `generate:check` is not run at the root. So the generated `supabase/migrations` are basis, and so is a file that holds `AUTO-GENERATED` blocks (a summary or a table inside a spec or a handbook page): a change that only regenerates them counts as a basis change, and a commit after the recorded `basis` cannot make it. Decided when the basis record became machine-checked: the strict state stays, because no change so far regenerated anything after its implementation. A change that has to regenerate after its implementation puts the regeneration in a final basis commit and moves the record (the check allows that, and both reviewers see it). The `generated` class stays in `scripts/classify-paths.sh` and its tests. Two ways to relax this are not taken: list a directory as generated once CI proves it fresh, and let a change after the basis commit touch a file with blocks when the text outside the blocks is byte-identical (compared as data). They are taken only when a real change shows the cost of the strict state.
20. **The basis record check starts to judge with the first pull request after the one that wires it into `pr-gate`.** `pr-gate` calls `scripts/check-basis-record.sh` with the base's own scripts and `basis-paths.tsv`, and fetches the head commit as data (`fetch-depth: 0`, one `git fetch` by sha). `pull_request_target` reads the workflow from the base branch, so the pull request that adds the call is itself judged by the old definition: it keeps the order (basis commits first, no basis change after the recorded `basis`) by procedure and review. Decided: enforced at once (no report-only mode). What remains: the first run of the call is on a real pull request and has to be checked by path, event and head sha (GitHub accepting a fetch by sha is checked there; the fallback is `refs/pull/N/head` with an equality check, which needs the wiring test's `refs/pull/` ban relaxed), a large pull request can hit the 5-minute timeout (that is red), and a private product needs an authenticated fetch (a product step). The content of the two answers is item 27.
21. **`implemented` (the implementation scope): catalogs are all-or-nothing.** The catalog checks (jobs, auth flow, guarantees, external, config, design tokens) are relieved or kept as a whole, because the owner is the catalog id. A product cannot put half a guarantee catalog in scope; a guarantee that is not yet enforced is declared `status: planned` instead. The guarantee catalog is a large share of a young product's errors, so its canary tests come in late.
22. **`implemented`: the dependency rule is not machine-checked yet.** A spec put in scope may rely on a spec that is still out of scope (for example an invariant enforced by another aggregate). Nothing flags it; the order (dependencies first) is a procedure and a review point (`development-flow.md`). The same holds for a guarantee that spans scopes and for the release condition.
23. **`implemented`: a rename looks like a removal.** P14 compares ids, so an id that disappears from `implemented` and from the specs passes (the spec was retired, or renamed). A renamed id is then silently out of scope. The count of such ids is printed in the P14 line; a `retired:` list that makes the retirement explicit is not built.
24. **Notification and job `test_cases` have no forward check.** Nothing calls the test-existence check for them (no `ofKind` for `notification_spec` or `job_spec`), so a declared test that does not exist is not reported. The scope's closed list does not claim them; closing the hole is separate work.
25. **The auth flow parser does not validate the form of a gate `implementation`.** H2 accepts `implementation: "file.ts::"` (an existing file, an empty symbol) with no finding, because the parser only requires a non-empty string and the symbol check is `includes('')`, which is always true. The fix is form validation in the auth parser (a non-empty `path::name`, exactly one `::`), test first, in its own change. Until then, H2 tags only a missing file behind a well-formed `path::name` as an absence under `implemented`.
26. **`implemented`: nothing in this repository passes `--implemented-base`.** The narrowing check (P14) exists in the CLI (`verify --implemented-base <file>`), and the CI of a product that declares a scope is meant to pass the base commit's product declaration. This repository's own CI does not call it, because its demo product declares no scope. Until a product wires it, the check that the scope never narrows is not enforced by a machine there; it is a procedure and a review point.
27. **The two basis answers are not read yet.** The basis record names two answers (`basis-opus`, `basis-codex`), each a comment of the pull request, and `development-flow.md` gives `pr-gate` the duty to check that the comment names the origin and the `basis` commit, and to print the comment ids and the hash of each body, which `merge-check` compares again before the merge. None of that is built. `scripts/check-basis-record.sh` checks the form of the lines, that both shas equal `basis`, and that the two links have the form of a comment of this repository and this pull request with two different ids; it fetches nothing. So the machine knows only that two such links are written: whether they are comments, and what they say, is not checked. It comes with `merge-check` (rollout step 5), which has the token and the permission to read comments. Until then the content of the answers is a rule and a review point.
28. **"The tests came first" is pinned by commit order only.** The basis record keeps the basis commits before the implementation commits, so a test cannot be written after the code it tests. The check does not see whether a test in the basis commit failed for the expected reason (the evidence is written in the pull request and kept by rule), nor whether a later basis fix was made to fit the implementation. Those are review points.
