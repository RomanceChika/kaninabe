# 画面テスト（screenTest）

`screen_spec` が宣言した画面の**構造と配線**が、実装で本当にそうなっているかを確かめるテストの規約。ブラウザも jsdom も使わず、RSC を関数として呼んで確かめる。

## 目的

- 画面仕様（`screen_spec` の `layout` / `navigations` / `requires_auth` / `variants`）を**実行時に観測できる事実**へ落とし、宣言と実装のずれを機械が見つけられるようにする（PRIN-0006）。静的検査（S 群）は「仕様どうしが食い違っていないか」までしか見られず、「宣言した部品が実際に描かれているか」は原理的に実行しないと分からない。
- 画面が**他の仕様を再実装していないこと**をテストの形でも守る。screenTest は偽のクエリ結果を渡すだけで、可視性・状態遷移の可否をここで確かめない（それらの正は RLS と状態機械であり、統合テストとユニットテストが既に守っている）。
- UI の変更の大半（スタイル・文言・部品の内部分割）で**落ちない**テストにする。落ちてよいのは配線が変わったときだけである。

## 参照するもの

- 仕様の書き方と検査: [screen-spec-writing.md](../../../specification/standards/screen-spec-writing.md)（S0〜S8）
- 生成物: `app/src/domain/generated/testids.ts`（骨格）・`app/src/domain/generated/screens.ts`（部品と遷移の一覧）
- 注釈（`@spec` / `@tc`）の規則: [action-spec-writing.md](../../../../backend/specification/standards/action-spec-writing.md) §test_cases
- 他のテスト層: [testing/unit.md](../../../../backend/system/standards/conventions/testing/unit.md) / [testing/integration.md](../../../../backend/system/standards/conventions/testing/integration.md)

## 方式

- **RSC は「依存を引数で受ける async 関数」にする。** 画面の本体は `app/src/app/_screens/{screen-name}.tsx` に置き、`page.tsx` は既定の依存を渡して呼ぶだけにする（分岐を持たない）。screenTest はその関数を偽の依存で呼び、返る要素木を検証する。
- **注入する依存が無い画面は `page.tsx` のままでよい。** 読むデータもセッションの解決も持たない画面（`home` / `login`）を `_screens/` へ出しても、渡す依存が空で `page.tsx` が 1 行増えるだけである。screenTest は `page.tsx` の default export を直接呼ぶ。**分ける理由は「テストから依存を差し替えられるようにする」ことだけ**であり、差し替えるものが無ければ分けない。
- **依存に渡すのは「読むもの」と「実行者は誰か」だけ**である。未ログインの行き先（`redirect('/login')`）は実装の `requireSession()` が持ち、テストから注入しない。注入できてしまうと、`requires_auth` の宣言と突き合わせる相手が消える。
- 要素木は `react-dom/server` の `renderToStaticMarkup` でマークアップにし、`data-testid` と `href` を取り出す。**DOM API を 1 つも使わない**ので、Node 環境のユニットテスト（`npm run test`）としてそのまま走る。
- 期待値は**生成物から引く**。宣言した部品の一覧は `screenRoutes[{画面名}].components`、遷移先の一覧は `.navigations` にあり、テストがその 2 つを手で並べることはしない。仕様に部品や遷移を足したらテストが落ちる、という向きの結び付きはここで成立する。

### なぜ静的マークアップまで通すのか

宣言したスロット部品の一部は `'use client'` のコンポーネントの内側に居る（`login_form` / `loan_form` / `own_loan_panel` / `submit_bar` / `app_header`）。要素木を自前で歩くだけでは、それらは「まだ呼ばれていない関数」のままで testid が現れない。呼ぶにはフック（`useState` / `useRouter`）が解決できる場所が要り、それはレンダラーの仕事である。

**これは DOM の問題ではない。** `useRouter()` はルーターの文脈が無ければ例外を投げるので、jsdom を入れても同じところで止まる。必要なのは文脈であって DOM ではない、という理由で jsdom を採っていない。

## 配置・命名

- テストは `app/src/app/__screens__/{screen-name}.test.tsx` に置く（1 画面 1 ファイル）。`{screen-name}` は `screen_spec` の `name` をハイフン区切りにしたもの。
- 共有の道具立ては `app/src/app/__screens__/` に 2 つある。**描画する側**（`harness.tsx`）だけがレンダラーとルーター文脈を知り、**宣言と突き合わせる側**（`declarations.ts`）だけが生成物（`screens.ts`）を知る。1 ファイル 300 行の制限に当たったときにこの線で割った（責務が 2 つあったので割れた）。操作のボタンの期待（`declaredActionLeaves`）だけは状態機械の索引（`STATE_MACHINES`）という別の生成物を引くので `declarations-actions.ts` に置き、呼ぶ口は `declarations.ts` から出している。
- **`app/src/app/__tests__/` と混ぜない。** あちらは実 DB を使う通しテスト（`npm run test:integration` の対象）であり、走るコマンドが違う。
- テスト名は日本語で、`screen_spec` の `test_cases[].implementation` の `::` 以降と一字一句一致させる。対応は `// @spec {仕様ID} @tc {テストケースID}` で示す（S8 が双方向に突き合わせる）。
- **1 画面につき 1 件以上のテストを必ず持つ**（S9 がエラーにする。免除の口は無い）。`requires_auth: true` の画面は、未セッションで `/login` へ送られることを確かめるケースを 1 本持ち、その `covers` に `forbidden` を書く。

## 確かめること

| 見るもの | 何が守られるか |
|---------|--------------|
| 宣言した部品の testid が全部ある | 仕様に部品を足したのに実装が置いていない／testid の骨格がずれた |
| 排他表示（`variants`）は片方だけ | 「同時には出ない」という宣言が実装で守られている |
| `requires_auth: true` は未セッションで `/login` へ | 入場の関門の宣言が、実装の `requireSession()` に対応している |
| `precondition` が成り立たないときに `on_fail` の画面へ送られる | 入場条件の宣言が実装で守られている（**静的な突合が無いので、ここが唯一の担保**。実例: `librarian_holds`） |
| 描画結果の `href` の行き先が `navigations` の中にある | 宣言していない画面へ勝手に繋がっていない |
| 描画結果の testid が骨格か**その葉**である | 仕様に宣言していない部品が画面に生えている（§葉の命名規則） |
| 重ね表示（`overlays`）の部品が宣言どおりの名前空間に居る | 重ね表示の骨格がずれた（§重ね表示） |
| 操作のボタンの集合が「宣言した `actions` ∩ 状態機械の遷移」と一致する | 宣言していない操作のボタンが生えた／宣言した操作のボタンが消えた（§操作のボタン） |

- **排他表示のグループは、どの状態を見ているかをテストが必ず宣言する。** 省略を「どちらでもよい」に倒すと、両方同時に描く実装が通ってしまう。
- 遷移の突合は**実装 → 仕様の片方向**である。「宣言したのに実装に無い」遷移は、押してみないと分からないもの（`router.push` / フォーム送信後）を含むため、この検査の守備範囲に入れない。

### 葉の命名規則（部品の内側の testid）

**葉は、宣言した部品の testid を接頭辞に持たなければならない。**

```text
item_detail.body.center                      スロット（器）  … 付けても付けなくてもよい
item_detail.body.center.loan_form           宣言した部品    … 必ず居る
item_detail.body.center.loan_form.title     葉（自由地帯）  … 名前は自由
item_detail.body.center.new_thing            ✗ 宣言外の部品  … 置けない
```

- **名前は自由、置き場所は自由でない。** 何という葉を置くか（`title` / `row` / `error`）は仕様の関心ではないが、**スロットの直下に宣言されていない名前を置くことは禁じる**。
- この 1 本の規則があると、描画結果の testid を「骨格（スロット・部品）」「骨格の葉」「それ以外」に**文字列の形だけで**振り分けられる。C-3 まで「宣言していない部品が描かれていても検出しない」という穴が残っていたのは、葉をどこにでも置けたために宣言漏れと葉が同じ形をしていたからである。
- **執行者は `declarations.ts` の `undeclaredTestIds()`**。許容集合（スロットと部品。重ね表示の分も含む）は生成物 `screens.ts` から引く（手で並べない）。画面ごとに 1 回以上呼び、**分岐した表示（エラー・空・排他のもう一方）はそれぞれ 1 回は通す** — 通っていない枝は誰も見ていない。
- 状態表示（`error` / `empty` / `not_found`）が「代わりに出る」ものなら、**代わりに出る相手の部品の名前空間**に置く（一覧の代わりなら `…item_table.error`、蔵書概要の代わりなら `…item_summary.error`）。器のスロットに置くと宣言外の部品と区別できなくなる。
- **エラーの葉は部品ごとに `.error` の 1 語彙にする。** 読み取りの失敗（`invalid_input`）も、操作の失敗（Server Action の拒否）も、**その表示が属する部品**の名前空間に `.error` で出す（`action_error` のような別語彙を作らない）。同じ部品で 2 つが同時に出ることは無い — 読み取りが失敗していれば部品そのものが描かれず、操作の拒否はその部品が描かれている状態でしか起きない。ボタンが部品の内側にあるなら、拒否もその部品の `.error` である（実例: `…transition_bar.error` / `…overlay.cancel_confirm.body.center.confirm_bar.error`）。
- **生成物の部品(`kind: form`)の葉は、生成物の葉の表から引く。** 手書きの部品の葉は自由地帯だが、生成物の部品の葉の名前(欄の名前・送信ボタン・拒否の表示)は生成器が決めるので、`screens.ts` の部品の `leaves` に載る。テストは `declarations.ts` の `leafOf(画面名, 部品のキー, 葉)` / `formLeafTestIds(画面名, 部品のキー)`(作成のフォーム)/ `updateFormLeafTestIds(画面名, 部品のキー, writable)`(編集のフォーム)で引き、**葉の名前を手で書かない**(仕様に欄を 1 つ足したときにテストが古い葉の名前を知っている状態にならない。表に無い葉・手書きの部品を指すと例外)。**編集のフォーム**は、どの欄が出るかが器の渡す `writable`(書き込みの規則 × 対象の状態)で決まるので、欄は表の `fieldsIfWritable`(「編集してよいときだけ」)に載り、テストは**器に渡したのと同じ `writable`** を `updateFormLeafTestIds` の第 3 引数に**必ず**渡す(既定は無い。作成のフォームの欄は `fields` = 必ず描かれるので `writable` は要らない)。**取り違えは例外**になる(編集のフォームを `formLeafTestIds` に渡す・作成のフォームを `updateFormLeafTestIds` に渡す) — `writable` の渡し忘れが「欄が 0 本の全数」として黙って緑になるのを防ぐ。
- **`kind: table` / `kind: detail` の部品の葉も同じく生成物の葉の表から引く。** 表の葉は `empty`(行が 0 件のときの表示)・`row`(行。行ごとに同じ testid)・`column.{欄}`(見出し。`shows` の順。併読の欄は `column.{併読名}.{欄}`)、詳細の葉は項目ごとの `{欄}`(値。`shows` の順)で、テストは `declarations.ts` の `tableLeafTestIds(画面名, 部品のキー)`(`{ empty, row, columns }` を返す)/ `detailLeafTestIds(画面名, 部品のキー)`(項目の全数)で引き、**葉の名前を手で書かない**。取り違え(表を `detailLeafTestIds` に・詳細を `tableLeafTestIds` に・フォームを両方に・手書きの部品を指す)は例外になる(`formLeafTestIds` と同じ理由 — 取り違えが「葉が 0 本」の期待に化けて黙って緑になるのを防ぐ)。**空の分岐も 1 回は通す**(`empty` の葉は行が 0 件のときだけ出るので、行のあるテストでは見えない)。表の行の中のセル・状態のセルの `data-state` 属性は葉ではなく属性なので、値を見るテストが生成物の字面でなく描画された属性を見る(状態の値の正は状態機械)。表・詳細の部品の内側に手書きの葉(行ごとの NextActions・分館なしの注記など)を足すときは、**部品の testid を接頭辞に持たせる**(葉の命名規則そのまま。生成物の葉の名前と衝突させない)。
- **操作を載せる表・ボタン列(`kind: table` の `edit` / `actions`・`kind: actions`)の葉も生成物の葉の表から引く。** 編集する表は、見出し(`column.{欄}`)と入力欄(`{欄}`)が器の渡す `writable` で決まるので、葉の表では「編集してよいときだけ」(`columnsIfWritable` / `fieldsIfWritable`)に載り、`tableLeafTestIds(画面名, 部品のキー, writable)` が **器に渡したのと同じ `writable`** を第 3 引数に**必ず**要る(編集する表に渡し忘れる・読むだけの表に渡すと例外 — 編集のフォームの `updateFormLeafTestIds` と同じ理由)。返り値の `fields`(入力欄)・`rowActions`(行ごとに必ず描かれる保存ボタン `save`)・`rowButtons`(行のボタン。遷移はイベントの名前・削除は `delete`。**行の状態と実行者のロールの交差で出ることがある**ので「必ず描かれる」ではない — 状態を持たない集約の削除は常に出る)・`rowError`(行の保存の拒否 `row_error`)・`buttonError`(ボタンの拒否 `error`)で、遷移のボタンの期待は `declaredActionLeaves`(宣言した操作 ∩ 遷移表)から作る。**ボタン列(`kind: actions`)**は `actionsLeafTestIds(画面名, 部品のキー)`(`{ buttons, error }`)で引く。取り違えは例外(ボタン列を `detailLeafTestIds` に・表を `actionsLeafTestIds` に など)。**確認の器は部品の葉ではなく重ね表示の部品**である — 確認が要る操作(削除・終端遷移)を載せた部品は、その部品を `opened_by` に持つ重ね表示を宣言し(S19)、テストは `declaredOverlayComponents` と `{重ね表示の `confirm_bar`}.confirm` / `.dismiss` で見る(確認の見出しは重ね表示の `label` から表示名の表 `{画面}Labels['overlay.{id}']` に載る)。
- 画面の名前空間の外にある testid（汎用コンポーネントが自分で付けるもの）は見ない。見るのはその画面と継承した共有クロームの名前空間に属するものだけである。

### 重ね表示（`overlays`）

**重ね表示の部品は「常に描かれているはず」の表に入れない。** 期待値は
`declaredOverlayComponents({画面名}, {重ね表示の id})` で別に引く（画面の部品は
`declaredComponents`）。混ぜると閉じた状態のテストが落ちるためである。testid の名前空間は
`{画面名}.overlay.{重ね表示の id}.{スロットパス}.{部品}`（[screen-spec-writing.md §testid](../../../specification/standards/screen-spec-writing.md)）。

- **開閉は要素の有無ではなく状態で表す。** 開いていないときに要素ごと消す作りにすると、
  宣言した部品が描画結果に 1 度も現れず、骨格を確かめる相手が居なくなる。`<dialog>` の
  `open` 属性のように「居るが閉じている」形にすれば、閉じた状態のままでも骨格を突き合わせられる
  （実例: `item_manage` の `cancel_confirm`）。
- **開いた状態そのもの（ボタンを押したら開く）は見ていない。** クリックは描画結果に現れない
  ので、これは押した結果の遷移と同じ「screenTest の外」の側にある（→ §E2E スモーク）。

### 操作のボタン

**画面がボタンにしてよい操作は「`screen_spec` の `actions` ∩ 状態機械の遷移（`from` / `by`）」の交差だけ**である（規則の正は [screen-spec-writing.md §先読みの線引き](../../../specification/standards/screen-spec-writing.md)）。テストはこの交差を**実装とは独立に生成物から組み立てて**突き合わせる。

- 期待値の材料は 2 つとも生成物である（`screenRoutes[{画面}].actions` と `{machine}.transitions.ts`）。テストが「draft なら publish と cancel」と手で書くと、状態機械を 2 か所に持ったことになる。**組み立ては共有の道具 `declaredActionLeaves(画面, { machine, state }, role)` を呼ぶ**（画面ごとに交差計算を書き写さない。返るのは遷移ボタンの葉名 = イベント名で、どの部品の名前空間に載るかは宣言が持たないので呼び出し側が前置きする）。
- 見るのは**等値**であって片側の包含ではない。「宣言に無いボタンが出ていない」（⊆）だけでは、宣言した操作のボタンが消えたことを見逃す — イベント → Server Action の対応表に穴が空いたときに起きるのがこれである。
- 全状態を回す。1 つの状態だけを見ると、交差ではなく偶然一致している実装（例: 常に全部出す）が通る。
- **予約 ID（`{entity}.create` / `.update` / `.delete`）はこの交差に乗らない。** 状態機械のイベントではないので `from` が無く、可否の条件は `access_spec` の `when`（ガード式）にしかない。**画面はその `when` を条件つきで先読みしてよい**（規則の正は [screen-spec-writing.md §予約 ID のガードを先読みしてよい条件](../../../specification/standards/screen-spec-writing.md) の 3 条件。Phase C-6 第 2 波の決定であり、それ以前の「ガードの先読みは一律禁止」は改められた）。**ただしテストの側は交差を組み立てられない** — 先読みの材料が `from` / `by` ではなく `when` の AST 評価であり、その評価には画面が現に描いている行の値が要るためである。したがってテストが確かめられるのは「宣言した操作それぞれに口があること」までである（実例: `librarian_holds` の 3 操作、`item_detail` の下書き削除）。等値で縛れないぶんだけ弱い保証であることを承知して書く。

## 確かめないこと（他の層が守る）

| 確かめたくなるもの | 正しい守り手 |
|-------------------|------------|
| 誰に何が見えるか・他人の行が混ざらないか | 統合テスト（実 RLS） |
| その状態でその操作ができるか | ユニットテスト（状態機械エンジン）と統合テスト |
| 入力の必須・最大長 | 生成 zod スキーマ（画面はそれを使うだけ） |
| スタイル・文言・アニメーション・部品の内部分割 | 何も守らない（実装の自由地帯） |
| クリック・入力・送信の実挙動、ハイドレーション | **E2E**（下記。貫通のスモーク 1 本 + 行の再描画の補強 1 本。ブラウザでしか観測できない種類だけ） |

## してはいけないこと

- **`vi.mock` でモジュールを差し替える。** 注入点は引数だけである（ARCH-BE-0001 の E6。ユニットテストと同じ規則）。
- **テストのためだけに本体へフックを足す。** 依存を引数で受ける形は本番の配線でもそのまま使われている経路であり、テスト専用の分岐ではない。
- **期待する testid を手で書く。** 骨格は生成物（`testids.ts` / `screens.ts`）から引く。手で書くと、仕様の `layout` を変えたときにテストだけが古い名前を知っている状態になる。
- **画面テストで可視性を確かめる。** 偽のクエリ結果を渡している以上、そこで「見えてはいけない行が見えない」ことは 1 つも保証されない。

## E2E スモーク（screenTest の守備範囲外を 1 本で回収する）

screenTest は要素木を静的マークアップにして見る方式なので、**押した後に起きること**を原理的に観測できない。その残余だけを、実ブラウザ 1 本の貫通シナリオで回収する（Phase C-6。C-3 で先送りにした判断の実行）。

- 置き場: `app/e2e/`（`smoke.spec.mts` が唯一のシナリオ。設定・シード・DB ガードが同居する）
- **認証はセッション注入で通る**（E1 決定）。本番のログインは example-idp の OAuth のみで、その実物はローカルで踏めない。テスト（統合・E2E・shots・walker）は**管理 API でユーザーを作り、supabase-js のセッションを cookie に注入**してログイン済み状態を作る（`app/e2e/session.mts`）。cookie の名前と属性は本番と同じ約束（セッションの adapter の `@kaninabe/adapter-supabase-session/cookie-policy`。`__Host-auth`・`HttpOnly`・`Secure`・`SameSite=Lax`）で置く —— Playwright の `addCookies` は `url` の形だと `__Host-` の cookie を拒むので、`domain` + `path: '/'` の形で渡す（`http://127.0.0.1` でも Chromium は `Secure` の cookie を受け付ける。2026-10-20 の実測）。この経路はサインインの composition を通らないので、**セッションプロフィール（`app_metadata.profile`。ヘッダの表示名と司書用リンクの出し分けが読む券）はシードが書く**（`app/e2e/session-profile.mts`。本物の `writeSessionProfile` は `server-only` の目印を持ち素の Node から読めないため、生成物 `SESSION_FIELDS` だけを読む最小限の写しを置く）。ヘッダの表示名はサーバーが描くときに渡す（`SessionProfileBoundary`）ので本文と同時に届くが、撮影は念のため表示名が出ていることを確かめてから撮る。ログイン UI の検証は**表示のみ**（screenTest / ハンドブックの SSR プレビュー）で、OAuth の往復は検証しない
- 実行方法: `cd app && npm run test:e2e`。ローカル Supabase の起動（設定の評価時） → `next build` + `next start`（webServer） → 多重起動ロック・マイグレーション・専用シード（globalSetup） → chromium の順に、**1 コマンドで完結する**（統合テストと同じ成立条件）。Playwright は webServer を globalSetup より**先に**実行するため、二重起動の衝突はビルドが終わってからしか報告されない（既知の癖であり、テスト自体は必ずシードの後に始まる）
- ブラウザは **chromium だけ**。見ているのは配線であって描画差ではない

### 回収する 4 種（これ以外を E2E に持ち込まない）

| screenTest が見られないもの | スモークが観測する形 |
|---------------------------|--------------------|
| ①実フォーム送信 | ブラウザから Server Action を呼び、結果が次の描画に出る（貸出の作成・確定・返却・締め・並べ替え・取消） |
| ②押した結果の遷移 | `router.push` の行き先（ログイン後・ログアウト後）と `router.refresh` 後の描画（排他表示の入れ替わり・操作ボタンの入れ替わり） |
| ③重ね表示の開いた状態 | 閉じた `<dialog>`（不可視）→ ボタンを押す → 開いた `<dialog>`（可視）→ 確定 |
| ④クライアント操作後の状態 | 並べ替えの編集状態（未確定表示）と、その一括反映。**未確定表示が消えることが反映の証拠**である（編集状態を捨てるのはサーバーの並びが変わったときだけなので、DB に届いていなければ消えない） |

### 原則

- **貫通のスモークは 1 本を維持する。** 網羅を E2E に担わせない。可視性は統合テスト（実 RLS）、可否は状態機械のユニットテスト、構造と配線は screenTest が既に守っている。**スモークが 2 本目を欲しがったら、それは他の層で確かめるべきものが紛れ込んだ合図**である（E2E は最も遅く最も壊れやすい層なので、増やすと費用だけが増える）。
- **例外は、`router.refresh()` を跨ぐ同一 mount の状態を見る補強 1 本と、実の認証基盤のセッションを使う補強 1 本だけ**である(製品側の E2E。「編集中の行が他の人の更新を受け取っても触った欄だけが保存される」)。screenTest は SSR を 1 回しか描かないので、refresh を跨ぐ挙動は screenTest には見えない。その境界は 製品側の E2E が見る（純関数 `@kaninabe/runtime/form-refresh` の単体テストは判定しか見ない。配線の**字面**は guarantees の見張り TC-007 が見るが、refresh を跨いで同じ mount に値が届く**挙動**は実ブラウザでしか観測できない）。もう 1 本の補強は認証基盤の操作（ADR-0019）で、製品側の E2E が実の認証基盤に別々の端末のセッションを作り、自分の端末の一覧・1 本とまとめての終了・司書による利用者の強制ログアウトを通す（偽の部品では実の `auth.sessions` の挙動と、強制ログアウトされた利用者の次の操作がログイン画面へ送られることが観測できない。権限表・接続・負例は生成テストが配線先の本物の組み立てで見る）。ほかの補強を足す前に、他の層で確かめられないかを先に問う。
- **セレクタは生成物の testid 定数を import して使う。** 文字列を直に書かない（screenTest と同じ規則）。E2E も仕様由来である。
- **任意の `sleep` を置かない。** 待ちは Playwright の自動待機（`expect` のポーリング）に任せる。時間で待つテストは、遅い環境で落ちて速い環境で通る＝ flaky の主要因になる。
- **節目ごとの最小のアサーション**にする。見るのは testid の出現・消滅であって、UI の文言や URL ではない（文言はいつでも変わってよい自由地帯である）。**ただしテスト自身が入力したデータの往復は見てよい** — それは UI の語彙ではなくデータであり、往復を見なければ「送った値が落ちる・別のフィールドに入る」型が通り抜ける。
- **リトライはローカル 0・CI 1**。ローカルで flaky をその場で見つけ、CI では 1 回だけ許して "flaky" として表に出す（緑に紛れさせない）。1 本しか無いので、不安定になればすぐ分かる。

### 実 DB ガードの共有

E2E は統合テストと**同じ advisory lock**（`@kaninabe/runtime/testing/local/db-lock.mts`）を取る。判断の基準は「その実行が共有 DB に破壊的な操作をするか」で、両方とも持つ — 統合テストは `db reset` / 全テーブル削除から始まり、E2E は舞台になる蔵書を毎回作り直す。別のキーにすると互いを排除できず、統合テストがスモークの舞台を消す（またはスモークの行が統合テストの数え上げに混ざる）。

**ただし E2E は `supabase db reset` をしない。** スキーマは `supabase migration up` で足り、壊す範囲を自分の固定データ（`e2e-` のアカウントと専用タイトルの蔵書）に閉じてある。開発用シード（`npm run seed:dev`）が作る `dev-` のデータには触らない。したがって integration.md 3節の「reset の最中にロックが外れる」問題は E2E 側には無い。

### シードの「冪等」の意味

スモークは蔵書を中止まで進めるので、「無ければ作る」だけでは 2 回目が動かない。E2E のシードは**毎回この初期状態にする**ことを冪等と呼ぶ — 舞台になる蔵書は捨てて作り直し（`loans` / `holds` は cascade で消える）、認証アカウントだけは作り直さない。

## 既知の穴

- **押した結果の遷移は、仕様との突合ではなく実測である。** `router.push` とフォーム送信後の遷移（`{イベントID}.success` の `navigations`）は描画結果に現れないので、screenTest は実装 → 仕様の片方向しか突き合わせられない。E2E スモークが通しているのは**その中の 1 本の経路だけ**であり、`navigations` の宣言を網羅的に確かめる機械は無い。
- **`chrome_spec` は自分のテストを持てない。** `chrome_spec` に書けるのは 6 項目だけで `test_cases` が無いため、共有クロームの部品は継承した画面のテストの中で確かめられる（画面側の宣言としてしか台帳に載らない）。
- **画面版の「必要な意味クラス」の導出が無い。** `covers` は書けるが、A7 のように「ドメイン仕様がこう書いてある以上このケースが要る」を導く規則が画面には無く、書き漏らしは検出されない。機械が数えているのは S9 の `forbidden`（入場の関門）1 クラスだけで、それ以外は人間のレビュー材料である。
- **`states.requires` と実装の突合が無い。** 表示義務（`loading` / `empty` / `error` / `not_found`）は生成物（`screens.ts`）に載っておらず、突き合わせる相手が存在しない。個々の screenTest が「空表示の testid があること」を確かめてはいるが、**それは `states.requires` に `empty` と書いたから要求されているのではなく、テストが手で書いたからそうなっている**。宣言を足しても対応するテストは要求されない。
