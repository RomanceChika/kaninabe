  id        … PROC-BE-XXXX を採番する
  doc_type  … process
  scope     … backend
  norms     … 上位概念(ARCH-BE-XXXX, PRIN-XXXX)を列挙する

standards 欄があるのは、**手順が依存する規約を機械が辿れるようにする**ためである。
本文の手順の節に書く「参照」ラベルと同じ ID をここにも並べ、メタと本文の両方で対応を保つ。
二重記帳に見えるが、片方だけでは「どの手順がどの規約に依存するか」と

process 直下のルートテンプレートとの違いは 2 つ。
  1. 手順の節で「実装場所」と「作業内容」を分け、「参照」を足している
  2. frontmatter に id / norms / standards を持つ(他のテンプレートは 2 キーのみ)

「（任意）」が付いた節は省略してよい。この表記が省略可否の宣言そのものであり、

# {タイトル}

この手順が何をするものかを 1 行で書く(実装手順・レビュー・品質チェックなど)。

## 目的

- この手順で何を達成するかを書く。

## 前提条件（任意）

あるものだけ書く。

- **事前に読むもの**: 参照すべき文書へのリンク。
- **入力**: 手順を始める前に存在していなければならないもの(対応する仕様が書かれていること、など)。
- **環境条件**: 実行に必要な環境。

## 全体の手順（概要）

`0.` から始まる番号付きで、手順名だけを並べる。

0. {手順 0 の名前}
1. {手順 1 の名前}
2. {手順 2 の名前}

本体は H3 で展開する。

### 手順N: {名前}

ラベルはこの順で固定する。

- **目的**: この手順で何が終わるか。
- **参照**: `[ルール名.md](パス) (PROC-BE-XXXX) - 簡単な説明`。この手順で参照すべき実装ルールを明記する。複数ある場合はカンマ区切り。ここに書いた ID は frontmatter の `standards` と対応させる。
- **実装場所**: どのファイル・どの層を触るか。
- **作業内容**: そこで何をするか。
- **確認事項**: 次へ進んでよいと判断する条件。
- **実行コマンド**(あれば): 実行するコマンド。
- **注意点**(あれば): 踏み抜きやすい落とし穴。

## 詳細（任意）

ファイル固有の参考情報(制約事項・注意事項・連携仕様など)を H3 でまとめる。
