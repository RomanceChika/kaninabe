# {id} — {短い名前}

H1 は `# {id} — {短い名前}` の形にする。

必須の節は **目的 / 概要 / スコープ / 構成** の 4 つである。見出しの末尾に「（任意）」が付いた 4 節は、
それぞれの**【書く条件】を満たすときだけ**書く。条件を満たさなければ節ごと落とす。

**本文に「関連」の節を作らない。** 参照関係はフロントマターの `norms` / `decisions` / `definitions` で
表現する(reference_policy・frontmatter_policy)。本文とフロントマターの二重管理になると、
機械が辿る参照グラフと人間が読む一覧が食い違う。

節の区切りには `---` の水平線を使う。

---

## 目的

**1〜3 行**。仕様書の**構成・配置・分割**について、それが何のために存在するかを書く。

対象が system(コード)ではなく**仕様書**であることを明記する。読み手が層構成の話だと誤読すると、以降の節を全部読み違える。

---

## 概要

**結論を先に出す。** 「仕様書をどう置き、どう分けるか」を簡潔に述べる。
複数文になるなら改行や箇条書きで読みやすくする。

---

## スコープ

**対象** と **対象外** の 2 項目を書く。

- **対象**: 影響する仕様書の範囲(例: `docs/specs/` 全体 / `docs/specs/backend/` のみ / `actions/` のみ)
- **対象外**: 縛らない範囲。誤解を防ぐために明示する

---

## 構成

仕様書の**ディレクトリ・ファイル構成とその役割**を書く。粒度の目安は「仕様の種類ごとに置き場所が一意に決まる」程度。

記載の単位は 2 つある。

- **ディレクトリ**: パスと役割(例: `actions/` = Server Action 仕様、`queries/` = 読み取りクエリ仕様)
- **ファイル**: 種別ごとの置き場所と命名の考え方。詳細な規則は「命名・分割方針」の節に委譲する

---

## 命名・分割方針（任意）

**【書く条件】** 1 リソース 1 ファイル制、ファイル名と ID の対応、サブディレクトリの切り方といった分割・命名ルールを明文化したい場合。

次の 3 項目を書く。

| 項目 | 書くこと |
|---|---|
| ファイル名 | 規則と例(例: 操作名と一致させ、`submit.md` とする) |
| 分割 | 1 ファイルの記載単位(例: 1 ドメインイベント 1 ファイル) |
| ID・リソースとの対応 | [id_policy.md](../../meta/standards/id_policy.md) や `docs/specs/` 側の命名との関係 |

---

## 制約・不変条件（任意）

**【書く条件】** 配置・命名・分割について、破ると一貫性が崩れるルールがある場合。

MUST / MUST NOT / SHOULD の 3 段で書く(例: MUST 新規の Server Action 仕様は `actions/` に置く)。

---

## 配置ルールと方針（任意）

**【書く条件】** 各種仕様ファイルの配置ルール・方針を詳述する場合。

---

## 補足（移行・トレードオフ）（任意）

**【書く条件】** 移行の経緯や、採らなかった案とのトレードオフを補足する場合。
