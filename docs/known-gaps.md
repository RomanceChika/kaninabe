# Known limitations (0.x)

kaninabe is at 0.x and not stable. The tree was carved from a larger private repository, so some things are missing or rough. Each item is meant to be closed by its own change.

1. **The demo product has no implementation tree.** `product.md` points at `app/`, but the repository carries only the specs and the generated `supabase/migrations`. Root `verify` is green; `generate:check` is not run at the root. Generator behaviour is checked by `test:spec-tools` on the samples.
2. **No sample covers some real-world checks.** A product-bound test of a real `config.toml` against an OAuth auth spec was removed; no sample has an auth flow with a callback and a `supabase/config.toml`, so that end-to-end check is untested here. Two scans (`session-alive`, `session-lifecycle`) run with lower thresholds until a sample covers them.
3. **Formal models (`formal/`, `check:formal`) are not included yet.** Their `SOURCE` pins name files that do not exist here and must be re-pointed first.
4. **Tests that fail only when run as root** (for example a test that makes a directory unreadable) pass as a normal user.
5. **Timing tests.** `markdown.test.ts` bounds CPU time in absolute milliseconds (30 s). Replace it with a machine-independent check: the CPU time ratio when the input length doubles.
6. **Vocabulary in tests and fixtures.** `framework/` and the rules under `docs/rules/` are neutral. The code, tests and fixtures under `legacy/spec-tools` still use the vocabulary of the project they came from in many files, including text rendered into the generated handbook examples. They are being replaced by the neutral sample domain.
7. **Guarantee ids.** `TC-GUAR-` is the namespace for a product's guarantee rows. Two generators emit fixed ids such as `TC-GUAR-HEADERS-001` that a product's rows must use, and no sample declares them yet. Add a sample row for each kind, or derive the ids from the product catalog.
8. **Dangling references and process residue.** Docs and comments still mention working files that are not in this repository (a notes file, a backlog, a review queue, a handoff folder, a nightly workflow) and numbered review rounds. `vitest.heavy.config.ts` lists test paths that do not exist.
9. **CI** lacks "generate --check on samples" and tests against a Postgres service, and the actions are pinned by tag, not by commit SHA.
10. **Docs describe machinery that is absent here** (an integration-test row in CLAUDE.md, enforcement-matrix figures, a pre-commit that "runs verify"). The pre-commit hook only scans for secrets.
11. **Runtime coverage exclusions.** The 100% threshold on `framework/runtime/src/**` was met partly by generated tests of the original product. 22 runtime files that only those tests reached are listed by name in the coverage `exclude` of `vitest.config.mts` instead of lowering the threshold. Close it by generating and running unit tests for a sample product, then delete the list.
12. **Citations of things that do not exist here.** Docs and comments cite historical migrations, `__tests__/dev-repo/...`, `lib/fs-io.ts`, `@kaninabe/runtime/rpc`, working files, round ids such as "束" and "点検 N 回目", and `NOTES.md` / `BACKLOG` pointers. Each is to be removed or reworded as history without a path.
13. **The push-before gate depends on the hook being called.** `scripts/push-gate.sh` and `.githooks/pre-push` work only where `core.hooksPath` is set (`scripts/setup-dev-env.sh` sets it); an environment without it, `--no-verify` and a push of a ref the hook does not see are not stopped. The rule is to check at the start of work that the hook path is set, and never to skip the hook. Nothing checks this. What a push is scanned over is the set of commits that the destination does not advertise on its branches (asked at push time with `git ls-remote --heads`; `scripts/push-range.sh` prints the set); commits it holds only under other refs (tags, pull request refs, hidden refs) are scanned again, which is only more work, and a destination that cannot be asked, or a history that cannot be read to the end, stops the push. The URL that is asked is the URL the push really goes to: `git ls-remote` applies `url.<x>.insteadOf` to a URL again, so `push-range.sh` compares the URL it was given with `git ls-remote --get-url` in the same configuration, and when they differ it subtracts nothing (every commit is scanned) rather than use another repository's answer. Both the hook and the reviewer's by-name call resolve the URL in the caller's configuration, the way push does. The repository is the caller's (`GIT_DIR`, `--git-dir`/`--work-tree`), found once in the caller's environment and handed to the clean environment; a bare repository, no work tree, or `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` stop the scripts with a reason. `push.recurseSubmodules` pushes a submodule with the hook of the submodule's own repository, which this repository's hook does not cover. A remote with several push URLs runs the hook once per URL, and each URL is asked about itself.
14. **The content review record can be written by the author.** `kaninabe.contentReviewed` stops a push whose commit has no record of having been read for publication, but anyone can write the sha without reading. That is a rule, not a check. The hook allows pushes to `refs/heads/*` only (a branch deletion passes), and compares the pushed object itself, not what it points to, with HEAD. A tag push, a deletion included, is refused (tags are created and deleted only by the tag workflow); so is any push to `refs/notes/*`, `refs/remotes/*`, a pull request ref and the like, and an annotated tag object pushed by id to a branch. Reason: the message of a tag, a note and any other non-branch object is not scanned, and the object reaches the destination's object store even when the ref update is refused afterwards.
15. **A branch with no pull request yet gets only the general scan in CI.** Before a pull request exists, the word list is applied only by the pre-push hook on the developer's machine. Until the CI rework, the older scan steps in `ci.yml` still read the word list on pull request runs (the new gate step does not); they are removed in a later change, after the new step has been seen running on the main branch. The word-list step of the gate in `ci.yml` is guarded by `if: github.event_name == 'push' && github.ref == 'refs/heads/dev'`, which only stops it from running by mistake; **it is not a boundary**: a branch or a pull request from this repository can change the workflow file and still read the secret. The boundary (the word list readable only by reviewed definitions that run from the base branch, for example an environment secret restricted to the main branch) comes with the CI rework and needs a repository setting that only the owner can make; until then the word list is readable by any workflow run of this repository. The public output of the old steps is limited to counts (`SCAN_QUIET` for the word scan; `scripts/gitleaks-public.sh` for the key scans, whose own error messages can name paths). Those old steps (plain `gitleaks dir .` and `gitleaks git .` in `ci.yml`) and the pre-commit hook also still honour a gitleaks config, an ignore file and inline `gitleaks:allow` comments that sit in the scanned tree; only the gate fixes its own config and closes those, and the old steps stay as they are until the gate replaces them.
16. **Parts of the gate in the design that are not built yet.** (a) Exclusions are not listed file by file with a reason: the scan skips lock files by a name glob, and the gate's key scan (`scripts/gitleaks-gate.toml`, which extends the tool's default rules) also skips the file kinds on gitleaks' built-in allowlist, so a key in a text file of such a kind (a `.svg`, a file named `gitleaks.toml`) is not found. The scanner change replaces both with exclusions named file by file, each with a reason. (b) Mail-address strings are not limited to reserved example domains and the noreply form: the allow pattern in `scripts/scan-rules.sh` is wider. (c) The host rule inside test and fixture trees does not exist. (d) The check of workflow permissions and secret shapes (the checks of "何から守るか") does not exist: the gate checks only that workflow files parse and pass actionlint. (e) Files the scans cannot read are skipped, not red. Measured with gitleaks 8.30.0 (the key scan) and `git grep -I` (the word, mail and path scans): files with NUL bytes (binary), archives (not opened: `--max-archive-depth` is 0), text in UTF-16 and other encodings that are not UTF-8, symbolic links (the link is not followed), and files under paths on gitleaks' built-in allowlist (for example a `node_modules` directory) are not scanned for keys; the other scans skip every file git calls binary. Files that a `filter=lfs` attribute makes LFS-managed: with a usual LFS setup, `git add` replaces the content with a pointer, the content stays in the local LFS store, and only the pointer is committed, so the scans see the pointer. Neither the gate nor the hook sends LFS objects, and the LFS hook of git-lfs is not run while `core.hooksPath` is set; a manual `git lfs push`, or an LFS hook in an environment without `core.hooksPath`, would send content that no scan has read. Files of any size are scanned (no size limit is set), and values encoded up to the tool's default decode depth (5) are decoded. A `.gitignore` is not honoured by gitleaks, and `.gitattributes` does not change what it reads (checked, with tests, for `filter=lfs` in the same commit, in a later commit and in a nested file). (f) The scans need git 2.40 or newer (they read no attributes from the tree, so that `.gitattributes` cannot make files unreadable to them); with an older git they stop instead of scanning less. (g) Workflow files are checked at the tip (`HEAD`) only, not at each intermediate commit. (h) State inside the repository (`.git/config`, `.git/info/attributes`, `.git/info/grafts`, `refs/replace/*`) does not change what the scans read: the history is read from a neutral repository that borrows only the objects (no config, no `info/`, no refs), with the range given as commit ids, and `GIT_NO_REPLACE_OBJECTS=1` is set in every clean environment. What still runs against the real repository is limited to finding the repository (`rev-parse --absolute-git-dir`, `--show-toplevel`, `--git-path objects`), resolving `HEAD` and a `--base` name to a commit id (replace refs ignored), the shallow check, and `remote get-url` / `ls-remote` (which are about the destination, in the caller's configuration, as push is). The neutral repository reaches the objects through the real object directory and whatever `objects/info/alternates` chain it holds; objects are addressed by their content, so a redirected alternate can only make an object missing (the scans then stop), not different. A repository whose objects are not all present (a shallow clone, a partial clone with missing objects) stops the scans instead of being scanned in part. (a) to (e) belong to the scanner change; the design text in `development-flow.md` ("security") describes them as required.
