# ルール文書の更新手順

既存のルール文書を変えるときの手順である。**変更そのものより、変更が波及する先を取りこぼさないこと**に重心がある。ルールは他の文書から参照されている前提で書かれており、参照元を放置した変更は「従っているつもりで従っていない」文書を生む(PRIN-0008)。

## 目的

- ルールの追加・変更・削除に伴う文書の更新
- **文書間の参照整合性の維持**
- 単一情報源(PRIN-0007)と追跡可能性(PRIN-0008)を保つこと

対象は `docs/rules/` の既存文書(principle / domain / architecture / process / decision)である。新規作成は [how-to-create-rules.md](./how-to-create-rules.md) へ。

## 前提条件

- 更新の要件(何をどう変えるか)が確定していること
- 対象の文書が `docs/rules/` に実在すること

## 参照先

- [frontmatter_policy.md](../standards/frontmatter_policy.md) — フロントマターの項目と必須条件
- [reference_policy.md](../standards/reference_policy.md) — 参照キーの意味と参照の可否
- [id_policy.md](../standards/id_policy.md) — ID の形式・再利用禁止・廃番の扱い
- [template_policy.md](../standards/template_policy.md) — テンプレートの解決手順
- [../standards/change_policy.md](../standards/change_policy.md) — ADR の要否と breaking change の定義

## 手順（概要）

1. 既存ルールを読む
2. フロントマターを更新する
3. 本文を更新する
4. 影響分析(このルールを参照している文書を洗う)
5. 参照の整合性をチェックする
6. テンプレート適合をチェックする

## 手順1: 既存ルールを読む

- 現在のフロントマター(`doc_type` / `scope` / `id` / `norms` / `decisions` / `definitions`)を確認する
- 本文のどこを直す必要があるかを特定する(更新 / 追加 / 削除)
- principle なら `stability` を確認する
- **このルールが他の文書から参照されているかを確認する。** ここで参照元の規模を把握しておくと、手順4 の見積もりが早い

## 手順2: YAMLフロントマターを更新

### stability（principle のみ）

| 値 | 意味 |
|---|---|
| `high` | 変更の可能性が低い。変更したときの影響は大きい |
| `medium` | 状況により変わりうる |
| `low` | 変更の可能性が高い。実験的 |

### norms / decisions / definitions の増減

- **`norms` を足す:** その `PRIN-*` / `ARCH-*` が実在するかを確認する。**外す:** その規範が根拠として不要になったかを確認する
- **`decisions` を足す:** その `ADR-*` が実在するかを確認する。**外す:** その決定と無関係になったかを確認する
- **`definitions` を足す・外す:** 定義の出典として正しいかを確認する。**`definitions` に書くのは定義文書の id であり、外部 URL ではない**(正は [reference_policy.md](../standards/reference_policy.md))

### 更新日について

**フロントマターに更新日の欄を足さない。** 項目一覧([frontmatter_policy.md](../standards/frontmatter_policy.md))に無く、実際の原則文書も持っていない。**いつ何を変えたかは git の履歴と `NOTES.md` が持つ**ので、文書の中に日付を二重に持たせない(PRIN-0007)。

## 手順3: Markdownボディを更新

フロントマターの変更に合わせて本文も直す。確認するのは 3 点である。

- 追加・変更した内容が明確に書かれているか
- 解決されるテンプレートの構造に従っているか
- **`norms` で参照している原則が本文に反映されているか。** フロントマターだけを直して本文が古いままだと、参照グラフと中身が食い違う

## 手順4: 影響分析（このルールを参照している他のドキュメント）

### 参照元を洗う

ID を持つ文書(principle / architecture / decision / directory_guide)は、その ID で全文検索する。

```bash
grep -rn "ARCH-BE-0013" docs/
```

**`norms` / `decisions` に並ぶ id と、本文中の言及の両方が引っかかる。** ID を一意にしてあるのは、この検索が成立するためである。

### 影響の件数で進め方を変える

| 参照元の件数 | 扱い |
|---|---|
| **10 件以上** | 大きな変更。breaking change の可能性が高い → **ADR の作成を検討する** |
| **5〜9 件** | 中程度。影響先を個別に確認する |
| **4 件以下** | 小さな変更。通常のフローで進める |

件数で機械的に切るのは、影響の大きさを書き手の主観で見積もらないためである。10 件を超える参照元があるルールは、もう「小さな変更」では済まない。

### 影響先を仕分ける

- **更新必要** — ルールの変更で、参照元の記述が不正確になった
- **更新不要** — 影響しない(軽微な文言の修正など)

確認すること: 全ての参照元を見たか / 影響の有無を判断したか / 更新が必要な文書を一覧にしたか / breaking change なら ADR の作成を検討したか。

## 手順5: 参照の整合性チェック

```bash
npm run verify
```

**見るのは 3 点である。**

1. **存在しない参照先** —— `norms` / `decisions` / `definitions` に実在しない ID が無いか(M3)
2. **循環参照** —— A → B → A の形になっていないか(M6)
3. **パスの妥当性** —— 本文の相対リンクが実在するファイルを指しているか(M4)

エラーが出たら、存在しない ID は削除するか正しい ID に直す。循環参照は参照の向きを整理して解消する —— 下位から上位への参照だけを残せば必ず解ける。

**実行のタイミングは自由である。** コミット前、更新の途中、確かめたくなったとき。ただし**verify が通らない状態でコミットしない**のは鉄則であり、CI が同じものを再実行する。

## 手順6: テンプレート適合チェック

**解決されるテンプレートを開いて、実物と比べる。**

- 必須の節(H2)が揃っているか
- 節の順序がテンプレートと合っているか
- フロントマターの必須フィールドが揃っているか

**必須の節の一覧はここに書き写さない。正はテンプレートそのものである**(PRIN-0007)。どのテンプレートが解決されるかは [template_policy.md](../standards/template_policy.md) の手順で決まり、H2 の突合は M5 が warning として報告する。

## ユースケース別の更新パターン

| パターン | フロントマターの変更 | 本文の変更 |
|---|---|---|
| principle に新しい適用例を追加 | なし | 適用の節に項目を足す |
| architecture に関連 ADR を追加 | `decisions` に id を足す | 関連する意思決定の節にリンクを足す |
| process に新しい手順を追加 | なし | 手順に項目を挿入する |
| principle の安定性を変更 | `stability` を変える | 背景に変更の理由を書き足す |
| **ルールを廃止する** | 下記 | 下記 |

### ルールを廃止する（削除ではなく非推奨化）

**ルールを削除しない。廃止のフラグを立てる。**

1. フロントマターに `deprecated: true` を足す
2. **本文の冒頭に廃止の警告ブロックを置き、理由・代替・廃止日を書く。** 以降の元の内容はそのまま残す
3. **代替となるルールを明記する**
4. **既存の参照元を洗い、参照を更新する**(手順4 の手順で)

削除しないのは、廃番を残すという [id_policy](../standards/id_policy.md) の約束の手順版だからである。ファイルごと消すと、過去の議論やコミットが指す先が消える。

理由・代替・廃止日を**本文に書く**のは、それらを表す専用のフロントマターキーが定義されていないためである。キーを増やしたくなったら、[frontmatter_policy.md](../standards/frontmatter_policy.md) を先に直す。

## チェックリスト

**更新前**

- [ ] 更新の要件を理解した
- [ ] 既存の内容を確認した
- [ ] 参照元を確認した

**フロントマター**

- [ ] `stability` を確認した(principle の場合)
- [ ] `norms` / `decisions` / `definitions` の増減が正しい
- [ ] 廃止する場合は `deprecated` を立てた

**本文**

- [ ] 変更を反映した
- [ ] テンプレートの構造に従っている
- [ ] `norms` で参照している原則が本文に反映されている

**影響分析**

- [ ] 参照元を検索した
- [ ] 影響先を一覧にした
- [ ] 更新が必要な文書を特定した
- [ ] 件数に応じて ADR の要否を判断した

**整合性**

- [ ] `npm run verify` が通る
- [ ] 影響先の文書も更新し、レビューした
