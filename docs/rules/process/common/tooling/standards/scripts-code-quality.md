# legacy/spec-tools のコード品質規約

`legacy/spec-tools/` 配下のツールコード(検証器・生成器・CLI)に適用する設計・実装・テストの規約。ルール(検証チェック)は今後も増え続けるため、追加が安全で局所的に行える構造を強制する。

## 目的・スコープ

- 対象: `legacy/spec-tools/` 配下のすべてのTypeScriptコード
- 目的: ①検証器の追加・変更が既存コードに波及しない構造 ②全ロジックがユニットテスト可能 ③ファイルの肥大化防止(300 行は信号。超えるなら理由と分割の検討を冒頭に宣言する)

## ルール

### 設計

- **すべきこと: インターフェース先行。** 新しい検証器・生成器は、共有インターフェース(`lib/check-api/contract.ts` の `Verifier` 等)を実装する独立モジュールとして追加し、レジストリ(`ALL_VERIFIERS`)に登録する。呼び出し側(CLI)の変更を伴ってはならない。
- **すべきこと: 検査は群の登録に載せ、全検査の表で列挙できるようにする。** 検査を足したら、その群の登録(`lib/<群>/checks.ts`。登録配列を持つ群は `verifiers/index.ts` も)に足す —— 検査 ID と題と実行の順を持つのはそこで、群の実行口(`run.ts`)は登録を上から回すだけにする。ID の綴りは検査器のファイルに 1 が赤にする(免除の表ではなく宣言の欄)。**載せ忘れは 3 つの網で止める**: ①検査器のコードに ID として書かれた綴りが表に無ければ赤(`check-registry.test.ts`)②実際に出た違反の `verifier` が表に無ければ赤(`emitted-check-ids.test.ts`。見る題材は製品・6 `reads`(どの入力に依るか・使えないと見ていないこと)を宣言し、**段へ渡る入力はその宣言で絞る**(`dataStep` が `narrowStepInput` で宣言した種類だけを実行時に渡し、型も `Pick` 相当に絞る。宣言を足し忘れて裏づけを読むと型で落ちる)。表の全体を前提とする段は `needsWhole` `gatesUnverifiedNote`。全部入りの出力は変えない)。
- **すべきこと: 検査への入力は「未選択 / 阻害 / 読込済み」に分けて渡し、実行しなかった検査は報告する**(部品化 ②-b。`lib/kernel/input-state.ts`)。検査が別の種類のカタログを要るとき、入力を任意の欄(`jobs?:`)にして「無ければ何も言わない」と書くと、**その種類を採っていない製品**と**採ったのに読めない製品**が同じ見え方(全部確認済み)になる。選択は製品が `product.md` の `uses` で宣言し(ファイルの有無から推定しない)、採っていなければ**未実施**・採ったのに渡せなければ**阻害**・渡せれば**実行**(0 件の空のカタログもここ)になる。実行は合格を意味せず、読み込みの診断(`loaderFindings`)と検査の診断(`verifierFindings`)は別々に持つ(全体へ足すのは読み込んだ側の 1 回だけ)。検査器は `catalogTraceVerifier` で定義すると、未実施・阻害が実行ログに理由つきで 1 行ずつ出て、サマリの「範囲を実行していません」の件数に入る。**任意の欄から 1 本ずつ移している途中**で、移し終えた検査は A13(`jobs`)・T2(`queries` / `data_tables`)・画面の到達を読む S13 / S16 / Y3 / Y5(`screens`)・A10(`external`)・A15 / A18 / A19(`data_tables`)・V16 / V17 / V18(`actions`)・V17 / V19(`data_tables`)・A 群の action_spec が前提の検査全体(`actions`)・Y8 / Y10 / Y12(`data_tables`)・X1(b) / X5(a)(`data_tables`)・T 群の `data_tables` 自体と T6 / T11 / T12 が裏づけに読む `actions` / `jobs` / `usecases` / `external` / `api`・X 群の `external` と X2 の接地先の `config`・画面の到達の `auth` の関門である(`TraceInput` / `VerifyContext` の残る任意の欄 —— `guards`(カタログではなくガード式のパーサー)・`applicationRefs`(実装の木の走査結果で、`uses` ではなく根の `app` の宣言が決める)— は従来どおり)。**未選択を「事実として無い」と扱うのは判定の母集合が入力そのものの検査だけ**(action_spec の `input` / `computes`・外部連携の `emits`・自分の種類を検査する群)で、入力の裏づけを見る検査(テーブル仕様)は未選択も「見られない」として行で言う(placement_policy.md「`uses` の移行と、状態つきの検査の範囲」)。複数の検査が同じ入力を読む値は、使えなかった入力を `gaps` で返し、報告の行は `verify/check-run-report.ts` の `describeInputGap` 1 本の書き方にそろえる(検査ごとに別の書き方を増やさない。一部の判定だけが阻害に依る形も、検査の全体が依る形も、`InputGapNote` の `gaps` の 1 本の口で言う)。
- **すべきこと: I/Oと純粋ロジックの分離。** ファイル読み込み・パスの解決は `lib/model/loader` とCLIだけが行う。検証器・生成器は構築済みのモデル(`SpecModel`)を引数に受け取る**純粋関数**として書く。**ファイルを読む(`node:fs` / `node:child_process`)のは io 層と、層の表で宣言された入口(ローダー・走査器・通し実行ほか)だけ**である。検証器の中で `fs` を import してはならない(構造テストが見る。実ファイルの中身を見る項は `lib/io/read-text.ts` の `readText` / `tryReadText` を通す。`fs` の入口は層の表で**実際に読むファイルを 1 本ずつ名指し**し、接頭辞つきの任意の名前を通さない)。**これは `node:fs` の綴りの規則であり、検証器の純粋性の保証ではない**(検証器は `io/paths.ts` の小道具や `repoRoot` を通して実ファイルを読む形が残っている)。入力を 2 段にする(読む層と検証する層を分ける)のは別の宿題である。
- **すべきこと: 依存はコンストラクタ/引数で注入する。** ガード式の評価などの共有サービスは `VerifyContext` 経由で受け取る。モジュール内で他モジュールの具象を直接 new しない。
- **すべきこと: 推論・探索は既製品に任せ、写像だけを自作する**(2026-09-11 のユーザー原則)。**充足性の判定器は Z3**(`z3-solver`。docs の devDependency。exact version で pin)であり、仕組み側が持つのは「ガード式 + 変数ドメイン → SMT-LIB」の写像(`lib/guard/smt.ts`)と、非同期の判定を同期の検証器へ届ける段取り(`lib/verify/z3-satisfiability.ts`)だけである。**自作の列挙器(`lib/guard/satisfiability.ts`)は先読み**であり、同期で呼べる場所(V8・UX・画面の入場判定・SQL の畳み込み)がそれを使う —— 消してはならないが、V9 / V10 の判定の正ではない。2 つが食い違わないことは fast-check の差分テストが実測する。新しい推論器を自作する前に、まず既製品で足りるかを見ること。
- **すべきこと: 仕様の意味を導く処理は出力側(`generate/render`)に置かない。検証と生成は同じ意味解析の結果を読む。** 「この操作はどの状態機械のどのイベントに接地するか」「この操作は確認が要るか」のように、**仕様のモデルとカタログだけから決まる事実**を導く純粋関数は意味解析の層(`lib/semantics/`)に置く。依存の向きは `model`(読み込み・型)→ `semantics`(意味の導出)→ 検証器・生成器(`verify` / `usecase` / `generate/render` …)で、**逆向き(意味解析が出力側や検証側を import する)は持たない**。出力側が持つのは、意味解析の結果に文言と形を与えることだけ(根拠の行・確認ダイアログの注意書き・表の組み立て)である。検証器が出力側の関数を借りて同じ判定を計算したくなったら、それは判定が置き場を間違えている印であり、**文脈が足りないからと軽量版を別に書かない**(画面が使う結果と検証が数える結果が食い違う)。足りない入力は意味解析の関数の引数として受け取る(例: `OperationCatalogs`。生成器の共有文脈 `GenerateContext` には依存しない)。 執行は下の「層の表」の `facts` の行(構造テスト `lib-layering.test.ts`)である。
- **すべきこと: 生成するデータは型つきのまま運び、汎用の値型に潰すのは文字列にする直前だけにする。** エンジンの規則表(`MachineTable` / `CreateTable` …)は、組み立てる関数(`engine-tables.ts`)が**その型を返す**。`LiteralValue` のような汎用の値型を返して、使う側が型アサーションで型を戻す形は**してはならない** —— エンジンの型の欄を変えても組み立ての箇所で型エラーにならず、発見が生成後の型検査やテストまで遅れる(外部レビュー ⑤。欄名を 1 つ変えると、いまは組み立てのその欄で `tsc` が赤になる)。文字列にする入口 `renderLiteral` は `Literalizable<T>` で「リテラルにできる形か(関数・`undefined` の値が無いか)」を**型で**見るので、`interface` で宣言したエンジンの型をそのまま渡せる。world の設計図(`eq-worlds` / `rls-worlds`)を組む関数は、返り値にハーネスの型(`EqWorld` / `EqSaveWorld` / `RlsWorld`)を付ける(欄名の変更が生成物の `satisfies` まで遅れず、組み立ての場所で赤になる)。**数えるのは AST で 2 つ**: **二段の型アサーション**(`x as A as B` / `(x as A) as B` / `<A><B>x`。間に `unknown` を挟んでも、他の型を挟んでも、改行で割っても同じ)と **`as any`**(`<any>x`・`as any[]` を含む)。`lib/**`(テストを除く)で**件数を固定**する(いまは 0 件): 残す箇所には直前に `型を戻す理由:` の行コメントを置き、ファイルごとの件数を宣言する(免除の一覧ではなく、増やすと赤になる数)。執行は構造テスト `legacy/spec-tools/__tests__/unit/gates/no-type-restoring-cast.test.ts`
- **すべきこと: 依存の向きが行数より先。** `lib/**` の import は下の「層の表」の向きにだけ流す。ファイルを割るときは**責務の境界**で割り、割った結果が互いを読み合うなら、それは境界の引き方が違う印である(共通の定義を下の葉へ出す・入口から下へ呼ぶ向きだけを残す・再輸出の入口を持たない)。**層の違反は数えて基線で固定し、束ごとに減らす**(移行中の新規の違反はその日から赤)。
- **してはいけないこと: 値の循環 import。** 実行時に効く import(副作用・動的・`export … from` を含む。型だけの import は除く)の輪がファイル単位で **0** であること。**基線を持たない**(常に 0)。`import type` の循環は実行時に消えるので数えない。
- **すべきこと: 300 行は信号として扱い、超えるファイルは冒頭の JSDoc に宣言を持つ**(テスト・生成コードを除く)。300 行は**上限ではない**(裁定 2026-09-30。「行数は本質ではない。必要があるなら長いファイルは問題ない」)。ただし何も意識しないと巨大な無駄なファイルもできるので、超えるなら次の 2 つを書く。
  - `@oversize` … **1 つの責務のまま超える妥当な理由**(例: 「1 つの表の全規則を 1 か所で読み通せるようにする」「状態機械の全遷移を並べて抜けを見えるようにする」)
  - `@split-review` … **責務で割れるかを検討した結果**(割る案と、採らなかった理由。割れるなら割る)
  - どちらも本文 10 文字以上。**行数そのものを理由に書かない**(「行数」「300 行」「制限」「上限」が本文にあると error —— 行数は理由にならない。理由は中身から書く)。**300 行以下のファイルに宣言が残っていても error**(腐った宣言を残さない)。宣言の無い超過は error のままである。
  - **宣言の本数に上限は置かない**(必要があれば長くてよい)。代わりに本数を `npm run verify` の W 群の 1 行に毎回出す(「300 行を超える宣言つきファイル N 本」。情報であり warning ではない。増え方が見える)。
  - **`@split-review` はそのファイル固有に書く。** 割る案は**そのファイルで実際に考えられる割り方**(例: 「状態ごとに割る」「読む側と書く側に割る」)で、採らなかった理由も**そのファイルの中身**から言う(例: 「遷移表は全状態を 1 枚で見ないと到達性が読めない」)。どのファイルにも貼れる文(「割ると 2 枚を行き来する」)は検討の跡にならない。**同じ本文の `@split-review` が 3 本以上あれば W4 が warning にする**(ファイルをまたぐ性質なので lint ではなく verify が見る。判定は `oversize.mjs` の `repeatedSplitReviews`)。理由が書けないなら、それは割れるということなので割る。
  - **執行**は `@kaninabe/lint-config` の自作規則 **`layer/declared-oversize`** 1 本(docs / app / framework の 3 つの木で `max-lines` を置き換える)。判定の純関数は `oversize.mjs` に 1 つだけ置き、lint と verify の本数の報告が同じ関数を呼ぶ。
- **すべきこと: 行数で割るときは責務の境界で割る。** 依存の向きが行数より先である(上の項)。**「行数の制限のために分けた。境界に意味は無い」と書く分割は禁止する** —— そう書かざるを得ない分割は、責務が 1 つなのに行数で切った印であり、くっつけて宣言(`@oversize` / `@split-review`)で通すか、責務の名前でファイルを割り直す。ファイルの冒頭の説明は**そのファイルの責務**を書く(「なぜ分けたか」を行数で説明しない)。執行は構造テスト `legacy/spec-tools/__tests__/unit/gates/no-oversize-split-excuse.test.ts`(C29)で、`lib/**` ・`cli/**` ・`framework/**` ・`app/src/**` のコメント(見出しも途中の節も)に「境界に意味は無い」という断定や、ファイルの大きさの制限を理由にした分割の説明があれば赤にする。**基線を持たない(常に 0 件)**。
- **すべきこと: 割るか・くっつけるかの判定の軸は「その部品を誰が使うか」である。** 行数でも、統合のしやすさでもない。
  - 小さい側のファイルを**別の使い手が直接 import している**なら、それは独立した部品であり、**割ったままが正しい**(冒頭の説明は「誰が何のために使うか」で書く)。例: 経路の探索(`model/path-hops.ts`)は欄の解決 `path-resolve.ts` のほかに、到達性の検査・スコープ条件の列パス・写しの列の参照パスが、探索だけを直接読む。
  - **責務の線が言えない**なら、くっつけて宣言(`@oversize` / `@split-review`)で通す(片方を読むのにもう片方が要る・値と型が往復する。使い手が 1 人でも、別の判定・別の責務なら割ったままでよい。例: `data/verifiers/t7-rls-helpers.ts`)。
  - 集約の族ごと・表ごとのように**意味のある境界**で割れているものも、割ったままにする(例: app の `database.rows.*` ・`database.functions.*` は集約の族ごと)。
  - **行数で割らないことは、くっつけることを意味しない。** 「行数のために分けた」と書く説明は、責務の名前で書き直すか(別の使い手がいる場合)、くっつけて宣言するか(いない場合)のどちらかにする。
- **してはいけないこと: 検証器同士の依存。** 各検証器は互いに独立で、実行順序に意味を持たせない。
- **してはいけないこと: 生成器が throw すること。前提は検査器へ。** 生成器は「検査を通った入力しか来ない」前提で書いてよい。したがって「決められない入力」は**検査器が Finding(場所・対処・反例)で先に止める**のが正しく、生成器が `throw new Error('…')` で守ってはならない —— それをすると**仕様の問題がスタックトレースとして出る**ので、どのファイルの何をどう直すかが読めず、しかも `verify` が緑のままなので「仕様は正しいのに生成器が壊れている」と読めてしまう(束 ⑱ の 4 題材が 4 件実測した)。
  - 生成時に前提が破れていたら、それは**仕様の問題ではなく検査の穴**である。唯一の出口は `lib/kernel/generator-precondition.ts` の `preconditionFailure(検査器ID, 問題[])` で、**その前提を先に見るべき検査器の ID を示して**止める(CLI が verify と同じ字面で印字する)。直し方は「示した検査器に判定を足す」であり、これが読めるようにするための宣言である。
  - 可能なら**型で除く**ほうが上である(例: 複合 RPC に渡せない供給元を `Exclude` で落とし、生成器の switch を網羅にして既定の枝を持たせない)。
  - 執行: `npm run lint`(`legacy/spec-tools/lib/generate/**` の `ThrowStatement` を禁止)。例外は「書き方の例」の章だけで、あれは入力が仕様モデルではなく**リポジトリの実ファイル**であり、失敗は仕様の問題ではなく鮮度エラーである([code-examples.md](./code-examples.md))。

仕組みは**製品の木の位置を 1 つも知らない**。知っているのは宣言ファイルの名前だけで、それ以外のパスは宣言から組み立てる。散文の正は [placement_policy](../../../../meta/standards/placement_policy.md)「根は製品が宣言する」。

- **すべきこと: 組み立ては `lib/model/product/paths.ts` の口だけを通す。** `specPath` / `bookPath` / `generatedPath` / `migrationPath` / `appPath`(実装の木の根そのもの) / `previewsPath` / `knowledgePath` / `joinPath` が全部であり、ここ以外でパスを文字列結合しない。**実装の木の中の位置**(ソースの根・ルーティング・E2E・設定の雛形・ハンドブックが写す資材ほか)は、`paths.ts` では組まない —— 置き場の配置の役割(`sourceRootPath` / `e2eRootPath` / `envTemplatePath` / `scriptRootPath` / `appResourcePath` ほか)が決める(部品化 ③-c6 で旧い口 `appSrcPath` / `routePath` / `endpointRoutePath` を消した)。
- **すべきこと: 宣言は上流で 1 回だけ読む。** CLI・パイプライン・通し実行が `loadProductRoots(repoRoot)` を呼び、以降は `ProductRoots` を引数として配る(検証器は `VerifyContext.roots`、生成器は `GenerateContext.roots`、画面は `ScreenContext.roots`)。検証器・生成器の中で宣言を読み直してはならない —— 同じ実行の中で根が 2 つになりうる。
- **してはいけないこと: 製品の根の綴りでパスを組み立てること。** `'app/src/...'` / `'docs/specs/...'` / `'supabase/migrations/...'` のような文字列リテラルを書かない。**執行は W3**(`npm run verify`。error)で、免除リストは無い。走査範囲は**検証器・生成器の置き場と CLI**である(`FRAMEWORK_SOURCE_DIRS`)—— CLI は宣言を読む入口そのものなので、そこに 1 本残ると「宣言を読んでいるのに 1 か所だけ綴りで実ファイルを読む」形になる。
- **仕組み自身の住所は綴ってよい。** 検証器・生成器の置き場・CLI・約束事のモデル・規約の木・ドキュメントサイトのルートは製品の根ではないので、この禁止の相手ではない。ただし**綴りは `lib/io/paths.ts` の定数 1 か所に置く**(`FRAMEWORK_DOCS_DIR` / `FRAMEWORK_RULES_DIR` / `FRAMEWORK_LIB_DIR` / `FRAMEWORK_CLI_DIR` / `FRAMEWORK_FORMAL_DIR`)。**製品の根から導いてはならない** —— 規約の木を「仕様の木の親の `rules`」として導くと、仕様の木を `spec/` に置いた製品で M 群が黙って消える。分離の手順 ② で住所が変わったらここだけが動く。
- **W3 の判定は 2 つある。** ①**根で始まるリテラル**(`'{根}/…'`)。②**`path.join` に渡した 1 語の根**(`path.join(repoRoot, 'app')`)—— ① だけだと 1 段の根の直書きがすり抜けるので、**第 1 引数が文字列リテラルでない**ことを条件に分ける(`join('src', 'app')` は層の並びを組んでいるので相手にしない)。
- **まだ届かない範囲がある(書き過ぎない)。** `path.join` 以外の口に 1 語の根を渡す形は W3 も型も止めない —— `appGrounded()` / `appPath()` が宣言を要求するのは「その口を**通るなら**」であって、直書きを禁じる力は無い。**ここは人が見る**。届く面積を広げたいなら W3 の判定を足す(免除を足すのではなく検査を足す)。
- **根の値を `?? ''` で空文字に潰さない。** 実装の木を持たない製品では `appPath()` が `null` を返す。潰すと `path.join('', 'app')` が相対パス `app` になり、**ホストの接続層と seed を書き潰す**(設計メモ §8 が名指した既知の脆さ)。線はこうである:
  - **実 I/O の起点・プロセスの起動・書き出し先には流さない。** 呼び出し側が「宣言が無いならその段を飛ばす」と書き、飛ばしたことを報告する(`scanAppTests` は `appRoot: string | null` を受け、`runGeneratedTests` は理由つきの失敗を返す)。通し実行のように**実装の木の宣言を前提にしてよい**層は、`sampleAppRoot()` のように総な口を 1 本置いて早く止める。
  - **人が読む文面には、空パスを書くより「示せない」と言う。** 生成物の doc コメント・検査の `suggestion` は、宣言が無いなら**その 1 文を落とす**か「この製品では決まっていない」と書く(空パスは嘘である)。
  - **読めなかったら鮮度エラーになる読み取り**(ハンドブックが写す実物・「書き方の例」の抜粋)は、空に倒しても**その場で赤くなる**ので許す。

### 実装

- **使われていない宣言を残さない**(未使用の import / 変数 / 引数)。意図して使わないものは `_` で始める —— 名前に書いてあるので免除リストも `eslint-disable` も要らない。執行は `npm run lint:spec-tools`(`@typescript-eslint/no-unused-vars`)。束 ①-c-d で足したとき、**300 行で割った跡の死んだ import を含む 54 件**が出た(どの検査も見ていなかった)
- 全エクスポート(関数・型・クラス)に**JSDocを付ける**。「何を・なぜ」を書き、引数と戻り値の意味を説明する。実装の逐次説明コメントは書かない
- **説明する相手を失った JSDoc(孤児)を残さない。** 300 行で割ったときに説明だけが取り残されると、宣言の側は JSDoc 無しになり(上の規則に反する)、残った説明は誰も直さない ——束 ①-c-c で実際にそうなった(`literals.ts` の末尾に「生成物の目印」の説明が残り、対象は別ファイルへ)。`no-unused-vars` は宣言を見る規則なので**宣言を持たないコメントは検査の範囲外**で、執行は構造テスト `legacy/spec-tools/__tests__/unit/gates/jsdoc-placement.test.ts`(JSDoc のあとに宣言が1 つも来ない = ファイルの終わり・閉じ括弧)。**捕らない形**(直後に別の JSDoc が来る形)はその JSDoc に実測つきで書いてある
- **ソースに生の制御文字を埋めない。** git がそのファイルをバイナリと判定して diff を 1 行も見せない(束 ㉔ で実際にレビューできなくなった)。区切りが要るならエスケープ表記で書く(意味は同じ 1 文字)。執行は `@kaninabe/lint-config` の自作規則 **`layer/no-raw-control-char`** 1 本で、**docs / app / framework の 3 つの木すべてに掛かる** —— `no-restricted-syntax` に相乗りさせていた形はフラット config の後勝ちで `lib/generate/**` と `lib/diff/**` から消えており、その穴の中に生きた違反が 1 件住んでいた(束 ①-c-d の独立レビュー。`app/e2e` にも 1 件)
- 検証結果は必ず `Finding` 型(何が・どこで・どう直すか+反例)で返す。`console.log` やthrowで違反を報告しない
- `any` 禁止。外部入力(YAML)の型付けはパース境界(loader)で行い、以降は型付きモデルのみを流す
- **生成物に出る日本語は文言表(`lib/messages/messages*.ts`)から引けるようにする。** 仕組みが**自分で持つ DB オブジェクト**の文言も同じである —— `lib/sql/api-base.ts` の関数の説明は `messages-ddl.ts` の `API_BASE_WORDS` に置き、`lib/sql/framework-tables.ts` の列の説明は宣言そのものを正として `frameworkTableWords()` で `messageFragments()` へ流す(表を 2 つ持たない)。説明できない日本語が生成物に出ていたら出力側の目(`__tests__/samples/generated-wording.ts`)が落とす。**`.ts` の生成物に写る文言だけが走査の対象**であり、SQL だけに出る文言(`API_BASE_WORDS`)は規約として表に置く

### テスト

- **テストのカバレッジ定義は「規約網羅」**: 対象ルール文書(domain-spec-writing.md のV1〜V12等)に書かれた各要求・各エラーケースに、対応するユニットテストが1つ以上あること。行カバレッジではない
- 検証器のテストは**モデルをテスト内でリテラル構築**して渡す(ファイルI/O不要 = loaderに依存しない)。fixtureファイルはloader自身のテストのみに使う
- 各検証器につき最低: 違反を検出するケース / 違反がなく通るケース / 境界ケース、の3種
- **検査の効き目は変異テストで実測する**(束 ⑳-5c)。「正しい仕様で緑になる」ことは、生成器・検査器・期待が**壊れたときに赤くなる**ことを示さない。仕様の宣言を機械で 1 か所壊し、どの検査が気づくかを実測する目録が `lib/mutation/**` にある(対応表はハンドブックの保証の章に生成される)。**捕る検査が 1 つも無い変異は検査の漏れ**であり、受け入れる口は持たない —— 直し方は検査を足すことだけである(書き方は [guarantee-spec-writing.md](../../../backend/specification/standards/guarantee-spec-writing.md) §変異の目録)。
- テストは `legacy/spec-tools/__tests__/unit/` 配下に、`lib/` のパス構造をミラーして置く
- **生成器は見るものの無い試験を出さない。出す試験には、落ちうる assertion が 1 つ以上ある**(fix27 A2)。見る相手の表(起動口・口・行)が空の題材では、その表を回すだけの `it()`(空の配列への `expect(...).toEqual([])`)は何も見ずに通るので、生成器の側で出さない(出さない条件は題材の実物の宣言から決まる)。実行時の網は vitest の `expect.requireAssertions`(アプリ本体・道具の設定と、題材の木の設定 `db-places.ts` の `REQUIRE_ASSERTIONS_LINE` が持つ。assertion の無い `it()` は赤)で、題材の木でも効くことは題材の表(`__tests__/samples/sample-coverage.ts`)の `guard:require-assertions` の行が、assertion の無い `it()` を実際に置いて赤になる数で見る。生成した試験の全部は同じ表で「回った it の数」を持ち、0 回の行・生成しない条件(`na.ungenerated`)が崩れた行は赤になる

### 配布の形の道具(ルートの `tools` の `dist`。dev 側だけに置き、配布の木に入らない)

仕組みだけの木を機械的に組み立て、混ざってはいけないものと単体で通らないものの**いまの件数を測って記録する**道具。`legacy/spec-tools` の外(ルートの `tools` ディレクトリ)にあり、この章の他の規約(層の表・300 行の宣言)の対象ではない。ここに書くのは、この道具自身の約束だけである(以下のパスは `dist` ディレクトリからの相対)。

- **依存を持たない。** Node の型除去でそのまま実行する(`cli/` の TS を `node` で直に起動する。ルートの `npm run dist:assemble` / `npm run dist:check`)。import の綴りは `.ts`。重い依存を足さない。
- **宣言は 2 つで、どちらも道具の中に置く。** `manifest.ts` が入れる / 入れないを理由つきで宣言し(追跡ファイルの全部がどちらか片方にだけ当たる = 閉世界。どちらにも当たらない・両方に当たる・どれにも当たらない規則は赤)、`dictionary.ts` が禁止語・鍵の形・移植の印を持つ。**辞書そのものが混入源なので、配布の木には入れない**(manifest が道具のディレクトリ全体を入れない側に置く)。
- **検査は木のファイルを受ける純関数にする。** `node:fs` / `node:child_process` に触れるのは `lib/fs-io.ts`・`lib/npm-ci.ts`・`cli/` だけ。組み立ての出力先はリポジトリの外(OS の一時ディレクトリ)で、中を指したら止まり、**印(`.dist-assembled`)のあるディレクトリか空・不在のときしか作り直さない**(別のディレクトリの中身を消さない)。起点は `git ls-files`(未追跡の原本置き場などを拾わない)。
- **鍵の形は値を持たない。** 指摘にも上限の記録にも、種類とファイル:行だけを書く(値を読み出す部品を作らない)。テストの偽の値は断片をつないで作り、テストのファイル自身が鍵の形を持たないようにする。
- **件数は上限(ラチェット)として `baseline.json` に記録する。** `dist:check` は増えたら赤(増えたファイルと今の行を名指す)・減ったら「上限を下げてよい」と出し、`--write-baseline` で書き直す(増加が残っていれば書かない。意図した増加だけ `--allow-increase`)。閉世界は上限を持たず常に 0 が条件。`npm ci` は試して結果を記録するだけで、落ちても赤にしない。
- **手元で回す。** CI には入れない(push の分数を増やさない)。単体テストは `__tests__/` にあり、ルートの vitest の projects に載る。

- `npm run typecheck`(tsc --noEmit)、`npm run test`(vitest)、`npm run lint` がすべて通ること

- 「行数の制限のための分割」の説明は `npm run test`(構造テスト `no-oversize-split-excuse.test.ts`)で機械検証する
- 生成器の `throw` 禁止は `npm run lint`(`no-restricted-syntax` の `ThrowStatement`)で機械検証する
- 借りる向き(app が `docs/` を import しないこと)は `cd app && npm run lint`(`no-restricted-imports`)で機械検証する — 執行の対応は [enforcement-matrix.md](../../../backend/system/standards/conventions/enforcement/enforcement-matrix.md) の B14。**逆向きの `import` は 0 本**であり(ADR-0013)、残るのは差分テストの宣言された例外 9 本だけである。**「0 本」は `import` と仕組みの写しの両方が 0 という意味である**(ハーネス本体 13 本は `@kaninabe/runtime/testing/**` へ出たので、通し実行が写す仕組みの実体は無い)。通し実行が `fixture` の一時ツリーへ `cpSync` で写すのは**製品の接続層の口の実装 1 本(`harness-ports.ts`)だけ**であり、これは仕組みの写しではなく、口の向こうを実 DB・セッションへつなぐ製品の手である。写しは import ではないので lint に映らないが、数えない理由はこれである
- 台帳(`NOTES.md` / `BACKLOG.md` / `docs/handoff/` の `review-queue.md` と `session-handoff.md`)の**形**は pre-commit が分岐より前に `check-ledger-shape.ts`(`tools` の `ledger`。開発用リポジトリだけの道具で、配布の木に入らない)で機械検証する(H1 がちょうど 1 本・`## ` 見出しの重複なし・H1 の癒着なし。台帳だけのコミットは中身の検査を飛ばすので、古い全文の書き足しで台帳が 2 重になる事故をここで止める)。**フックから直接呼ぶ道具は依存を `node:` の標準だけにする**(`lib/` を import しない = 検証器の起動を挟まず台帳のコミットが遅くならない。Node の型除去で動かすので、型だけを消せば JavaScript になる書き方に限る)。固定は `ledger-commit-gate.test.ts`(本物のフックを使い捨ての git リポジトリで動かす)
- 配布の形の道具(`tools` の `dist`)は `npm run test:dist`(単体テスト)・`npm run typecheck:dist`(型)で検証する。`tools` の `dist` と `ledger` のコード規約は `npm run lint:tools`(仕組み側のパッケージと同じ規則を `tools` の ESLint 設定が流用する。`process.env` の読み方の禁止だけは設定の閉世界(K1)が読む木に合わせて掛けない)で機械検証する
- 組み立てた木への検査は **pre-commit が台帳だけのコミット以外で毎回回す**(`dist:assemble` + `dist:check`。`--build` なし = 組み立てと走査だけで実測 数秒。出力先はリポジトリの外の一時ディレクトリで、`mktemp -d` なので並行のコミットでも衝突しない)。上限(`baseline.json`)を超えて増えると赤で、増えたファイル:行を名指す。**意図した増加は `npm run dist:assemble && npm run dist:check -- --write-baseline --allow-increase` で上限を書き直し、同じコミットに含める**。木の中の型検査・テスト(`--build`。分単位)は手元で回す(CI にも pre-commit にも入れない)
- 鍵の形の検査は配布の木の外にも当てる。`npm run secrets:check` が `git ls-files` の全部に同じ `scanSecrets` を当て、pre-commit(台帳だけのコミット以外)と CI の docs ジョブが回す。鍵でないと確かめた行だけを `SECRET_REPO_EXCEPTIONS`(ファイルと行の字面で閉じる。実在しない行を指すと赤)で外す
