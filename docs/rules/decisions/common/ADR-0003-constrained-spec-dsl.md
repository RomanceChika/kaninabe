# ADR-0003: 仕様DSLの表現力を意図的に制限し、列挙ベース検証を採用する

## Status

accepted (2026-08-06)

---

## Context

### 背景

ドメイン仕様（状態機械・権限・不変条件）を機械検証可能にするにあたり、「どこまで形式的に書けるようにするか」を決める必要がありました。

#### 1. **検証の目的は網羅性であって定理証明ではない**

このフレームワークが解こうとしている問題は「AI が書いた仕様に穴がある（特定の状態 × イベントの扱いが未定義、あるロールの読み取り権限が書き忘れられている）ことを人間が目視で見つけられない」ことです。必要なのは「全マスが埋まっていること」の保証であって、任意の性質の証明ではありません。

#### 2. **表現力を上げると検証が決定不能になる**

DSL に算術・関数呼び出し・集計・時相論理を入れると、充足可能性・矛盾検出が一般には決定不能、少なくとも SMT ソルバー級の外部依存を必要とします。検証器が重く・遅く・壊れやすくなり、「validator がなければ rules はただの紙」という前提が崩れます。

#### 3. **メンテできない検証器は存在しないのと同じ**

小規模な体制で、SMT ソルバーへの式変換層やモデル検査器の面倒を見続けることは現実的ではありません。検証器自身がバグると仕様への信頼が失われます。

#### 4. **不変条件は「書いたのに何も守っていない」が起きやすい**

不変条件を宣言できるようにしても、それが DB 制約・ガード・アプリコードのどこで執行されているかが宣言されていなければ、文書として書かれただけで終わります。

### 前提条件

- 対象は典型的な Web アプリのドメイン（承認フロー、EC 注文、予約と上限、締切・時間駆動、状態条件付き編集）。
- 状態・イベント・ロール・enum の組み合わせは高々数百〜数千のオーダー。
- 検証は CI で毎回回る（ミリ秒〜秒のオーダーで終わる必要がある）。
- テストは AI が仕様から導出する。仕様が「テストの基準」として機能することが前提。

## Decision

### 決定内容

**仕様 DSL にチューリング完全な記述を一切許さず、書ける内容を有限の状態・イベント・ロール・制限された比較式に絞る。その代わり全検証を決定可能にし、列挙ベースの単純な検証器で完結させる。**

具体的には次を採用します。

1. **閉じた集合しか使わせない**
   - フィールドの `type`、access の `scope`、invariant の `formal.type`、`enforced_by.kind` はすべて列挙された値のみ。
   - ガード式は `path op literal` / `path in [...]` / `path contains ref` と `and` / `or` / `not` の組み合わせのみ。**関数呼び出し・算術・ネストした括弧は書けない**。
   - 結果として全変数のドメインが有限または区間になり、充足可能性・矛盾検出が**決定可能**になる（判定器は 2026-09-12 に既製品へ替えた。末尾の追記）。

2. **未定義をエラーにする（全域性）**
   - 全状態 × 全イベントは「遷移として定義」か「理由付きで禁止（`otherwise_forbidden`）」のいずれかに必ず分類される。理由の省略はエラー。
   - 全ロール × 全エンティティの読み取りスコープは明示必須。`scope: none` を書かない限りエラー。
   - 許可リストに載っていないものは拒否（deny by default、PRIN-0009 / PRIN-0010）。

3. **検証器は列挙ベースで実装し、外部ソルバー依存を持たない（v1）**（充足性の判定だけ 2026-09-12 に Z3 へ移した。末尾の追記）
   - V1〜V11 のチェック（スキーマ適合・参照整合・全域性・到達可能性・デッドエンド・final 不変・決定性・ガード充足性・不変条件の執行・ロール接地）を全組み合わせの走査で実装する。
   - `now`（現在時刻）は順序付き不透明値として扱い、区間整合性まで検証する。決定可能性は維持される。

4. **不変条件は v1 では「執行点の宣言 + テスト義務の発行」までとする**
   - `enforced_by` で執行点（`db_constraint` / `trigger` / `guard` / `application`）と ref を宣言させ、検証器は「宣言があること」と「ref の実在」を機械チェックする。
   - そこから**テスト義務**（この執行点に対する統合テストが存在すること）を発行し、trace 検証で未達を検出する。
   - **遷移列探索（「この操作列で INV が破れる」の反例生成）は v2 に送る**。時相的性質（「いつか必ず通知される」）は対象外のままとする。

5. **集計等は DSL の外に置き、純粋関数 + テスト義務で保証する**
   - 「貸出の合計冊数が蔵書の所蔵数を超えない」のような集計制約は DSL で書けないことを設計として明示する。
   - operation 内の**純粋関数に隔離**することを規約で強制し、invariant 側は `enforced_by: application` で宣言する。

### 適用範囲

- `docs/specs/domain/` の 5 doc_type すべて（role_spec / entity_spec / state_spec / access_spec / invariant_spec）
- 検証器（`legacy/spec-tools/verifiers/`）の実装方針
- ドメイン仕様の書き方標準（process/common/specification/standards/domain-spec-writing.md）

## Consequences

### Positive（メリット）

- **網羅の根拠が「証明」になる**。状態・権限・フィールド制約の層は有限列挙で検証されるため、「テストすべきこと」は検証済みマトリクスの機械的な読み上げとして導出でき、網羅率 100% が定義から従う。
  - 定義された遷移 1 つ → 成功テスト 1 件
  - 禁止マス 1 つ → 拒否テスト 1 件
  - ガード 1 つ → 真偽の境界 2 件
  - 権限 1 行 → 許可ロール・非許可ロール各 1 件
- **default-deny が論理的に閉じる**。「許可を列挙し残りは自動禁止」が成立する条件は (a) 空間が有限、(b) 補集合が一意、(c) 許可側に曖昧さがないこと。(c) は V8（決定性）が保証し、唯一の落とし穴である「許可し忘れて詰む」は V5 / V6（到達可能性・デッドエンド）が拾う。**採用案 + V5 / V6 / V8 のセットで論理的に閉じる**。
- **検証器がメンテ可能**。外部依存ゼロ、全列挙、数百〜数千の組み合わせをミリ秒で処理。検証器自体を単純に保てるので信頼できる。
- **人間の作業が減る**。頭の中でパターンを列挙する作業が機械に移る。全域性を埋める過程で、運用上ありがちな遷移（差し戻しなど）が自然に洗い出される副次効果も確認された。
- **不安の所在が 1 箇所に限定される**。保証レイヤーは次のとおりで、証明がないのは 2 行目の「中身の質」だけになる。

  | 層 | 保証のされ方 | 網羅の根拠 |
  |---|---|---|
  | 状態・権限・フィールド制約 | 仕様検証 + 機械導出テスト | **証明**（有限列挙） |
  | 集計等のビジネスルール | 純粋関数隔離 + テスト義務 + AI 作成テスト | 義務の存在は機械、中身の質はテスト設計 |
  | DB 制約・RLS・クエリ | 統合テスト（実 DB） + pgTAP | 義務発行 + 主要パス |
  | 意図そのもの | 人間の仕様レビュー | 人間 |

### Negative（デメリット・トレードオフ）

- **書けないものがある**。集計・算術・階層状態機械・並行状態機械・時相的性質は DSL では表現できない。これらは通常のコード + テストの領域に落ちる。
- **DSL 外に落ちた制約の保証が弱い**。テスト義務の発行までは機械化できるが、境界値などケースの中身の質はテスト設計に依存する（従来のソフトウェア開発と同じ信頼度）。
- **表現できない要求が来たときに DSL 側の拡張判断が必要になる**。「書けない」を毎回どちらの領域で扱うか判断するコストが残る。
- **不変条件の破れを事前に見つけられない**（v1）。「この操作列で INV が破れる」は実行時・テスト時にしか分からない。

### Neutral（その他の影響）

- 実運用のドメイン形状に対するストレステストで、DSL の拡張が 4 点必要と判明し採用済み（複数直交状態フィールド / cardinality の複合キー / invariant の `where` 句での関連状態参照 / `now` の全イベント開放）。いずれも決定可能性は維持している。
- 「DSL に入れるべき制約とテストでいい制約の線引き」は、実際のドメイン記述（item / loan / hold）で DSL 外に漏れる制約のリストを見てから再評価する。
- 台帳（ポイント残高・ローリング期限）は v2 で `ledger` 専用 doc_type を検討する。

## Alternatives Considered

### Option 1: 形式手法をフル装備する（TLA+ / Alloy / SMT ソルバー）

- **Pros**:
  - 任意の性質を検証できる。不変条件の破れを操作列レベルで反例つきで発見できる
  - 時相的性質（「いつか必ず通知される」）も扱える
- **Cons**:
  - 検証が決定不能または非常に高コストになり、CI に乗らない
  - 仕様 → モデル記述への変換層が必要で、その変換自体が信頼できるかという問題が発生する
  - 小規模開発の体制でメンテできない。学習コストも高い
  - 解こうとしている問題（仕様の穴の検出）に対して過剰
- **Why rejected**: 目的に対して過剰であり、メンテ不能。「メンテできない検証器は存在しないのと同じ」。

### Option 2: 表現力を制限せず、検証を人間レビューに委ねる

- **Pros**:
  - 何でも書ける。表現の壁にぶつからない
  - DSL の設計・実装コストがゼロ
- **Cons**:
  - まさに解こうとしている問題（人間が目視で穴を見つけられない）が解決しない
  - AI が書いた仕様の抜けを検出する手段がなくなる
  - PRIN-0006（判定可能性）が人間の努力目標のままになる
- **Why rejected**: フレームワークの中核の主張を放棄することになる。

### Option 3: 全マスを手書きさせる（完全明示の遷移表）

- **Pros**:
  - 全状態 × 全イベントの扱いが 1 マスずつ明示され、最も正確
  - 状態ごとに固有の禁止理由を書ける
- **Cons**:
  - 状態数 × イベント数のマスをすべて手で書くのは冗長で、腐りやすい
  - 状態を 1 つ増やすたびに全イベント分の追記が必要になり、更新漏れが常態化する
- **Why rejected**: 「イベントごとに 1 つの包括的な禁止理由（`otherwise_forbidden`）」を最低ラインとし、**マトリクス（state × event マトリクス）を生成物として人間に見せる**方式を採用。暗黙の禁止も目視でき、冗長さは生成側が吸収する。状態ごとに理由を分けたい場合だけ明示的な `forbidden:` ブロックを書けるようにして、正確さの逃げ道も残した。

### Option 4: 不変条件を v1 から遷移列探索まで検証する

- **Pros**:
  - 「この操作列で INV が破れる」を事前に発見できる
  - 不変条件の保証が実装から独立する
- **Cons**:
  - 状態空間の探索が必要になり、列挙ベースの単純な実装から外れる
  - 不変条件と遷移の意味論を正確に接続する設計が重く、v1 の立ち上げを遅らせる
- **Why rejected**: v1 は「執行点の宣言 + テスト義務の発行」で止め、v2 の候補として明示。まず 1 本のループ（仕様 → 検証 → 実装 → 突合）を通すことを優先した。

## Notes

### 汎用性のストレステスト結果

典型的な Web アプリのドメイン形状に対して、この表現力で足りるかを確認した結果。

| ドメイン形状 | DSL での表現 | 結果 |
|---|---|---|
| 承認フロー（申請→承認/却下/差し戻し） | state_spec そのまま | ✓ |
| EC 注文（決済連携） | 決済確定 = Webhook 発の `by: [system]` イベント | ✓ |
| 予約と上限 | cardinality 不変条件 + 親フィールド参照上限（例: `max: item.hold_limit`） | ✓ |
| 締切・時間駆動 | Cron 発の `by: [system]` イベント + `now` 予約語 | ✓ |
| 下書き中だけ編集可 | access_spec の `writes:`（状態条件付きフィールド更新権限） | ✓ |
| 集計を含む制約（合計時間上限等） | **意図的に DSL 外** — operation のコード + テスト + `enforced_by: application` 宣言 | 線引きとして明示 |
| 階層状態・並行状態機械 | **v1 では非対応**（フラットな状態機械のみ）。直交軸は複数状態フィールドで合成 | 必要になったら ADR を書いて拡張 |

実在サービス（イベント予約・時間駆動進行・ビデオ通話・決済・ポイント経済）との突き合わせでも、上記の拡張 4 点で表現可能であることを確認した。同時に、そのサービスのドキュメント間に実在した矛盾（キャンセル境界・還元単価・判定タイミング）と仕様起因のバグ（セッション URL 紐付け・時間窓バイパス・チャット混線）が、いずれも本フレームワークの防御対象（SoT + 鮮度検証 + 時間条件付き RLS + スコープの仕様明示）と一致していた。

### 「これが書けない」はバグではなく設計

DSL の表現力の壁にぶつかったときの判断順序:

1. 既存の構文の組み合わせで表現できないか（例: 時間駆動 → `by: [system]` イベント + Cron の `emits`）
2. 表現できない場合、それは DSL 外（純粋関数 + テスト義務）で扱うべきものか
3. 典型的な Web アプリの形状として頻出し、かつ決定可能性を壊さない拡張なら、ADR を書いて DSL を拡張する

**追記(2026-09-12。束 ⑳-5c)**: Decision 3「検証器は列挙ベースで実装し、外部ソルバー依存を持たない(v1)」のうち、**充足性の判定器だけ**を既製品に替えた —— `z3-solver`(WASM。docs の devDependency。exact version で pin)である。ユーザーの決定(2026-09-11。BACKLOG「形式手法の導入」(b))「推論・探索の道具は既製品を採り、写像だけを自作する」に従う。

変えていないことのほうが重要である。

- **DSL の表現力は 1 ミリも増えていない**(Decision 1・2 はそのまま)。算術・関数呼び出し・集計・時相論理は今も書けない。変えたのは「誰が判定するか」だけである。
- 仕組み側が持つのは**写像だけ**である(`lib/guard/smt.ts` の 1 ファイル。ガード式 + 変数ドメイン → SMT-LIB)。Context 3 が心配した「SMT ソルバーへの式変換層やモデル検査器の面倒」のうち、**モデル検査器の側は持たない**。
- **自作の列挙器は消さない**(`lib/guard/satisfiability.ts`)。判定が非同期になったので、同期で呼べる場所(V8 の共存判定・UX・画面の入場判定・SQL の畳み込み)は今も列挙器を使う —— そこでは「先読み」として働き、V9 / V10 の判定の正ではない。2 つが食い違わないことは fast-check の差分テストが実測する。
- 得たものは、列挙器の 3 つの上限(finite の直積・自由な原子の数・その積)で `unknown` になっていた式に**答えが出る**ことである。残る `unknown` は Z3 のタイムアウトだけであり、そのときは V9 が warning で報告する。
