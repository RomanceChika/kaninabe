# 拡張候補の台帳

`npm run verify` の警告を**区分に分けて管理する**ための台帳である(拡張候補と未分類。2026-10-20 に受け入れた危険を足した)。ユーザーの言葉(2026-10-03 午後):
「警告の中にも管理の仕方を分けた方がいい。仕組みを拡張すれば吸収すべき問題か、仕組みは変えるべきでないが警告になる例外か。同じ扱いだと後々ややこしい。拡張するかもしれないリストを作り、当てはめと、該当しない場合はその他で理由」。

| 区分 | 何か | 管理の場所 |
|---|---|---|
| **拡張候補** | 仕組みを拡張すれば吸収すべき問題。**仕組みの宿題**であって、仕様を書く人が読まなくてよい | この台帳(上の YAML。1 行 = 1 候補) |
| **未分類** | どの拡張候補にも当たらない警告 | 台帳に載せるか、検査ごとの既存の受け入れの形を作るかを判断する(review-queue へ) |
| **受け入れた危険** | 仕様が**理由つきで「外す」と宣言した**結果の警告(いまは多要素認証の `mfa: { exempt: 理由 }` の H6 だけ) | 理由は宣言の側(この台帳ではない)。警告の `acceptance` が宣言の位置と理由を指し、W5 が接地を見る |

**「受け入れた危険」の区分を作った(2026-10-20)。** 以前は「その他(理由)」の口を作らない、と決めていた(仕組みは変えるべきでない例外として警告になるものが 0 件だったため)。ユーザーの決定(2026-10-20: 多要素認証は「フレームワーク上は入れる前提にしたいけども、入れなくてもいいという警告付きオプションが付けられるようにして、趣味用では逃れられるようにしておこう」)で方針が変わり、**外せるが毎回警告で名指す**例外が 1 件できたので、3 つ目の区分を足した。形は当時の方針どおり**検査ごとの既存の受け入れの形に揃える** —— 理由は宣言の側(`mfa.exempt`)が持ち、この台帳には**理由を書く欄を持たない**(未知のキーは W5 が落とす)。1 本の汎用の理由欄(免除リスト)にはしない。

- 区分は警告の `acceptance`(宣言の位置と理由)で決まり、台帳の候補より先に判定する。受け入れた危険は候補に当たらない。
- `npm run verify` は警告に `(受け入れた危険 — 理由)` を付け、末尾の内訳に `受け入れた危険 A / ` を足す(0 件なら出さない)。**`--fail-on-unclassified` はこれでは落ちない**(未分類ではない)。
- **検査が勝手に付けて門を抜けないよう、W5 が接地を見る。** 組み立ての根が読めた仕様から受け入れの宣言を集めて W5 に渡し、警告の `acceptance` がそのどれかと位置も理由も一致しなければ error、理由が空なら error。
- 台帳が無い・読めない構成では、受け入れた危険も未分類に倒す(W5 が回らないので、受け入れを確かめられない)。
- ハンドブックに受け入れた危険の一覧を出すのは後続の束である(いまは verify の出力まで)。

| キー | 中身 |
|---|---|
| `id` | `X-` 接頭辞のケバブケース。台帳の中で一意 |
| `statement` | 何が書けない・組めないか。製品の語を書かない(仕組みの言葉で) |
| `rules` | この候補に当たる検査の ID。**その検査の警告は、この候補の宿題として数える**(`scope` があれば絞った分だけ)。候補どうしで当たる範囲が重ならない |
| `scope` | (任意)当たる警告を、`rules` の検査の中でさらに絞る鍵。値域は閉じた語 — `framework_tables`(仕組みが所有する表の警告のうち、**製品がその表を持ち場とする関数〔data_table の `functions[]`〕を 1 つも宣言していないもの**だけ。T2。関数を宣言していれば製品が `lookup` に索引の要求元を書けるので、仕組みの宿題ではなく未分類に落ちる)・`trigger_formal_inexpressible`(執行点がトリガで、不変条件の形式定義が DSL の写像の外 = 数の上限・状態依存・形式定義なしの警告だけ。T16。T8・T11 と同じ理由の軸で、形式定義が書けるのに宣言していない = 製品が直せる分は含まない)。`trigger_cross_aggregate`(執行点がトリガで、形式定義が `check` なのに式が自集約以外の集約の欄を見る = 別の集約の欄との一致の警告だけ。T16)・`compute_child_set`(`computes` の材料に子の行の集合を宣言して、計画に積めない警告だけ。A19。材料の宣言が 1 つも無い警告は含まない)・`trigger_condition_inexpressible`(トリガが名指す不変条件が形式定義を持たないために、宣言の条件をトリガ関数の中身と照らせない警告だけ。T17。名指しの誤り・読めない式などは含まない)。**絞りの鍵が存在する検査(T2・T16・T17・A19)を `rules` に挙げる候補は `scope` が必須**(W5 が error にする。鍵なしだと検査 ID の全体に当たり、製品の側で直せる警告まで宿題に吸い込むため)。鍵の無い検査(T8・T11・T15 など)は書かなければ検査 ID の全体に当たる。**鍵ごとに絞れる検査が決まっていて**、他の検査に付けると W5 が error にする |

## 区分の決め方と検査(W5)

- 区分は**検査 ID + 任意の `scope`** で決まる。`scope` を書かない候補は、検査 ID の全体(その検査の別の理由の警告も)に当たる。**検査の警告に製品の側で直せるものが混ざる**(T2 の「引かれない索引」は仕組みの表にも製品の表にも出る)なら、`scope` で候補の言い分に当たる分だけに絞る。絞らずに当てると、仕様を書く人が消すべき警告が「読まなくてよい側」へ落ちる。
- `npm run verify` は警告 1 件ごとに `(受け入れた危険 — 理由)` か `(拡張候補 X-…)` か `(未分類)` を付け、末尾で `警告 N 件(拡張候補 M / 未分類 K)` と数える(受け入れた危険があれば `受け入れた危険 A / ` を前に足す)。区分は警告の性質を変えない(警告のまま数える)。
- W5 が見るのは 6 つ。受け入れた危険の警告が、読めた仕様の受け入れの宣言(位置と理由)に接地していなければ・理由が空なら **error** / `done` の候補に当たる警告が残っていれば **error** / `rules` に全検査の表(`lib/compose/all-checks.ts`)に無い ID があれば **error**(検査を消せば表から消えるので、同じ綴りが別の文字列に残っていても通らない) / `scope` を、その鍵で絞れない検査に付けていれば **error** / **絞りの鍵が存在する検査を `rules` に挙げる候補が `scope` を持たなければ error**(鍵は `lib/extension/scope.ts` の `SCOPES` の `verifiers` から導く) / 候補どうしの当たる範囲が重なれば **error**(同じ検査でも `scope` が別なら重ならない)。`scope` の値が値域に無いのはスキーマの error。
- **「0 件になったから done にしてよい」とは言わない。** 候補は仕組み全体の宿題で、1 つの製品の検証で 0 件でも終わったとは言えない(出る警告は製品ごとに違う)。状態は**人がこの台帳で管理する**。W5 が見るのは「done と言いながら警告が残っている」嘘だけである。
- 起票の手順は [dsl-extension-triage.md](../../docs/rules/process/common/specification/playbooks/dsl-extension-triage.md)(**表現力を買う前に、形を変える**)。拡張が済んだら `status` を `done` にして、当たる警告が消えていることを W5 に確かめさせる。
- 書き方の正と検査の位置づけは [enforcement-matrix.md](../../docs/rules/process/backend/system/standards/conventions/enforcement/enforcement-matrix.md)(W5)。
