# PRIN-0003 — テスト可能性を保つ

設計の合格条件を「動くか」ではなく「**検証可能か**」に置く原則。

## 原則 {#statement}

- 設計の前提条件は**検証可能性**である。動くことは必要条件であって十分条件ではない。
- 依存は**差し替え可能**に保つ。
- 境界(モジュール・コンポーネント・入出力)は**明確**に保つ。
- 手動確認への依存を排し、自動で検証できる形を維持する。

## 背景 {#rationale}

テスト可能な設計は 2 つの働きをする。変更したときの安全網であることと、**仕様と実装を照合する手段**であることである。

後者が [PRIN-0001](./PRIN-0001-spec-as-truth.md) の前提になる。実装が仕様を満たしているかを検証する手段が無ければ、「仕様が正」という宣言は運用できない。乖離を検出する方法が無いのだから、乖離が無いことにするしかなくなる。

さらに、実装と検証を AI が行うという前提がここでも効く。AI がユニット・統合・E2E を回し、結果を仕様と突き合わせられるための条件が、**依存の差し替え可能性**と**境界の明確さ**である。この 2 つが無い設計は、AI にとって「実行はできるが何を確かめたのか言えない」設計になる。

つまりこの原則は、設計の合格基準を「動けばよい」から「検証可能である」へ一段引き上げるものである。

## 影響 {#implications}

- **依存**: 外部リソース・他モジュール・外部サービスへの依存は、テスト時に差し替えられるようにする。手段はスタック次第である(インターフェース経由・モック・スタブなど)。依存の**向き**をどう定めるかは [architecture](../../architecture/README.md) の担当であり、この原則はそこに踏み込まない。
- **境界**: 境界ごとに「ここで何を検証するか」を決められる粒度で切る。ユニット・統合・E2E のどこが何を担当するかという割り当ては、この原則の**適用**として backend / frontend それぞれの process・規約側に置く。
- **仕様との照合**: 仕様に書いた振る舞いと制約は、可能な範囲でテストにする。**検証できないと分かったら、仕様の記述方法かテスト戦略のどちらかを直す。** 検証不能なまま放置することは認めない。

## 例外 {#exceptions}

- 調査・PoC の一時コードは緩和してよい。本番・共有対象へ昇格させる時点で条件を満たす。
- 実装上の制約で検証が極端に困難な場合(外部システムへの初回接続、認証フローなど)は例外扱いにできる。ただし条件として、**decision に「対象範囲」と「代替手段(手順・手動チェックリスト)」の両方を明示する**。範囲を書かない免除も、代わりの確かめ方を書かない免除も認めない。
