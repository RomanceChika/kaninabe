# 依存の脆弱性を直す期限と更新の方針

使っている第三者の部品に脆弱性が見つかったとき、**いつまでに・どう直し・出荷をどう決めるか**を決める文書である。検出は `npm run deps:check`(手元の pre-commit。夜間の出荷の前は同じ検査を止める側に倒した `npm run deps:check:gate` — 公開から 7 日未満の版と通信の失敗の未実施も赤 — が回り、pre-commit を通らない変更も出荷の前に通る。夜間の CI の `npm audit` は二重の網。夜間の audit は main が動かない日もコミットの一致では飛ばさず、最後に成功した監査から 7 日(`STALE_DAYS`)を超えた夜に回る — 毎晩の検出ではなく、最長約 8 日の鮮度の保証である。印の時刻は監査の終わりで、判定は次の夜の始まりに数えるので、7 日目の夜は印がまだ 7 日以内で飛び、8 日目の夜に回る。取り込みの台本の段 deps は、最後に全部を確かめて通った `deps:check` の印が 7 日以内で、印が確かめた lockfile の中身の sha256 が今の lockfile の全部と同じときだけ回さない)、直さずに受け入れる指摘は [dependency-accepted.md](./dependency-accepted.md) が持つ。

## 目的・スコープ

- **目的:** 脆弱な部品が「気づいたら放置」にならないよう、重大度ごとの直す期限と出荷の判断を先に決める(ASVS V15.1.1)。使う部品の目録(SBOM)をいつ作って保つかも決める(ASVS V15.1.2)。
- **スコープ:** その製品の全 lockfile(ルート・ワークスペース外の道具・docs など)の、出荷物に載る部品と開発用の部品。期限は**検知した日から**数える。

## ルール

### 重大度ごとの期限

| 重大度 | 期限(検知から) | 一時の手当ての例 | push の判断 |
|---|---|---|---|
| critical(悪用が公開されていて到達できる) | 24 時間以内に手当て、72 時間以内に修正 | 該当の口を閉じる・機能を止める・WAF のルール | **CI の予算に関わらず push を提案する**(理由を添えて、ユーザーに先に聞く) |
| high | 7 日以内 | 同上(到達できるなら) | 到達できるなら push を提案する(先に聞く)。到達できなければ次の区切り |
| moderate | 30 日以内 | なし | 次の区切りの push に載せる |
| low | 次の定期の更新(90 日を超えない) | なし | 同上 |

重大度が分からない指摘は **high と同じに扱う**(出どころが言わないものを長く置かない)。

### 直す手順

1. **影響の見極め** — その部品をどこで使うか・脆弱な関数に届くか・本番の構成で露出するか。届かないと分かったら、直さずに[受け入れ表](./dependency-accepted.md)へ理由つきで残す。
2. **一時の手当て** — 上の表の例。修正が間に合わない間の露出を減らす。
3. **修正** — 版を上げる・`overrides`・代替の部品。手元の全検査を通す。
4. **出荷** — 上の表の push の判断に従う。**push は毎回、ユーザーに理由を添えて先に聞く**(勝手に push しない)。
5. **記録** — 何が・いつ検知され・何をしたか。受け入れたなら理由と見直しの期限を表に残す。

### 受け入れ表の期限

**lockfile の取得元と固定も `deps:check` が赤にする(受け入れ表では受け入れられない)。** `node_modules/` の下の全エントリは、`resolved` が公式の登録簿(`https://registry.npmjs.org/`)で、`integrity` が単一の sha512 でなければならない(workspace のリンク・`file:` の手元のパス・親に同梱された部品だけ除く)。lockfile は JSON として読むので、字面の揺れで素通りしない。通信できるときは、lockfile の `integrity` を登録簿の目録の `dist.integrity` とも突き合わせる(食い違えば赤。通信できなければ未実施)。

受け入れ表の `見直しの期限` は、**今日から数えて重大度の期限を超えてはならない**(critical は 3 日・high は 7 日・moderate は 30 日・low は 90 日。重大度が不明なものは high と同じ)。`deps:check` がこれを見て、超えた行は赤にする。期限は更新できるが、そのたびに理由を読み直す。期限切れの行も赤になる。

### 部品の目録(SBOM)

- 出荷のたびに `npm run deps:check -- --sbom` で CycloneDX の SBOM(出荷物に載る部品だけ)を lockfile ごとに `tmp/deps-check/sbom-*.json` へ作る。
- 作った SBOM は**その出荷の記録に添えて保つ**(`tmp/` は追跡しないので、出荷の記録の置き場へ写す)。新しい出荷で作り直し、古い版は出荷の記録とともに残る。
- 部品の取得元は登録簿(registry.npmjs.org)だけで、lockfile の `resolved` と `integrity` を `dist:check` が見る。

## 検証方法

```bash
npm run deps:check            # 検知と期限の確認。赤が 0 件なら通過
npm run deps:check -- --sbom  # 続けて SBOM を作る(出荷のたび)
npm run deps:check:gate       # 出荷の関門(夜間の deploy の前。依存を入れずに node で直に回る)
npm run test:spec-tools       # 期限の上限と SBOM の書き出しは legacy/spec-tools/__tests__/unit/deps/ の表駆動テスト
```

合格条件は、赤が 0 件であること(期限内の受け入れは赤にならない)と、出荷のたびに SBOM が lockfile の本数だけ出ること。期限の遵守そのもの(検知から本当に期限内に直したか)は機械で確かめられないので、出荷の記録のレビューで見る。
