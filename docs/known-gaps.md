# Known limitations (0.x)

kaninabe is at 0.x and not stable. The tree was carved from a larger private repository, so some things are missing or rough. Each item is meant to be closed by its own change.

1. **The demo product has no implementation tree.** `product.md` points at `app/`, but the repository carries only the specs and the generated `supabase/migrations`. Root `verify` is green; `generate:check` is not run at the root. Generator behaviour is checked by `test:spec-tools` on the samples.
2. **No sample covers some real-world checks.** A product-bound test of a real `config.toml` against an OAuth auth spec was removed; no sample has an auth flow with a callback and a `supabase/config.toml`, so that end-to-end check is untested here. Two scans (`session-alive`, `session-lifecycle`) run with lower thresholds until a sample covers them.
3. **Formal models (`formal/`, `check:formal`) are not included yet.** Their `SOURCE` pins name files that do not exist here and must be re-pointed first.
4. **Tests that fail only when run as root** (for example a test that makes a directory unreadable) pass as a normal user.
5. **Timing tests.** `markdown.test.ts` bounds CPU time in absolute milliseconds (30 s). Replace it with a machine-independent check: the CPU time ratio when the input length doubles.
6. **Vocabulary in tests and fixtures.** `framework/` and the rules under `docs/rules/` are neutral. The code, tests and fixtures under `legacy/spec-tools` still use the vocabulary of the project they came from in many files, including text rendered into the generated handbook examples. They are being replaced by the neutral sample domain.
7. **Guarantee ids.** `TC-GUAR-` is the namespace for a product's guarantee rows. Two generators emit fixed ids such as `TC-GUAR-HEADERS-001` that a product's rows must use, and no sample declares them yet. Add a sample row for each kind, or derive the ids from the product catalog.
8. **Dangling references and process residue.** Docs and comments still mention working files that are not in this repository (a notes file, a backlog, a review queue, a handoff folder, a nightly workflow) and numbered review rounds. `vitest.heavy.config.ts` lists test paths that do not exist.
9. **CI** lacks "generate --check on samples" and tests against a Postgres service, and the actions are pinned by tag, not by commit SHA.
10. **Docs describe machinery that is absent here** (an integration-test row in CLAUDE.md, enforcement-matrix figures, a pre-commit that "runs verify"). The pre-commit hook only scans for secrets.
11. **Runtime coverage exclusions.** The 100% threshold on `framework/runtime/src/**` was met partly by generated tests of the original product. 22 runtime files that only those tests reached are listed by name in the coverage `exclude` of `vitest.config.mts` instead of lowering the threshold. Close it by generating and running unit tests for a sample product, then delete the list.
12. **Citations of things that do not exist here.** Docs and comments cite historical migrations, `__tests__/dev-repo/...`, `lib/fs-io.ts`, `@kaninabe/runtime/rpc`, working files, round ids such as "束" and "点検 N 回目", and `NOTES.md` / `BACKLOG` pointers. Each is to be removed or reworded as history without a path.
13. **The push-before gate depends on the hook being called.** `scripts/push-gate.sh` and `.githooks/pre-push` work only where `core.hooksPath` is set (`scripts/setup-dev-env.sh` sets it); an environment without it, `--no-verify` and a push of a ref the hook does not see are not stopped. The rule is to check at the start of work that the hook path is set, and never to skip the hook. Nothing checks this. What a push is scanned over is the set of commits that the destination does not advertise on its branches (asked at push time with `git ls-remote --heads`; `scripts/push-range.sh` prints the set); commits it holds only under other refs (tags, pull request refs, hidden refs) are scanned again, which is only more work, and a destination that cannot be asked, or a history that cannot be read to the end, stops the push. The URL that is asked is the URL the push really goes to: `git ls-remote` applies `url.<x>.insteadOf` to a URL again, so `push-range.sh` compares the URL it was given with `git ls-remote --get-url` in the same configuration, and when they differ it subtracts nothing (every commit is scanned) rather than use another repository's answer. Both the hook and the reviewer's by-name call resolve the URL in the caller's configuration, the way push does. The repository is the caller's (`GIT_DIR`, `--git-dir`/`--work-tree`), found once in the caller's environment and handed to the clean environment; a bare repository, no work tree, or `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` stop the scripts with a reason. `push.recurseSubmodules` pushes a submodule with the hook of the submodule's own repository, which this repository's hook does not cover. A remote with several push URLs runs the hook once per URL, and each URL is asked about itself.
14. **The content review record can be written by the author.** `kaninabe.contentReviewed` stops a push whose commit has no record of having been read for publication, but anyone can write the sha without reading. That is a rule, not a check. What the record is bound to is checked: it is `<head sha> <range id>`, where the range id is a sha256 over the destination URL actually contacted, the head sha and the exact ordered list of commits to scan (`scripts/push-range.sh` prints it, with the command that records it). The hook recomputes it at push time and refuses when it differs (the destination's branch was deleted or moved, another URL is pushed to, a commit was added); the gate is given the id of the commit list and stops if it would scan another list. A record in the old form (a commit id only) is refused, and so is a record or a computed range id that is not 64 lowercase hex digits (one shared check). A remote with several push URLs has one range id per URL, so a record fits one of them. The hook allows pushes to `refs/heads/*` only (a branch deletion passes), and compares the pushed object itself, not what it points to, with HEAD. A tag push, a deletion included, is refused (tags are created and deleted only by the tag workflow); so is any push to `refs/notes/*`, `refs/remotes/*`, a pull request ref and the like, and an annotated tag object pushed by id to a branch. Reason: the message of a tag, a note and any other non-branch object is not scanned, and the object reaches the destination's object store even when the ref update is refused afterwards.
15. **A branch with no pull request yet gets only the general scan in CI.** Before a pull request exists, the word list is applied only by the pre-push hook on the developer's machine. Until the CI rework, the older scan steps in `ci.yml` still read the word list on pull request runs (the new gate step does not); they are removed in a later change, after the new step has been seen running on the main branch. The word-list step of the gate in `ci.yml` is guarded by `if: github.event_name == 'push' && github.ref == 'refs/heads/dev'`, which only stops it from running by mistake; **it is not a boundary**: a branch or a pull request from this repository can change the workflow file and still read the secret. The boundary (the word list readable only by reviewed definitions that run from the base branch, for example an environment secret restricted to the main branch) comes with the CI rework and needs a repository setting that only the owner can make; until then the word list is readable by any workflow run of this repository. The public output of the old steps is limited to counts (`SCAN_QUIET` for the word scan; `scripts/gitleaks-public.sh` for the key scans, whose own error messages can name paths). The old key-scan steps in `ci.yml` now run through `scripts/gitleaks-public.sh`, which uses the gate's fixed config and neutralising flags (no in-tree config, ignore file or inline allow) and prints counts only (never a rule name, path or other text derived from the tool's output; to see details, run gitleaks yourself on a copy). Its `git` scan is the gate's: `gitleaks git` over the neutral repository, one commit at a time, with each commit checked (16(h)). A result it cannot read is reported as such with exit 2, never as zero findings. What stays true: the pre-commit hook still honours a gitleaks config, an ignore file and inline `gitleaks:allow` comments of the scanned tree, and the old `dir` step still uses the tool's default allowlist (16(a)). In the gate, public output is counts only too, and an unreadable gitleaks or actionlint result stops the gate (exit 2).
16. **Parts of the gate in the design that are not built yet.** (a) Exclusions are not listed file by file with a reason (the history scan, the scan of the tree of `HEAD` and the old `dir` step all still skip them): the scan skips lock files by a name glob, and the gate's key scan (`scripts/gitleaks-gate.toml`, which extends the tool's default rules) also skips the file kinds on gitleaks' built-in allowlist, so a key in a text file of such a kind (a `.svg`, a file named `gitleaks.toml`) is not found. The scanner change replaces both with exclusions named file by file, each with a reason. (b) Mail-address strings are not limited to reserved example domains and the noreply form: the allow pattern in `scripts/scan-rules.sh` is wider. The entries for the noreply domain and for the example domains end the address (so extra text after them on the same address is a finding), but the other entries are prefix-style and accept anything after them on the same address: `@(types|kaninabe|supabase|vitest|next|axiomhq)[./]`, `@[0-9]`, `@127.0.0.1`, `@registry.npmjs.org`, `@api.axiom.co`, `@auth.external`, `^evil` and `^git@github.com`, and the file-extension entry `\.(ts|tsx|js|mjs|json|md|png|svg)$`, which treats an address that ends like a file name as a file name (and one of those endings, `.md`, is also a real top-level domain, so an address on it is accepted); they are for the scanner change. (c) The host rule inside test and fixture trees does not exist. (d) The check of workflow permissions and secret shapes (the checks of "何から守るか") does not exist: the gate checks only that workflow files parse and pass actionlint. (e) Files the scans cannot read are skipped, not red. Measured with gitleaks 8.30.0 (the key scan) and `git grep -I` (the word, mail and path scans): files with NUL bytes (binary), archives (not opened: `--max-archive-depth` is 0), text in UTF-16 and other encodings that are not UTF-8, symbolic links (the link is not followed), and files under paths on gitleaks' built-in allowlist (for example a `node_modules` directory) are not scanned for keys; the other scans skip every file git calls binary. Files that a `filter=lfs` attribute makes LFS-managed: with a usual LFS setup, `git add` replaces the content with a pointer, the content stays in the local LFS store, and only the pointer is committed, so the scans see the pointer. Neither the gate nor the hook sends LFS objects, and the LFS hook of git-lfs is not run while `core.hooksPath` is set; a manual `git lfs push`, or an LFS hook in an environment without `core.hooksPath`, would send content that no scan has read. Files of any size are scanned (no size limit is set), and values encoded up to the tool's default decode depth (5) are decoded. A `.gitignore` is not honoured by gitleaks, and `.gitattributes` does not change what it reads (checked, with tests, for `filter=lfs` in the same commit, in a later commit and in a nested file). (f) The scans need git 2.40 or newer (they read no attributes from the tree, so that `.gitattributes` cannot make files unreadable to them); with an older git they stop instead of scanning less. (g) Workflow files are checked at the tip (`HEAD`) only, not at each intermediate commit. (h) State inside the repository (`.git/config`, `.git/info/attributes`, `.git/info/grafts`, `refs/replace/*`) does not change what the scans read: the history is read from a neutral repository that borrows only the objects (no config, no `info/`, no refs), with the range given as commit ids, and `GIT_NO_REPLACE_OBJECTS=1` is set in every clean environment. What still runs against the real repository is limited to finding the repository (`rev-parse --absolute-git-dir`, `--show-toplevel`, `--git-path objects`), resolving `HEAD` and a `--base` name to a commit id (replace refs ignored), the shallow check, and `remote get-url` / `ls-remote` (which are about the destination, in the caller's configuration, as push is). The neutral repository reaches the objects through the real object directory and whatever `objects/info/alternates` chain it holds; objects are addressed by their content, so a redirected alternate can only make an object missing (the scans then stop), not different. The commit-graph and the multi-pack-index of the borrowed object directory are not content-addressed (git reads parent links from a commit-graph), so the neutral repository turns both off (`core.commitGraph=false`, `core.multiPackIndex=false`, in its own config, which also applies to gitleaks' git); a test forges a commit-graph that cuts the tip's parent. A SHA-256 repository is not supported: the neutral repository is SHA-1, so the scans stop; a shallow clone stops them too. Both are one shared check (`neutral_git_setup`) used by the gate, push-range, scan-public and the old-step wrapper. History is read by `gitleaks git` over the neutral repository, **one commit at a time** (`--log-opts="-1 -m <id>"`, ids only, never names), in the gate and in the `git` mode of `gitleaks-public.sh` (one shared implementation). Each commit is checked on its own: `git diff-tree --root -m -M --numstat -z` (status checked, any failure is exit 2) says whether the commit adds at least one line of text (a number above 0; a binary file, a deletion, a mode change, an empty file and a pure rename add none), and the "N commits scanned" line in gitleaks' info log (kept in a private temporary file, never printed) must be a number and must be 1 when text was added, and 0 or 1 when none was; anything else is exit 2. Findings are summed over the commits. Measured with gitleaks 8.30.0 for text add, line replace, lines removed from an existing file, file deletion, symlink add, blank-line add, empty commit, mode only, binary add, 0-byte file, rename only, rename with edit, clean merge, merge with a resolution, octopus merge, submodule change and a root commit: the rule "text added is 1 scanned" holds in every case. Because gitleaks reads the history itself, the history scan uses the path again: gitleaks' default path allowlist applies (the situation of 16(a); a key added under `node_modules` or in a `.svg` is not found), and rules that match by path and regex work in history. **Chunks:** `gitleaks stdin` and `gitleaks dir` cut large input into chunks and can lose a secret that straddles a chunk boundary (measured: about 4.8 MB of short lines with 5000 keys, 4993 found by `stdin`; about 50 MB with 500 keys, 497 by `stdin` and by `dir`; `git` found all). The scan of the tree of `HEAD` (`gitleaks dir`) reads large input that way and can miss a secret that straddles a boundary; this is covered only when the content is inside the scanned commit range, because the history scan (`gitleaks git`, which does not chunk) reads it. The text of a commit is the whole raw commit object read from the neutral repository (`git cat-file commit`: tree, parents, author and committer lines, every other header such as `mergetag`, `gpgsig` and any extra header, and the whole message), with each NUL byte turned into a line break (the formats of `git log` stop at a NUL, so text after it would otherwise be unread); the status of both steps is checked and one function (`neutral_commit_text`) makes it for the gate and for `scan-public.sh`. It is not re-encoded: a commit with an `encoding` header carries non-UTF-8 bytes, which are scanned as they are (gitleaks reads bytes; the word list runs once in the locale of the scan and once byte for byte). A word written in an encoding that is not UTF-8 does not match a pattern in UTF-8: the limit of (e) applies to commit text too. The key scan of the text (`gitleaks stdin`) is bounded instead: texts are put together in batches that stay at or under 64 KiB (65 536 bytes), each text followed by one separator line break that counts toward the bound (a text that does not end with a line break never joins the line of the next), one `gitleaks stdin` per batch, so no boundary can occur inside a batch, and a single text above 64 KiB stops the gate (exit 2, "the text of a commit is over 64 KiB"). Findings in texts are counted, not named. A step that fails never reads as "nothing found" or as a smaller list, in `push-gate.sh`, `push-range.sh`, `gitleaks-public.sh`, `scan-public.sh`, `scan-pr-text.sh` and the helpers they source (`neutral-git.sh`, `scan-rules.sh`, `range-id.sh`, `repo-context.sh`): a `grep` in a condition is `grep_q` (found, not found, or failed = exit 2); stages that decide something go through files with every status checked, not through a pipe; a gitleaks report is read by one function (`x_count`); every number that is compared or added is read once, from one `wc` with its status checked and digits only (`wc_num`; a count from a gitleaks report is `x_count`, one from its log is checked to be digits), and a `wc` that fails or prints anything else is exit 2, never 0 and never a skipped bound (a failing `wc` used to read as "no commits" and as a text under 64 KiB); **the rule for every script that scans or decides** (`push-gate.sh`, `push-range.sh`, `range-id.sh`, `neutral-git.sh`, `gitleaks-public.sh`, `scan-public.sh`, `scan-rules.sh`, `scan-pr-text.sh`, `repo-context.sh` and `.githooks/pre-push`): no pipeline at all, no `|| true` or `|| :`, and no bare `grep` (a search is `grep_q`, or `scan_grep` which is `grep_q`; the one place that runs `grep` itself is `grep_q`, marked on its line). A multi-stage computation goes stage by stage through files in the private temporary directory (or a checked substitution of a single command), with each status checked, including the ones once called fail-closed (`scan_attribution` and `scan_bad_email` read standard input into a file, `gl_scanned` and the hash of a range are file stages, the hook cuts its lines with parameter expansion). A test (`tests/push-gate/no-pipes.test.mjs`) reads those files and fails on any such line unless it carries the marker `# GATE-EXCEPTION: <reason>`; the only marked line is `grep_q` itself; the same test also refuses `egrep`, `fgrep`, `\grep`, `command grep`, a path to grep, `eval` and `sh -c`, and a one-line group `{ a; b; }` or `( a; b )` whose status or output is used (only the last command of a group counts, so each command is joined with `&&`). It does not see a group that spans lines, a construct built at run time, or a function called in a condition (where `set -e` is off) that relies on `set -e` inside: that last one is a review item, and every function of these files that is ever called in a condition (`if f`, `f || …`, `f && …`, `! f`) checks the status of each of its commands explicitly (`|| return`, `case`, `[ … ]`). A loop over a list is complete or the run stops: `scan_history` (called under `||`, where `set -e` is off, so a list that cannot be opened would otherwise read as "no findings") checks the list is readable and compares the lines its loop processed with `wc_num -l` of the list; the other loops over a file or a list of commits (`push-range.sh` advertised commits, `gitleaks-public.sh` tips, `scan-public.sh` scoped words and commits, the commit texts in `push-gate.sh`) do the same count at top level, so that a read that fails midway, or a last line without a line break, is exit 2; the loops over arguments and the hook's loop over the lines git sends on standard input have no file to count (the hook's input is git's own); each script has exactly one `trap ... EXIT`, holding both its cleanup and `guard_exit` (a second trap on the same signal replaces the first, so it would drop one of them; a test checks this), and a command that fails under `set -e` with exit 1 (which means "found something") is turned into exit 2 by that trap (`guard_exit`), unless the script set `verdict_exit` just before its own exit 1. The word list is read by one function (`word_list_read`) for the gate, `scan-public.sh` and `scan-pr-text.sh`: a list that contains a NUL byte, a carriage return (a CRLF file), a UTF-8 byte order mark at the start of a line, or a line that is not valid UTF-8 is exit 2 with a fixed reason (a CR would become part of a pattern and a BOM part of the first word, so a word would silently not match) (a `grep` in a UTF-8 locale would silently drop such a line, so a word in another encoding would leave the list), a list that is named (`SCAN_WORDS_FILE` set) but missing or empty is exit 2 in the scans, and no line of the list is ever shown. (The old-step wrapper `gitleaks-public.sh` does not scan commit texts; only the gate does.) In `scan-public.sh` the word list, the attribution check and the mail check read the same text. The mail check reads that text with one thing taken out: from the first `author` line and the first `committer` line, only the first `<...>` (from the first `<` to the first `>` after it), which is the address git itself reads as the author's and the committer's address and which the identity rule checks (GitHub's web-flow committer address is allowed there). The name, anything after the address (the date, and any text after it in a hand-built object), a second such line, a line after the headers, and the `tagger` line inside a merged `mergetag` are all read by the mail rule, and an address there that is not a noreply or reserved-domain one is a finding. The identity rule reads only the four identity fields as git parses them (AI words in the names; every address must be exactly a GitHub noreply form, `[<number>+]<login>@users.noreply.github.com` with a login of letters, digits, `-` and `_`, or GitHub's web-flow address (the `noreply` account at `github.com`); the pattern is anchored at both ends and applied to one address per line, so text before or after the address, or a second address inside the same `<...>`, is not a pass): an address that is empty, because the line has no `<...>` or one that is never closed, is not a noreply address and is a finding, not a pass. The rule keeps to those fields because its meaning is who the author is, not what a message says. Measured with gitleaks 8.30.0: on `stdin` input of 65 536 and of 98 000 bytes, 40 inputs each with about 33 000 to 49 000 keys at random offsets (single line and one per line), every key was found; at 140 000 bytes some were lost (70 375 of 70 391, 70 400 of 70 422) and at 400 000 bytes more (201 083 of 201 270). The first boundary is near 100 000 bytes, so a batch within the bound cannot straddle one. A file that git treats as binary shows no content in a patch, so a key inside is not found (as before; it stays with the scanner change). A log line at level ERR or FTL in gitleaks' own log makes the run "could not run" (exit 2) even when it exits 0 or reports findings. A repository whose objects are not all present (a shallow clone, a partial clone with missing objects) stops the scans instead of being scanned in part. (a) to (e) belong to the scanner change; the design text in `development-flow.md` ("security") describes them as required.
17. **The history scan costs one `gitleaks git` start per commit, and CI scans the whole history several times on every event.** The gate prints the wall time of each step and of the whole run (from the very start of the gate to its end) in whole seconds (`push-gate: step gitleaks: ok (N commit(s)) in S s`; the `git` mode of `gitleaks-public.sh` prints its time too). Measured with `--mode general --all` on a synthetic repository of small commits (one new file each), gitleaks 8.30.0, **one machine** (the figures are for orders of magnitude, not a guarantee): 100 commits 58 s in all (step gitleaks 55 s, scan-public 3 s), 500 commits 287 s (269 s, 18 s). The time is linear in the number of commits: about 0.55 s per commit for the gitleaks step, nearly all of it the start of one `gitleaks git` per commit (a bare gitleaks start, which loads the default rules, costs about 0.5 s whatever the input), and about 0.04 s per commit for scan-public. The texts of the commits (names, emails, message) are scanned in batches of at most 64 KiB, so they cost almost nothing per commit; before that was done, the same figures were 105 s and 535 s (100 and 500 commits) and 2184 s for 2000. On this repository `--base origin/dev` over 33 commits took 63 s. **How often:** CI runs the whole history on every event: twice in the same job on most events (the old `gitleaks-public.sh git` step, about 0.5 s per commit, and the gate's general mode, about 0.57 s per commit), and three times on a push to the main branch (plus the gate's words mode, another 0.57 s per commit). The job has a 15 minute timeout (`ci.yml`). With the figures above (about 1.1 s per commit on most events, about 1.7 s per commit on the main branch, the fixed costs of installing and of the tree scans left out) the job times out at roughly 800 commits on most events and roughly 500 commits on a push to the main branch. Reaching it fails closed, but it makes every push and pull request red, so it is the deadline for the CI rework. The old scan steps in `ci.yml` are removed only after the new step has been seen passing on the main branch **and its time there has been recorded**. Narrowing what CI scans per event (a range for pull requests, the whole history on the main branch and in the nightly run; an unknown range means the whole history) belongs to the CI rework and is not done here.
