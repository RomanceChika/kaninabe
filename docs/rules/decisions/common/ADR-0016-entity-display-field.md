# ADR-0016: `entity_spec` が「行を人に名指す欄」を宣言する — `display_field`

## Status

accepted (2026-10-03)

---

## Context

### 背景

画面の生成(設計記録 screen-generation-boundary。非公開)が確認ダイアログの文を組むようになった(束 画面 4a〜4c。[ADR-0015](./ADR-0015-layout-component-kind.md) の改訂 2)。文は `{確認の見出し}。{注意書き}` で、見出しは重ね表示の `label`、注意書きは操作の属性から導く。旧手書きの確認文は「分館「X」を台帳から消します」「{表示名} さんを退会…」のように**どの行についての確認か**を出していたが、生成の文には**行の名前を出す口が無い**。名前を引くには、集約のどの欄が「行を人に名指す欄」かを知る必要があり、それを書く場所が仕様に無かった(束 4a で退行として受理した)。

同じ欄は 3 か所で要る。(1)確認の本文の先頭、(2)詳細(`kind: detail`)の見出し(将来)、(3)参照の欄の選択肢の表示名(`kind: form` の `reads` の第 2 列)。いまは (3) だけが「第 2 列は読みの projection の 2 欄目」という**読みの側の規則**で持たれていて、(1) と (2) には口が無い。

### 前提条件

- 名前の欄は集約ごとに綴りが違う(利用者 `display_name`・分館 `name`・蔵書 `title`・購入希望 `subject`・巻 `label`・招待 `code` …)。命名の規約は無く、揃える工事は既存のスキーマ・生成 zod・全テストに及ぶ。
- 生成物は仕様に書かれた欄の名前を引く(`{entity}FieldLabels` が欄の表示名、`entity` の `label` が集約の表示名)。**名前の欄の宣言だけが無い**。
- 拡張の手順は [dsl-extension-triage.md](../../process/common/specification/playbooks/dsl-extension-triage.md) に従った。下の「トリアージの記録」がその結果である。

### トリアージの記録

- **手順 0(宣言の欠落として 1 行に)**: entity_spec に、「この集約の行を人に名指す欄はどれか」を書きたいが文法に無い。書きたい形は `display_field: title`(`fields` に居る文字列型の 1 欄)。
- **手順 1(迂回パターン集)**: P-1〜P-10 に該当なし。どれも可視性・ガード・参照の表現力の話で、集約の表示の欄の宣言ではない。
- **手順 2(別の見方)**: **規約で導く**(欄の名前が `name` / `title` / `display_name` のどれかなら名前の欄) → 実測した集約の命名は揃っておらず(`subject` / `label` / `code` も名前として使われている)、規約を決めると「欄の名前を変えたら確認文が変わる」になる。**選択肢の読みの第 2 列から引く**(`branch_options` の `[id, name]` の `name`) → 第 2 列は「参照の欄の選択肢のための宣言」であって集約の名前の宣言ではない。選択肢を持たない集約(蔵書・購入希望・招待)には引き先が無く、選択肢の読みを持つ集約でも、確認文が選択肢の読みの存在に依ることになる。**`label` を流用する**(欄の `label` は欄の表示名で、行の名前ではない)。
- **手順 3(2 実例)**: 同じ製品の中で、名前の欄が要る集約が 9 つ以上ある(利用者・分館・蔵書・購入希望・巻・蔵書点検表・招待・館の案内ページ・付箋)。**ただし 1 製品の中の数え方であり、「別ドメイン・別プロジェクトでの再現」ではない**(手順 3 の数え方では 1 実例)。それでも導入するのは、**生成の確認文が退行している事実**(束 4 で受理した退行の 1 つ。旧手書きが出していたものを生成が出せない)を戻すのに、規約からは導けず他に置き場が無いためである。**実例が 1 製品なので、2 つ目の製品で再点検する**(Negative に残す)。
- **手順 4(決定可能性)**: 変数は有限。`display_field` は集約ごとに高々 1 つで、`fields` の部分集合(全列挙で検査できる)。書き間違いは新しい検査 V22(実在・型)と、パーサー(V1。キーの閉世界・空文字)が落とす。

## Decision

### 決定内容

**`entity_spec` のトップレベルに任意のキー `display_field` を足す。値は `fields` に居る `string` / `text` の欄 1 つの名前。**

```yaml
entity: item
label: 蔵書
display_field: title        # この集約の行を人に名指す欄
fields:
  - name: title
    type: string
```

1. **`display_field` は任意**で、書かなければ生成物は行の名前を出さない(従来どおり)。名前にあたる欄が無い集約は書かない。
2. **V22 が実在と型を見る**。`fields` に居ない欄は error・文字列でない欄(数値・日時・参照 id)も error。`personal` の欄を指すこと自体は止めない(利用者の名前のように、行を名指す欄が個人情報であるのは普通で、出してよいかは画面の可視性の宣言の領分)。
3. **生成物が引く場所は 3 つ**:
   - **確認ダイアログの本文**: `「{display_field の値}」{確認の見出し}。{注意書き}`。行の表の行のボタンと、1 行に対するボタン列(`kind: actions`)の確認が対象で、**名前は client 側で行(`row`)から引く**(器から関数を渡さない)。確認の器を持つボタンがあり、読みがその欄を返すときだけ行の型に足す(返さない読みには要求しない)。名前が空・無いときは付けない。
   - **詳細(`kind: detail`)の見出し**: 生成の詳細はいま見出しを持たないので、現時点で変わるものは無い。見出しを足すときはこの欄を引く。
   - **参照の欄の選択肢の表示名**: 選択肢の読み(`kind: form` の `reads`)の第 2 列の規則はそのまま。**参照先の集約が `display_field` を宣言していれば、第 2 列はその欄でなければならず、食い違えば S18 が error にする**(同じ集約の行が、確認文と選択肢で別の名前に化けない)。宣言の無い集約は従来どおり第 2 列を問わない。
4. **同時に入れる口は、語彙を足さない層 (c) の props である**(DSL の変更ではない): 確認ダイアログの注記の差し込み(`ConfirmDialog` の `note`・生成部品の `confirmNotes`)・空の選択肢の語(`emptyOptionLabel`)・操作が 1 本も無いときの案内(`kind: actions` の `.empty` の葉と既定の文)。製品固有の文言(分館未定の言い換え・終了の確認に出す残りの件数)は、生成の文に語彙を足さず、器が node / 文字列で渡す。

### 適用範囲

- `docs/specs/domain/{集約}/entity.md` のトップレベル `display_field`(V22)・S18 の選択肢の規則・画面の生成物(行の表・ボタン列の確認文)。
- 採用時に実測した製品(いまの `docs/specs` のデモ製品とは別で、集約の数や名前は説明のための数字である)は 9 集約に宣言した(利用者 `display_name`・分館 `name`・蔵書 `title`・購入希望 `subject`・巻 `label`・蔵書点検表 `title`・招待 `code`・館の案内ページ `title`・付箋 `title`)。

## Consequences

### Positive（メリット）

- 「行を人に名指す欄」が**宣言として読める**。生成物は欄の綴りを推さず、宣言を入力にする。確認文が「どの行についての確認か」を出せる(束 4 で受理した退行が戻る)。
- 確認文と選択肢で同じ集約の行が別の名前に化けない(S18 が見る)。
- 迂回の余地がない。書き間違いは V1 / V22 / S18 が落とし、免除の語を持たない。

### Negative（デメリット・トレードオフ）

- **語彙が 1 つ増える(`display_field`)。** 書き場所は entity_spec のトップレベルに閉じ、誤った記述は V1 / V22 が止める。
- **実例は 1 製品の中の複数集約である(手順 3 の数え方では 1 実例)。** 退行を戻すために導入した。2 つ目の製品を立てる日に、この語彙が本当に一般か(1 集約に複数の名前の欄が要らないか・複合の名前を要らないか)を再点検する。
- **宣言しても生成物が引かない集約がある**(行の表やボタン列を持たない集約・選択肢を持たない集約)。書いたが誰も読まない宣言にはなりうるが、名前の宣言は検査の対象ではなく仕様の文書(ブックの章)としても読めるので、書くことは止めない。
- **1 つの集約に名前の欄は 1 つ**。「姓 + 名」「題名 + 著者」のような複合の名前は表せない(欄を 1 つ選ぶ)。
- **サーバー描画には確認ダイアログの名前が現れない。** 名前は押された行が決まってから client 側で組むので、閉じたダイアログの骨格(サーバー描画)には無い。配線は生成物のテストが、文の組み立ては `row-actions-state` の単体テストが見る。

### Neutral（その他の影響）

- 生成物の確認文の形が `{見出し}。{注意書き}` から `「{名前}」{見出し}。{注意書き}` になる(宣言があるときだけ)。注意書きの導出は変わらない。
- 選択肢の読みの第 2 列の規則(`[id, 表示名の 1 欄]`)は変わらない。宣言がある集約に限り、第 2 列の欄を縛る。

---

## Alternatives Considered

### Option 1: 欄の名前の規約で推す(`name` / `title` / `display_name` のどれかが名前)

- **Pros**: 新しい語彙が要らない。
- **Cons**: 実測した集約の命名は揃っておらず(`subject` / `label` / `code` も名前に使う)、規約の外れは黙って名前が出ないままになる(検出できない)。欄の名前を変えると確認文が変わる。
- **Why rejected**: 語彙の発明であり、宣言の代わりにならない(手順 2)。

### Option 2: 選択肢の読みの第 2 列から引く

- **Pros**: 既存の宣言(`[id, 表示名]`)だけで済む。
- **Cons**: 第 2 列は参照の欄の選択肢のための宣言で、集約の名前の宣言ではない。選択肢の読みを持たない集約(蔵書・購入希望・招待)には引き先が無く、確認文が選択肢の読みの存在に依ることになる。
- **Why rejected**: 表せない集約がある。

### Option 3: 欄の `label` を名前に流用する

- **Pros**: 宣言が増えない。
- **Cons**: 欄の `label` は欄の表示名(「蔵書タイトル」)で、行の名前(「地域の歴史」)ではない。取り違えると確認文に見出しが入る。
- **Why rejected**: 別の概念を 1 つの宣言に畳むと、どちらかの意味が壊れる。

## Notes

**確認文の「名前 → 見出し」の順。** 名前は見出しの**前**に鉤括弧で付ける(`「地域の歴史」終了処理。…`)。見出しは重ね表示の `label`(「分館を削除する」)で、目的語を含むことが多いので、名前の後ろに助詞を足すと文が組めない。名前を前に置けば、見出しの語に触れずに「どの行か」だけが先頭で読める。

**注記・空の選択肢・案内を DSL にしない理由。** 終了の確認に出す「残りの件数」・分館の「未定・分館なし」・「（自分）」の印は、製品固有の文言である。仕様の語彙にすると、文言の違いごとに属性が増える。生成物は**口**(`confirmNotes`・`emptyOptionLabel`・`rowExtras`)だけを持ち、中身は器が渡す(層 (c))。ここに検査を置かない(検査が要ると思ったものは層 (a) か (b) に属している)。

**操作が 1 本も無いときの案内。** `kind: actions` の生成物が、行の状態と実行者のロールの交差が空のとき `.empty` の葉と既定の文(「いまできる操作はありません」)を出す。以前の手書きのボタン列が出していた案内で、導出が完全なので生成物が持つ(どの画面に置くかは `kind: actions` を置く画面の判断)。

**料金確定ボタンが押せなくなる挙動は戻さない。** 旧手書きは、承認待ちが残っていると確定ボタンを押せなくしていた。生成の形は「押すと拒否が出る」で、**判断は DB(RPC)が持つ**([ADR-0012](./ADR-0012-db-as-authority.md))という線に沿う。理由の文(`ConfirmFeesNote`)は残る。

**目録型の 7 つ目(UX 原則の台帳)の再裁定。** **`ux_principles_spec`(2026-10-03)は目録型の 7 つ目にあたり、この再訪条件に到達した。再裁定: 7 つ目でも一般化しない(共通部分の括り出しもしない)。** 理由は、6 つの台帳は項目の意味も検査も違い、共通化で消えるのはフロントマターの読み方だけで、それは `lib/model/decl-list.ts` が既に担っているからである。**次に再訪するのは 8 つ目のカタログを作るとき**。(判断の正は [doc_types.md](../../meta/standards/doc_types.md)「現構成で使わない doc_type」。)
