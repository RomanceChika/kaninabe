# ADR-0002 — 法律的な階層構造による文書体系

`docs/rules` を、法体系に倣った 6 つの階層 + スコープ別のディレクトリへ再構築することを決めた記録。**このリポジトリの文書構造そのものの根拠**である。

## Status

accepted(2026-08-06 — このリポジトリの立ち上げ時に採用)

## Context

この構造は、発案者が前身の体系(前職で自ら構築・運用したもの)で設計・実証したものを、**このリポジトリの立ち上げ(2026-08-06)時点で初日から採用した**ものである。前身では当初 `backend/rules/` の下にルールをフラットに置いており、そこで 5 つの問題が顕在化し、法階層構造への再構築で解消された。以下はその教訓であり、このリポジトリがフラット構造を経ずに 6 階層で始めた根拠である。

1. **ルールとスキルの肥大化** — ファイルが増え続け、どこに何があるか分からない。関連するルールが分散して全体像が掴めない。1 ファイルが大きくなり、目的の記述を見つけるのに時間がかかる。
2. **視認性の問題** — フラット構造では、原則・アーキテクチャ・プロセスの区別が曖昧になる。不変の原則と可変の手順を見分けられない。ルールの優先順位と重要度が伝わらない。
3. **整合性の問題** — 複数のルールファイルに矛盾する記述が生まれる。原則と手順が混在し、どちらに従うべきか判断できない。変更時の影響範囲が追跡できない。
4. **AI の参照忘れ** — ルールが分散しているため、AI が全件を参照できない。重要なルールを見落としたまま実装が進む。**スキルの側でルールを名指ししても、対象が多すぎてコンテキスト長に収まらない。**
5. **拡張性の欠如** — バックエンド専用の構造で、フロントエンドと共通事項に対応できない。新しいルールをどこに足すかの方針が無い。ドメイン固有の知識(用語・不変条件)を置く場所が無い。

このリポジトリでの前提条件: モノレポ構成であること / AI(Claude Code)を活用した開発であること / `specs` のツリーと併走すること / ルールの整合性と AI の参照精度が重要であること。

## Decision

**法律的な階層構造に基づく文書体系を採用する。**

文書を 6 つのディレクトリに分類し、それぞれに明確な責務と参照関係を持たせる。

| ディレクトリ | 責務 |
|---|---|
| `meta` | メタ情報。文書の種類・配置・参照のルール |
| `principles` | 原則。憲法レベルの、変えてはいけない大原則 |
| `domain` | ドメイン知識。用語・不変条件・業務例 |
| `architecture` | アーキテクチャ。構造と技術選定 |
| `process` | プロセス。手順・規約・実装例 |
| `decisions` | 意思決定記録(ADR) |

各階層の下に `common/` `backend/` `frontend/` を置き、**スコープ別に管理する**。

適用範囲: プロジェクト全体の文書体系、`rules` 配下のすべて。**`specs` には影響しない**(既存の仕様書体系を維持する)。

## Consequences

**Positive**

1. **明確な階層と責務** — 原則・アーキテクチャ・プロセスが分離される。「何が変えられないか」が一目で分かる。優先順位が階層そのもので表現される。
2. **視認性の向上** — 番号台で直感的に分かる(10 番台は原則、40 番台は手順)。目的の情報を見つけやすい。各階層の README が入口になる。
3. **整合性の担保** — `meta` で参照関係を定義する。**下位層は上位層を参照できるが、上位層は下位層を参照しない。** 参照キー(`norms` / `decisions`)で依存関係を明示する。
4. **AI の参照精度の向上** — 参照すべき階層を明示できる。必要なルールだけをコンテキストに読み込める。**`norms` フィールドが参照忘れを防ぐ。**
5. **拡張性** — `common` / `backend` / `frontend` でスコープを分離できる。新しいスコープを追加できる。`domain` で AI の知識不足を補える。
6. **AI へのより多くの委譲** — ドメイン固有のルールを参照して仕様を検討できる。原則とアーキテクチャを参照して適切な実装を選べる。プロセスと例を参照して一貫した実装を生成できる。

**Negative**

1. **移行コスト** — `backend/rules` からの移行、分類と再配置、リンク切れの修正。
2. **学習コスト** — 階層構造の理解、どの階層に何を書くかの判断、`meta` の理解。
3. **管理の複雑化** — 階層とファイル数の増加、参照関係の管理、ID の採番。
4. **過剰な構造化のリスク** — 小さなルールでも形式に従わなければならない。階層が深くなりすぎると、かえって分かりにくくなる可能性がある。

**Neutral**

- `specs` は変更しない。
- スキルの実装を新しい構造に合わせて更新する必要がある。
- AI への指示の仕方が変わる。

## Alternatives Considered

**Option 1: 既存の `backend/rules` をそのまま維持する**

- Pros: 移行コストがゼロ。既存の運用を続けられる。学習コストが要らない。
- Cons: 肥大化・視認性・整合性の問題が解決しない。AI の参照忘れが続く。フロントエンドと共通事項に対応できない。
- 却下理由: 根本的な問題が解決せず、スケールしない。

**Option 2: フラット構造でカテゴリ別のディレクトリを切る**(`principles/` `architecture/` `conventions/` `processes/` `examples/`)

- Pros: シンプル。カテゴリが明確。移行コストが比較的低い。
- Cons: **階層による優先順位を表現できない。** 不変のものと可変のものの区別が曖昧になる。スコープの分離が二次元になってしまう。
- 却下理由: 法体系型の階層が持つ明確さが失われ、優先順位の伝達力が落ちる。**番号(00〜50)を振ること自体が優先順位の表現である**、というのがこの決定の骨子だからである。

**Option 3: Wiki や Notion で管理する**

- Pros: リッチな編集ができる。リンクが簡単。検索が強力。
- Cons: コードと分離される(バージョン管理が別になる)。**AI がアクセスしにくい。** オフラインでの作業が難しい。マークダウンの標準化が難しい。
- 却下理由: コードと一緒に管理したい。AI との統合が重要である。

**Option 4: ADR だけで管理する(決定の記録のみ)**

- Pros: シンプル。変更履歴が明確。広く使われている手法である。
- Cons: 原則・アーキテクチャ・プロセスを記録する場所が無い。**「現在の状態」を把握しにくい**(決定の積み重ねを全部読まないと今が分からない)。ドメイン知識を置けない。
- 却下理由: ADR 単体では足りない。原則・アーキテクチャ・プロセスの置き場も必要である。

## Notes

**法律の階層との対応づけ**(日本の法体系を参考にしている)。この対応づけは、以後この体系を説明するときの装置として繰り返し使われる。

| 法体系 | この体系 |
|---|---|
| 憲法(国の基本原則) | `principles` |
| 法律(具体的な構造・制度) | `architecture` |
| 政令・省令(実施の詳細) | `process` |
| 判例・解釈(適用の記録) | `decisions` |

**段階的移行の順序**: ① `process/backend/system/standards` を整備(完了)② `decisions` を追加(完了)③ `principles` を整備(完了)④ `domain` を整備 ⑤ 最後に `backend/rules` を削除(完了)。

**`domain` に置くもの**: 用語集(業務用語の定義)/ 不変条件(守るべきビジネスルール)/ 例(具体的な業務シナリオ)。AI が仕様を検討するときに参照し、ドメイン知識の不足を補うためのものである。

**追記(2026-08)**: 決定時の適用範囲宣言「`specs` には影響しない」は、その後の展開によって覆っている。現在の `docs/specs` は制約付きの仕様 DSL(YAML フロントマターが正)として作り直され、[ARCH-SP-0002](../../architecture/specification/common/ARCH-SP-0002-domain-spec-structure.md) / [ARCH-SP-BE-0001](../../architecture/specification/backend/ARCH-SP-BE-0001-backend-spec-structure.md) という仕様専用のアーキテクチャ文書と、検証器・生成器を持つ。また Context 4(スキルでルールを名指ししてもコンテキストに収まらない)への対処は、階層化だけでは足りず、CLAUDE.md のルーティング表と「オーケストレーターがサブエージェントに必読文書のパスを明示する」という運用が上乗せされている。Negative 4 に挙げた「過剰な構造化のリスク」も、実体 0 本のディレクトリと、実体とずれた README の一覧という形で現実になった。**これらは ADR-0002 の決定を覆すものではないが、この決定だけを読んで現在の構造を推測すると外れる。**

**追記(2026-08-25)**: ディレクトリの採番(`00_` 〜 `50_`)は廃止し、`meta` / `principles` / `architecture` / `process` / `decisions` の名前だけを使う。Positive 2 に挙げた「番号台で直感的に分かる」は、読む順をルーティング表(CLAUDE.md)とハンドブック(`docs/book/`)が配るようになった時点で効果を失っていた。あわせて **`domain` 層は rules から削除した**(実体 0 本のまま。上の「未完了」と「段階的移行の順序 ④」は中止である)。ドメイン知識(W)は規範ではなくプロジェクトの所有物であり、住所は `docs/specs/` の隣である。
