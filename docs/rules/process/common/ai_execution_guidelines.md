# AI 実行の共通ガイドライン

スキルや playbook を実行する AI が、**どの作業でも同じように従う作法**を定める。中身は 2 つだけである。**進捗をどう追うか**と、**コンテキストが飛んだあとどう戻るか**。

適用範囲は**すべてのスキル・playbook の実行時**である。個別の手順文書はこのガイドラインを前提にしてよく、**同じことを書き直さない**。手順文書ごとに進捗管理の作法を書き始めると、作法が文書の数だけ増えて、どれが正か分からなくなる(PRIN-0007 のこの文書における適用)。

## 目的

- スキル・playbook を実行する AI が、**どの作業でも同じ作法で進捗を追う**状態にする。
- コンテキストが圧縮されても、**タスクの記録だけで作業を再開できる**状態にする。
- 進捗管理の作法をこの 1 枚に集め、手順文書ごとに書き直させない(PRIN-0007)。

## 全体の手順・流れ（概要）

どの作業でも踏むのはこの 2 段だけである。本体はそれぞれ H3 で展開する。

0. 進捗管理 — 作業の初めに全手順を一括登録し、開始・完了ごとに状態を更新する
1. コンテキスト管理 — 圧縮や中断が起きたら、タスクの記録から現在地を取り戻す

### 進捗管理

#### タスク管理ツールで進捗を追う(義務)

**すべてのスキル・playbook の実行時に、タスク管理ツールで進捗を管理する。** 記憶と会話の流れで進捗を持たない。

理由は 2 つである。**セッションをまたいで保持されること**と、**タスク間の依存関係を持てること**である。どちらも会話の履歴では代わりにならない。履歴は圧縮されるし、圧縮された履歴に「次にどれをやるべきか」は残らない。

基本のフローは 4 段である。

1. **作業開始時** — playbook の各手順をタスクとして**一括で**登録する。1 つずつ足していくと、全体像がどこにも無い時間が生まれる。
2. **手順開始時** — そのタスクを進行中に更新する。
3. **手順完了時** — そのタスクを完了に更新する。
4. **コンテキスト圧縮後** — タスク一覧を引いて、いま自分がどこに居るかを確認する。

#### タスクの 3 フィールドの書き分け

| フィールド | 何を書くか | 形 |
|---|---|---|
| `subject` | タスクのタイトル | **命令形**(「action_spec を書く」) |
| `description` | 詳細 | **playbook の該当節へのリンク + 短い説明だけ** |
| `activeForm` | 進行中の表示文言 | **現在進行形**(「action_spec を書いている」) |

**`description` に手順そのものを写さない。** 手順の正は playbook の側にあり、タスクに写した瞬間に同じ手順が 2 か所に存在することになる。playbook を直したのにタスクの写しが古いままだと、AI は古いほうを読んで作業する。リンクと短い説明にとどめれば、正は 1 つのままである。

#### 依存関係

タスク間に順序の制約があるときは、「〜が完了するまで開始しない」形のブロック指定を設定できる。仕様を書き終える前に実装のタスクを始められない、といった制約はここで表す。

#### タスクリストの分離(環境変数)

**推奨は「環境変数を設定しない」である。既定のまま使う。**

未設定のとき、セッション ID がそのままタスクリストの ID になり、**各セッションが独立したタスクリストを持つ**。この既定にはメリットが 3 つある。

- 設定が要らず、分離が完全に自動である
- 複数の課題を並行して進めても互いに干渉しない
- worktree ごとに自動で分かれる

デメリットは 1 つで、**セッションの終了やコンテキストの初期化でタスクが消える**ことである。

永続化したい場合は、課題を識別できる ID を環境変数で明示的に指定できる。ただし**通常は環境変数なしで足りる**。永続化が要るのは、同じ作業を日をまたいで続けると分かっているときだけである。

### コンテキスト管理

#### 圧縮からの復帰(3 段)

長い作業の途中でコンテキストの圧縮が起こりうる。起きた前提で、次の 3 段で戻る。

1. **タスク一覧を引く** — いまの進捗を確認する。
2. **現在のタスクの詳細を取得する。**
3. **`description` が指す playbook の節を読み直し**、続きから再開する。

この 3 段が成り立つのは、`description` が playbook へのリンクを持っているからである。手順を写していたら、圧縮で失われた文脈をタスクからは取り戻せない(上の「`description` に手順を写さない」と対になっている)。

#### 中断と再開

タスクは永続化されるため、次の 3 つの状況で作業を継続できる。

- セッションを終了したあとの再開
- worktree の切り替え
- 複数日にまたがる作業

**ただし例外がある。** 環境変数を設定していない場合は、新しいセッションで新しいタスクリストが作られるため、**前回のタスクは参照できない**。上の「メリットとデメリット」と対になる注意であり、自動分離を取るということは、そのぶん永続化を捨てるということである。

## 使用例

**多段手順の作業** — `/add-operation`(ドメイン操作を 1 つ足す)のように、宣言の軸の判定 → verify → action_spec → generate → operation 実装 → RPC migration → テスト → 全検査、と段が続くもの。全手順を開始時に一括登録し、1 つずつ進行中と完了へ更新していく。ビルダー×レビュアー体制で回す場合は、設計凍結・実装・独立レビュー・裁定の反映がそれぞれ節目になる。

**複数課題の並行作業(worktree)** — 課題ごとに `.claude/worktrees/` の別ディレクトリで起動する。環境変数を設定していないので、それぞれがセッション固有のタスクリストを持ち、**完全に分離される**。片方の進捗がもう片方に混ざらない。
