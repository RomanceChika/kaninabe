# 拡張トリアージ — DSLの表現力を買う前に、形を変える

仕様DSLで「これが書けない」に当たったとき、**拡張候補として起票する前に**必ず通す判定手順である。

**原則: 表現力を買う前に、形を変える。** DSLの拡張は決定可能性・検証器の単純さ・レビュー可能性を消費する**最後の手段**であり、
支払う前に「別のモデリングで同じ要求が満たせないか」を確かめる。根拠は [ADR-0003](../../../../decisions/common/ADR-0003-constrained-spec-dsl.md)(表現力を意図的に制限し、列挙ベース検証を採用する)の系譜である。

この手順が要るのは、**表現力の壁に当たったときの反応が「DSLを拡張する」に偏るから**である。
実測でも、拡張必須と結論された要求のいくつかは、別の関心事(キャッシュ・セキュリティ・運用・告知の安定性)の見方で見ると
モデリングの変更で解けている。その検討を、人の気づきに任せず手順として固定する。

## 目的

- 拡張の提案を、起票の前に**必ず一度モデリングの変更と突き合わせる**。
- 一度採った迂回を**再利用可能な型**として残し、同じ判断を毎回やり直さない([迂回パターン集](#patterns))。
- それでも拡張が要るときに、**何を消費するのか**(決定可能性・検証器・レビュー)を起票時に明示させる。
- 迂回が常に正しいわけではないことも同時に定める。**迂回が仕様を痩せさせるなら、拡張のほうが正しい**([迂回の限界](#limits))。

## 前提条件

- **事前に読むもの**
  - [ADR-0003](../../../../decisions/common/ADR-0003-constrained-spec-dsl.md) — とくに Notes の「これが書けないはバグではなく設計」(判断順序の1〜3)
  - [domain-spec-writing.md](../standards/domain-spec-writing.md)「DSL の外に置くもの」 — 何が最初から守備範囲外かの線引き
- **入力**: 「書けなかった」具体箇所。どの仕様のどのキーで、何を書こうとして、verify が何と言ったか(あるいは何も言わずに通ってしまったか)。
- **適用範囲**: 主対象は `docs/specs/domain/` のDSL(V群)。`query_spec` / `screen_spec` の語彙(Q群 / S群)を増やしたくなったときも同じ手順を当てる。

## 全体の手順・流れ（概要）

0. **「書けない」を1行にする**
1. **迂回パターン集と突合する**
2. **別の見方から検討する**(キャッシュ / セキュリティ / 運用 / 告知の安定性)
3. **2実例ルールを当てる**
4. **それでも要るなら、決定可能性への影響を書いて起票する**

手順1〜3のいずれかで解けたら、そこで打ち切る。**起票しないことが正常な終わり方である。**

### 手順0: 「書けない」を1行にする

- **目的**: 症状(不便)ではなく、宣言の欠落として言い直す。
- **作業内容**: 「{どの doc_type} の {どのキー} に {何} を書きたいが、文法に無い」の形で1行にする。書きたい式そのものも添える。
- **確認事項**: その1行が、要求(業務の言葉)ではなく**宣言の語彙**で書けていること。要求のままだと、次の手順で別の形が見えない。
- **注意点**: 「書いたのに効いていない」(未知キーの黙殺・値の無検査)は表現力の問題ではなく**検査の穴**である。この手順ではなく、検査の追加として BACKLOG に回す。

### 手順1: 迂回パターン集と突合する

- **目的**: 過去に同じ形で当たった壁を、もう一度考え直さない。
- **作業内容**: [迂回パターン集](#patterns)の「症状」列を上から読み、当たっているものを探す。当たったらその迂回を自分のドメインに当てはめて書き直してみる。
- **確認事項**: 書き直した仕様が verify を通り、かつ**元の要求が宣言のどこかに残っている**こと(残っていない場合は [迂回の限界](#limits)へ)。
- **注意点**: パターン集に無い形だったことは、拡張が要ることの証明にはならない。手順2へ進む。

### 手順2: 別の見方から検討する

- **目的**: 仕様の表現力の問題に見えるものが、別の関心事から見ると設計の問題であることを見つける。
- **作業内容**: 次の4つの問いを順に当てる。**1つでも「はい」があれば、その方向のモデリングを先に試す。**

| 見方 | 問い | 「はい」のときに向かう形 |
|---|---|---|
| **キャッシュ** | その読み取りは、条件を持たなければ**誰にでも同じ答え**になるか | 条件付き可視性をやめ、公開側を別集約に切る。[ARCH-BE-0016](../../../../architecture/system/backend/ARCH-BE-0016-read-path.md) は「キャッシュを挟むと『誰に見せてよいか』がキャッシュキーの設計問題に化ける」としており、条件を持ち込むほど読み取り経路が重くなる |
| **セキュリティ(不在による安全)** | 見せない情報を「隠す」のではなく、**そこに置かない**ことはできるか | 公開側に公開情報しか物理的に存在しない形にする。漏れる経路が構造的に無くなり、[PRIN-0009](../../../../principles/common/PRIN-0009-secure-by-default.md)(deny by default)の極致になる |
| **運用** | その条件の切り替えは、**人の操作**として切り出せるか | 実行時の条件ではなく `publish` のような遷移にする。遷移なら状態機械に書けて、実行権限もガードも既存の語彙で宣言できる |
| **告知の安定性** | 見せる内容は、**次に人が操作するまで変わらないほうがよい**か | 時点のスナップショットを写す。「いつ見たかで内容が変わる」ことが業務上むしろ不都合なら、条件付き可視性は要求の誤読である |

- **確認事項**: 検討の結果(採った / 採らなかった理由)を、起票または `NOTES.md` に1行残す。次に同じ壁に当たった人がやり直さないため。
- **注意点**: 見方は**代替案を出すためのもの**であって、拡張を否定するためのものではない。4つとも「いいえ」なら、それ自体が起票の材料になる。

### 手順3: 2実例ルールを当てる

- **目的**: 1件の要求のためにDSLを広げない。
- **作業内容**: **同じ拡張を必要とする独立した実例が2つ以上あるか**を数える。同じドメインの中の4か所は1実例と数える(要求の出所が1つだから)。別ドメイン・別プロジェクトでの再現を数える。
- **確認事項**: 実例が1つなら**原則として見送る**。見送った記録(どの実例で、どう迂回したか)をパターン集か `NOTES.md` に残す。2つ目が出た時点で起票する。
- **注意点**: 例外は「いま入れないと後から入れられない」場合である。可視性・権限のように**実装とテストに固着してから直すと全面改修になる**ものは、1実例でも起票してよい。ただしその理由を起票に書く。

### 手順4: 決定可能性への影響を書いて起票する

- **目的**: 拡張が何を消費するかを、決める人が見える形にする。
- **作業内容**: 起票(`BACKLOG.md` またはストレステストのC表)に次の4点を書く。
  1. **設計スケッチ1行** — どのキーに何を足すか。閉じたテンプレに絞れるならその形まで
  2. **決定可能性への影響** — 変数のドメインが有限または区間のままか。全列挙で検査できるか。できないなら、その拡張は ADR-0003 の決定そのものを変える提案である
  3. **検査の追加** — その構文を書き間違えたときに何が落ちるか(V番号 / Q番号)。**落ちる検査を設計できない拡張は、書けるようになるだけで守られない**
  4. **迂回検討済み** — 手順1〜3の結果。当てはめたパターンID、または「該当なし」とその理由
- **確認事項**: 4点すべてが埋まっていること。空欄がある起票は未完成として差し戻す。
- **台帳に 1 行足す**: 起票した拡張が `npm run verify` の警告(warning)として現れているなら、**拡張候補の台帳** [`legacy/spec-tools/extension-candidates.md`](../../../../../../legacy/spec-tools/extension-candidates.md) に 1 行足す(`rules` に、その警告を出す検査の ID。**その検査が製品の側で直せる別の理由の警告も出すなら、`scope` で候補の言い分に当たる分だけに絞る** —— 絞らないと、仕様を書く人が消すべき警告まで「読まなくてよい側」に落ちる)。台帳に載った警告は verify の出力で `(拡張候補 X-…)` と区分され、仕様を書く人が読まなくてよい仕組みの宿題になる。拡張が済んだら `status` を `done` にする(当たる警告が残っていれば W5 が error にする)。載せずに警告が出つづけると `(未分類)` として数えられる。
- **注意点**: 採否そのものはこの手順の範囲外である。DSLを実際に広げるときは ADR を書く(ADR-0003 の適用範囲を変える変更になる)。

## 詳細

### 軸と語 — 値域をどちらが持つか {#axis-and-word}

**軸は仕組み、語はアプリ。** 検証器・生成器(`legacy/spec-tools/lib`)が**分岐に使う区別**(値域の種類・形)は体系側が固定してよいが、**その区別が取りうる具体的な値の一覧**はアプリの事情であり、仕組み側のコードに書かない。

書きたくなったのがどちらかは、この 1 行で見分けられる: **「別のアプリでこの体系を使うとき、この値も一緒に使うか」**。使わないなら語であり、仕様側の宣言に置く。

これは思いつきの原則ではなく、実際に複数箇所で破られていた。

| 何が固定されていたか | 住んでいた場所 | 移した先 |
|---|---|---|
| `STATE_SETTLES = ['fees']`(状態が確定させるものの語彙) | `lib/model/types-state.ts` | state_spec 先頭の `vocabulary.settles`(id + label) |
| `AUDIENCE_RECIPIENT`(通知の宛先 → 実装の宛先種別の対応表) | `app/src/operation/jobs/handlers.ts` | notification カタログの `vocabulary.audience[].recipient` |
| `MEMBER_ABSENT` / `INVITATION_OUTCOMES`(認証フロー決定表の軸の値) | `lib/model/auth/types.ts` | auth.md の `axes`(`kind: state` の `absent`・`kind: enum` の `values`) |
| `STAFF_ROLE_ID` / `GATE_SUBJECTS` の `role_staff`(認証の関門が見るロール) | `lib/model/auth/types.ts` | auth.md の `gates[].role`(`guards: role_gate` の関門だけが持つ) |
| `allStaff()`(`'staff'` を直接比較する特権判定) | `lib/semantics/operation-facts.ts`(当時は `lib/generate/render/action-attributes-facts.ts`) | role_spec の `kind: authenticated_default` を含まないことに再定義(ロール名に依らない) |
| `globalRole()`(`'anonymous'` / `'patron'` を直接返すグローバルロール解決) | `app/src/operation/_template/actor.ts` | role_spec の `kind` 宣言 → 生成物 `GLOBAL_ROLES`(`app/src/domain/generated/roles.ts`) |
| `BYPASS_ROLE = 'system'`(RLS バイパスロールの決め打ち。3 ファイルで重複) | `lib/generate/render/{code-rls-expectations,code-api-expectations,book/access-view}.ts` | `role_hierarchy.ts` の `systemRoleId(roles)`(role_spec の `kind: system` を引く) |
| `notificationAudience(...) === 'public_channel'`(通知の宛先語を outbound 判定に直接使う) | `lib/generate/render/action-attributes-derive.ts` | `recipient.kind === 'channel'`(フレームワーク固定の self/role/channel で判定) |

どれも同じ形の穴だった: **軸の「種類」(settles を持つ / 宛先の種類 / 決定表の列 / 関門が見る対象 / 特権かどうか / グローバルロールの解決 / RLS バイパス)は体系が正しく固定していたが、軸が取りうる「値」まで一緒に固定してしまっていた**。値が増える・変わるたびに `lib/` 側や `app/src` の仕組み側コードを直す必要があり、しかもその変更は verify を素通りする(体系のコードは仕様ではないので、どの検査も「値を変えたのに宣言が追随していない」を検出できない)。

**執行**: [enforcement-matrix.md](../../../backend/system/standards/conventions/enforcement/enforcement-matrix.md) の **C19(W1)** が仕組み側コードの全域(`legacy/spec-tools/lib` 全体・`app/src/operation/_template` / `app/src/operation/jobs` / `app/src/components` / `app/src/domain/engine` / `app/src/infrastructure/supabase` / `app/e2e/walker*.mts`)の文字列リテラルを走査し、仕様が宣言した**全 id**(集約・ロール・状態・イベント・語彙 id)と一致するものが無いかを見る(束⑫a で新設・束⑫a2 で全域へ拡張)。**通知 id・ジョブ id・設定 id(環境変数名)は対象外**である — これらはカタログ側の N1 / J1 / K1 が「実装が該当 id を**文字列リテラルとして**参照していること」を要求する設計であり(逆方向の契約)、W1 に含めると直接矛盾する。**例外リストは持たない**方針だが、実測で見つかった 2 種類の誤検出だけは構造的に除く。

1. **`type X = 'a' | 'b';` 形の文字列リテラル型**(`scan.ts` の `collectTypeAliasLiterals` が自動判定)。`type World = 'closed' | 'open';`(code-zod.ts)のような直接のユニオン型宣言は、値ではなく**型の判別子**であり、ファイル内に限って対象から除く。`const X = [...] as const` からユニオン型を導く形(`GATE_SUBJECTS` 等)は対象にしない — この形は `STATE_SETTLES` のような実在した漏れも同じ構文で書けるため、構文だけでは安全に判定できない。
2. **`w1-vocabulary-leak.ts` の `KNOWN_COLLISIONS`**(ファイルを絞った個別の言い訳)。auth 決定表の軸 ID(`patron` / `invitation` / `activate`)が YAML のキー名として使われる自己衝突、`FIELD_KEYS` / `SCHEDULE_ONLY_KEYS` / `ACTION_UX_CONFIRM_VALUES` のような DSL 自身のスキーマ語(`required` / `confirm` / `endpoint`)が config カタログの語彙とたまたま同じ綴りになる衝突、`ROLE_KINDS`(フレームワーク固定の 3 スロット名)がこのアプリのグローバルロール id(`anonymous` / `system`)と同じ綴りを選んだ衝突、config-spec-writing.md と external-spec-writing.md が共有する規約契約(`optional_degrades` 等)、実装上の実測由来の例外表(`loan_companion` の置き場所)がこれに当たる。**理由をそこに書く**(除外の判断は実測に基づく。builder-report-12a2.md 参照)。

**未解決のまま残した穴は無い(2026-10-03、束 F-w1 で消した)**: かつて `TRANSACTION_EFFECT_KIND = 'transaction_effect'`(`lib/semantics/operation-catalogs.ts`)が job_spec の `vocabulary.kind` の値を直接比較していたが、「書き込みと同一トランザクションで実現される(キューに積まれない)」という軸を **`vocabulary.kind` の語の宣言(`in_transaction: true`)** に開き、体系は語を比べず宣言を読む形にした(拡張トリアージの結果: 実例は「同一トランザクションで実現済みの種類」と「匿名化」の 2 つの語・10 行 + 1 行。行ごとのキーではなく**語の側**に付けたのは、1 行の書き忘れが黙って別の種類として扱われるのを避けるため)。W1 の `status: unresolved`(受理ではなく報告)の機構は、次に穴が見つかった日のために残してある(いまの表に未解決の項は無い)。

#### 散文の語彙漏れ（W2）と「例示の印」

W1 が見るのは**文字列リテラル**だけである。しかし「軸は仕組み、語はアプリ」が破れる形はもう 1 つあり、**仕組み側の doc コメントがアプリの語で仕組みを説明している**箇所が実測で残っていた（検査の漏れ探し 2026-09-12 §6。`_template/actor.ts` の「集約ごとに違う（`loan.patron_id` / `item.librarian_id`）」等）。実行時の挙動は変わらないが、読み手には仕組みがその集約を知っているように見え、別のアプリに移した瞬間に嘘になる文である。

**W2** は同じ語彙を**アプリ側の仕組みの層**（`app/src/components`・`vocabularyScan: true` の置き場・`app/e2e/walker*`）のコメントに探し、**ファイル 1 件につき 1 件の warning** を出す。

| 判断 | 書き方 |
|---|---|
| **例として挙げている** | その行に `例:` を書く。印のある行は走査から外れる |
| **仕組みの説明にアプリの語が要る** | それは軸の宣言が足りないサインである（W1 と同じ読み方）。散文を一般語に書き換えるか、軸を仕様側に開く |

**規則は「アプリの語を書くな」ではなく「例だと明示せずに書くな」である。** 例示は読み手のために要るものであり、禁じると doc コメントが痩せる。明示させれば、**仕組みが知っている事実**と**説明のための例**が機械にも人にも区別できる。

**`legacy/spec-tools/lib`（検証器・生成器）の散文は対象外である。** あの木は体系が自分を説明する散文であり、`docs/rules/**` の規約文書と同じく「このアプリを例に説明する」ことが本来の仕事である（実測で 254 行がその形だった）。アプリ側の仕組みの層は逆に、そのアプリのことを知っていてはいけないコードなので、同じ文がそこにあれば漏れである。

**重さが warning なのは、散文の文脈が緩いからである。** error にすると「コメントを書くな」という別の規則に化ける。

**誤検出の免除は W1 と同じ形で宣言する。** 体系側の値域・DSL のキー名・道具の名前が、このアプリの id と同じ綴りを選んだために衝突する語は `PROSE_COLLISIONS`（`w2-prose-leak.ts`）に **1 項ごとに「語 / 範囲 / 扱い / 理由」を書いて**外す。範囲は `'all'`（ファイルを問わない）かパスの部分一致で、扱いは W1 の `KNOWN_COLLISIONS` と同じ `accepted`（誤検出。除く）/ `unresolved`（仕組み側の穴として残っている。除かずに warning に出し続ける）である。裸の語の集合を全域に効かせる形は採らない —— 免除には必ず理由を添えるのがこの体系の流儀である（束 ㉑ の独立レビュー 6-B）。

現在 `'all'` で外している語は `system` / `anonymous` / `none` / `required` / `accept` / `generate` の 6 語で、どれも W1 が同じ理由で `accepted` にしている語である（役割の 3 スロットの呼び名・`ReadScope.kind` の判別子・DSL のキー名・コマンド名）。

### 迂回パターン集（追記専用） {#patterns}

**過去に実際に採った迂回だけを載せる。** 思いつきの設計案は載せない(出典のある実例が1つ以上あることが掲載条件)。

| ID | 症状(「書けない」の形) | 迂回の形 | 実例と出典 | 代償・限界 |
|---|---|---|---|---|

**追記の作法。**

- **行を消さない。** 迂回が誤りだと分かったら「代償・限界」列に実測を足すか、[迂回の限界](#limits)へ移す。消すと「一度試して駄目だった」が失われ、同じ迂回が再発明される。
- **掲載条件は実例と出典。** どのドメインの、どの記録(findings のID / `NOTES.md` の日付)から来たかを書く。出典の無いパターンは載せない。
- **IDは追番**(P-7、P-8…)。既存のIDを再利用しない(起票の「迂回検討済み」欄が過去の記録を指すため)。

### 迂回の限界 — 迂回してよいかの判定基準 {#limits}

**判定基準は1つである: 迂回したあとも、その意図が宣言のどこかに残るか。**

| 迂回後の姿 | 判定 | 実例 |
|---|---|---|
| 意図が**別の宣言に移った** | 迂回が正しい | P-1(何を公開したかが公開側集約の行として残る)。P-4(従属関係が3本の `check` として残る) |
| 意図が**どこにも残らない** | **拡張のほうが正しいことがある** | P-2(ストレステストの題材 B-5)。分岐条件は日本語の関数名の中にしかなく、状態機械にも invariant にも現れない |
| 意図が**ずれた場所に残る**(書いてあるが、書いてある場所が間違っている) | **どちらでもない**。deny by default は効く(安全)が、読んだ人が誤解する。拡張の実益と誤読の代償を比べて判断する | あるサンプルの C-22(遷移が書き換えるフィールドを宣言できず、`writes: by: system, when: {遷移前の状態}` で近似した。5 か所: `loan.late_fee_amount` / `loan_companion.fee_amount` / `loan_companion.patron_id` / `item.flat_surcharge_amount` / `item.surplus_amount`)。宣言上は「司書が書ける列」に見えるが、実際に書き込むのは確定の遷移だけであり、**宣言と実装の時点が 1 つずれる**。findings 発見3 | 元の製品 v2 では**拡張しない**判断(C-22 は「誤解を招くだけで穴ではない」。後から `events[].sets` を足しても既存の `writes` を消して移すだけで済む) |
| 意図が**嘘の写しとして**残る(認証基盤が持つ状態を、ドメインの集約・表に写して宣言する) | **写しをドメインに持つ迂回は不可**。写しの同期の責任が生まれ、集合に対する操作(例: 他の端末を全部終える)は遷移に写らず、宣言が実体を写さない。拡張が正しい | セッションの管理(`auth_session` 集約案 A の却下。ADR-0019・設計メモ「セッションの管理の画面」§2。裁定 2026-10-23 U-6) |
| 意図が**「書かないこと」でしか表せない** | 形による。下の非対称を見る | あるサンプルの匿名化射影(C-19) |

**「書かないこと」で守る形には、安全なものと無防備なものがある。** この非対称を見誤らない。

- **安全**: 許可の不在が拒否を意味する宣言(`writes: []` / `deletes: []` / `reads` に書かないロール)。deny by default が効いており、**後から誰かが1語足せば宣言として現れる**(ストレステストの題材 A-10 / A-11、元の製品 v2 A-14)。
- **無防備**: 許可リストに載せないことでしか表せないもの(`projection` に書かない列、`filters` の1行)。**後から1語足すと壊れるのに、verify は緑のまま通る。** あるサンプルの変異注入で実測されている —— `projection` に `patron_label` を足しても素通り(内輪の利用者名が公開サイトに出る)、`filters` から `visibility == public` を消しても素通り。

後者に落ちたなら、迂回は限界に達している。**手順4へ進んで起票してよい**(あるサンプルの C-14 / C-19 がこの経路で挙がった候補である。ただしそこでも P-1 の公開時スナップショットが同じ要求を満たしうることが後から判明しており、**限界の判定と迂回の探索は一度で終わらない**)。

### 制度への配線

- **ストレステストのC表(拡張候補)に「迂回検討済み」列を1本足す。** 値はパターンID(P-1〜)か「該当なし」+ 理由。**次回の `docs/design/*/findings.md` から適用する。** 列が空のC項目は起票として未完成であり、優先順位づけの対象にしない。
- **意味レビューからはこの文書を参照する。** [domain-spec-change.md](./domain-spec-change.md) の手順5で「書けないので `application` に逃がした」が挙がったら、この手順を回す。**レビュー観点の側にトリアージの中身を書き写さない**(PRIN-0007。書き写した瞬間に判定基準が2か所になる)。
- **ADR-0003 の判断順序との接続。** ADR-0003 Notes は「①既存の構文の組み合わせ → ②DSL外で扱うべきか → ③頻出かつ決定可能性を壊さないなら拡張」という順序を定めている。**この文書は①と②の間に入る** —— 既存の構文で書けないと分かった直後、DSL外に逃がすか拡張するかを決める前に、**モデリングそのものを変える選択肢を必ず1回通す**。
