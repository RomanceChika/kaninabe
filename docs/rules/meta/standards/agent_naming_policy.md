# 役割分担と名付け — 生成と評価を分ける

AI に作業を任せるとき、**役割を名前から判別できる**ようにするための分類体系である。名前が役割を表していれば、誰に何を渡すかの判断が名前を見るだけで済む(PRIN-0008)。

**この体系の核は 1 つだけである。生成する者と評価する者を分ける。** AI は自分の成果物を自分で評価するのが苦手だからで、生成した本人に「これで良いか」を聞くと、ほぼ必ず良いと答える。分離して初めて品質のループが機能する。

## 目的

- 役割の名前に一貫性を持たせる
- **名前から役割を判別できるようにする** —— 何を任せる相手なのかが、呼ぶ前に分かる

## 分類体系

4 分類である。**分類の軸は「その成果物が評価の対象になるかどうか」である。**

| 分類 | 何をするか | 評価との関係 | サフィックス |
|---|---|---|---|
| Planner | 要件の分析と計画の立案 | 成果物の評価は受けない | `-planner` |
| Generator | 評価の対象になる成果物を生成する | Evaluator が評価する | `-generator` |
| Evaluator | 成果物を評価する | 評価は受けない | `-evaluator` |
| Creator | 評価の対象外である外部リソースを作成する | 評価ループの外 | `-creator` |

### Generator と Creator の区別

- **Generator** は、Evaluator による評価を受ける成果物(コード・テスト・仕様書・変更差分)を生成する。**生成 → 評価の品質ループの一部**である
- **Creator** は、評価ループに入らない外部リソース(課題票の起票など)を作成する

この区別が要るのは、評価ループに入れるべきものを Creator の名前で作ってしまうと、**誰も見ないまま成果物が確定する**からである。名前が役割を表すというのは、そういう取りこぼしを名前を付ける時点で防ぐという意味である。

### Evaluator の細分化

評価の範囲で 3 つに分かれる。

| サブ分類 | 評価の範囲 | 名前 |
|---|---|---|
| Diff | 変更差分のみ(コードの品質) | `{scope}-diff-evaluator` |
| Global | プロジェクト全体(整合性) | `{scope}-global-evaluator` |
| PR | 要件の充足(課題票や計画との突合) | `{scope}-pr-evaluator` |

## 命名パターン

- **実行者:** `{スコープ}-{対象}-{分類サフィックス}`
- **入口:** `{スコープ}-{対象}-{動詞}`

**動詞は 4 分類の動詞形に固定し、独自の動詞を導入しない。**

| 動詞 | 呼ぶ相手 |
|---|---|
| `-plan` | Planner |
| `-generate` | Generator(単体、または Generator と Evaluator の品質ループ全体) |
| `-evaluate` | Evaluator |
| `-create` | Creator |
| `-solve` | 複数の分類をまたぐフルオーケストレーション |

**`-generate` が 2 つの意味を兼ねるのは意図である。** Generator を単体で呼ぶ場合も、Generator と Evaluator のループ全体の入口としても `-generate` を使う。**Evaluator は内部の品質保証機構であり、呼ぶ側から見えるアクションは「生成」だけだから**である。呼ぶ側に「評価も走るのか」を意識させると、評価を省略する選択肢を与えてしまう。

## 現在のエージェント一覧

**分類ごとに分かれたエージェントは現在存在しない。** `.claude/agents/` は無く、実在するのは `.claude/skills/` の 3 本 —— `add-operation` / `add-query` / `add-screen` —— である。これらは仕様と実装を追加する手順の索引であり、上の命名パターンには従っていない。

**スキルの命名の正はこの文書ではない。** CLAUDE.md が「スキルは手順の索引であり正典ではない」「`docs/rules/` 側にスキルの規約は作らない」と定めており、この文書はスキルに規約を課さない。

**代わりに動いているのはビルダー×レビュアー体制である。** 設計を凍結し、ビルダーが実装し、独立したレビュアーが**実装を読まずに仕様と正典から期待を組み立てて**突き合わせ、裁定はユーザーが下す。分類体系との対応は次のとおりで、**生成と評価を分けるという核は同じ**である。

| この文書の分類 | 現行の実運用 |
|---|---|
| Generator | ビルダー(設計凍結の後に実装する) |
| Evaluator | レビュアー(実装を読まず、仕様と正典から期待を組み立てる) |
| Planner | 設計凍結の段。オーケストレーターとユーザーの対話で行う |
| Creator | 該当なし |
| 判定 | 裁定者はユーザーである。合否を AI が確定させない |

レビュアーが「実装を読まない」のは、評価の独立性を名前ではなく**手順**で担保するためである。実装を読んだ時点で、評価は実装の追認に寄る。

## 新規エージェント・スキル追加時のルール

1. **命名の拠り所は上の分類体系である**
2. **Generator と Creator の判別基準は、成果物が評価の対象になるかどうかである**。それ以外の理由で分けない
3. **どの分類にも当てはまらない場合は、役割を最も端的に表す動詞で代替する**。無理に 4 分類へ押し込まない
4. **スコープの接頭辞は対象に合わせる。** `api-` を付けてよいのはバックエンドの API を扱うものだけで、フロントエンドなら `fe-` のようにスコープ別に変える
