# process/backend/system/standards/conventions/testing — テスト規約

テストを 4 種類に切り分け、それぞれが**何を保証する係なのか**を定める箱である。種類ごとに担当する境界が違うので、同じことを二重に確かめない。ここでは切り分けと共通の定義を示し、書き方の詳細は配下の各文書に置く。

## テストの種類

| 種類 | 目的 | 詳細 |
|---|---|---|
| ユニットテスト | 内側の層(`app/src/domain` / `app/src/operation`)の**仕様網羅**と、依存方向の健全性の診断 | [unit.md](./unit.md)。実行は `cd app && npm run test` |
| 統合テスト | **境界の保証**。ローカル Supabase(実 Postgres)に対して infrastructure・RLS・Server Action の通しを確かめる | [integration.md](./integration.md)。実行は `cd app && npm run test:integration` |
| UI テスト | **画面仕様 ⇔ テストの 1 対 1 対応**(screenTest)。RSC を関数として呼び出し、宣言された部品と配線を突き合わせる | frontend 側の [screen-test.md](../../../../../frontend/system/standards/conventions/screen-test.md)。実行は `cd app && npm run test` |
| E2E | ブラウザでしか観測できない**残余の疎通確認**。実フォームの送信、押下後の遷移、重ね表示の開閉、クライアント操作後の状態 | [screen-test.md](../../../../../frontend/system/standards/conventions/screen-test.md) の E2E スモークの節。実行は `cd app && npm run test:e2e` |

**E2E は貫通のスモーク 1 本と、`router.refresh()` を跨ぐ行の再描画の補強 1 本(計 2 本)だけとする。網羅を担わせない。** ブラウザを起動するテストは遅く、壊れやすく、落ちたときに原因が特定しにくい。数を増やすほど「赤いが誰も直さないテスト」に近づくので、上限を設計として固定する。

ユニットテストと統合テストは同じ [template.md](./template.md) に従い、それぞれ目的・範囲・実行方法・配置・記述ルールを [unit.md](./unit.md) / [integration.md](./integration.md) に書く。

## CI の内と外 — L1〜L4(網羅の担い方)

**E2E をハッピーパス 1 本に絞った代わりに、網羅は CI の外の 4 層に分けて持たせる。** ブラウザ E2E で全パターンを踏もうとすると「遅い・壊れやすい・原因不明」になる(上の「E2E は貫通シナリオ 1 本だけ」の理由そのもの)。網羅性を諦めるのではなく、担う場所を変える。

| 層 | 何をするか | 実体 |
|---|---|---|
| L1 | CI に常設。ハッピーパスのスモーク 1 本 + 行の再描画の補強 1 本(上の表の E2E。計 2 本) | `cd app && npm run test:e2e` |
| L2 | 「一通り試す」の定義を仕様から機械的に導いた**生成台帳**。状態遷移の成立/不成立・画面 × 操作・読み取り経路 × 実行ロール・通知・ジョブの各行に、既存の `test_cases` から証拠を機械的に埋める。**判定はしない**(赤くしない) —— どこまで機械の突合で押さえていて、どこからが手動確認に残るかを人に見せるだけ。通知・ジョブの証拠は帰属規則(導出 = effects から辿った遷移の成功ケース / 直接 = その通知・ジョブ自身の ID を `spec_ids` に挙げる test_cases)で 2 種類に分かれ、`source: schedule` / `manual` のジョブは直接のテストケースの宣言が 1 つも無いと `npm run verify` の A13 がエラーにする | `docs/book/sweep.html`(`npm run generate` の生成物) |
| L3 | モデルベースのランダムウォーク。ランダムな操作列を実行し、生成済みの遷移表・不変条件・可視性宣言をオラクルに、仕様が予言しない動作を機械検出する | `cd app && npm run walk`(CI 外。テストではない) |
| L4 | LLM が Playwright を運転し、意地悪な操作(戻る・二重送信・同時操作・変な入力)を発想する。正誤判定は AI ではなく仕様オラクル(L3 と同じ) | 未着手 |

**核心は「仕様がオラクル問題を解いている」ことにある。** 遷移表・不変条件・可視性宣言はいずれも仕様からの生成物であり、ランダムに実行した操作が「合法か違法か」「見えてよいか」を判定する基準としてそのまま使える。だから L3 / L4 は手書きの期待値を 1 つも持たずに「間違った動作が静かに通る」を機械検出できる。順序は L1(常設)→ L2 → L3 → L4 で、後段ほど網羅は広がるが、判定の確からしさ(構造化されているか・機械オラクルで判定できるか)は下がる。

## 貫いている 2 つの定義

**定義 1: 「unit 100%」は仕様網羅率であって、行カバレッジではない。** 数えるのは実行された行ではなく、**仕様の側の項目**である —— 状態 × イベント × ロールの組、ガードの境界、不変条件、action_spec の `test_cases`。これらに対応するテストが揃っている状態を 100% と呼ぶ。行カバレッジで測ると、意味のない行を通すだけのテストが数字を作ってしまい、仕様との対応が切れる(PRIN-0008)。

**定義 2: 内側の層で 100% に届かないのは、テスト不足ではなく依存方向の破綻の兆候である。** 「テストを書きたいのに書けない」「書くために実物の DB や外部サービスが要る」という状態は、内側にあるべきでないものが内側に入り込んでいる合図である。**対処はテストの工夫ではなく、層の分割の是正**である([ARCH-BE-0001](../../../../../../architecture/system/backend/ARCH-BE-0001-app-layer-structure.md))。ここを読み違えて「テストを頑張って書く」方向に進むと、依存の破綻がテストの複雑さとして固定される。

理想形(模範例)は、`legacy/spec-tools/__tests__/` のテストと [題材](../../../../../../../../legacy/spec-tools/__tests__/fixtures/samples) にある。**食い違ったら実物が正**である。

## UI テスト DSL の先送り（意図的な空白）

画面仕様に対応する UI テストの書き方は、当初この階層では**意図的に空白**にしてあった。理由は判断基準のほうにある —— **不完全な UI テストは net-negative である。** 中途半端に書かれた UI テストは、通っても何も保証せず、落ちても仕様違反かテストの脆さか区別できず、しかし「テストがある」という安心だけを与える。したがって取れる道は**本気でやるか、明確に空白のままにするかの二択**であり、実物の画面と併走して設計できる段になるまで着手しないと決めていた。

**その段はすでに到来しており、空白は埋まっている。** 現在は screenTest(画面仕様と 1 対 1 に対応する RSC の関数呼び出しテスト)と E2E(スモーク 1 本 + 行の再描画の補強 1 本)が実在し、正は frontend 側の [screen-test.md](../../../../../frontend/system/standards/conventions/screen-test.md) にある。画面を 1 枚足す手順にも標準で組み込まれている。仕様側の取り決めは [template.screen_spec.md](../../../../../../../specs/frontend/screens/template.screen_spec.md) と screen-spec-writing にある。

上の**二択の判断基準そのものは残す**。別の種類のテストを新設するかどうかを迷ったときも、同じ基準で決める。
