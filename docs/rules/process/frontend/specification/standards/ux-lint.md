# UX 経験則の機械検査（U 群）

画面仕様（`screen_spec`）とドメイン仕様から導ける **UX の経験則**を機械で検査する U 群（U1〜U5）の定義と、UX 原則の台帳・閾値・画面ごとの受け入れ（`ux:`）の書式。

## 目的

- UX の経験則（「取り返しのつかない操作には確認を挟む」「行き止まりを作らない」「選択肢を並べすぎない」）のうち、**宣言から機械的に判定できる部分**をレビュアーの記憶から機械へ移す（PRIN-0006）。判断そのものは人間に残す。
- そのために**新しい事実の宣言を要求しない**。U 群が読むのは既存の `state_spec` の `tone` / `settles` / `events` の `label`、`access_spec` の `deletes` / `writes`、`screen_spec` の `actions` / `overlays` / `layout` の部品 / `navigations`、action_spec の `ux`（上書き）だけである。UX のために仕様を書き足させた時点で、この検査は続かない（PRIN-0007）。
- 経験則から意図的に外れた場所を、**理由つきの一覧**として残す（PRIN-0004）。画面ごとの受け入れ（`ux:`）がその一覧で、ハンドブックに出る。

## 参照するもの

- **画面仕様の書き方と S 群**: [screen-spec-writing.md](./screen-spec-writing.md)（`overlays` / `navigations` / `actions` の語彙はここが正）
- **ドメイン仕様の書き方**: [domain-spec-writing.md](../../../common/specification/standards/domain-spec-writing.md)（`final` / `deletes` / `writes` / ガード式の文法）
- **UX 原則の台帳**: 製品の仕様の木の `ux-principles.md`(`ux_principles_spec`。原則・見張る検査・閾値。雛形は [template.ux_principles_spec.md](../../../../../specs/frontend/template.ux_principles_spec.md))
- **受け入れの置き場**: 各 screen_spec の `ux:`（下の「画面ごとの受け入れ」。書式の正は [screen-spec-writing.md §ux](./screen-spec-writing.md)）
- **設計の出所**: 非公開の設計記録 ux-lint-draft（構想と、第 2 弾・第 3 弾に回した検査の一覧）
- **検証器の実装規約**: [scripts-code-quality.md](../../../common/tooling/standards/scripts-code-quality.md)

## 原則：U 群はすべて warning

**U 群の経験則の指摘(U0〜U5)は 1 件残らず warning であり、`verify` の「エラー 0」条件に影響しない。**(例外は U8 — 台帳が自分の宣言と食い違っていないかという真偽の問いなので error。下の「台帳の整合」) S 群が問うのは「仕様どうしが食い違っていないか」という真偽の決まる問いだが、U 群が問うのは「その UI は使いやすいか」という**正解が一意でない**問いで、機械が言えるのは「経験則から外れている」までである。外れていること自体が正しい設計でありうるので、error にすると「黙らせるための確認ダイアログ」が量産される。

出力は `verify` の中に 1 行で混ざる。

```
U 群(UX 経験則): screen_spec 9 件に対し U1〜U5 を実行しました(warning 4 件 / 受け入れの掃除漏れ 0 件 / 理由つきで受け入れ 0 件)。
```

3 つの数は性質が違うので分けて出す。**warning** は人間の判断待ちの指摘、**受け入れの掃除漏れ**（U0）は
機械的に直せる不整合、**受け入れ**は理由つきで消した数である。混ぜると「掃除すれば減る数」と
「判断しないと減らない数」の区別がつかなくなる。

## 検査の一覧

| # | 何を見るか | 指摘の条件 | 受け入れの subject（画面の接頭辞は付けない） |
|---|-----------|-----------|---------------|
| **U1** | 破壊的操作の確認 | **確認が要る操作**（操作の属性の導出 `confirmRequired` = `negativeTone ∨ destructive ∨ (irreversible ∧ affects_others) ∨ settles`。action_spec の `ux` の上書き適用後。[action-spec-writing.md §方針の導出](../../../backend/specification/standards/action-spec-writing.md)）を発火する操作が、`opened_by` を持つ `overlays` の `actions` に載っていない | `{操作 ID}` |
| **U2** | 操作の語 | 同じ操作（イベント ID / 予約 ID）に、**画面と画面の間**で違う語が当たっている（画面が書いた重ね表示の `label` → `kind: form` の部品の `label`、無ければ状態機械のイベントの `label`） | `{操作 ID}` |
| **U3** | 行き止まり | その画面の外へ出る `navigations` が 1 本も無い（chrome から継承した遷移を含めて数え、**自分自身へ戻る遷移は出口に数えない**） | （省略 = 画面そのもの） |
| **U4** | 同時操作数 | 1 つの状態で同時に並びうる操作の数が閾値を超える（`kind:` を持つ部品は部品ごと、部品に載らない操作は画面の和） | `{機械}.{状態}`（状態機械に触れない画面は省略）・部品なら `{部品}/{機械}.{状態}` |
| **U5** | フォーム長 | 1 つの状態で同時に編集できるフィールドの数が閾値を超える | `{編集 ID}/{機械}.{状態}`（状態を持たないエンティティは `{編集 ID}`） |
| **U0** | 受け入れ宣言そのもの | `ux:` の項目に対応する指摘が出ていない／存在しない原則の ID を書いている／同じ画面の同じ `principle` + `subject` の宣言が重複している | （受け入れできない） |

**U1 は導出を 1 本にした。** 以前の U1 は「終端状態への遷移・局所的に不可逆な遷移・物理削除」を自前で数えていて、画面の生成・S19・Y5 が読む方針の式とは別の導出だった（確認ダイアログは出るのに U1 は黙る、またその逆が起こる）。いまは U1 も同じ `confirmRequired` を読む。action_spec の `ux: { confirm: none }` で「確認は要らない」と決めた操作は、U1 も要らないものとして扱う（裁定の置き場が action_spec の 1 か所になる）。

**統一で U1 の射程が変わった（狭まる方向がある）。** 以前の U1 は「終端状態への遷移・局所的に不可逆な遷移・物理削除」を数えたので、**本人だけに効く不可逆の遷移**（題材 expenses の `claim.submit` / `claim.approve` のように、戻る遷移が無いが他の人には影響しないもの）にも確認を要求していた。方針の式は `(irreversible ∧ affects_others)` なので、**他の人に影響しない不可逆は確認を要求しない**。U1 は式の結果だけを読むため、これらの遷移は確認の overlay が無くても U1 は黙る（画面の生成・S19・Y5 と同じ答えになる）。**意図して確認を要求したいときは、action_spec の `ux: { confirm: required, reason }` で式を上書きする**（理由は 1 文。上書きは U1 だけでなく生成物の確認ダイアログにも効く）。

**U2 の範囲。** 比べるのは画面と画面の間だけで、**単一画面の中の「ボタンの語と確認の語が違う」は対象外**（確認の見出しは「何をしようとしているか」を言う語で、ボタンと同じである必要はない）。予約 ID の既定の語（生成された表の「登録」「保存」「削除」）は汎用の語で役割が違うので比べない。**語は宣言から生成物へ引かれる**（状態機械のイベントの `label` は `{machine}EventLabels` になる）ので静的に比べられる —— U2 が長く空き番号だったのは、ボタンの語が実装の手書きだったためである。

**U2 の限界（2 件。どちらも「見えている語しか比べない」方向）。**

- **手書きの部品（`kind:` を書かない部品）の字面は見ない。** 手書きの部品がボタンに何と書いているかは実装の中にあり、仕様に無い。比べるのは、仕様に宣言された語（重ね表示の `label`・`kind: form` の部品の `label`・状態機械のイベントの `label`）だけである。手書きの部品が操作を載せる画面では、その画面のその操作は「イベントの `label`」を当てたものとして数える（手書きが別の語を書いていても検出できない）。
- **重ね表示の `label` は、その重ね表示が載せる操作すべての語として読む。** 1 つの重ね表示に複数の操作が載っていて、`label` が実際には 1 つの操作の語でしかないとき、他の操作にも同じ語が当たったと数えてしまう（過大に出る方向。当たったときは重ね表示を操作ごとに分けるか、画面の `ux:` で受け入れる）。

### 数え方（U4 / U5）

どちらも**状態を固定して数える**。宣言だけを数えると、`item_manage` の 7 操作は「常に 7 個並ぶ画面」に見えるが、遷移表と突き合わせれば同時に並ぶのは最大 4 個である。状態を無視した検査は、正しく設計された画面ほど叱ることになる。

- **U4 は部品ごとに数える**: `kind:` を持つ部品（`form` / `table` / `actions`）は部品ごとの実数 —— 行のボタン = 遷移表との交差の結果・フォーム = 1・`actions` = 状態ごとのボタン数・表の `edit` = 1。**別々の部品に分かれて並ぶ操作を 1 つに足さない**。部品に載らない操作（手書きの部品が持つもの）は従来どおり画面の和で数える。
- **遷移イベント**は `from` にその状態を含むときだけ数える（＝ screen-spec-writing.md §先読みの線引きが言う「宣言 ∩ 遷移表」）。
- **予約 ID**（`create` / `delete` / `update`）は `access_spec` の規則の `when` がその状態と**両立し得る**ときだけ数える。判定にはガード式の共存判定（V8 が決定性に使うのと同じもの）を流用する。
- **U5 はロールでも絞る**。画面の `for` から実行し得ない `writes` の規則は数えない（S4 と同じ交差。ロール階層を辿る）。
- 判定できないもの（接地しない ID・解析できない条件・別の状態機械に属する操作）は**数える側に倒す**。U 群が出すのは「同時に並びうる最大数」の**上界**であり、数え落として警告が出ないほうが、多めに数えて人間が確認するより悪い。

### 既知の限界

U4 の 2 つは**過大に出る方向**の限界であり、当たったときは受け入れ（画面の `ux:`）で受けることを前提にしている。

- **U1 は重ね表示の中身が確認になっていることまでは見ない。** 見ているのは「`opened_by` を持つ `overlays` の `actions` に載っているか」という構造だけで、`opened_by` が指す部品が本当に確認 UI かは判定できない（形だけの overlay で黙らせられる）。中身の妥当性は screenTest とレビューの領分である。
- **U1 の「戻る遷移が無い」判定（導出の `irreversible`）はガードを見ない。** 戻る遷移が状態機械の形として存在するかだけを見る。戻る遷移はあるがガード条件（時刻・承認など）が現実には満たせない、という場合は可逆と判定してしまう（過小に出る唯一の方向。他の限界と逆で、こちらは見逃す側に寄ることに注意）。
- **U4 は、部品に載らない操作の和と `overlays` の `actions` を同時に並ぶものとして数える。** 手書きの部品がどの操作を持つかは仕様に無いので全部を足す。モーダルの中のボタンは画面本体のボタンと同時には並ばないが、**どちらが開いているか**は仕様が持たない情報なので判定できず、上界として数える（`kind:` の部品が載せた操作の確認ダイアログは、その部品の操作として数え直さない）。
- **U4 は `variants`（排他表示）を解けない。** 同じスロットの排他グループからは 1 つしか描かれないが、どの操作がどの variant に属するかは宣言されていない（`layout` は部品の排他を持ち、`actions` は操作を持つが、両者の対応は仕様に無い）。したがって排他の分だけ過大に数える。

## UX 原則の台帳（ux_principles_spec）

U 群の原則は、これまで 3 か所に散っていた —— このファイルの散文・検査器の定数・ユースケースの予算（Y5）。
**1 枚にまとめたのが UX 原則の台帳(`ux-principles.md`。雛形は [template.ux_principles_spec.md](../../../../../specs/frontend/template.ux_principles_spec.md))** である。
新しい事実を宣言する場所ではなく、既存の宣言から原則を導く検査の ID と閾値の置き場である。

```yaml
principles:
  - id: U4                                  # 台帳の中で一意。U1 / Y5-steps の形
    statement: 1 つの状態で同時に並ぶ操作は、目安の数を超えて並べない   # 日本語 1 文
    derives: [screen_spec の actions と layout の部品(kind), state_spec の events, access_spec の when]
    enforced_by: U4                          # 見張る検査の ID。見張る検査が無ければ advisory
    budget: { limit: 7 }                     # 閾値(任意)
  - id: U1
    statement: 取り返しのつかない操作には確認を挟む
    enforced_by: U1
    affects: confirm_required                # 生成物が引く属性の名前(U1 の行だけ)
```

- **すべきこと:** 原則の文は規約の散文を**移す**。新しい原則を台帳で発明しない(足したい原則はまずこのファイルに検査として書く)。
- **すべきこと:** 閾値を変えるときは台帳の `budget.limit` を書き換える(検査のコードは触らない)。**閾値ちょうどは指摘しない**(超えたときだけ)。台帳が無いときは検査器の定数が既定値で動く(ユースケースの予算と同じ形)。
- **すべきこと:** 機械が判定できない・まだ検査していない原則は `enforced_by: advisory` で台帳に残す(U6 / U7)。「まだ検査していない原則」の一覧が消えないための席である。
- **してはいけないこと:** `affects` を U1 以外の行に書く。**原則が生成物の形を直接決めてはいけない**(原則 → 属性 → 生成物。台帳が決めるのは属性の値と閾値だけで、生成器は台帳を読まない。属性の名前と生成物の形は、原則の文を直しても変わらない)。
- **知っておくこと:** `affects` は**生成物が読む属性の名前の記録**であって、読まれて何かを起こす欄ではない。検査も生成器も `affects` の値を読んで動かない（U8 が U1 の行にだけあることを見るだけ）。確認が要るかを決めるのは action_spec の事実属性から導く式と `ux` の上書きで、台帳の `affects` や `statement` を書き換えても生成物は変わらない（原則 → 属性 → 生成物の「属性」は台帳の外にある）。
- **してはいけないこと:** `advisory` の行に `budget` を置く(誰も読まない数字は目録を嘘にする)。

### 台帳の整合（U8）

U8 は台帳そのものの検査で、U 群の他の検査と違い **error** である(U 群の warning は「その UI は使いやすいか」という正解が一意でない問いだが、U8 が問うのは台帳が自分の宣言と食い違っていないかという真偽である)。

| 見るもの | 指摘の条件 |
|---|---|
| スキーマ | 必須キー(`id` / `statement` / `enforced_by`)の欠落・知らないキー・`id` の形・`id` の重複・`budget.limit` が正の整数でない・`affects` が閉じた値域(`confirm_required`)の外・`statement` が 2 文以上 |
| `enforced_by` の実在 | `advisory` でも実在する検査 ID(U 群の検証器・Y5)でもない |
| 行が揃っていること | U 群の検証器(U1〜U5)のどれかを見張る行が無い / Y5 の 6 指標(`Y5-steps` など)のどれかの行が無い |
| 余り行 | `enforced_by: Y5` なのに `id` が `Y5-{指標}`(6 指標)のどれでもない(未知の原則 id。Y5 は指標の名前で台帳を引くので、余った行の `budget` は誰も読まない) |
| `budget` | U4 / U5 / Y5 の行に無い(検査が台帳から読む数字が無い) / `advisory` の行にある |
| `affects` | U1 の行に無い / U1 以外の行にある |

## 閾値と根拠

| 原則 | 既定値(台帳が無いときの定数) | 台帳の行 |
|------|-------|------|
| U4(同時操作数) | `MAX_SIMULTANEOUS_ACTIONS` = 7(`legacy/spec-tools/lib/model/ux/types.ts`) | `U4` の `budget.limit` |
| U5(フォーム長) | `MAX_WRITABLE_FIELDS` = 7(同上) | `U5` の `budget.limit` |
| Y5(認知の予算 6 指標) | `DEFAULT_USECASE_BUDGET`(`lib/model/usecase/types.ts`。値は [usecase-spec-writing.md](./usecase-spec-writing.md) §認知の予算) | `Y5-steps` など 6 行の `budget.limit`(`usecase_spec` の `budget:` が先に効く) |

根拠は **Hick の法則**（選択肢が増えるほど決定時間が伸びる）と**ミラーの 7±2**（短期記憶の幅）である。ただし **7 という数そのものに理論的な必然性は無い**。ここは**プロジェクトごとに変えてよい閾値**であり、次のような場合は上げ下げしてよい。

- 業務用の管理画面で**一覧性そのものが価値**になる → 上げる
- 初見の利用者が触る導線・モバイル主体 → 下げる

閾値を変えるときは**台帳を書き換える**（検査のコードは触らない）。**閾値ちょうどは指摘しない**（超えたときだけ）。

## 画面ごとの受け入れ（ux:）

指摘を受け入れる（＝この画面ではこの UX でよい）と決めたら、**その画面の screen_spec の `ux:`** に理由つきで書く。action_spec の `ux: { confirm, reason }`（導出の上書き）と**同じ「UX 原則への態度」の口**で、名前も揃えてある。違うのは形と向きである。

| 口 | 場所 | 書くもの | 向き |
|---|---|---|---|
| `ux: { confirm, reason }` | action_spec | 確認が要る / 要らないの**上書き**（導出を信じない理由） | 事実の導出を変える（画面の生成・S19・Y5・U1 が同じ結果を読む） |
| `ux: [{ principle, subject, reason }]` | screen_spec | 原則から外れてよい場所の**受け入れ**（理由つき） | 導出は変えず、指摘だけを消す |

画面側は**受け入れだけ**で、事実の欄（`confirm: required` のように画面が方針を決める欄）は開けない（画面が方針を再定義する口にしないため。画面は属性の導出を渡せない、という守りと同じ線である）。

```yaml
ux:
  - principle: U4
    subject: item_publication.published
    reason: 数えているのは手書きの部品が持つ操作の和で、独立したカードに分かれて並ぶ（部品を kind の生成物にすれば部品ごとの実数で数えられる）
```

- `principle` は原則の ID（`U1`〜`U5`）。存在しない ID は U0 が警告する。
- `subject` は**指摘の `反例: subject=...` に出る文字列をそのまま書き写す**。上の表の形式でもある。**画面は自明なので `screen-{name}/` の接頭辞は付けない**。画面そのものへの指摘（U3 など）は省略する。
- `reason` は日本語で「なぜその UX でよいのか」。空だと仕様として受理しない（S0）。**数を書くときは実数を書く**（指摘の文面に出る個数と食い違う理由は、読み手に別の画面の話に見える）。
- **画面 + `principle` + `subject` の 3 つが一致したときだけ**指摘が消える。どれか 1 つが違うと消えず、その宣言は用済みとして U0 が警告する。画面をまたぐ指摘（U2）は、語を書いた画面のどれかに書けば消える。
- 指摘が出なくなったのに宣言が残っていると U0 が警告する（**受け入れの一覧がそのまま「原則から意図的に外れた場所の一覧」である**ことが、この方式の価値である）。
- 同じ画面に同じ `principle` + `subject` の宣言が重複していても U0 が警告する。受け入れは 1 つあれば効くので後続は無害に見えるが、**理由が食い違う重複は「どちらの判断が生きているか」を読めなくする**。
- U0 が 1 つの宣言に出す指摘は最大 1 つである（重複した宣言に「用済み」まで重ねて言わない）。
- **受け入れの一覧はハンドブックの「UX 原則」の章に出る**（原則の表・閾値・画面ごとの受け入れの表。理由つき）。

## warning の運用（未決）

**warning をいつ・誰が棚卸しするかは未決である。** CI は U 群では止まらないため、放っておけば warning は増え続け、やがて誰も読まない出力になる。少なくとも次のどちらかが要るが、どちらにするかはユーザーレビューで決める。

- 仕様レビューのたびに U 群の warning を読み、**免除するか直すかをその場で決める**（＝ warning 0 を保つ運用）
- 定期的な棚卸しの儀式を設け、その間は warning が積まれることを許す

決まるまでは「**U 群の warning が増えたら、その差分は必ず人間が見る**」だけを守る。

## 検査しないこと

- **美しさ・文言・メンタルモデルへの適合**は対象外のまま（AI レビューと人間の層が担う）。
- **U6（a11y のランドマーク構造・コントラスト比）** — 台帳では `advisory`。 — 前者は `chrome` / `layout` から導出可能でワイヤーフレーム生成の拡張、後者はデザイントークンの確定後。
- **U7（ガード付き操作の理由表示）** — 台帳では `advisory`。実装側に検査の器が無いため規約＋レビュー。`ActionErrorView` の使用が事実上の充足。
- **ナビゲーション深度の上限・モバイル到達圏** — 閾値の根拠が画面数に依存するため、画面が増えてから。

## 実装

- 検証器は `legacy/spec-tools/lib/ux/verifiers/` に 1 検査 1 ファイルで置き、`verifiers/index.ts` の `ALL_UX_VERIFIERS` に登録する（S 群と同じ構造。CLI の変更は不要）。
- 受け入れの照合と用済み宣言の検出は `lib/ux/run.ts` が 1 箇所で行う。**各検証器は受け入れを知らない**（純粋関数のまま保つため）。
- 受け入れ（`ux:`）の読み取りは画面仕様のパーサー（`lib/model/screen/parse-screen-ux.ts`。S0）。台帳は `lib/ux-principles/`。
- U1 が読む確認の要否は `lib/semantics/operation-attributes.ts` の `deriveOperationAttributes`（`lib/ux/confirm.ts` が接着する）。
