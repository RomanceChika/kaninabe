# 変更ポリシー — 何を変えるときに記録を残すか

ルール文書を変えるときに、**判断を後から復元できる状態で残す**ためのポリシーである。原則や構造の変更は影響が広く、記録が無いと同じ議論を何度も繰り返すことになる(PRIN-0004)。

**運用は任意である。** ADR を必須にするか推奨に留めるかは決めていない。ただし、下の「変更時の最低チェック」だけは全ての変更に効く。

**このリポジトリの実際の記録先は 3 つに分かれている。** change_policy はその一番外側 —— 正典に昇格した後の話 —— を扱う。

| 台帳 | 何を書くか | 正典か |
|---|---|---|
| `NOTES.md` | 決定に至った経緯と作業ログ | 正典ではない |
| `BACKLOG.md` | 未処理の項目。消し込み式 | 未処理項目の正 |
| `docs/handoff/review-queue.md`(開発用リポジトリの台帳) | ユーザーの判断待ちの論点 | 判断待ちの正 |

決定はまず `NOTES.md` に記録し、**正式化できるものだけを `docs/rules/` に昇格させる**。この文書が扱うのはその昇格のときであり、昇格に伴って ADR を残すかどうかを次の基準で決める。

## どの doc_type の変更に ADR が必要か

| 変更対象 | ADR |
|---|---|
| `principle` / `architecture` の変更 | **推奨**(影響が広いため。必須にしてもよい) |
| `domain_glossary` / `domain_invariant` / `domain_example` / `domain_design_context` の用語・概念の変更 | 他文書への影響が大きい場合は推奨 |
| `process` の変更 | 手順の大幅な変更なら推奨 |
| `decision` の追加 | 対象外(新しい ADR を足すだけなので) |
| `spec` の変更 | 通常は不要。ただし**仕様の前提を変える**変更なら、関連する decision の更新か新規 ADR を検討する |

## breaking change の定義

次のいずれかに当たるものを breaking change とする。

1. **既存の principle / architecture の削除、または結論の逆転**
2. **既存 ID(`PRIN-*` / `ARCH-*` / `ADR-*`)の意味の変更。** 「〇〇とする」を「△△とする」に書き換えること
3. **参照関係の禁止化。** 今まで参照してよかったものを禁止にすること

**breaking change を行う場合は必ず ADR を残し、理由と移行方針を書く。**

2 番目が見落とされやすい。ID を残したまま中身をすり替えると、その ID を `norms` に持つ全ての文書が、知らないうちに別のものに従っていることになる。これは [id_policy](./id_policy.md) の「ID を再利用しない」と対になる規範である —— **番号を使い回さないことと、番号の意味を書き換えないことは、同じ約束の裏表である。**

## 変更時の最低チェック

変更のたびに次の 4 つを確認する。

1. **変更対象の doc_type を確認し、上の表に従って ADR を書くかを決める**
2. **[reference_policy](./reference_policy.md) を満たすか確認する。** 禁止されている向きの参照を増やしていないか
3. **[id_policy](./id_policy.md) に従うか確認する。** ID を再利用していないか、廃番の扱いは正しいか
4. **影響を受ける他の文書(参照元・参照先)を洗い出し、必要ならそれらも更新する**

手順としての詳細 —— 影響件数の見積もりや、廃止するときの作法 —— は [../playbooks/rule-update.md](../playbooks/rule-update.md) にある。

### 機械が見る部分

上の 4 項目のうち、2 と 3 と 4 の一部には執行者がいる。`npm run verify` の M2(id の一意性と形式)・M3(参照先の実在)・M4(リンク切れ)・M6(循環参照)がそれである。**verify が通らない状態でコミットしない**のがこのリポジトリの鉄則であり、CI が同じものを再実行する。

機械が見ないのは「ADR を書くべきだったか」と「影響を受ける文書を本当に洗い出したか」である。ここは人の判断が要る。設計を凍結してから実装し、独立したレビュアーが正典の側から期待を組み立てて突き合わせる —— **ビルダー×レビュアー体制**が、この判断を 1 人の思い込みに落とさないための仕掛けである。裁定はユーザーが下し、その結果は `NOTES.md` に戻る。
