# 人間レビューの手引き — ハンドブックの読み方と判断の下し方

このフレームワークで作られたシステムを**人間がどう読み、どこで何を判断するか**の手順である。
[system-spec-route.md](./system-spec-route.md)(作る側の手順)と対をなす**読む側の手順**であり、
この 2 つが揃って初めて体系を他のシステムに応用できる — 機械の手順だけ持ち出しても、
人間が何をすべきか分からなければ開発は回らない。

## 目的

- 人間の読む場所を **`docs/book/`(ハンドブック)ただ 1 つ**に固定する。仕様の生ファイル(`docs/specs/`)は
  機械の領土であり、人間が歩く必要がある状態は仕組みの失敗として扱う。
- レビューを「読み物を読みながら、埋め込まれた判断ポイントでその場で判断する」行為にする。
  別立ての監査台帳を読ませない(読めない入口はレビューコストを下げるという目的に反する)。
- 判断の結果の**落とし先**を固定し、判断が宙に浮かないようにする。

## 前提条件

- ハンドブック(`docs/book/`)が生成されていること(`npm run generate`。鮮度は `generate:check` が保証)。
- 仕様の手書きの標識は**必ずちょうど 1 つのブロック**(章の 1 節 × 仕様ファイル 1 枚)に載り、章が引用する。
  どのブロックにも属さない標識と、章が引用していない標識は `npm run generate` が**エラー**で止める
  (基線なしで 0 件。割り付けは `blockOf`)。母集合から外すのは案内文書(`directory_guide`)・雛形(`template.*`)・
  用語の台帳(`term_ledger`)の 3 種類だけで、理由は `exemptionOf` に宣言してある。
- ハンドブックは**全ページ生成物**である。読んで直したくなっても book を編集しない —
  直す先は常に仕様(YAML)であり、book はその写像である。

## 全体の手順・流れ（概要）

読み方は 2 モードある。

### モード A: 初見(このシステムが何かを理解する)

| 順 | 読むもの | 分かること |
|----|---------|-----------|
| 1 | `book/index.html`(表紙) | 規模・**集約関係図**(何と何が結びついているか)・ロール(誰がいるか) |
| 2 | `book/domain/`(集約の章) | 各集約のデータ・ライフサイクル(状態機械図)・操作・見え方・不変条件 |
| 3 | `book/screens.html` | 画面の全体像(ナビグラフ・ワイヤーフレーム・各画面でできること) |
| 4 | `book/visibility.html` | 誰に何が見えるか(可視性の地図) |
| 5 | `book/design.html` | 意匠(トークン・コントラスト)。実物は `book/screens.html` の画面カード(SSR プレビュー)で |

### モード B: レビュー(変更に ○× をつける)

| 順 | やること |
|----|---------|
| 0 | **`npm run spec:diff -- --base <前の版>` の出力を先に読む**(CI では push / PR ごとに実行の Summary に出ている) — 2 版の**生成物**(結果表・期待表・規則の表)の差から「誰の権限が広がった / 何が新しく公開される / どの操作ができなくなる / 見える行が増えた / 誰に飛ぶ通知が変わった / どの画面から起こせるようになった」の 6 軸だけを日本語で出す(この 6 軸は**導出の側** —— 公理を変えた帰結として機械が出した結果)。出力には「見えていないもの」の節の次に**「公理の側の差分」の節**があり、人が読むのはこちらである(不変条件の言明・状態の表示名・イベントの呼び名・要約の文が動いたか。`formal`・access の絞り込み・計算式の変更は生成物の形に畳まれるので、帰結が 6 軸に出る)。**読む順は出力の順どおり**である —— ①「判定できなかった生成物」と「結果表が答えていない操作」(**そこだけは差分が出なくても変わっているかもしれない**)→ ② **公理の側の差分**(基点つきで人が読む節)→ ③ **🔓 の節**(権限・可視・公開が増える変化。導出の側のレビューの主役)→ ④ 軸ごと。6 軸にも公理の側にも差分が 0 なら「意味の差分はありません」とだけ出る —— **そのときは全量を読み直さない**。**公理の側に 1 件以上あるときは、この文を出さず「6 軸(導出の側)に差分はありません。公理の側の差分が N 件あります」と出す**(見出しだけ読む人に差分なしと読ませない)。仕様(YAML)の差ではなく生成物の差なので、並び替えやコメントの変更には 1 行も反応しない。**読めなかったものがあると赤で止まる**(黙って緑にしない) |
| 1 | `book/review-guide.html`(手引き)を開く — **どの章に標識が何本・判断ポイントが何件あるか**を機械が配る(2 つは単位が違うので足さない。数える単位はブロック = 章の 1 節 × 仕様ファイル 1 枚で、章の頭の 1 行と手引きのブロックごとの表も同じ集計から出る)。「流し読みで良い」章は読まない(**理由つきの宣言がある章だけがこう出る**) |
| 2 | **「未分類(要確認)」の章が出たら、読まずに飛ばさない** — それは「標識も判断ポイントも無い」ではなく「**その章の標識と判断ポイントの集計が仕組みに無い**」の意味である。レビューを進める前に BACKLOG に 1 行起票し、章の定義に `reviewFree` の理由を書く(= 精読不要だと宣言する)か、集計を母集合に足す(= 件数を数えられるようにする)ことをビルダーに求める |
| 3 | 精読対象の章を読み、**埋め込まれた判断ポイント**(§詳細)で判断する |
| 4 | 判断の結果を**落とし先**(§詳細)に落とす |

読む順は **タスク → 画面 → 結果表 → ドメイン(句として)** である(ADR-0011 §5 の順に
**結果表**を 1 段足したもの)。宣言(誰が何を実行できる)まで読んでも「**どういう場合に落ちるか**」は
形からは読めないので、**結末**の段をそのあいだに置く —— 結果表は操作カードと保存点の直下に
折り畳んである(`book/actions.html` / `book/usecases.html`)。

## 詳細

### 章に埋め込まれた判断ポイント(何を見たら判断するか)

| 目印 | 意味 | 人間が答える問い |
|------|------|----------------|
| **⚠(scope: all)** | 全員に見える宣言 | **見せていいか** — 本当に全ロールに公開してよい情報か |
| **マトリクスの ✓/✗** | 状態×操作の可否 | **できていいか** — 形式的には合法でも業務的に変なマスはないか(機械には見えない) |
| **「条件の意味」列(guard)** | 遷移の条件式 | 条件は業務として足りているか・過剰でないか |
| **結果表の ❌**(操作カード・保存点の直下) | その実行者・その状態・その境界での**結末** | **その落ち方でいいか** — 落ちる相手と理由(権限 / 状態違い / 前提)が業務として正しいか。境界(締切の前後など)はセルの中の注記に出る |
| **「機械は守れない → テストが守る」マーク** | DSL 外の不変条件 | コードとテストに委ねてよい性質か |
| **標識(引用ブロック)** | 仕様に残された手書きの判断(否定・線引き) | **その判断でいいか** — 違うと思ったら異議を出す |
| **variants / 束ね方**(画面の章) | 表示分岐と操作の配置 | 保証したい表示分岐は variant に昇格させるか・操作の束ね方は動線として自然か |

### 判断しなくていいもの(レビューコストの下限)

機械が保証済みの範囲は**読まなくてよい** — フィールドの型と実装の対応・遷移表と実装の一致・
テストケースの存在と対応・testid・リンク切れ・生成物の鮮度。これらを人間が確かめている状態は
仕組みの失敗であり、直すのはレビューの頑張りではなく検査か生成である
([保証マップ](./system-spec-route.md))。

### 判断の落とし先

| 判断 | 落とし先 |
|------|---------|
| ○(このままでよい) | 何もしない(無言=承認ではないので、依頼されたレビューには ○ を伝える) |
| ×・異議(仕様を変えるべき) | 会話で伝える → 決定は `NOTES.md` へ → 仕様(YAML)を直して再生成 |
| 保留(いま決めない) | **保留の仮定** → レビューキュー(`docs/handoff/review-queue.md`) |
| 機械の指摘を意図的に受け入れない | **免除台帳**(理由必須)。黙殺の経路は作らない |
