【なぜ親テンプレート(conventions/template.md)を使わないか】

親テンプレートは 4 つの節に通し番号を振っている:
  1. 目的・スコープ / 2. ルール / 3. 注意点・例外 / 4. 関連ドキュメント

一方 enforcement 配下の文書は、トピックによって必要な節が変わる。
  - 「前提となる考え方」(二段の防衛線・縛りの粒度・ID からの変換規則など)が要るトピックと、要らないトピックがある
  - ルールの示し方が正誤コード例で足りるトピックと、表のほうが読めるトピックがある
  - 執行できていない範囲を明示すべきトピック(例: DB 側の防衛線)と、そうでないトピックがある

節の要不要が文書ごとに違う以上、見出しに通し番号を振ると、省略した文書で欠番が発生する
(「2 と 4 はあるが 3 が無い」という読みにくい形になり、番号での参照も意味を失う)。

そこでこのディレクトリでは番号を振らず、省略してよい節の見出しに「（任意）」を付ける。
本文から別の節を指したいときは、番号ではなく見出し名で参照する(例: 「◯◯の表のとおり」)。

必須の節(目的・スコープ / ルール / 注意点・例外 / 関連ドキュメント)は親テンプレートと同じなので、
読む順路は conventions 配下の他の規約と揃う。

frontmatter は doc_type: process と scope: backend の 2 キーだけでよい。
以下の見出しをコピーし、不要な「（任意）」の節は節ごと削除する。

# {ルールのトピック}の機械執行

{何を機械が保証しているかを 1 行で。あわせて対応表のどの行の詳細かを書く。例: 対応表の B1〜B9 の詳細}

## 目的・スコープ

- **目的:** {このルールがあることで壊れなくなること}。根拠の原則（`PRIN-xxxx`）を添える
- **スコープ:** {執行の対象になるパス}。あわせて**対象外のパス**も書く（対象外が書かれていない文書は、読み手に「全部に掛かっている」と読まれる）
- **正の所在:** {このルールの定義がどの文書にあるか}。上位の ARCH か、別の規約か、この文書自身か

## 前提となる考え方（任意）

ルールを読む前に共有しておくべき前提を置く。二段の防衛線、縛りの粒度、ID から実装名への変換規則などがこれに当たる。前提の要らないトピックでは**この節ごと省く**。

## ルール

個別ルールごとに H3 を立てる。見出しには対応表の行番号を必ず入れる。

### {個別ルールの要約}（{対応表の行番号}）

- **すべきこと:** {守られている状態}
- **してはいけないこと:** {落ちる書き方}
- **執行者:** {ESLint ルール名 / tsc オプション名 / DB 制約名 / コマンド名}

**執行者に書いてよいのは実在する ID・オプション名・制約名・コマンド名だけである。** まだ執行者が無いものは「**未実装**」と明記する。存在しない執行者の名前が書かれた文書は、読んだ人に「ここは守られている」と誤解させる。文書が嘘をつかないことが、この箱全体の前提である。

## コード例（任意）

正しい形と誤った形を**対**で置く。片方だけでは境目が読めない。

### この例が示すルール: {何を示すか}（{行番号}）

```ts
// OK: {なぜ通るか}
```


## 直し方（任意）

違反したときに何を直すかを書く。コード例では示しにくい指針の置き場である（例: 行数超過時に、層ごとにどう分割するか）。

## 執行できていないこと（既知の限界）（任意）

この執行者では守れない範囲を書く。**抜け穴は隠さずに明示する。** 書いていない抜け穴は、読み手からは「塞がっている」と同じに見え、そこを踏んだときに初めて分かる。塞ぐ予定があるなら、何が要るのか（型情報つきのルールが必要、実ブラウザ実行が必要、など）まで書く。

## 注意点・例外

適用外の範囲、他の規則との免除範囲の違い、このルールを緩めるときに**同時に直すもの**を書く。免除の範囲は規則ごとに違うので、「テストは全部免除」のような大雑把な書き方をしない。
