# PRIN-0006 — 仕様は判定可能な形で記述する

仕様を「正しいかどうかを**判定できる形**」で書くことを要求する原則。[PRIN-0001](./PRIN-0001-spec-as-truth.md) が形骸化しないための前提条件である。

## 原則 {#statement}

- 仕様は、**正否を判定できる形**で書く。
- 曖昧な表現を減らし、受け入れ条件・制約・例を添える。
- **テスト・レビュー・観測のいずれかで照合できる**状態を保つ。
- **自己位置づけ**: [PRIN-0001](./PRIN-0001-spec-as-truth.md) が成立するには、「何が正か」を判定できなければならない。本原則はその前提を満たすための記述方針である。

## 背景 {#rationale}

「仕様が正である」と宣言しても、その仕様が曖昧なら、実装が仕様を満たしているかどうかを誰も判定できない。

判定できない仕様は、乖離の検出もレビューもできない。**そのとき PRIN-0001 は形骸化する。** 宣言は残るが、宣言を運用する手段が無い状態になる。

あいまい語を減らし、受け入れ条件・制約・例を添えることで、人間と AI の双方が、テスト・レビュー・観測のどれかで仕様と現物を照合できるようになる。

## 影響 {#implications}

- **曖昧語の削減**: 「適切に」「必要に応じて」のような語は、判定可能な条件・基準・例に置き換える。やむを得ず残す場合は、**誰がどう見て判定するのかを併記する**ことが条件である。
- **受け入れ条件・制約・例**: それぞれの振る舞いに受け入れ条件と制約を付ける。可能な範囲で、正常・異常・境界の例も添える。
- **照合手段は 3 択**: テスト(自動)・レビュー(人間)・観測(ログ・メトリクス)のいずれかである。最低 1 つで照合できるようにする。どれでも照合できない記述は、**判定可能な形に書き換える**か、**対象外である旨を明示する**。
- テンプレート・用語・フォーマットといった個別の記述ルールは、この原則の**適用**として process・specs の規約側に置く。

## 例外 {#exceptions}

- 調査中・検討中の記述、および意図的に「未定義」として残す部分は、**判定可能性の対象外である旨を明示すれば**免除される。明示が条件であり、黙って曖昧にしておくことは免除に当たらない。確定した時点で判定可能な形に更新する。
