# PRIN-0001 — 仕様を唯一の正とする(Spec as Truth)

判断の基準点を実装ではなく**合意された仕様**に固定する、このリポジトリの第一原則。

## 原則 {#statement}

- **実装が従うべき基準は、合意済みの仕様である。** 仕様が唯一の正(truth)であり、実装・テスト・文書はそこから導かれる派生物として扱う。
- **コードを先行して変えることは認めない。** 「先に実装して仕様を後追いさせる」順序を取らない。
- **仕様と実装の乖離はバグである。** 「まだ直っていない状態」ではなく「不具合」として扱う。
- **暗黙の挙動は存在してはいけない。形式化できないことは、形式化しないまま仕様に書く。** 「機械で検証できないから仕様に書かない」は、仕様の外に振る舞いを置く口実になる。検証できる形にできないなら、散文の宣言のままでよいから仕様に置く。

## 背景 {#rationale}

仕様と実装が離れていくと、品質が落ちるだけでなく、変更の履歴が読めなくなる。「なぜ今こうなっているのか」を答える相手が、仕様でもコミットログでもなく、コードそのものになってしまうからである。

この体系の前提は、**実装と検証を AI が主導する**ことにある。基準点を仕様に固定しないと、実装側の暗黙の判断と自己解釈がそのつど積み上がる。何が正かを問い直せる場所が仕様にしか無い、という状態を作ることが、その解釈の余地を閉じる唯一の手段である。

だから「正」の所在を仕様に集中させ、実装はその従属物と位置づける。これは仕様を書く手間を増やすための規律ではなく、**判断を一点に集める**ための規律である。

調査・PoC の一時コードにこの原則を緩める例外は**置かない**(2026-09-03 に撤廃)。以前の例外は、稼働中のシステムへ仕組みを部分導入しながら置き換えていた時期の名残であり、仕組みを先に作る前提ではどのコードも仕組みの範囲内で書ける。例外を残すと「PoC」として書いたコードが免除の出口を持たないまま本番へ混ざる。

形式検証を重視するあまり、「機械で検証できるもの」だけを仕様と呼んでしまう失敗がある。通知・告知・コピペ導線のように検証しにくい機能は、副作用 ID 1 本を残して実装に落ち、**どの操作で誰に何が飛ぶかがどの仕様書にも無い**という穴になった(2026-08-26 の是正 — 通知は `notification_spec` として一級市民に戻した)。検証可能性は仕様に書く条件ではない。書いたうえで、検証できる部分だけを機械に渡すのが正しい順序である。

## 影響 {#implications}

- **仕様に無い振る舞いを実装してはならない。** 実装したくなったら、先に仕様を足す。
- **コードの差分は、仕様または decision の差分と対応していなければならない。** 対応が無い差分は、仕様に書き忘れているか、書くべきでない振る舞いを足しているかのどちらかである。
- 乖離を見つけたら、その場でバグとして扱う。放置して「そのうち仕様を直す」に流さない。
- 乖離の解消手段は、**仕様を更新する**か**実装を修正する**かのどちらかである。どちらを選ぶかは必ず決める。「どちらも正しい」という決着はしない。

## 例外 {#exceptions}

- **仕様側で「未実装」と明示してある**振る舞い・項目は、実装が無くても乖離として扱わない。これは仕様が現状を正しく記述している状態であって、乖離ではない。免除は「明示してあること」が条件であり、黙って実装しないことは免除に当たらない。
- 実装上の制約で仕様がそのままでは成立しないと分かった場合は、**decision を経由して仕様を先に更新し、その後に実装する**。順序を逆にしない。
