# 機械執行ルール（enforcement）の案内

`app/` と `supabase/` に対して**機械が自動で執行しているルール**を、人間が読む形で書き起こした箱である。設定ファイルを開かずに「このリポジトリでは何が保証されているのか」を把握するための入口をここに置く。

## まずここを読む

対象範囲は `app/`（アプリ実装）と `supabase/`（DDL・RLS）に掛かっている自動執行のルール全部である。読み手が最初に開くのは次の 1 本だけでよい。

| 文書 | 内容 |
|---|---|
| [enforcement-matrix.md](./enforcement-matrix.md) | 全ルール対応表。ESLint / tsc / バンドラ / DB / CLI の**全執行者を横断した一覧**で、列は ルール・保証内容・理由・執行者の具体名・詳細へのリンク |

対応表には、ルールの行そのものに加えて次の 2 つが載る。

- **[ARCH-BE-0001](../../../../../../architecture/system/backend/ARCH-BE-0001-app-layer-structure.md) の執行対象 E1〜E11 との対応**（E1 依存方向違反の禁止 … E8 行数上限、E9 配置 ⇔ 命名の一致、E10 公開シンボルの説明、E11 層にも入口にも属さないファイルの検出）。上位の architecture が「何を執行するか」を宣言し、対応表が「どの行がそれを実装しているか」を引き受ける
- **適用範囲の除外一覧**。テスト・生成物・設定ファイルなど、執行が掛かっていない範囲を明示する

なお、日々の作業で対応表に飛ぶ経路は `CLAUDE.md` のルーティング表であり（「リンターに怒られた / ルールの意味を知りたい」の行）、この README は経路の途中に置かれた案内である。

### 設定ファイルは執行者であり、正はここの文書である

`app/eslint.config.mjs` / `app/tsconfig.json` / `supabase/migrations/` は、ここに書かれたルールを**実行する手段**であって、ルールの定義ではない。この向きを守ることから、次の 2 つが従う。

- **執行者の設定を変える変更は、必ず対応する文書の改訂を伴う。** ルールの追加・削除・緩和を設定だけで済ませてはならない。逆に、文書だけを変えて設定を放置してもならない（PRIN-0007）
- **リンター製品を差し替えるとき**（例: ESLint → oxlint）に移植すべき対象は、設定ファイルの記法ではなく**ここの各行**である。記法は道具の都合であり、保証の内容ではない

### 縛るのは境界だけであり、関数の内側は縛らない

機械執行の対象範囲は「**層の境界**」「**ファイルの配置**」「**公開シンボル**」までである。関数の内部は対象外とする。

理由は粒度ごとに違う。境界は複数人・複数層が同時に依存する場所なので、読み手の注意力ではなく機械で固定する（PRIN-0005 / PRIN-0009）。一方で内側は、1 ファイル 300 行以下という**読み切れる単位**に保っておけば読めば分かるので、そこは自由にしておく（PRIN-0002）。「全部縛る」でも「全部任せる」でもなく、境界で固めて内側を開けるのがこの箱の方針である。

## トピック別の詳細

対応表の行のうち、正誤コード例や直し方まで要るものはトピックごとに文書を分けてある。

| 文書 | 対応表の行 | 内容 |
|---|---|---|
| [layer-boundaries.md](./layer-boundaries.md) | B1〜B12 | 対象は 2 点、6 層の依存方向と層外入口の扱い。方式は allowlist（既定禁止）、許容する逆流は依存性逆転型のみ。テストの扱いも規定する |
| [server-client-separation.md](./server-client-separation.md) | S1〜S3 | サーバー専用コードのクライアント混入防止。`server-only` の宣言、`useEffect` 内 `fetch` の禁止、三重の防衛線 |
| [testing-constraints.md](./testing-constraints.md) | T1・T2 | モジュール差し替え（`vi.mock` / `jest.mock`）の禁止と、それが成立する前提 |
| [type-strictness.md](./type-strictness.md) | Y1〜Y13 | 規定は 3 点、`any` 不可・Promise の取りこぼし不可・tsc の厳格オプション群を適用 |
| [naming-and-placement.md](./naming-and-placement.md) | P1〜P4 | ドメインイベント ID から実装パスと export 名が一意に確定すること |
| [public-symbol-docs.md](./public-symbol-docs.md) | J1〜J4 | export されたシンボル（関数・クラス・型）への JSDoc を必須にする |
| [file-size.md](./file-size.md) | F1・F2 | 300 行を超えるファイルの宣言（信号であり上限ではない）と、超えたときの層ごとの直し方 |
| [database-guards.md](./database-guards.md) | D1〜D18 | DB 側の防衛線（権限・RLS・CHECK・トリガー・書き込み RPC）。コードがバグっても守られる層と、その既知の限界 |

**トピック別文書を持たない行は、対応表の中に直接書かれている。** React / Next.js の既定セット（N 群）、入力スキーマの導出（I 群）、読み取り経路（Q 群）、画面の testid（U 群）、拒否の語彙（R 群）、構造化ログ（L 群）、視覚層（G 群）、コマンド検査（C 群）、文書の整合（M 群）がそれに当たる。この表に文書が無いことは「執行されていない」ことを意味しない。全件を知りたいときは常に対応表を見る。

## この配下に書くこと / 書かないこと

**書くこと**: 機械が執行しているルールの**保証内容・理由・執行者の具体名・正誤コード例**。

**書かないこと**は 3 つあり、いずれも行き先が決まっている。

| 書かないもの | 行き先 | 理由 |
|---|---|---|
| 機械執行されていない実装のきまり | [server-actions.md](../server-actions.md) や [testing/unit.md](../testing/unit.md) / [testing/integration.md](../testing/integration.md) などの規約本体 | この箱の読み手は「機械が止めてくれる範囲」を知りに来る。止まらないものが混ざると、その境目が読めなくなる |
| 層の構造・責務の定義 | [ARCH-BE-0001](../../../../../../architecture/system/backend/ARCH-BE-0001-app-layer-structure.md) | 構造の正は architecture にある。ここは「その構造をどう執行しているか」だけを書く |
| `legacy/spec-tools/` 側のツールコードの規約 | [scripts-code-quality.md](../../../../../common/tooling/standards/scripts-code-quality.md) | 対象が別（この箱は `app/` と `supabase/`）。方針が共通の項目（`any` 禁止・300 行制限）は**参照で済ませ、転記しない**。同じ規範を 2 か所に書くと、片方だけが古くなる（PRIN-0007） |

## 新しいルールを増やすとき

次の 4 手順を、**この順序で**行う。

1. **根拠を確認する。** そのルールがどの原則（PRIN）・どの architecture（ARCH）・どの決定（ADR）から出てくるかを先に押さえる。**根拠が無いルールは追加しない**
2. **[enforcement-matrix.md](./enforcement-matrix.md) に行を追加する。** ここで門番が 1 つ働く —— **「なぜ」を 1 文で書けないルールは、まだ言語化できていない**。言語化未了のものは却下し、書けるようになるまで待つ。理由の書けないルールは、後から誰も緩和の可否を判断できない
3. **トピック別文書に正誤コード例を足す。** 既存のトピックに収まらない場合に限って新規文書を作り、同階層の [template.md](./template.md) に従う。この配下の雛形が親の [conventions/template.md](../template.md) と違うのは 2 点で、**見出しに番号を振らない**ことと、**トピックによって要不要が変わる節に「（任意）」を付ける**ことである（理由は雛形の冒頭にある）
4. **最後に執行者（設定・DDL）を変更する。**

**順序を逆にしない。文書が先、設定が後である。** 設定を先に書くと、そのルールは「リンターがそう言うから」という理由で存在することになり、理由が誰にも読めないまま残る。読めない制約は、次に困った人が黙って外す。
