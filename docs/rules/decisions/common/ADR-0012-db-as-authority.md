# ADR-0012: DB を権威にする — 規則の執行点は RPC に生成し、TS の判定は同じ仕様から生成した先読みにする

## Status

accepted (2026-09-11)

---

## Context

### 背景

束 ⑯(ADR-0011)で、保存点を「既存の操作 RPC を順に呼ぶ複合 RPC」として生成した。その検収でユーザーが指摘した継ぎ目がこの決定の発端である: **複合 RPC の経路は、アプリコード(operation)にしか無い挙動を通らない。** 具体的には 3 つ。

1. `enforced_by: application` の不変条件は operation の `persist` が手書きで判定している。複合 RPC はそれを知らない(hooks を要求する範囲を狭めたため、漏れたものは黙って通る)。
2. operation の `loadFacts` / `persist` に、仕様に無い挙動が手書きで置かれうる(束 ⑯e で「招待の採番」「リマインド時刻の逆算」の 2 件を DB 側へ移した。残りが無いことは機械が確かめていない)。
3. ガードの評価に使う事実の組み立てが二重実装になっている(operation の手書き `guardEnv` と、生成した実行計画の `guardFacts`)。両者が同じ事実を見ている保証が無い。

根本は 1 つで、**同じ規則を評価する場所が 2 つあり、片方(operation)が仕様から導出されていない**ことである。

### 前提の変更

ユーザーの方針(2026-09-11): 「急いではいない。このフレームワークを 5 年 10 年と複数システムに当てはめていくための最初の段階であり、先のコストを消すために今コストを払うのはよい。重いかどうかを判断のマイナスに入れなくてよい。」この前提では、「当座の検査で塞ぐ」より「継ぎ目そのものを無くす」のが正しい。

---

## Alternatives Considered

1. **アプリ側で operation を順に呼び、トランザクションだけを束ねる** — app から Postgres に直結する接続(BEGIN … COMMIT)が要る。API スキーマ・RLS・service_role の設計と「書き込みは RPC 専用」の保証(guarantee `writes_only_via_rpc`)を迂回し、serverless の接続管理を複数システムに配るたびに背負う。app が tx の権威になるので、将来の別クライアント(ジョブ・管理スクリプト・モバイル)は app を経由しないと守られない。**採らない。**
2. **いまの形(判定は TS、書き込みは SQL)を保ち、継ぎ目を検査で塞ぐ** — hooks の漏れを warning にする・guardEnv と guardFacts の変数集合を突合する・operation の手書きを lint で縛る。どれも「二重実装がある」事実は変えず、規則を足すたびに検査も足す運用が続く。**当座の手当てとしてのみ採る。**
3. **DB を権威にし、TS の判定を同じ仕様からの生成物にする**(採用)— 規則(ガード・ロールの束縛・不変条件)の執行点を RPC の本文に**生成**する。RPC 単体で仕様の全部を守るので、どの経路からも迂回できない。TS の engine は同じ仕様から生成した**先読み**(人に読める拒否理由を、DB に行く前に速く返す役)になり、権威ではなくなる。2 つの評価器が同じ答えを返すことは、仕様から生成した突合テストで証明する。

---

## Decision

### 1. 権威は DB

書き込みの規則(権限・状態機械・ガード・不変条件)は、**RPC の本文が執行する**。RPC は仕様から生成する(決定性の格上げ ⑤)。手書きの RPC は、仕様の 5 形に乗らない合成だけに限る(現状の `erase_patron` 等)。

- ガード式は決定可能な制限文法(V9)なので SQL の述語に落とす。
- ロールの束縛(`{entity}.{field} == actor.id`)は行の列と `p_actor_id` の比較に落とす。セッション由来のグローバルロール(`kind` を持つもの)は、app が解決して `p_actor_roles text[]` で渡す(service_role でしか実行できないので信頼できる)。行の属性が根拠のロール(`staff`)は、その根拠を仕様に宣言してから(BACKLOG)。
- 不変条件は DB のコミット時評価(deferrable constraint trigger。ADR-0011 の束 ⑯c-1c で一般則化)へ寄せる。集計を伴うものも SQL で数える。SQL に置けないもの(外部呼び出しを伴う等)だけを `enforced_by: application` として**宣言された例外**にし、その一覧はハンドブックに出す。

### 2. TS の判定は同じ仕様からの生成物

`domain/engine` と生成表(権限・遷移・ガード)はそのまま残すが、役割は「先読み」になる。operation は仕様から**生成**する(決定性の格上げ ④)。`guardEnv` / `loadFacts` / `persist` の手書きを消し、何を読み・何を書くかは仕様と実行計画(束 ⑯c-2 の `usecase-plans.ts` と同じ導出)から決める。個別の操作と保存点は同じ導出器を使う。

### 3. 一致の証明は生成する

仕様から「状態 × ロール × 入力」を列挙(または性質ベースでサンプル)し、TS の判定と SQL の判定(RPC を実 DB で叩いた結果)が一致することを突合するテストを**生成**する。既存の「期待表 ⇔ pg_catalog の閉世界突合」を、判定の意味にまで広げる。

### 4. 順序

④(operation の生成)→ ⑤(RPC 本文の生成。ガードとロールを含む)→ 不変条件を DB へ → 一致の証明の生成。④ が先なのは、⑤ の生成器は「operation が何を読み何を書くか」が仕様から一意に決まって初めて書けるから。各段は独立にコミットでき、途中で止まっても手書きが減っているだけで損はない。

### 5. 名前

旧 `src/interactor` は Composition Root(配線だけ)であり、Clean Architecture の interactor ではない。複数システムに配る前に `src/composition` へ改名する(④ と同じ束で。束 ⑰-2 で実施済み)。`operation`(1 操作)と `usecase`(目的の単位。ADR-0011)は変えない。ハンドブックの用語集に 3 語の対応表を出す。

### 6. 変えないもの

- 2 実例ルール(dsl-extension-triage)。予算があっても投機的な抽象は腐る。抽象を買う条件は変えず、買うと決めたら徹底する。
- 「仕様が正」「免除は仕様側の理由つき宣言だけ」「軸は仕組み・語はアプリ」。

---

## Implementation

- 当座(この決定の前に済ませる小さな手当て): hooks の要求範囲を狭めた判断を warning で見えるようにする / operation の `guardEnv` の変数集合と実行計画の `guardFacts` の突合(ズレが 0 であることを実測してから ④ に進む)。
- 束の割り当て: ④ = BACKLOG「決定性の格上げ ④ Server Action の生成」を operation まで広げる / ⑤ = 同「⑤ RPC 5 形の SQL 生成」にガードとロールの生成を足す / 不変条件の DB 化 / 一致の証明の生成器。順に設計を凍結してビルダーに渡す。
- 完了の定義: `app/src/operation/**` に手書きが**宣言された例外**(hooks / `computes` の純関数 / `runner: manual` の操作 / `scans:` の経路)以外に無い / `supabase/migrations` の 5 形 RPC が全部生成物 / 一致の証明が CI で緑。
  - ④ は束 ⑰-3 で完了した(操作の実装・Server Action・Composition Root・ユニットテストが生成物になり、手書きの operation 56 本とその単体テストが消えた)。閉世界は `app/src/operation/__tests__/structure/` が仕様から母集合を作って見る。
  - ⑤ は 3 束で進めた —— ⑳-1(ガード式とロールの SQL 翻訳器 + 差分テスト)・⑳-2(定型 5 形の本文の
    生成。意味を変えない段)・⑳-3(`by` とガードを本文へ。引数 `p_actor_roles` と拒否の 3 分類)。
    続けて ⑳-4a(RLS の `USING` 句と補助関数の生成 + `pg_policies` との意味の突合)・⑳-4b(RLS の
    挙動テストの生成。オラクルは TS の別写像)・⑳-5a / 5a2(engine ⇔ RPC の一致の証明を単発 40 操作
    3,969 通り + 保存点 4 本 276 通りで全列挙生成。食い違い 0)・⑳-5b(結果表 44 本をハンドブックへ。
    同じ列挙・同じオラクル)・⑳-5c(充足性の判定を Z3 に。生成器の変異テストで「どの変異をどの検査が
    捕るか」の目録を生成)で **⑤ は完了した(2026-09-13)**。宣言された例外は `handwritten:` 2 本・
    `shape: composite` 14 本・`runner: manual` 13 操作で、執行点を持たない書き込み規則は A18 が報告する。
  - **表示規則を含む写しの値も DB が決めてよい**(2026-09-11 の裁定。migration `20260828000029` の「連結は表示の規則なので SQL に置くとユニットテストで縛れない」を覆した)。縛りはユニットテストから統合テスト(`data-table-parity` / `rpc-parity`)へ移る。

---

## Consequences

### 良い点

- 迂回できる経路が無くなる。複合 RPC・将来の別クライアント・管理スクリプトのどれからでも、規則は DB が守る。
- 二重実装が「同じ仕様からの 2 つの生成物 + 生成した一致の証明」になる。規則を足すときに検査を足す運用が要らない。
- operation の手書きが消えるので、「下位モデルに任せてもやることが一意に定まる」(ユーザー方針)に一段近づく。

### 代償

- ガードとロールの SQL 生成器・operation の生成器・一致の証明の生成器を作る(束 3〜4 個)。
- RPC の引数が増える(`p_actor_roles`)。既存 RPC の署名変更は drop → create の migration。
- SQL に置けない不変条件は「宣言された例外」として残る(一覧が要る)。
