# 参照の辿り方 — 「なぜこのルールなのか」を上へ遡る

作業中に「なぜこのルールなのか」を知りたくなったとき、**フロントマターの参照をどう遡るか**を書いたガイドである。

**この文書は入口ではない。** 各ディレクトリの入口は README.md ひとつであり([ADR-0005](../../decisions/common/ADR-0005-single-entry-point.md))、責務・構成・次に読む場所の案内はそちらが持つ。ここが担当するのは、その README から先 —— 参照を辿り始めてからの話である。

作業そのものの入口はさらに手前にある。**CLAUDE.md のルーティング表**が「やること → 読む正典」の対応を持っており、通常はそこから目的の文書へ直接飛ぶ。このガイドを開くのは、飛んだ先のルールが自明でなかったときである。

## 階層構造の理解

各層の入口は次のとおり。

| 層 | 入口 | 役割 | 抽象度 |
|---|---|---|---|
| meta | [../README.md](../README.md) | 文書体系そのもののルール | — |
| principles | [../../principles/README.md](../../principles/README.md) | 普遍的な原則 | 最も抽象的 |
| architecture | [../../architecture/README.md](../../architecture/README.md) | システム設計・構造 | 中程度 |
| process | [../../process/README.md](../../process/README.md) | 実装・運用の手順と規約 | 具体的 |
| decisions | [../../decisions/README.md](../../decisions/README.md) | 意思決定の記録 | 中〜具体的 |
| specs | `docs/specs/`(製品ごとの仕様の木。雛形は `template.*`) | 実装仕様 | 最も具体的 |

参照の向きは**下位から上位へ**の一方向である。

```text
specs ──┐
process ──┐
architecture ──┐
principles ←─ norms で「従うべき規範」を指す

decisions ←─ decisions で「なぜそうしたか」を指す(全層から参照してよい)
```

**上位ほど抽象的・本質的、下位ほど具体的・実装的である。** したがって `norms` を辿ると必ず抽象度が上がり、いずれ原則に行き着いて止まる。循環しないことは M6 が保証している。

なおドメイン知識層(W。用語・不変条件の意味・業務例)は rules の外にある。ドメインの形式定義は `docs/specs/domain/` 側にあり、W の住所も `docs/specs/` の隣である。

## フロントマター参照キーの意味

| キー | 何を指すか | 判断基準 |
|---|---|---|
| `norms` | 従うべき規範・ルール・契約 | 「これに違反してよいか?」→ NO なら `norms` |
| `decisions` | どの ADR に基づくか | 「なぜこうなっているのか?」と聞かれたときに開く文書か |
| `definitions` | 正として参照している定義の出典 | 「定義が衝突したらどれを正とするか?」 |

キーの定義そのものは [reference_policy.md](./reference_policy.md) が正である。

## 参照の辿り方

**辿るトリガーは 2 つある。** 背景や理由を知りたくなったとき、そしてルールが自明でないと感じたときである。

- 自明なルール → 読まなくてよい
- 自明でないルール → 参照を辿って背景を理解すべきである

手順は次のとおり。

1. **現在の文書のフロントマターを確認する**
2. **目的に応じて参照先を選ぶ**
   - `norms` → **上位の階層**へ。得られるのは「なぜこのルールが必要か」「守るべき原則は何か」
   - `decisions` → **意思決定の記録(ADR)**へ。得られるのは「なぜこの設計にしたか」「トレードオフの理由」
   - `definitions` → **定義の出典**へ。得られるのは「この用語・概念の正確な定義」「何が正か」
3. **参照先の文書を読む**
4. **さらに必要なら、参照先のフロントマターから繰り返す。** `norms` ならさらに上位へ、`decisions` なら関連する他の決定へ、`definitions` なら定義の元へ

## 具体例

### 例1: 規約の手順の背景を理解する

[server-actions.md](../../process/backend/system/standards/conventions/server-actions.md) が「Server Action は 4 手順の定型で書く」と決めている。なぜその形なのかを知りたい。

1. server-actions.md の `norms` に `ARCH-BE-0013` がある
2. [ARCH-BE-0013](../../architecture/system/backend/ARCH-BE-0013-server-action-structure.md) を読むと、Server Action の構造と責務の分割が書いてある
3. ARCH-BE-0013 の `norms` に `PRIN-0001` がある
4. [PRIN-0001](../../principles/common/PRIN-0001-spec-as-truth.md)(仕様を唯一の正とする)まで遡ると、定型が「実装が仕様から導かれる形を保つため」のものだと分かる

**3 段で原則に着く。** これが典型の長さである。

### 例2: テスト規約の背景を理解する

[testing/unit.md](../../process/backend/system/standards/conventions/testing/unit.md) が「テストに `@spec` / `@tc` の注釈を必須にする」と決めている。

1. unit.md の `norms` に `PRIN-0008` がある
2. [PRIN-0008](../../principles/common/PRIN-0008-traceability.md)(追跡可能性)を読むと、仕様とテストの対応が辿れるべきだと書いてある
3. 同じ `norms` の `ARCH-BE-0001` を読むと、どの層で何をテストするかの分担が分かる

注釈は書式の面倒ではなく、**仕様⇔テストのトレース(A 群)が成立するための条件**だと理解できる。

### 例3: レビュー時に設計の妥当性を判断する

実装が規約に沿っているかだけを見ると、規約の隙間を通った設計を見落とす。

1. 対象の規約を読む
2. その `norms` を確認する
3. 上位の architecture と principle まで遡り、**設計の意図**を掴む
4. 実装がその意図に沿っているかで判断する

## いつ参照を辿るべきか

**辿るべきとき**

- ルールの背景・理由を知りたいとき
- ルールが自明でないと感じたとき
- 複数の選択肢があり、どれが正しいかを判断する必要があるとき
- レビューで設計の妥当性を判断するとき
- 実装中にトレードオフを判断するとき

**辿らなくてよいとき**

- ルールが自明で、背景を知らなくても問題ないとき
- 単純な作業で、上位の原則を理解しなくても実行できるとき

**この線引きは意図的である。** 全ての文書を毎回読むのはコンテキストの浪費であり、判断の質はむしろ落ちる。辿るのは、迷ったときと、迷うべきときだけでよい。

## まとめ（AI向け実行ルール）

0. **層の全体像が必要なときは、まず各層の README.md を読む**(入口は README ひとつ)
1. **背景を知りたいとき・自明でないと感じたときに、フロントマターの参照を辿る**
2. **キーの違いを理解する** —— `norms` は守るべきもの、`decisions` はなぜそうしたか、`definitions` はどれが正か
3. **参照先の性質を理解する** —— `norms` の先は上位で抽象的、`decisions` の先は意思決定の背景とトレードオフ、`definitions` の先は用語・概念の正確な定義
4. **実装やレビューで品質を高めるために参照先を理解する。** 辿ること自体が目的ではない
