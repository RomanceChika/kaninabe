# ユニットテスト

`app/` の内側の層（`src/domain` / `src/operation`）と実行時パッケージ（`framework/runtime/src`）に対するテストの規約。**「unit 100%」は仕様網羅率であって行カバレッジではない**という定義をここで固定する。

## 1. Overview

- ランナーは **vitest**。対象は `src/domain`（純粋関数・エンジン・生成物を使う判定）と `src/operation`（IF を DI で受ける業務手順）。
- **カバレッジの定義は「仕様網羅」**: ドメイン仕様（状態 × イベント × ロール、ガード境界、不変条件）と `action_spec` の `test_cases` に挙がった仕様 ID が、すべてテストに対応していること。
- ユニットテストは**アーキテクチャの診断装置**でもある。内側の層で 100% が達成できない場合、テストの不足ではなく**依存方向が壊れている**と読む（ARCH-BE-0001）。

## 2. Scope

**含む**

- `src/domain` の純粋関数、状態機械エンジン、リトライ方針などの判定ロジック
- `src/operation` の業務手順（Repository IF・外部連携 IF をモック注入）
- 生成物（zod スキーマ・遷移テーブル）を入力とする判定の確認

**含まない**

- DB・Supabase・外部サービスの実体との結合（→ [integration.md](./integration.md)）
- Server Action の境界（→ integration）
- UI コンポーネントの操作・見た目（クリック・入力・スタイル）

**同じコマンド（`npm run test`）で走るが、別の規約に属するもの**

- 画面テスト（screenTest。`src/app/__screens__/`）→ [screen-test.md](../../../../../frontend/system/standards/conventions/screen-test.md)。RSC を「依存を引数で受ける関数」として呼ぶ形は同じだが、守っている対象が仕様の層ごと違う（画面の配線であってドメインの判断ではない）

## 3. 実行方法

**基本方針:** テストの実行は **プロジェクト定義のタスクランナーのコマンドをそのまま使う**。個別のテストランナーコマンドは、タスクランナーで代替できない場合以外は使わない。

- 使用するコマンド: `npm run test`（`app/` パッケージ）
- 実行場所: `app/`
- 注意事項: 外部依存（DB・ネットワーク）を一切必要としない。必要になった時点で、それは統合テストの対象である。

## 4. 配置・命名

### 操作のユニットテストは生成物である（束 ⑰-3）

**計画で走る操作のテストは手で書かない。** `npm run generate` が
`app/src/operation/__tests__/generated/{集約}/{イベント}.test.ts` を書き、A7 が仕様から導く意味クラス
（成功・ロールごと / ガード不成立 / 遷移元でない / 権限なし / 不変条件違反 / 競合 / 対象なし）の場面を
1 本ずつ置く。場面の値（どの状態で・どの列が誰を指して・RPC が何を返すか）も仕様から解いたもので、
`action_spec` の `test_cases` も**その名前を指す生成ブロック**である。

- **「対象なし」は A7 の要求を待たずに置く**（束 ⑰-3b）。A7 がこれを要求するのは削除だけだが、
  「見えない」と「権限が無い」を区別しないのは権限に直結する設計判断であり、行を読む計画なら
  場面はゼロ費用で作れる。行を 1 つも読まない計画（作成など）にだけ出ない。
- fake の `FactReader` / `RpcCaller` は共有のハーネス `__tests__/plan-harness.ts` が作る。行は
  **表と id の組**で引くので、「入力が指す行ではなく実行者の行を読む」取り違えはそこで落ちる。
- 成功と「RPC の結末だけが違う」場面は、**呼び出した関数の名前だけでなく名前つき引数まで**確かめる
  （束 ⑰-3b）。値の出どころは場面そのもの（実行者・行に載せた状態・作った入力）であり、
  計画の写しではない —— 値を別の引数に載せる配線の取り違えがそこで落ちる。
- **不変条件違反の場面が載せるのは、RPC が実際に返しうる不変条件だけ**である（DB 制約・トリガ。
  `enforced_by: application` の ID は載せない）。該当が無ければ場面は作られず、A7 が
  「不変条件の宣言が足りない」と鳴る。
- 加えて操作ごとに**性質**が 1 本出る（`__tests__/plan-property.ts`。fast-check）。判断に効く列を
- 無作為の検査(fast-check とハンドブックの無害化の検査)の種は**既定で固定**で、CI と pre-commit は固定のまま回る。取り込みの定型だけが環境変数 `FUZZ_SEED` で毎回新しい種を渡して出力する。夜間の workflow は作らない。赤になった種は直して固定の反例集(`legacy/spec-tools/__tests__/helpers/book-fuzz.ts` の `COUNTEREXAMPLE_SEEDS`。fast-check はそのテストの反例)へ足す。
  ランダムに振り、「計画の判定 = エンジンの判定」が必ず一致することを確かめる。反例は縮小して出る。
- 手で書くのは**宣言された例外**のテストだけである（`runner: manual` の操作・`scans:` の経路・
  DSL の外に置いた純関数）。生成ブロックの外に `type: unit` として宣言する。

### 手書きのテストの置き場

- テストは対象と同じ層の `__tests__/` に、`src/` のパス構造を**ミラーして**置く。
  - `app/src/operation/loan/check_out.ts` → `app/src/operation/__tests__/loan/check_out.test.ts`
- ファイル名は `{対象}.test.ts`。
- テスト名は**日本語で、仕様の文をそのまま使う**（例: `受取待ちの貸出を受け取れる`）。`action_spec` の `test_cases[].implementation` が `{パス}::{テスト名}` で参照するため、テスト名は仕様側の宣言と一字一句一致させる。
- 仕様との対応は各テストに `// @tc TC-LOAN-CHECK_OUT-001` を書く（[action-spec-writing.md](../../../../specification/standards/action-spec-writing.md)）。

## 5. 記述ルール

- **依存は引数で注入する**。operation のテストは、Repository IF・外部連携 IF のテスト用実装（インメモリ or スタブ）を引数で渡して呼ぶ。
- **モックは IF に対してのみ作る**。テスト用実装は `__tests__/fakes/` に置き、複数のテストで共有してよい。
- **現在時刻・乱数・ID 生成は引数で受ける**。テスト内で固定値を渡す。
- **仕様から導出する**。テストは仕様（状態機械・ガード・不変条件・`action_spec`）から導き、実装を読んで書かない。実装を見てから書いたテストは、実装のバグをそのまま追認する。
- **1 テスト 1 仕様**。1 つのテストに複数の仕様 ID を詰め込まない（`spec_ids` が複数になるのは、1 つの振る舞いが複数の仕様に同時に対応する場合に限る）。
- 境界値（ガードの `>=` / `>`、`max_length` の前後）は独立したテストにする。

## 6. Constraints

- **してはいけないこと:** モジュール差し替え（`vi.mock` / `vi.doMock` 等）で依存を置き換える。注入点は IF と DI に限る（ARCH-BE-0001 の E6。リンターで機械執行する）。
- **してはいけないこと:** ユニットテストから DB・ネットワーク・ファイルシステムに触れる。
- **してはいけないこと:** 行カバレッジの数値を目標にする。目標は仕様網羅であり、行カバレッジは参考値としてすら扱わない。
- **してはいけないこと:** 生成物（`src/domain/generated/`）そのものの内容をテストする。生成物の正しさは生成器のテストと `generate:check` が担保する（ADR-0006）。
- **してはいけないこと:** テストのためだけに本体へフックを足す（テスト用の分岐・環境変数による挙動変更）。

## 7. Testing Rules

- **domain**: 仕様網羅 100%。エンジンは全機能が依存する単一障害点であり、状態 × イベント × ロール × ガードの全組み合わせに対する確認を妥協しない。
- **operation**: 仕様網羅 100%。IF モック注入で、成功・3 分類の拒否（ガード不成立 / 権限なし / 不変条件違反）・`effects` の積み込みを確認する。**仕様に対応するテストは操作ごとに書く**（`action_spec` の `test_cases` は操作に紐づくため、ここは定型化で減らない）。
- **4 形の定型（`src/operation/_template/`）**: 操作とは別に、**合成の表**（生成物ではなくテスト内にリテラル構築した `MachineTable` / `CreateTable` 等）で定型自身の約束を確かめる（`src/operation/__tests__/_template/`。`domain/__tests__/engine/machine.test.ts` と同じ位置づけ）。ここで確かめるのは 4 手順の順序・②の照会を**全項目に**適用すること（バルク形）・拒否の写像・ドメインイベントIDの導出であって、ドメインの意味ではない。
- **カバレッジが緩んだことはテストを削る根拠にならない**: 結末の分岐が定型に集まったので、行カバレッジは「同じ形の操作すべてで全結末を書く」ことを要求しなくなった。**テスト十分性の正は仕様網羅（A6 / A7）であり、行カバレッジではない**（6節）。なお関数カバレッジは下限を残す — 各操作の設定コールバック（`loadFacts` / `actorRoles` / `guardEnv` / `persist` / `toResult`）は 1 つでも呼ばれなければ未カバーとして落ちる。
- **infrastructure / app**: ユニットテストの対象外。実体との結合が本質であるため統合テストで扱う。
- **実行時パッケージ（`@kaninabe/runtime`）**: 同じ 100% の閾値が掛かる（[ADR-0013](../../../../../../decisions/common/ADR-0013-framework-runtime-package.md)）。評価器は束 ①-b で `app/src/domain/engine/` からパッケージへ出たが、**数字は移す前と同じ**である。**実行の根はリポジトリルート**（`vitest.config.mts` の projects）であり、閾値の宣言もそこ 1 か所が持つ —— 根を `app/` に置くと v8 プロバイダがパッケージを測らず、「テストは走るのに閾値が掛からない」状態になる（実測）。テストの置き場は動かさない: 製品のテストが製品の語でパッケージのコードを実行するのは今までと同じ形であり、**パッケージ単体で製品なしに実行できるテストを揃えるのは公開パッケージにする段の受け入れ条件**である。
- **`src/proxy.ts`（層に属さないフレームワーク入口）**: 同じ理由でユニットテストの対象外（カバレッジ計測からも除外する。リポジトリルートの `vitest.config.mts`）。中身は infrastructure への委譲だけで、リクエストと cookie という実体が無いと何も確かめられない。保証は手動確認と、前段を通した実挙動（セッション更新）で置く。
- **達成できないときの読み方**: `src/domain` / `src/operation` のテストに DB やフレームワークが必要になったら、それは依存方向の違反である。テストを工夫するのではなく、層の分割を直す。
