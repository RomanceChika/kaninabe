# {id} — {短い名前}

H1 は `# {id} — {短い名前}` の形にする。

必須の節は **目的 / 概要 / スコープ / 構成** の 4 つである。見出しの末尾に「（任意）」が付いた節は、
それぞれに書いてある**【書く条件】を満たすときだけ**書く。条件を満たさなければ節ごと落とす。
節を埋めるために内容を捏造させないための仕掛けであり、空の節を残すより落とすほうが正しい。

節の区切りには `---` の水平線を使う。

---

## 目的

**1〜3 行**で「何のために存在するか」を書く。背景説明ではなく**存在理由**を書く節である。
「〜という事故を防ぐため」「〜を 1 か所に集めるため」のように、無くなったら何が壊れるかが読める形にする。

---

## 概要

**結論を先に出す。** どういう構造・方針を取るのかを簡潔に述べる。
複数文になるなら改行や箇条書きで読みやすくする。ここだけ読んで構造の輪郭が掴めることを狙う。

---

## スコープ

**対象** と **対象外** の 2 項目を書く。

- **対象**: この文書が縛る範囲
- **対象外**: この文書が縛らない範囲。誤解を防ぐために明示する

対象外を省くと「書いていないから自由」と「書いていないが縛られている」の区別が付かなくなる。

---

## 構成

主要な要素(コンポーネント / レイヤー / 役割)とその責務を並べる。

- 記法は `- {要素}: {責務}` の形
- 粒度は「**実装場所を特定できる**」程度。それより細かいものは process 側へ寄せる

---

## フロー（任意）

**【書く条件】** 処理の流れを追わないと理解できない場合、または順序が重要な場合(認証・外部連携・非同期処理など)。

箇条書きか図で書く。単に「A を呼んで B を呼ぶ」だけなら構成節で足りるので、この節は作らない。

---

## 制約・不変条件（任意）

**【書く条件】** 破るとバグや事故になるルールがある場合。

MUST / MUST NOT / SHOULD の 3 段で書く。

| 段 | 意味 |
|---|---|
| MUST | 絶対に守る |
| MUST NOT | 絶対にやらない |
| SHOULD | 原則守る(外れるなら理由を書く) |

単なる実装方針は制約ではない。process 側の規約へ寄せる。

---

## 実装配置（任意）

**【書く条件】** 実装場所が分散している場合、誤解されやすい場合、または AI に「触る場所」を明示したい場合。

`path:` と `pattern:` を記載し、どのディレクトリのどの命名のファイルが対象かを一意にする。

---

## 境界・レイヤーに関する追加情報（任意）

**【書く条件】** その文書の主題が「境界・層・責務分離」そのものである場合に限る。
境界を**定義する**文書だけが書く節であり、既にある境界を**前提として使うだけ**なら書かない。

H3 で次の 3 つを立てる。

- **置いてよいもの / 置いてはいけないもの**(OK / NG)
- **依存方向**(依存してよい / 依存してはいけない)
- **入出力(境界面)**(exports / imports)

---

## 取得方針（任意）

**【書く条件】** Infrastructure 層や読み取り経路など、DB からの取得戦略(単純な SELECT か、JOIN・集計か)を明示する必要がある場合。
