# migration の規約(採番・不変則)

`supabase/migrations/*.sql` のファイル名の採番と、書いたあとの扱い(直してよいか)を固定する規約。
このリポジトリは複数のビルダー(人間・エージェント)が同じ共有ワークツリーで並行に作業するため、
migration は**衝突しやすい資源**である — 実際に採番の衝突(欠番)とコメント修正の可否判断が
それぞれ発生した(NOTES.md 2026-08-13 / 2026-08-19)。

## 1. 目的・スコープ

- **目的:** ①ファイル名の採番方式を 1 つに固定し、並行作業での衝突を「起きたら直す」ではなく
  「起きにくくする・起きても迷わない」形にする。②書いたあとの migration を直してよい条件を
  明文化し、「コメントだけなら直してよいか」を毎回考え直さずに済むようにする。
- **スコープ:** `supabase/migrations/` に置くファイルの命名と改変の可否。DDL の書き方そのもの
  (RLS・トリガー・RPC の中身)は対象外 — それぞれの規約([data_table テンプレート](../../../../../../specs/backend/data/template.data_table.md)・
  [ARCH-BE-0013](../../../../../architecture/system/backend/ARCH-BE-0013-server-action-structure.md))が持つ。

## 2. ルール

### 採番

#### 形式

`{YYYYMMDD}{6桁連番}_{説明}.sql`(例: `20260904000042_update_patron_chat_user_id.sql`)。

- **すべきこと:** 6 桁連番は**リポジトリ全体を通した 1 本のグローバルな連番**にする。
  **日付が変わってもリセットしない。** `supabase/migrations/` の全ファイルの中で連番部分が
  最大のものを見つけ、その次の番号を使う(`ls supabase/migrations/ | tail -1` で足りる)。
  実例: `20260828000029` の次は `20260829000030`(日付が変わっても連番は 29 → 30 のまま)。
- **してはいけないこと:** 連番を「その日の何本目か」で数える(`20260904000001` のように日ごとに
  1 から振り直す)。過去に 1 度、時刻ベースの採番(`20260809120001` 形式)が混入した実績があり、
  読み手が「これは通し番号か時刻か」を毎回判定する負荷になった。**通し番号 1 本に統一する。**
- **日付部分(先頭 8 桁)は「実際にその日書いたか」の記録であり、適用順序を決めるキーではない。**
  適用順序を決めるのは連番のほうである(Supabase CLI はファイル名の**辞書順**で適用するため、
  結果として両方が単調増加でなければならない — 日付を今日にして連番だけ古い値に戻す、逆に
  連番だけ進めて日付を古いままにする、のどちらも壊れる)。

#### 並行作業での予約

- **すべきこと:** 番号を決めたら、**本文を書き終える前に空(またはヘッダコメントだけ)のファイルを
  その場でリポジトリに作る**。同じ共有ワークツリーで他のビルダーが同時に次の番号を数えている
  可能性があるため、「次の番号を計算する」と「その番号のファイルを作る」の間を空けない。
  ファイルが存在すれば、後から数えたビルダーは自然に 1 つ先の番号を拾う。
- **すべきこと:** 番号を決める直前に `ls supabase/migrations/ | tail -3` で最新を確認する
  (キャッシュした一覧を使い回さない — 直前に他のビルダーが 1 本足しているかもしれない)。
- **衝突したら(2 人が同じ番号を同時に作った場合):** 先にコミットされた側がその番号を持つ。
  後にコミットしようとした側は、コンフリクトした時点で**採番をやり直す**(自分のファイルを
  次の空き番号にリネームする)。**内容を調整して両方を残す(番号を分けずに 1 本にまとめる)は
  しない** — 2 つの独立した変更を 1 つの migration に混ぜると、どちらか一方だけを打ち消したい
  ときに切り離せなくなる。
- 欠番(例: `…010` の次が `…012`)が過去に 1 件残っている(2026-08-13 前後)。**欠番は埋めない。**
  一度捨てた番号を後から別の内容で使うと、「その番号は何を指すか」が履歴の時点によって変わる
  ことになり、②の不変則(下記)と矛盾する。欠番は事故の記録として残してよい。

### 不変則(書いたあとに直してよいか)

migration は**追記専用の歴史**として扱う。これは監査ログ(`domain_events`)を追記専用にした
判断(製品の `domain_events` を作る migration)・
RPC 本文の突合(`rpc-parity`)を「生成 SQL で置き換えず、追記専用の歴史として実 DB と突き合わせる」
方式にした判断(NOTES.md 2026-08-27 E3-gen)と同じ考え方を、ファイルそのものに広げたものである
(**この引用は歴史である** —— 定型 5 形の本文はいまは生成物であり、下の §生成 migration が
「ファイル名を仕様に宣言させる」ことで追記専用と両立させている。ファイルそのものを追記専用に
扱うというこの節の判断は変わっていない)。

- **してはいけないこと: コミット済みの migration ファイルの本文を書き換える。** 値・条件式は
  もちろん、**コメントだけの修正も含む**。理由は 2 つ:
  1. Supabase CLI はローカルで一度適用した migration の内容を(チェックサム相当で)追跡しており、
     適用後にファイルを書き換えると `supabase migration list` / `db push` が「ローカルとリモートが
     食い違っている」型の警告を出す(他のビルダーが既に自分の環境で適用していれば、そのビルダーの
     環境でも同じ警告が出る)。コメントだけの変更でも file 全体のハッシュは変わるため、この検知は
     内容の意味を区別しない。
  2. 「この migration は何を書いたか」の履歴としての価値は、**一度コミットされた版のまま動かない**
     ことに支えられている。あとから書き換えを許すと、`git blame` や過去の PR レビューが指している
     内容と、実際にリポジトリにある内容が食い違う(監査ログを追記専用にしたのと同じ理由)。
  - **すべきこと: 直したくなったら新しい migration を書く。** 番号を新しく採番し、`create or replace`
    (関数)・`alter table`(列・制約)・新しい `update`(データ訂正)など、DDL/DML として素直な形で
    「直す」。RPC の引数を増やすときに **署名が変われば `create or replace` が効かない**ため
    `drop function` してから作り直す、という個別の判断は既存の migration
    (製品の `domain_events` を作る migration の
    コメント)にも書かれている(**定型 RPC の生成 migration では、この `drop` は生成器が出す** —
    下記 §生成 migration)。
- **例外: まだコミットしていない(自分のワークツリーにしか無い)場合は自由に直してよい。**
  不変則は「共有された時点で凍結する」という意味であり、コミット前の作業中ファイルまで縛らない。
  境界は `git log` にその migration の変更が 1 つでも現れているかどうかである。
- **例外: `supabase db reset` でスキーマを作り直す運用そのもの(ローカル・CI)は対象外。**
  reset は「全 migration を最初から適用し直す」だけであり、ファイルの中身を書き換える操作ではない。
  この規約が禁じているのは、**歴史の 1 ページを後から差し替えること**である。

### 生成 migration(仕様から本文まで決まるもの)

**例外はここだけである。** 次の表に並ぶ種類は `npm run generate` が**ファイル全体を書き出す
生成物**であり、手で書かない・手で直さない。**種類の全数はこの表そのもの**である —— 本文で数を
言うと、行を足したときに数だけが古くなる(実際に「7 種」と書かれたまま行が 8 本になっていた)。

RLS のポリシーが生成物なのも同じ理由である —— 誰にどの行が見えるかは `access_spec` の `reads`
（`scope` / `filters`）とロールの根拠（`kind` / `claim` / `binding`）で決まりきっている。名前だけを
生成していたあいだは、`..._within_{列}` という名前のポリシーに `USING (true)` と書いても全部緑だった。
**ポリシーは `create or replace` を持たないので、`drop policy if exists` → `create policy` で置き換える**
（何度流しても同じ結果になる）。補助関数の連番は**全ポリシーより前**でなければならない（ポリシーが
関数を参照するので、DB を最初から作り直すときに関数が無い状態のポリシー作成に当たる。T7 が見る）。

**生成する SQL の識別子（ポリシー・関数・トリガ・索引・制約・表・ビュー・型・ドメイン・順序・スキーマ・ロールの名前、列の名前、`rename … to` の新しい名前）は 63 バイト以内でなければならない。** PostgreSQL は超えた分を
**エラーにせず黙って切り詰める** —— 切り詰めた結果が別の名前と同じになれば、`drop policy if exists` が別のポリシーを消し、
`create or replace function` が別の関数を上書きする。名前は仕様の名前（表・ロール・欄）を継いで組み立てるので、長い名前が 2 つ並ぶと
切り詰められた先頭が一致する。そこで RLS のポリシー・補助関数は組み立ての段（T7 が error）で、生成する全 SQL は `generate` が
書く前に（`lib/sql/identifier-length.ts`。何も書かずに止まる）止める。直し方は名前の出どころ（集約名・ロール名・欄名・
data_table の宣言）を短くすること。バイトは UTF-8 で数える（日本語の名前は 1 字 3 バイト）。

定型 5 形(作成 / 編集 / 削除 / 遷移)の本文が生成物なのは、**何をどう書き込むかが宣言から決まる**からである ——
許可列は access_spec の `writes`、楽観的並行制御は引数の `p_expected_…`、監査ログの語彙は操作 ID、
副作用は `effects`、空を渡された列の扱いは state_spec の `clears` である。決まっているものを手で書き写すと、
写し間違いを見張る機械が別に要る。定型なのに本文が生成できないものは、`handwritten` に理由を書く(T6)。

表の DDL が生成物なのも同じ理由である —— 列・型・NOT NULL・フィールド制約の正は entity_spec、
索引・外部キーの ON DELETE・排他制約・列の既定値の正は data_table であり、**どちらにも決める余地は
残っていない**。それでも 310 列ぶんの DDL は手で書き写されていて、突合があったのは列名だけだった
（型・NOT NULL・主キー・導出の既定値・`comment on` は無検査で、宣言に無い導出 CHECK が約 100 本あった）。
**DDL は `create or replace` を持たないので、中身を冪等な形にする** —— `create table if not exists` /
`add column if not exists` / `create index if not exists` / CHECK・外部キー・排他制約は
「定義が食い違うときだけ」の do ブロックであり、何度流しても結果が同じで、既に宣言どおりの DB に
当てれば**何も起きない**（CHECK まで do ブロックにしてあるのは、`add constraint … check` が
ACCESS EXCLUSIVE ロック + 全行検証だからである —— 結果が同じでも毎回全表スキャンが走るのは
冪等とは呼べない）。
**列は足すだけである**（落とさない・型は変えない・既存の列に NOT NULL を付けない）—— データに触る
判断は生成器が持たず、食い違いは統合テスト `ddl-parity` が error で名指して人の手書き migration に回す。
**部分でないインデックスの定義を変えるときは、新しい名前で作ってから古いものを落とす**(`create index if not exists` は同じ名前なら何もしないので、名前を据え置くと定義が変わらず突合が赤のまま残る)。

**表の DDL は権限（`grant`）を出さない。** 権限は**系に 1 本**（`{14 桁}_grants.sql`）であり、
出すのは**特権ロール（`service_role`）のぶん**と、**ポリシーを 1 本も持たない表**の `surface` のロールの
剥奪である。ポリシーを持つ表の `surface` のロール（`anon` / `authenticated`）の権限はポリシーの
migration が持つ（正は `reads`）。執行者を分けてあるので**当てる順序に依らない** —— 権限の
migration は `surface` のロールに触らず、ポリシーの migration は特権ロールに触らない。1 つにまとめると、
可視性を 1 行変えただけで権限のバイト列が変わり、**採番をやり直す**ことになる。
`revoke all … from service_role` を先に出すのは、Supabase が `postgres` の作る表に
`TRUNCATE` / `REFERENCES` / `TRIGGER` / `MAINTAIN` を既定で与えるからで、「与えていない」は
剥奪してはじめて成り立つ。逆に `select` は既定に無いので、明示しないと空の DB では特権ロールが
自分の表を 1 行も読めない（2026-09-23 に 4 題材の実行で実測）。

**なぜ表ごとではなく系に 1 本なのか。** 与える権限は**どの表でも同じ 1 組**なので、表ごとの
ファイルに複製すると「仕組みの 1 行を変える日」のコストが**表数に比例**する —— 実測で 16 本の
migration が動き、表ごとの差分は 4 行だった（2,893 行を書き直して意味は 2 行）。60 表のプロダクト
なら 60 本になる。系に 1 本なら常に 1 本であり、**形の正が無い内部テーブルも同じ一覧に載る**
（形は導けなくても権限は仕組みの 1 組で決まる。それまでその表だけが「特権ロールから TRUNCATE
できるまま」ACL の閉世界の外にいた）。引き換えは**表を 1 枚足す日に 1 本増える**ことである。

**仕組みが自分で持つ 2 表**（`jobs` / `domain_events`）と **公開スキーマの土台**も同じ生成物である
（`framework:` / surface_spec の `surface_base_migration`。ARCH-SP-BE-0001 §テーブル仕様）。列の正は entity_spec ではなく
仕組みの設計図（`legacy/spec-tools/lib/sql/framework-tables.ts`）にあり、`domain_events.entity` の値域だけが
ドメイン仕様の集約の全数から出る —— **集約を足すたびに人が migration へ 1 語足していた**作業
（6 本の migration が実際にそうしていた）が `generate` に置き換わった。

- **してはいけないこと: 生成 DDL を 1 文ずつ autocommit で当てる。** CHECK を作り直す
  `drop constraint` → `add constraint` の間は**同一トランザクションの中**にあることが前提であり、
  `psql -f`（`-1` 無し）のように 1 文ずつ当てるとその間を違反行が通れる。CHECK は落とすと
  **緩む**方向なので、ポリシーの `drop` → `create`（落とすと見えなくなる = fail-close）とは
  リスクの向きが逆である。**`supabase migration up` は 1 ファイルを 1 トランザクションで流す**ので、
  通常の経路ではこの前提が満たされている。
- **外部キーの置き場は生成器が決める**（**両側の表のファイル**に、存在ガードつきで出す）。
  表を作るのは表ごとの DDL なので、両方の表が在って、その列にまだ外部キーが無いときだけ張る ——
  先に当たった側は通り過ぎ、後から当たった側で張られるので、新しい DB に順に当てても
  `add constraint … references` が落ちない。**相互参照する 2 表**（番号では依存順を表せない組）も
  これで解ける。連番そのものに順序の規約は無く、T12 が見るのは参照先の表が data_table にある
  ことだけである。
- **してはいけないこと: 置き場を連番の大小で決める。** 再発行は番号を必ず上げるので置き場が
  動き、**中身が 1 バイトも変わらない隣の表のファイルを付け替える連鎖**が起きる（実測: 中心の表に
  列を 2 本足した束で 9 本が動き、8 本は旧ファイルとバイト同一 = **嘘の履歴**だった）。存在ガードで
  置き場を連番から切り離すと、列を 1 本足す日は 10 本 → **2 本**（その表の DDL と api ビュー）に
  なる。採番の器も同じ理由で連番を読まず、**名指す全表**のファイルに出す
  （`create sequence if not exists` は冪等である）。引き換えは「参照先が現れなければ外部キーが
  静かに欠ける」経路で、それは `data-table-parity` の外部キーの双方向突合が見る。
  設計の経緯は非公開の開発記録。

追記専用の歴史という不変則との両立は、**ファイル名を仕様に宣言させる**ことで取る。

- **してはいけないこと: 生成された migration を手で編集する。** 次の `generate` で消える。
  中身を変えたいなら usecase_spec(手順・入力・状態機械)を直す。
- **してはいけないこと: SQL が変わる仕様変更をしたのに `migration:` / `policies_migration:` / `ddl_migration:` の名前を据え置く。**
  据え置くと、既に適用済みのファイルの中身が書き換わり、上の不変則をそのまま破る。
- **すべきこと: SQL が変わったら `migration:` / `policies_migration:` / `ddl_migration:` の連番(先頭 14 桁)を新しく採番し直す。**
  旧ファイルは適用済みの歴史としてそのまま残り(生成対象から外れる)、新ファイルが
  `create or replace` で同じ名前の関数を置き換える。
- **生成 SQL に出る「文言」も、適用済み migration に固着する。** 上の 3 項は主語が**仕様側**
  だが、同じ不変則は**仕組み側の文言表**(`lib/messages/messages-ddl.ts` 等の節の見出し・
  `comment on` の文)にも掛かる —— 仕様を 1 文字も変えていなくても、文言を直せば生成物の
  バイト列が変わり、適用済みのファイルが書き換わる(C23 が落とす)。逃げ道の
  「採番し直す」は `ddl_migration` が**表ごとの宣言**なので、1 語のために**全表の採番を
  やり直す**ことになり事実上使えない。したがって**生成 DDL の文言は、生成物の意味の一部と
  して扱い、後から良くしない**。実測: 束 ③-3 で執行トリガの節の見出しを直したところ、
  適用済みの `{n}_ddl_domain_events.sql` の鮮度エラーになった(文言を戻し、変えない理由を
  文言表の docstring に残した)。
- **署名が変わったときの `drop` は生成器が出す。** `create or replace` は引数の型が 1 つでも
  変わると置き換えではなく**もう 1 本**を作るので、権限の付いた旧署名が呼べるまま残る。**RPC の
  3 種すべての**生成 migration が先頭に **do ブロック**を持ち、同名で引数型の並びが宣言と違う関数だけを
  `drop function` する(何度流しても同じ結果になる)。手で `drop function` を書く必要は無い ——
  この do ブロックを定型 5 形にしか置いていなかった束 ⑳-2 の形では、複合 RPC の署名に引数を
  足した瞬間に**旧 4 引数版が残り、位置引数で呼ぶ経路だけが古い本文に落ちた**(束 ⑳-3 の統合
  テストが反例)。
  残ってしまった多重定義は `rpc-signatures-parity`(同名は 1 本だけ)と data-table-parity の
  関数の閉世界(名前 + 引数型)が赤にする。
- **採番をやり直したら、前の名前で書き出したファイルを消す。** ローカル DB に適用済みなら、
  履歴も戻す(`supabase migration repair --local --status reverted {旧連番}` →
  `supabase migration up --include-all --local`。`db reset` は要らない)。`generate:check` は
  「宣言に無い生成ファイル(AUTO-GENERATED ヘッダを持つのにどの宣言からも出ないもの)」を
  **余分エラー**として落とす —— ただし**まだコミットしていないもの**だけが対象である
  (適用済みの生成 migration は、名前を新しくする規則により宣言から外れたまま歴史として残る)。
- **鮮度の執行**: `npm run generate:check`(CI・pre-commit)が「仕様を直したのに生成していない」
  (鮮度エラー)と「宣言から出ない生成ファイルが残っている」(余分エラー)を落とし、統合テスト
  `usecase-rpc-parity` / `rpc-parity` / `policy-parity` が「生成したのに適用していない」を落とす
  (RPC は `pg_get_functiondef` の本文とファイルの本文を、ポリシーと RLS 補助関数は**生成ファイルを
  トランザクションで適用して読み直した姿**と実 DB の姿を突き合わせる)。
- **形式と一意性の執行**: 保存点は Y7、定型 RPC は T6(`{14 桁}_rpc_{関数名}.sql` の形・全 data_table を
  通した一意性・`migration` と `handwritten` の排他)、表の DDL は T12(`{14 桁}_ddl_{テーブル名}.sql` の形・
  全 data_table を通した一意性・`entity` を持つ表での必須)。

## 3. 注意点・例外

### 執行

- **不変則の執行者: `npm run check:migrations`(C23)。** 基点のコミットに**存在する**
  `supabase/migrations/*.sql` が変更・削除・改名されていたら赤になる。基点は呼ぶ側が決める ——
  **pre-commit は `HEAD`**(ステージとの差分。`.githooks/pre-commit` の supabase スコープ)、
  **CI(push)は `main` で最後に成功した実行のコミット**(`changes` ジョブが決めて `outputs.base` で配る。`.github/workflows/ci.yml` の docs ジョブ)、
  **本番 DB へ当てる直前の deploy ジョブ(夜間の `nightly.yml`)は前回成功した夜間のコミット**(前回の出荷から今回までに入った変更を全部見る)。どれも**同じ 1 本**を基点だけ変えて呼ぶことは
  `legacy/spec-tools/__tests__/dev-repo/unit/gates/scope-parity.test.ts` が突き合わせる。
  - **未コミットのファイルは基点に存在しない**ので、上の「例外: まだコミットしていない場合は
    自由に直してよい」はそのまま成り立つ(生成器が同名の migration を何度書き直しても、
    コミットするまでは何も言われない)。
  - **リベース・squash との相性**は、基点をコミットに取ることで自然に解ける —— 書き換えが
    差分に現れるのは「基点に既にあったファイル」を触ったときだけであり、履歴の畳み直しそのものは
    ファイルの中身を動かさない。ただし force push で基点が欠けた場合は `HEAD~1` まで縮み、
    縮んだことが実行ログに出る(見える範囲が 1 コミット分になったことを黙らない)。
- **採番の執行者も `npm run check:migrations`(C23)である。** 不変則と同じ 1 本が、
  **この変更が足した migration** のファイル名を見る。判定は上の「すべきこと」そのものであり、
  **足したファイルが「辞書順で最後のファイル」の次に並ぶこと**である ——
  ①辞書順で末尾より後に並ぶ ②6 桁連番が末尾の連番より大きい(日付をまたいでも振り直さない)
  ③名前が `{8 桁の日付}{6 桁の連番}_{説明}.sql` として読める。違反は error。
  2 本以上足したときは末尾が 1 本ずつ進む(互いの順序も見る)。
  - **飛ぶのは通る。埋めるのは赤。** 欠番そのものは破れではない(番号が飛んでいるだけ)。
    だが**欠番の内側に後から挿すのは赤**である —— それは上の「**欠番は埋めない**」を
    そのまま破る行為であり、辞書順で末尾より前に並ぶので `末尾より前` として落ちる。
    (前後の 1 本ずつと比べる形では、欠番の内側は前後の単調性を保ってしまい必ず素通りする。
    このリポジトリには欠番が 8 区間残っているので、理論上の穴ではない —— 独立レビュー
    2026-09-23 が実データで再現した。)
  - **連番の「最大」とは比べない。** 時刻ベースの採番が混入した回(`…120003` = 連番 120003)が
    全体の最大なので、最大と比べると**以後のすべての追加が赤になる**。辞書順の末尾と比べれば
    その回は末尾ではないので影響しない。
  - **歴史に残る破れ 2 件は触らない。**(時刻ベースの採番が混入した回・日ごとに振り直した回。
    **適用済み migration は改名できない**以上そこは直せない。)免除リストではない ——
    名前を並べた表はどこにも無く、判定の母集合が「足したファイル」なので基点どうしの比較が
    1 度も起きないだけである。
  - **生成 migration の名前の形式と一意性は Y7 / T6 / T7 / T12**、鮮度は `generate:check`、
    実 DB との一致は `usecase-rpc-parity` が別に見る(こちらは連番の前後関係だけを見る)。
  [enforcement-matrix.md](./enforcement/enforcement-matrix.md) の D19 と C23 が対応する行である。
