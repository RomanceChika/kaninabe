# 参照ポリシー — 参照キーの意味と、参照してよい向き

文書どうしの参照に**意味の種類**を与え、**どの層がどの層を参照してよいか**の向きを固定する。目的は、勝手な参照と暗黙の依存を防ぐことである。

参照関係は「読む順番」ではない。**文書どうしの意味的な関係(グラフ)を機械可読に表したもの**であり、その関係は 2 つのレベルに分かれる。

- **概念レベル** — `norms` / `decisions` / `definitions`
- **実装レベル** — `dependencies`

**執行者は `npm run verify` の M3(参照先の実在)と M6(循環参照)である。** M3 は `norms` / `decisions` に並ぶ id が実在する文書の id かを見る。実在しない id は「規範に従っているつもりで何にも従っていない」状態であり、参照グラフを静かに壊す。M6 は参照グラフが循環していないことを見る —— 循環すると「規範の根拠」が自分自身に戻り、上へ辿るという読み方が成立しなくなる。

## 概念レベルの参照

3 つのキーがある。どれも複数の id を列挙してよい。**どのキーに置くかは、参照先との関係が何であるかで決まる。**

| キー | 関係 | 判断基準 |
|---|---|---|
| `norms` | 規範への準拠 | 「これに違反してよいか?」→ NO |
| `decisions` | 意思決定・根拠 | 「なぜこうなっているのか?」と聞かれたら参照すべきか |
| `definitions` | 定義の出典 | 「この用語・概念の定義はどれを正とするか?」 |

## norms（規範への準拠）

この文書が従うべき規範・ルール・契約を指す。**`norms` の参照先に違反することは、設計違反・バグ・レビュー NG として扱われる。**

- **対象の例:** 原則(`PRIN-*`)、契約(ID 規約・フォーマット定義・仕様の書き方)、コーディング規約、強制力のあるアーキテクチャルール(`ARCH-*`)
- **判断基準:** 「これに違反してよいか?」に NO と答えるなら `norms`。YES なら `norms` ではない

違反が問題にならないものを `norms` に並べると、キーの意味が薄まる。「参考にした」程度のものは本文リンクで示す。

## decisions（意思決定・根拠）

この文書の内容がどの ADR に基づくかを指す。「なぜこうなったか」の参照先である。

- **対象の例:** ADR、技術選定の理由、トレードオフの結論
- **判断基準:** 「なぜこうなっているのか?」と聞かれたときに開くべき文書か

## definitions（定義の出典）

この文書が正として参照している定義を指す。**定義が食い違ったときに「どれが正か」を決める基準**になる。

- **対象の例:** 用語集(`TERM-*`)、不変条件(`INVARIANT-*`)、例(`EXAMPLE-*`)
- **判断基準:** 「この用語・概念の定義はどのドキュメントを正とするか?」

現構成にはまだドメイン知識層(W。住所は `docs/specs/` の隣)の実体が無く、`definitions` を実際に使っている文書はほぼ無い。キーとしては生きている。

## 実装レベルの依存

`dependencies` は、この文書の**実装**が依存するリソース(データテーブル・サービス)を指す。概念レベルの 3 キーとは別の軸であり、「何に従うか」ではなく「何を使うか」を書く。詳細は [dependency_policy.md](./dependency_policy.md)。

## 使用しない関係について

- **読む順番・要約関係はフロントマターに載せない。** 本文のリンクで表現する。これらは文書間の意味的な関係ではなく、読み手の都合だからである
- **`applies` / `derived_from` のような動詞的なキーを使わない。** 「適用する」「派生した」は関係の方向も強さも曖昧で、書き手ごとに解釈が割れる。運用と自動処理の両方で破綻する

## 最小原則まとめ（AI向け）

4 つのキーで参照関係は網羅される。迷ったらこの 1 行ずつに当てはめる。

- **`norms`** = 守らなければならないもの
- **`decisions`** = なぜそうしたか
- **`definitions`** = どれが正か(用語・概念の定義)
- **`dependencies`** = 何を使うか(データテーブル・サービス)

## 徹底ルール：参照はフロントマターに載せる

**参照する可能性が僅かでもある文書は、該当する意味キーにフロントマターで id を書く。** 本文リンクだけに依存してはいけない。

**参照グラフが完結する場所はフロントマターである。** id から辿れることが条件であり、そこが唯一の出典である(PRIN-0007)。したがって、**「関連」のような本文の節に同じ id を並べる必要はない。** 本文リンクは読み進めるための案内であって、グラフの一部ではない。

**README やまとまりの入口も対象である。** `standards/README.md`、`layers/README.md`、`conventions/README.md` のような入口の文書も、**まとまり全体に共通でかかる規範があれば `norms` を書く**(必要なら `decisions` / `definitions` も)。理由は 2 つある。

1. **宣言の場所が個別の `xx.md` と入口の両方になることで、「このカテゴリ・この層の全体が準拠する原則」が明示される。** 個別文書だけに書くと、まとまり全体に効いている規範が見えない
2. **層全体・カテゴリ全体に効く原則(全層共通のセキュリティ原則など)は、専用の `xx.md` が無くても入口 README の `norms` に載せてよい。** 規範を宣言するために文書を 1 本増やす必要はない

実例として、テスト規約のまとまりの入口([conventions/testing/README.md](../../process/backend/system/standards/conventions/testing/README.md))は `norms` に `ARCH-BE-0001`(app の層構造)・`PRIN-0003`(テスト可能性)・`PRIN-0008`(追跡可能性)を宣言している。テスト層だけを対象にした architecture 文書は存在せず、まとまり全体に効いているのは層構造とこの 2 つの原則である。

## 参照の可否（誰が誰を参照してよいか）

行が参照する側、列が参照される側である。

| ↓が参照する \\ →される | principle | domain | architecture | process | decision | spec |
|---|---|---|---|---|---|---|
| **meta** | 可 | 可 | 可 | **不可** | 可 | **不可** |
| **principle** | 可 | 可 | 可 | **不可** | 可 | **不可** |
| **domain** | 可 | 可 | 可 | **不可** | 可 | 可 |
| **architecture** | 可 | 可 | 可 | **不可** | 可 | **不可** |
| **process** | 可 | 可 | 可 | 可 | 可 | 可 |
| **decision** | 可 | 可 | 可 | 可 | 可 | 可 |
| **spec** | 可 | 可 | 可 | 可 | **推奨** | 可 |

- 「不可」は**参照してはいけない**という意味である。依存の向きを守るための禁止であり、破ると層構造が崩れる
- 「推奨」は**参照すべき**という意味である。spec は関連する decision を `norms` か `decisions` で明示するとよい

**この表で最も重要なのは、principle / architecture / meta から process への参照が不可であることである。** 上位の層が下位の手順に依存してはいけない。原則が「この手順に従う」と書いた瞬間、手順を変えるたびに原則を直すことになり、原則が原則でなくなる。手順の側が上位を参照する —— 向きは常にそちらである。

## metaとprincipleの関係

**meta は principle を参照できる。** 根拠は 3 つある。

1. **位置づけ。** meta は「ルール文書の形式・構造」を定義するメタレベルにあり、principle は「内容・価値観」を定義する。次元は違うが、**meta 自身も文書である以上、原則に従う必要がある**
2. **整合性の保証。** meta が単一情報源(PRIN-0007)や追跡可能性(PRIN-0008)に従わなければ、ルールの書き方そのものが整合を失う。書き方が壊れれば、その書き方で書かれた全文書の品質を保証できない
3. **向き。** meta → principle は可、principle → meta は通常不要である。原則は内容を定義し、書き方は meta に委ねる、という分業だからである
