# ADR-0004: 遷移テーブル生成 + 汎用エンジン方式で仕様と実装の乖離を構造的に排除する

## Status

accepted (2026-08-06)

---

## Context

### 背景

PRIN-0001（仕様を唯一の正とする）は「実装と仕様に乖離がある状態はバグ」と定めています。問題は**その乖離をどうやって検出・防止するか**です。

#### 1. **突合による検出には限界がある**

仕様と実装を静的解析で突合する方式は、型名・ID・アノテーションのようなシンタクティックな一致しか見られません。「状態機械の遷移条件が仕様と実装で違う」のような意味の乖離は、突合では原理的に拾えません。

#### 2. **手書きの遷移ロジックは必ず腐る**

`if (loan.state === 'requested' && role === 'patron') { ... }` のような分岐を機能ごとに手で書くと、仕様が更新されたときに実装側の追随漏れが起きます。分岐が増えるほど、どのマスが実装されているかを人間が把握できなくなります。

#### 3. **AI の書き方が発散する**

Server Action の実装を AI に任せると、バリデーションの位置・権限チェックの位置・副作用の積み方が毎回違う形になります。レビューの負荷が上がり、「この仕様ならこの書き方しかない」という状態から遠ざかります。

#### 4. **DSL の検証が実装に届かない**

仕様側で V1〜V11 の検証を通しても、実装がその仕様を読んでいなければ、検証の成果はドキュメントの中に閉じたままになります。

### 前提条件

- ADR-0003 により、状態機械・権限・フィールド制約は有限で決定可能な形で仕様に書かれている。
- 実装スタックは Next.js（App Router）+ Supabase。DB アクセスは必ずサーバー（Server Action / RSC）経由。
- 非同期副作用は outbox パターン（ドメイン書き込みと同一トランザクションでジョブ行を積む）。
- テストは仕様から導出する（テスト Generator には実装コードを見せない）。

---

## Decision

### 決定内容

**状態機械の仕様から遷移テーブルデータを生成し、実装は生成データを読む汎用エンジンにする。遷移ロジックを人が書く場所を作らない。**

1. **生成物**
   - `state_spec` → `src/domain/generated/{machine}.transitions.ts`（`as const` の遷移テーブルデータ）
   - `entity_spec` → `src/domain/generated/{entity}.schema.ts`（zod スキーマ + TS 型）
   - `access_spec` → スコープ定義データ（クエリ層のフィルタ + RLS ポリシーとの突合リスト）
   - 生成物は手書きしない。手書きしても次回生成で上書きされ、YAML が正であり続ける（PRIN-0007）。

2. **汎用エンジン**
   - `src/domain/engine/` に**手書きの小さなエンジンを 1 回だけ書く**: `canFire(table, ctx)` / `nextState(...)` / ガード式インタープリタ。
   - このエンジンを徹底的にユニットテストする。個別機能の実装は、生成された遷移テーブルをエンジンに食わせるだけ。

3. **Server Action の定型**
   - すべての Server Action は次の形に固定する:
     1. 生成 zod スキーマでパースする
     2. エンジンに遷移可否を聞く（状態 × イベント × ロール × ガード）
     3. リポジトリで永続化する
     4. `effects` を outbox に積む
   - フォーム（即時フィードバック）と Server Action（本検証）は**同じ生成スキーマを import** する。

4. **乖離の排除方法を「突合」から「構造」に変える**
   - 遷移ロジックを手で書く場所が存在しないため、仕様と実装の乖離は**検出するものではなく、起こりえないもの**になる。
   - 突合（trace 検証）は引き続き行うが、その対象は「仕様 ⇔ テスト」および「イベント ID ⇔ 画面 / Server Action / Webhook」に絞られる（PRIN-0008）。

### 適用範囲

- ドメインの状態遷移・権限判定・フィールドバリデーションを伴うすべての実装
- `src/domain/generated/`、`src/domain/engine/`、Server Action の実装形
- 生成器（`legacy/spec-tools/generators/`）の実装方針

## Consequences

### Positive（メリット）

- **仕様と実装の乖離が構造的に起こらない**。遷移ロジックの唯一の実体はエンジン + 生成テーブルであり、仕様を変えれば実装が変わる。
- **テストが集約される**。機械導出されたテスト（遷移・禁止マス・ガード境界・権限）は実質「エンジンの正しさの確認」に収束し、機能ごとに手書きし直すものではなくなる。
- **AI の書き方が一意に絞られる**。Server Action が定型化されるため、「この仕様ならこの書き方しかない」が実現し、レビュー対象が意味の正誤に絞られる。
- **フォームとサーバーのバリデーションが一致する**。同じ生成スキーマを import するため、二重定義もズレも発生しない（PRIN-0007）。
- **検証の成果が実装まで届く**。V1〜V11 を通った仕様がそのまま実行される。

### Negative（デメリット・トレードオフ）

- **生成器とエンジンという基盤への先行投資が必要**。最初の 1 機能を作るまでのコストが素朴な実装より高い。
- **エンジンのバグが全機能に波及する**。単一障害点になるため、エンジンのユニットテストは妥協できない（この集中は利点でもある — テストすべき場所が 1 箇所に集まる）。
- **生成物をリポジトリに置くか生成時に作るかの運用が必要**。生成物の鮮度検証（仕様と生成物の再生成比較）を CI に組み込む必要がある。
- **DSL で表現できないロジックはこの構造の外に出る**。集計などは operation の純粋関数として手書きされ、エンジンの保証は及ばない（ADR-0003）。
- **デバッグの間接性**。実行時の挙動を追うには「生成テーブル + エンジン」の 2 段を読む必要があり、直接的な if 文より初見の可読性は落ちる。

### Neutral（その他の影響）

- `effects` は outbox ジョブの接続点として仕様に現れる。ワーカーも通常の operation 関数であり、同じ層構成・同じ仕様突合・同じテスト戦略に乗る。
- 副作用の実体（通知の文面など）は `specs/backend/external` が定義し、ドメイン仕様には ID だけが現れる。
- RLS は第二防衛線として全テーブルに書き、`access_spec` のスコープ定義データとの突合リストで整合を確認する。

## Alternatives Considered

### Option 1: 仕様と手書き実装を静的解析で突合する

- **Pros**:
  - 実装の自由度が高い。既存コードにも適用しやすい
  - 生成器・エンジンの実装が不要
- **Cons**:
  - 突合できるのはシンタクティックな一致（型名・ID・アノテーション）まで。遷移条件の意味の乖離は拾えない
  - 実装が仕様に追随しなかった場合、乖離は「検出できたらラッキー」になる
  - 機能ごとに遷移ロジックが手書きされ続けるため、腐りの発生源が減らない
- **Why rejected**: 乖離を減らす方向にしか働かず、ゼロにできない。PRIN-0001 の要求に対して弱い。

### Option 2: 状態機械ライブラリ（XState 等）に仕様を書く

- **Pros**:
  - 実績あるランタイム・可視化ツールが手に入る
  - 遷移ロジックの手書きは避けられる
- **Cons**:
  - 仕様の正がライブラリの記法になり、DSL 側の検証（V1〜V11）・権限 3 軸・不変条件・生成物との統合が難しくなる
  - 表現力が広く（アクション・サービス呼び出し等）、ADR-0003 で意図的に絞った境界が崩れる
  - ライブラリのバージョン・思想に仕様体系が依存する
- **Why rejected**: 仕様の正は YAML（検証器が読む形）に置きたい。エンジンは `canFire` / `nextState` 程度の小さなもので足り、外部依存を負う理由が薄い。

### Option 3: 仕様からコードを丸ごと生成する（Server Action のフルスキャフォールド）

- **Pros**:
  - 実装の手書きがさらに減る
  - 生成された時点で仕様どおりであることが保証される
- **Cons**:
  - 生成コードに手を入れたくなった瞬間に破綻する（再生成で失われる／生成器が肥大化する）
  - 永続化・エラー処理・UI 連携など、仕様に書かれていない部分が生成器の暗黙知になる
  - 生成器のメンテコストが跳ね上がる
- **Why rejected**: 生成するのは**データ（遷移テーブル・スキーマ）だけ**に留め、振る舞いは手書きの小さなエンジンに閉じるほうが、生成器もエンジンも単純に保てる。

### 生成物一覧

| 生成元 | 生成物 | 用途 |
|--------|--------|------|
| state_spec | mermaid 状態遷移図 + 遷移表 + state × event マトリクス（✓遷移 / ✗理由） | 人間レビュー（本文に AUTO-GENERATED） |
| state_spec + access_spec | ロール × 操作の権限マトリクス表 | 人間レビュー（本文） |
| entity_spec | zod スキーマ + TS 型（`src/domain/generated/{entity}.schema.ts`） | フォーム & Server Action の共通バリデーション |
| state_spec | 遷移テーブルデータ（`src/domain/generated/{machine}.transitions.ts`、`as const`） | 実装（汎用エンジンが読む） |
| access_spec | スコープ定義データ | クエリ層のフィルタ + RLS ポリシーとの突合リスト |
| invariant_spec | テスト義務リスト（この INV を検証する統合テストの ID） | trace 検証（仕様⇔テスト突合）への入力 |

### 「生成」と「突合」の役割分担

- **生成で消せる乖離**: 状態遷移・遷移権限・フィールド制約 → 実装が生成物を読むので乖離が発生しない。
- **突合が必要な乖離**: 仕様 ⇔ テスト（機械導出テストの実在）、ドメインイベント ID ⇔ 画面 / Server Action / Webhook の宣言、`access_spec` ⇔ RLS ポリシー、不変条件 ⇔ 執行点。ここは生成では消せないので trace 検証で担保する。
